Cobalt Strike" /></header></div><div class="cms-block-shell cms-block-translucent" style="--cms-block-bg-opacity:0.3"><section class="section-block"><div class="cms-content"><p><a href="https://www.blackhillsinfosec.com/team/kyle-avery/" target="_blank" rel="noreferrer noopener">Kyle Avery</a> //</p> <figure class="size-large cms-blog-figure"><img loading="lazy" decoding="async" width="1024" height="576" src="/uploads/media/blog/dns-over-https-for-cobalt-strike/thumbnail-blog-chalkboard-00572-1024x576-b13096c948.jpg" alt="" class="wp-image-20278 cms-blog-image"></figure> <h3>Introduction</h3> <p>Setting up the C2 infrastructure for red team engagements has become more and more of a hassle in recent years. This is a win for the security community because it means that vendors and professionals have learned from previously successful techniques and implemented effective mitigations in their networks.</p> <p>DNS over HTTPS is an underappreciated channel for command and control. This blog will show you how to utilize DoH with Cobalt Strike in a way that requires no third-party accounts or infrastructure setup, encrypts traffic with a valid SSL certificate, and sends traffic to reputable domain names.</p> <h3>Existing Techniques</h3> <p>Attackers and offensive security professionals have been using different redirector implementations for some time. The first redirectors that I used were simple Apache and Nginx servers configured with various rules to forward traffic based on predefined criteria.</p> <p>Redirectors are great for making infrastructure more resilient, but they can also bypass defenses that rely on domain categorization. For example, once Content Delivery Networks (CDN) became more accessible to developers, attackers moved from traditional redirectors to these platforms because they often provide a valid domain name and even SSL certificate to the user, reducing the work of an attacker.</p> <p>A technique known as “domain fronting” was later discovered and used heavily by many testers. More recently, however, CDN providers have been cracking down on this behavior. Many sites prevent domain fronting entirely or actively search for those using it. Microsoft in particular has been known to shut down Azure Subscriptions in the middle of our operations.</p> <p>I have recently turned to other cloud services such as Azure App Services and Cloudflare Workers for traffic redirection. These have the same benefits as traditional CDNs but are less heavily monitored. While these services work well, cloud providers could decide to start watching these with the same dedication as they watch CDNs any day.</p> <h3>DNS over HTTPS</h3> <p>Traditional DNS Beacons are relatively straightforward to detect. I have never used the Cobalt Strike DNS listener on an operation, limiting me to the previously described HTTPS listener and redirectors.</p> <p>DNS over HTTPS for Beacon provides us reputable domains and valid SSL certificates without needing an account or any configuration of the redirector. This reduces an operator’s setup time even further and eliminates the risk of account shutdown.</p> <h3>Today’s Topic: DNS over HTTPS for Cobalt Strike</h3> <p>The use of DNS over HTTPS was first presented to me on Twitter by <a href="https://twitter.com/ilove2pwn_" target="_blank" rel="noreferrer noopener">Austin Hudson</a>. His tweets over the last year detailed his progress towards this capability and resulted in an open-source tool: <a href="https://github.com/secidiot/TitanLdr" target="_blank" rel="noreferrer noopener">TitanLdr</a>. This Cobalt Strike user defined reflective loader (UDRL) hooks the Cobalt Strike Beacon’s import address table (IAT) to replace the API call responsible for making traditional DNS queries (DNSQuery_A) with a function that makes DoH requests to dns.google (8.8.8.8 and 8.8.4.4).</p> <p>This alone is an excellent capability, but TitanLdr’s DNSQuery_A hook is generic enough to work with many different DoH servers! I have tested the following domains and confirmed that they work as drop-in replacements:</p> <ul class="wp-block-list">
<li>dns.quad9.net</li> <li>mozilla.cloudflare-dns.com</li> <li>cloudflare-dns.com</li> <li>doh.opendns.com</li> <li>ordns.he.net</li>
</ul> <h3>Using TitanLdr</h3> <p>TitanLdr is the key to integrating this capability into Cobalt Strike. You can grab the original TitanLdr, which beacons to a single DNS provider over HTTPS server here: <a href="https://github.com/secidiot/TitanLdr" target="_blank" rel="noreferrer noopener">https://github.com/secidiot/TitanLdr</a>. You can change the DNS server on line 111 of the DnsQuery_A.c file in the hooks directory.</p> <figure class="ql-align-center size-full cms-blog-figure"><img loading="lazy" decoding="async" width="452" height="182" src="/uploads/media/blog/dns-over-https-for-cobalt-strike/picture1-1-f2aacf22d8.png" alt="" class="wp-image-20263 cms-blog-image"><figcaption class="wp-element-caption"> <em>Line 111 in TitanLdr/hooks/DnsQuery_A.c (Original Repository)</em> </figcaption></figure> <p>I have since <a href="https://github.com/kyleavery/TitanLdr" target="_blank" rel="noreferrer noopener">forked</a> TitanLdr to allow for multiple DoH servers to be specified. Each time a callback is made, the Beacon will randomly select one from a hardcoded list. If you want to use multiple DoH servers, you can download my fork here: <a href="https://github.com/kyleavery/TitanLdr" target="_blank" rel="noreferrer noopener">https://github.com/kyleavery/TitanLdr</a>. You can modify the list of servers at line 116 of the DnsQuery_A.c file in the hooks directory.</p> <figure class="ql-align-center size-full cms-blog-figure"><img loading="lazy" decoding="async" width="373" height="199" src="/uploads/media/blog/dns-over-https-for-cobalt-strike/picture2-1-7ea4dab394.png" alt="" class="wp-image-20264 cms-blog-image"><figcaption class="wp-element-caption"> <em>Line 116 in TitanLdr/hooks/DnsQuery_A.c (Forked Repository)</em> </figcaption></figure> <p>Once downloaded, you will have to build the program. This will require a Linux host with NASM and MinGW installed. Once you have these programs, run the <strong>make</strong> command to create the necessary files.</p> <figure class="ql-align-center size-full cms-blog-figure"><img loading="lazy" decoding="async" width="617" height="161" src="/uploads/media/blog/dns-over-https-for-cobalt-strike/picture3-1-2b2d0e81e6.png" alt="" class="wp-image-20265 cms-blog-image"><figcaption class="wp-element-caption"> <em>Building TitanLdr</em> </figcaption></figure> <p>Import the Titan.cna Aggressor script into Cobalt Strike, and you are ready to use DoH! Configure a DNS listener as you usually would. The <a href="https://www.cobaltstrike.com/help-dns-beacon" target="_blank" rel="noreferrer noopener">Cobalt Strike documentation</a> goes more in-depth on configuring this listener.</p> <figure class="ql-align-center size-full cms-blog-figure"><img loading="lazy" decoding="async" width="409" height="384" src="/uploads/media/blog/dns-over-https-for-cobalt-strike/picture4-1-45a637a9a8.png" alt="" class="wp-image-20266 cms-blog-image"><figcaption class="wp-element-caption"><em>Configuring a DNS Listener</em></figcaption></figure> <p>Once the Beacon is running, we can see that only one DNS request is made to resolve the DoH server address. Afterward, all of the traffic is encrypted HTTPS.</p> <figure class="ql-align-center size-full cms-blog-figure"><img loading="lazy" decoding="async" width="621" height="163" src="/uploads/media/blog/dns-over-https-for-cobalt-strike/picture5-1-2ef0023a75.png" alt="" class="wp-image-20267 cms-blog-image"><figcaption class="wp-element-caption"> <em>DoH Beacon Network Traffic</em> </figcaption></figure> <h3>Drawbacks of DNS over HTTPS</h3> <p>We’ve already discussed the benefits a DNS over HTTPS Beacon has over a traditional HTTPS Beacon, but there are also some definite drawbacks.</p> <p>First, more packets are needed to communicate the same information back to the team server. A DNS TXT record can only contain a maximum of 255 characters, meaning we can only send a small amount of data in each packet.</p> <p>Second, we have no control over the path or domain names of available servers. It seems easier for an environment or appliance to deny outbound 443/TCP to the list of popular or known DoH servers than block Microsoft’s *.azurewebsites.net or Cloudflare’s *.workers.dev. You could solve this by using more obscure DoH servers or by building your own and categorizing them over time, depending on how the environment is configured.</p> <h3>Potential Detection Methods</h3> <p>Current detection techniques may have gaps when it comes to detecting DNS over HTTPS.</p> <ul class="wp-block-list">
<li>Current detections targeting malicious HTTPS traffic typically utilize domain reputation, rendering them potentially ineffective against DoH since the domains in use are reputable.</li> <li>Current detections targeting malicious DNS traffic typically monitor for many DNS requests, rendering them potentially ineffective against DoH since the traffic is no longer using the DNS protocol.</li>
</ul> <p>A combination of traditional DNS monitoring and SSL inspection could be a potential solution, but I do not know of any current tools or products that do this.</p> <p>My understanding is that the primary defense against this attack is blocking outbound 443/TCP to known DoH servers that an organization is not using. Most networks I encounter still use traditional DNS, often with a local DNS server running as part of the Active Directory environment. In this case, there is no need to allow HTTPS traffic to dns.google, cloudflare-dns.com, or any others mentioned in this post.</p> <h3>Closing Thoughts</h3> <p>There are absolutely more DNS over HTTPS servers that could be used with this configuration. In addition, the user could set up their own DoH server, maybe even behind a CDN or other cloud service, to introduce a variation on this technique.</p> <p>TitanLdr is limited to Cobalt Strike, but the DoH implementation could be ported to any other C2 framework.</p> <p>This method will not be the best in every scenario, but it is another tool in the toolkit that I hope you can take advantage of. Feel free to contact me with any questions or comments on Twitter <a href="https://twitter.com/kyleavery_" target="_blank" rel="noreferrer noopener">@kyleavery_</a>.</p> <h3>Credits</h3> <ul class="wp-block-list">
