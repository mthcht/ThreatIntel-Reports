<p align="center"><img alt="" src="/content/dam/fortinet-blog/article-images/individual-images/trickintro.png" data-style="width: 380px; height: 231px;"/></p>

<p>One month ago we captured a Word document infected with malicious VBA code, which was detected as WM/Agent!tr by the Fortinet AntiVirus service. Its file name is InternalFax.doc, and its MD5 is <code>4F2139E3961202B1DFEAE288AED5CB8F</code>. &nbsp;By our analysis, the Word document was used to download and spread the botnet TrickBot. TrickBot aims at stealing online banking information from browsers when victims are visiting online banks. The targeted banks are from Australia, New Zealand, Germany, United Kingdom, Canada, United States, Israel, and Ireland, to name a few.</p>

<p><strong>How TrickBot is downloaded to the victim&rsquo;s system</strong></p>

<p>When a victim opens the malicious Word document, Figure 1 shows what the document looks like:</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-989.png" data-style="width: 432px; height: 267px;"/></p>

<p align="center">Figure 1. The Word document is opened</p>

<p>As you can see, a warning message is shown in the foreground. However, in the background, its VBA code is downloading the TrickBot sample from hxxp://fax-download.com/lindoc1.exe or hxxp://futuras.com/dodocdoddus.exe.&nbsp; Figure 2, below, shows the downloaded TrickBot sample. Its MD5 is <code>D58CD6A8D6632EDCB6D9354FB094D395</code>, and can be detected as W32/Generik.LWVNLMZ!tr by Fortinet AntiVirus service.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-990.png" data-style="width: 264px; height: 38px;"/></p>

<p>&nbsp;</p>

<p align="center">Figure 2. The downloaded TrickBot sample</p>

<p><strong>TrickBot is installed on victim&rsquo;s system</strong></p>

<p>The original TrickBot is a program developed with Visual Basic 6.0. To increase the difficulty of debugging and analyzing it, the malware developer used a large number self-defense techniques, including code self-modification, code dynamic-extraction, and code/data encryption, etc. Let&rsquo;s go ahead and see how it works.</p>

<p>When TrickBot is launched it dynamically extracts code from itself, puts it into a heap space, then calls its entry point. The main purpose is to call the Windows API <em><code>CreateProcessW</code> </em>to run as a child process with the creation flag &ldquo;CREATE_SUSPENDED.&rdquo; This means that when the new process is created successfully, it&rsquo;s in suspended status. So the malware could get a chance to modify the child process&rsquo; code as expected, then send the child process a signal by calling an API to let it resume and run the modified code. This is usually what the malware does to protect its code. Figure 3 shows the calling of the API CreateProcessW.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-991.png" data-style="width: 433px; height: 172px;"/></p>

<p align="center">Figure 3.&nbsp; Call CreateProcessW with CREATE_SUSPENDED flag</p>

<p>As mentioned above, it&rsquo;ll call <code><em>ZwUnmapViewOfSection</em>, <em>ZwAllocateVirtualMemory</em>, <em>ZwWriteVirtualMemory</em>, <em>ZwGetContextThread</em>, <em>ZwSetContextThread</em> and <em>ZwResumeThread</em> </code>APIs to modify the child process&rsquo; code. It then modifies the thread context and finally resumes its execution. After that, the parent process finishes its job and is going to exit soon. From now on, the code in the child process will take over and continue the TrickBot&rsquo;s job.</p>

<p>Let&rsquo;s move on and see how the child process works.</p>

<p>Actually, the child process is a loader, which loads a named resource from itself into heap space. Of course, the content of the resource is encrypted, but after decryption it &nbsp;appears as an executable code block. Soon the child process will call the executable&rsquo;s entry point. The named resource is &ldquo;IDR_X86BOT&rdquo; or &ldquo;IDR_X64BOT.&rdquo; It depends on whether the victim&rsquo;s system is 32-bit or 64-bit. In our analysis, according to the system type, the named resource is &ldquo;IDR_X86BOT&rdquo;. This also affects what executable files are downloaded from the C&amp;C server later.</p>

<p>The code in heap contains the main job of the child process. At first it creates a named mutex object by calling the function <code><em>CreateMutex</em></code>. This is used to check if another lindoc1.exe is running. If yes, it stops doing other things and exits the process. In this way, it can ensure that only one lindoc1.exe can be run at one time. The following ASM code snippet shows how the named mutex object is created.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-992.png" data-style="width: 600px; height: 517px;"/></p>

<p>Next, TrickBot tries to add itself as a task named &ldquo;Bot&rdquo; to the Task Scheduler, so that the TrickBot can be executed in a timely manner. Figure 4 and 5 show the screenshots of TrickBot&rsquo;s task in Task Scheduler.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-993.png" data-style="width: 432px; height: 286px;"/></p>

<p align="center">Figure 4. New Task &ldquo;Bot&rdquo; in Task Scheduler</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-994.png" data-style="width: 431px; height: 223px;"/></p>

<p align="center">Figure 5. The action of the TrickBot task</p>

<p>The task named &ldquo;Bot&rdquo; is able to start &ldquo;lindoc1.exe&rdquo; with &ldquo;SYSTEM&rdquo; account permission. As you might notice, the original &ldquo;lindoc1.exe&rdquo; has been moved to &ldquo;C:\Windows\system32\config\systmprofile\AppData\Roaming\lindoc1.exe&rdquo; because this folder is just like &ldquo;%AppData%&rdquo; for local &ldquo;SYSTEM&rdquo; account.</p>

<p>TrickBot creates a security identity (SID) to check if the user running this process is &ldquo;SYSTEM&rdquo;. If not, then it will soon exit the process. See the following code snippet for detailed info on how it checks the account.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-995.png" data-style="width: 500px; height: 729px;"/></p>

<p>Of course, the current account is owned the user who signed into Windows, and not &ldquo;SYSTEM.&rdquo;&nbsp;As you may recall, only when TrickBot is executed by the Task Scheduler, the account is &ldquo;SYSTEM&rdquo; (see Figure 4.) So the child process exits itself without doing any further things.</p>

<p><strong>TrickBot is executed by Task Scheduler</strong></p>

<p>When TrickBot is executed by the Task Scheduler with &ldquo;SYSTEM&rdquo; account permission, it can pass the SID check. It then tries to get victim&rsquo;s public IP address by sending following HTTP requests.</p>

<p>The public IP address will be used for communication with C&amp;C server later.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-996.png" data-style="width: 300px; height: 132px;"/></p>

<p>It should be noted that most of the data, meaning files generated by TrickBot, are encrypted. TrickBot continually loads encrypted resource data with the name &ldquo;CONFIG.&rdquo; After decryption, it contains some information about TrickBot, including its version, group tag, and the IP addresses of its C&amp;C servers. All this information is used to communicate with its C&amp;C servers. If there is already a &ldquo;config.conf&rdquo; file, it reads the file and decrypts it to get the &ldquo;CONFIG&rdquo; data instead. The content looks like this:</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-997.png" data-style="width: 500px; height: 394px;"/></p>

<p>After the IP addresses of C&amp;C servers are received, TrickBot will connect them. I&rsquo;m going to take one request as an example to show you what the command looks like:</p>

<p><em>GET /lindoc1/AAA-PC_W617600.CA836C89ADF141D19A16BFA7397AD021/5/spk/</em></p>

<ul data-style="list-style-type:circle;">
	<li>&ldquo;lindoc1&rdquo; is the group tag.</li>
	<li>&ldquo;AAA-PC_W617600.CA836C89ADF141D19A16BFA7397AD021&rdquo; is the client id that is generated by current user name, Windows version and 32 random hexadecimals.</li>
	<li>&ldquo;5&rdquo; is the command id. According to my analysis, command 5 is used to request downloading something from the C&amp;C server, so the server will reply with data to this command.</li>
	<li>&ldquo;spk&rdquo; is an additional information &nbsp;for command 5.</li>
</ul>

<p>Next, I&rsquo;m going to show the requests and responses of some main commands in chronological order. In the requests I use &ldquo;Client_ID&rdquo; to replace the real long client id in order to reduce the request length. Note that the response data are all encrypted, so I decrypted them here for readability.</p>

<p><strong>[Command 0 request]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/0/Windows7x86/1012/PUBLIC </em></code></p>

<p><code><em>IP/BC1A53480DD53727D4E197BC8DF20B0E8D113AA14C</em></code></p>

<p>This provides the C&amp;C server with the Windows version, and the public IP address of the victim&rsquo;s machine. The server then replies with an expiration time and new IP address, which are used to download DLLs later.</p>

<p>[Response]:</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-998.png" data-style="width: 500px; height: 220px;"/></p>

<p>&ldquo;1480550400&rdquo; is a date/time value. After conversion it&rsquo;s &ldquo;16:00 11/30 2016.&rdquo; It tells us the C&amp;C server&rsquo;s expiration date and time. The IP address and port &ldquo;37.1.213.189:447&rdquo; points to a specific C&amp;C server that holds the DLL files.</p>

<p><strong>[Command 23 request]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID /23/1000004/</em></code></p>

<p>This sends the TrickBot version to the C&amp;C server to fetch the latest &ldquo;CONFIG&rdquo; of the C&amp;C server. When TrickBot runs into any errors in connecting to the C&amp;C server, it&rsquo;ll send such request. As you can see, the latest version for now is 1000008. It&rsquo;s going to replace the previous &ldquo;CONFIG&rdquo; data as well. Also, the original response data is saved in (or replaced, if it existed) &ldquo;config.conf,&rdquo; which is checked first when it&rsquo;s executed next time.</p>

<p>[Response]:</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-999.png" data-style="width: 600px; height: 553px;"/></p>

<p><strong>[Command 5/systeminfo]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/5/systeminfo32/</em></code></p>

<p>When the victim&rsquo;s system type is 32 bit, it sends command 5 to download &ldquo;systeminfo32,&rdquo; a 32-bit DLL that is used to steal the victim&rsquo;s system information. &ldquo;systeminfo64&rdquo; is for 64-bit systems. The request is sent to a C&amp;C server, whose IP address and port are obtained from Command 0&rsquo;s response. In my analysis, it is &ldquo;37.1.213.189:447.&rdquo; The encrypted systeminfo32 is saved as &ldquo;.\Modules\systeminfo32.&rdquo;</p>

<p>Later, it is executed in a newly-created process, &ldquo;svchost.exe,&rdquo; which focuses on collecting the victim&rsquo;s system information, including its Windows version, CPU type, RAM capacity, user accounts, installed software, and services. Here is the system information collected from my testing system.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1000.png" data-style="width: 600px; height: 808px;"/></p>

<p>Later, the data is sent to a C&amp;C server as body part of command 63 POST request, like this:</p>

<p><code><em>POST lindoc1/CLIENT_ID/63/systeminfo/GetSystemInfo/c3VjY2Vzcw==/systeminfo</em></code></p>

<p><strong>[Command 5/injectDll]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/5/injectDll32/</em></code></p>

<p>This is a command 5 &ldquo;Get&rdquo; request to download injectDll32 file from the C&amp;C server whose IP address comes from Command 0&rsquo;s response i.e. &ldquo;37.1.213.189:447.&rdquo; The encrypted injectDll32 is saved as &ldquo;.\Modules\injectDll32.&rdquo; In my analysis, this is a very important DLL, which finally is able to inject malicious code into web browsers (IE, Chrome and Firefox) or to monitor the victim&rsquo;s online banking. I will explain how it works in a later section.</p>

<p><strong>[Command 5/sinj]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/5/sinj/</em></code></p>

<p>This is kind of a configuration file for &ldquo;injectDll&rdquo;. It contains many online banks. The encrypted response data is saved in &ldquo;.\Modules\injectDll32_configs\sinj&rdquo;.</p>

<p><strong>[Command 5/dinj]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/5/dinj/ </em></code></p>

<p>This command will going to download &ldquo;dinj&rdquo; file. It&rsquo;s another configuration file for &ldquo;injectDll&rdquo; that also contains online bank information. It&rsquo;ll be saved in &ldquo;.\Modules\injectDll32_configs\dinj.&rdquo;</p>

<p>Below is an example.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1001.png" data-style="width: 450px; height: 313px;"/></p>

<p><strong>[Command 5/dpost]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/5/dpost/</em></code></p>

<p>This command downloads a dpost file from C&amp;C server, which contains another IP address and port that will work together with dinj. When the banks in the dinj file are matched, some stolen bank information will be sent to this IP address. It&rsquo;s also saved as &ldquo;.\Modules\injectDll32_configs\dpost.&rdquo; The content of this file looks like this:</p>

<p><em><dpost></dpost></em></p>

<p><em><handler>hxxp://188.138.1.53:8082</handler></em></p>

<p><strong>[Command 25]:</strong></p>

<p><code><em>GET /lindoc1/Client_ID/25/zm9ew0pP4BD8HxR5zzem/</em></code></p>

<p>Command 25 is used to get a new link to a bin file. The bin file is going to be the new version of TrickBot. Before exiting this child process, the downloaded bin file will replace the old TrickBot and gets executed by calling the <em>CreateProcessW</em> function. In this way it can update itself automatically. During my analysis I could see that the downloaded bin has been changed many times. They include:</p>

<div data-style="background:#eee;border:1px solid #ccc;padding:5px 10px;">
<p><em>hxxp://substan.merahost.ru/fog.bin</em></p>

<p><em>hxxp://susan.merahost.ru/sonya.bin</em></p>

<p><em>hxxp://susan.merahost.ru/shevchenko.bin</em></p>

<p><em>hxxp://susan.merahost.ru/kabzon.bin</em></p>

<p><em>hxxp://susanlaneg.temp.swtest.ru/kabzon2.bin</em></p>

<p><em>hxxp://susanlaneg.temp.swtest.ru/peter.bin</em></p>

<p><em>hxxp://susanlanegh.shn-host.ru/roma.bin</em></p>
</div>

<p><strong>How injectDll steals online banking information</strong></p>

<p>TrickBot keeps updating its config files from time to time. In the latest version of sinj and dinj files, it tries to steal online bank information from dozens of banks.</p>

<p>When injectDll32 is executed by svchost.exe, it enumerates all running processes to check if it&rsquo;s a browser by comparing process names. See the following code snippet for the details.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1002.png" data-style="width: 500px; height: 1070px;"/></p>

<p>From the above code, we know it only focuses on &ldquo;Chrome&rdquo;, &ldquo;IE&rdquo; and &ldquo;Firefox&rdquo; browsers. After it picks one process it uses the process ID to make a combination with a constant string as the name of pipe. This named pipe is then used to communicate between svchost.exe and the browser to transfer the content of sinj, dinj and dport. Then injectDll prepares the code that will be injected into browser, and calls <code><em>CreateRemoteThread</em></code> to execute the injected code. This can be seen in the following code snippet.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1003.png" data-style="width: 500px; height: 730px;"/></p>

<p>On the browser side, it creates several thread functions. One is to communicate with injectDll32 by named pipe, and others are to set Hook functions on some HTTP-related API functions and the keyboard.</p>

<p>It also creates the following registry entries, so that IE can be hooked and monitored better:</p>

<ul>
	<li>HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings\Zones\3\2500 = DWORD:3</li>
	<li>HKCU \Software\Microsoft\Internet Explorer\Main\TabProcGrowth = DWORD:0</li>
	<li>HKCU \Software\Microsoft\Internet Explorer\Main\NoProtectedModeBanner = DWORD:1</li>
</ul>

<p>In thread function1, it sends commands to the svchost.exe by that named pipe, to transfer bank information (i.e. the content of sinj, dinj and dpost) to browser. Later in thread function2, it is going to set some hooks on WinINet and Nss3 APIs. In this way, the injected code can capture all HTTP requests from the browsers. Then the local hook functions are able to do further filtering on the HTTP requests with the bank information. If the HTTP request matches the listed banks, this HTTP request will be copied and sent to the C&amp;C server. Let&rsquo;s see what functions are hooked.</p>

<p><strong>For WinINet:</strong></p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1004.png" data-style="width: 600px; height: 285px;"/></p>

<p><strong>For Nss3:</strong></p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1005.png" data-style="width: 600px; height: 111px;"/></p>

<p>Following 2 screenshots show the original entry code and the hooked entry code of <em>HttpSendRequestA</em>.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1006.png" data-style="width: 431px; height: 166px;"/></p>

<p align="center">Figure 7. Hooked entry code of HttpSendRequestA</p>

<p>It also sets a global keyboard hook so that it can monitor and collect the victim&rsquo;s keyboard input. In this hook function it checks to see if the keyboard input is from the browser controls. Figure 8 shows how the global keyboard hook is set.</p>

<p><img alt="" src="/content/dam/fortinet-blog/new-images/uploads/deep-analysis-of-the-online-banking-botnet-trickbot-1008.png" data-style="width: 431px; height: 212px;"/></p>

<p><strong>Conclusion</strong></p>

<p>Through this analysis, we know how TrickBot installs itself on victim&rsquo;s machine, and how it communicates with the C&amp;C server, as well as what and how it steals online banking information from the victim&rsquo;s browser, and finally how it upgrades itself from time to time.</p>

<p>Fortinet has published an IPS signature, &ldquo;Trick.Botnet&rdquo; to detect the communication between TrickBot and its C&amp;C servers.</p>
