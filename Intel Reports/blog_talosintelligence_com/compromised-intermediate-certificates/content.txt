    <h1 class="text-center">Compromised eMudhra intermediate certificates</h1>

    <div class="text-center m-1">
        <div class="post-author">
            <span>By </span>
                <a href="https://blog.talosintelligence.com/author/cisco/">Cisco Talos</a>
        </div>

        <br/>
        <time class="post-datetime" datetime="October 21, 2026 16:43">
            Wednesday, October 21, 2026 16:43
        </time>

        <div class="m-3">
                            <a href="/category/threat-advisory/" class="category primary-category">
                                Threat Advisory
                            </a>
                        
        </div>
    </div>

    <section class="post-content-wrapper mt-5">
        <div class="post-content" id="post-content">
            <p>Cisco Talos is aware of eight intermediate certificates belonging to the intermediate certificate authority, <a href="https://emudhra.com/en/post/certificate-security-incident">eMudhra</a>. Rather than possessing the mandatory 384 bits of pseudo-random security, several private keys evaluated single-digit and double-digit integers. This misconfiguration allows an attacker with the private key of any of the compromised intermediate CAs to impersonate any website or service. Six of the TLS certificates, trusted by Chrome, Mozilla, and Apple have been blocked by these vendors already. Two other certificates, used for codesigning by Microsoft, have also been blocked. Talos expects there will be additional patches available across a variety of technologies as software applications work to remediate the certificates’ exposure.</p><p>Following the disclosure, eMudhra has revoked the compromised certificates and stopped issuing new certificates under its G3 root.</p><h2 id="compromise-details">Compromise details</h2><p>The cause of this issue, originated during an April 30, 2025 key generation activity conducted by eMudhra under its&nbsp;emSign Root TLS CA - G3&nbsp;and cross-signed&nbsp;Comodo AAA Certificate Services. &nbsp;During a key generation ceremony for 24 subordinate CAs, a flaw in eMudhra’s key generation process created a second set of weak P-384 keys during a wrap/unwrap step. Those keys were mistakenly used for eight intermediate CA certificates.&nbsp;This flaw took the encryption from 384 bytes of entropy down to 3 – 8, making recovering the private keys trivial. The following are the impacted certificates, as illustrated in <a href="https://bugzilla.mozilla.org/show_bug.cgi?id=2083449">Mozilla’s bug report</a>:</p>

<p></p><h2 id="cve-2026-111943">CVE-2026-111943&nbsp;</h2><p>Unlike languages that defer entirely to external dynamic system libraries (like OpenSSL), the Go programming runtime implements its own X.509 chain verification engine in the standard library (crypto/x509). While Go usually queries platform certificates, several platforms or static container environments rely on embedded or legacy root certificate pools where certificate revocations are ignored.&nbsp;</p><p>To eliminate exploitation across the entire cloud-native ecosystem including Docker, Kubernetes, Terraform, and Prometheus, the Go team&nbsp;designated the compromised certificates as a vulnerability,&nbsp;<a href="https://www.cve.org/CVERecord?id=CVE-2026-111943">CVE-2026-111943,</a>&nbsp;and released Go versions&nbsp;1.27.3&nbsp;and&nbsp;1.26.10.&nbsp;</p><p>&nbsp;The fixed versions filter out chains containingthe SHA-256 hashes of the SubjectPublicKeyInfo (SPKI) for all eight compromised eMudhra intermediate certificates.</p><p></p><h2 id="impact">Impact</h2><p>These compromised certificates could allow adversaries to impersonate servers and intercept or modify traffic. The impact of their exposure is far more than just web browsers. Other programs that check for TLS certificates might still be impacted since they may not check revocation lists. One clear example is related to virtual private networks (VPNs); these technologies will likely require software updates to mitigate the issue. Based on this guidance, Talos strongly recommends users update software using and handling TLS certificates as fixes become available.</p><p>Talos is actively monitoring the impact of these compromised certificates and has not seen any malicious incidents involving them in the wild yet (as of October 21, 2026 14:00 UTC / 10:00 a.m. ET).</p><p></p><h2 id="significance-of-this-breach">Significance of this breach&nbsp;&nbsp;</h2><p>Public key infrastructure relies on trust being delegated through certificate chains: root CAs authorize intermediate CAs, which can issue certificates within the scope of their authority. An attacker who obtains an intermediate CA’s private key may be able to issue fraudulent certificates that clients accept, subject to the intermediate certificate’s constraints and each client’s validation controls. In this incident, six compromised intermediates were for TLS and two were for code signing.</p><p>&nbsp;For TLS, an attacker able to intercept or redirect a connection could use a fraudulent certificate to impersonate a server and potentially read or modify traffic if the client still trusts the affected key and no applicable protection blocks it. Protections such as revocation, key distrust, certificate transparency enforcement, and certificate pinning can prevent or expose such an attack. Browser vendors have blocked the affected TLS keys, but other applications may rely on separate trust stores or validation paths:</p><p></p><p><strong>Enterprise infrastructure and VPNs</strong></p><p>Organizations should assess TLS-using software and appliances, including proxies, reverse load balancers, VPN clients, and gateways. Exposure depends on the certificate chain being validated and the trust store and revocation behavior in use. A stale or separately managed trust store may need an application, operating-system, firmware, or trust-bundle update; verify the required action for each product.</p><p><strong>Software supply chains and CI/CD</strong></p><p>Build runners and package managers may be exposed if they fetch content over TLS while still trusting an affected key and an attacker can intercept the connection. A fraudulent TLS certificate could enable registry impersonation, but it would not by itself bypass separate package integrity checks, such as lockfile hashes, checksums, signatures, or provenance controls. Assess the actual package-manager configuration and dependency path.</p><p><strong>Industrial IoT and embedded systems</strong></p><p>Review devices that use bundled or independently managed CA stores, especially where certificate revocation or trust-store updates may be limited. Some devices may require a vendor update or compensating control, but the necessary action depends on each device’s validation and update mechanisms.</p><p>Talos recommends updating affected software and trust stores as vendor fixes become available.</p><p></p><h2 id="coverage">Coverage</h2><p>The following SNORT® SIDs provide coverage for this threat: 67363 - 67374.</p><p>&nbsp;</p><p>Talos would like to highlight the efforts of Chris Morrison for providing emergency coverage and mitigations for this threat.</p>

  function coverageView() {
    const coverageTable = document.getElementById('coverage-block');
    const sidebar = document.getElementById('side-bar');
    const postContent = document.getElementById('post-content');
    const currentWidth = window.innerWidth;  
  
    if (coverageTable && sidebar && postContent) {
      if (currentWidth < 1000) {
        // For viewport less than 1000px, append to post content
        postContent.appendChild(coverageTable);
      } else {
        // For viewport 1000px and wider, check for subscribe button
        const subscribeButton = sidebar.querySelector('.subscribe-button');
        
        if (subscribeButton) {
          // Insert coverage block after the subscribe button
          subscribeButton.insertAdjacentElement('afterend', coverageTable);
        } else {
          // No subscribe button found, prepend to top of sidebar
          sidebar.prepend(coverageTable);
        }
      }
    }
  }
  
  window.addEventListener("resize", coverageView);
  window.addEventListener("load", coverageView);
