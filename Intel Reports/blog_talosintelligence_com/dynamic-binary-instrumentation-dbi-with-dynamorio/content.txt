    <section class="post-content-wrapper mt-5">
        <div class="post-content">
            <ul><li>This blog introduces dynamic binary instrumentation (DBI) and guides you through building your own DBI tool with the open-source DynamoRIO framework on Windows 11.</li><li>DBI enables powerful runtime analysis and modification of binaries critical for malware analysis, security auditing, reverse engineering, and performance profiling — all without access to source code.</li><li>Learn DynamoRio's strengths, its practical applications in evading anti-analysis techniques, and step-by-step instructions for developing and testing your own instrumentation clients.</li><li>Explore hands-on examples with access to a GitHub repository with sample code to jumpstart your own research and tooling.</li></ul><p>Binary instrumentation involves inserting code into compiled executables to monitor, analyze, or modify their behavior — either at runtime (dynamic) or before execution (static) — without altering the original source code. Tools like DynamoRIO, Intel PIN, Valgrind, Frida, and QDBI are commonly used in the field. Static binary instrumentation (SBI) injects code before a binary runs, typically by modifying the file on disk, whereas dynamic binary instrumentation (DBI) operates in memory while the program runs. These techniques are widely used for profiling, debugging, tracing, security analysis, and reverse engineering.</p><h2 id="introduction-to-dynamorio">Introduction to DynamoRIO</h2><p><a href="https://dynamorio.org/"><u>DynamoRio</u></a> (DR) is a matured, well-maintained, and frequently updated open-source DBI framework. HP and the Massachusetts Institute of Technology (MIT) developed the first version in collaboration around 2000. Derek Bruening, DynamoRio's lead developer, described the main concept in his<a href="https://www.burningcutlery.com/derek/phd.html"> <u>PhD Dissertation</u></a> in 2004, and further information about the history of DR can be found<a href="https://dynamorio.org/page_history.html"> <u>here</u></a>.</p><p>The main reasons why Talos uses DR for Windows- and Linux-based malware analysis is its low performance impact at execution time, the excellent transparency (the target application does not recognize it is instrumented), and the open source license. Table 1 provides a brief comparison of some of the common instrumentation frameworks used in the industry. Please consider this as a general reference only, as this comparison might be biased by our use cases and may not remain accurate over time due to the ongoing development of the different frameworks. There is also not a best overall toolkit, as it depends on the use case.&nbsp;</p><p>It should also be noted that it always depends on the user code how well a certain instrumentation framework works. Even the best framework cannot fix bad user code.</p>

However, here are some examples:</p><h3 id="anti-anti-vm-detection">Anti-anti-VM detection</h3><p>Malware samples can be executed on real hardware and still be monitored and analyzed. Alternatively, VM detection functions can be patched at runtime to make sure the malware does not recognize it is running in a VM.</p><h3 id="anti-anti-analyzing-techniques">Anti-anti-analyzing techniques</h3><p>Malware uses many simple but common anti-X techniques (such as anti-debugging, anti-emulation, anti-tamper, anti-disassembler, self modification, etc.) that do not recognize DBI or do not have any impact on the DBI analysis. Many code runtime manipulation techniques which the frameworks are using are either transparent or hidden to the malware or the malware is just not trying to find them. The latter probably applies to the majority of malware today.&nbsp;</p><h3 id="de-obfuscation">De-obfuscation</h3><p>For example, code traces and memory dumps based on certain conditions can give the analyst a better idea of what the malware is actually doing.</p><h3 id="finding-interesting-functions-within-the-malware">Finding interesting functions within the malware</h3><p>It is relatively simple to build a shellcode execution detection tool with DBI to find a second stage in a packer by looking for functions which are allocating RWX memory, copying data into it and jumping into these memory areas later. You can also look for cryptographic constants which might be hidden in Mixed-Boolean-Arithmetic functions and are rebuilt at runtime to find unpacking routines or string obfuscation functions. Another example would be to count how often functions are called to find interesting functions which might be used to decode strings.</p><h3 id="dumping-memory-and-gather-runtime-information">Dumping memory and gather runtime information</h3><p>With DBI you can monitor the execution and get runtime values of registers or memory locations. You can also trigger on certain values of registers or other conditions to do dynamic memory dumps at runtime.&nbsp;&nbsp;</p><h3 id="automation">Automation</h3><p>Build an unpacker or config extractor for frequently seen malware families</p><h2 id="inside-dynamorio">Inside DynamoRio</h2><p>Before starting to write your own client, it is important to understand some basics about how DR works under the hood. DR is a process virtual machine (PVM). In the context of DR, this refers to a virtual execution environment that allows DR to dynamically instrument, monitor, and modify the behavior of a running application at the level of individual processes. DR operates entirely in user space (ignoring some experimental features). When DR starts a target application, it injects itself into the process and hooks or intercepts system calls. It takes control before the target application begins execution and starts copying the first basic block(s) of the target application into a code cache, which is a memory region DR has full control over. Then it redirects the execution flow to this code cache. This enables DR to monitor and modify the original instructions of the target application. It relocates addresses and modifies the target application code in a way that it is working semantically exactly like it would if it is executed natively (Figure 2).</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/Fig.1-1.jpg" class="kg-image" alt="" loading="lazy" width="1801" height="1291" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/Fig.1-1.jpg 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/Fig.1-1.jpg 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/Fig.1-1.jpg 1600w, https://blog.talosintelligence.com/content/images/2025/10/Fig.1-1.jpg 1801w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 1. Code Cache transformation.</span></figcaption></figure><p>For performance optimization, the basic block code cache is extended with a trace cache (Figure 3). DR monitors and measures the execution of basic blocks in the basic block cache and builds groups of basic blocks which are frequently executed in the same order. At a certain threshold it combines these basic blocks and copies them into the trace cache including the instrumentation code and some inline checks. In reality, it is not a simple counter, it depends on multiple factors. This technique speeds up the execution time due to the fact that less context changes are necessary. In this context a context change means a switch between the target application code and DRs core and dispatching routines.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/Fig.3.jpg" class="kg-image" alt="" loading="lazy" width="1801" height="1291" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/Fig.3.jpg 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/Fig.3.jpg 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/Fig.3.jpg 1600w, https://blog.talosintelligence.com/content/images/2025/10/Fig.3.jpg 1801w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 3. DynamoRio code cache and trace cache diagram.</span></figcaption></figure><p>All these operations should be transparent/hidden to the target application. It should appear to the program as if it were running natively on hardware — unaware of and unaffected by any instrumentation. DR takes care about the following side effects:</p><ul><li>Register states: DR saves and restores all registers it modifies so that the application sees the original values.</li><li>Stack and memory: Internal data used by DR (e.g., for managing its own state) is hidden from the application.</li><li>Instruction semantics: A transformed or instrumented instruction behaves identically to the original — no change in meaning or side effects.</li><li>Control flow: Even if DR adds trampolines or modifies jumps, the logical flow of execution remains the same from the program’s point of view.</li><li>Signals and exceptions: Any exceptions (e.g., SIGSEGV) or signals are handled in a way that preserves original behavior and context.</li></ul><p>More details can be found <a href="https://dynamorio.org/overview.html#sec_intro"><u>here</u></a>.</p><h2 id="writing-a-simple-client">Writing a simple client</h2><p>The development environment used:</p><ul><li>Windows 11 Version 24H2 (Default Settings)</li><li>Visual Studio 2019, CMAKE (incl. in VS)<ul><li>The DR homepage recommends VS 2019 for building its source code, for building clients with the latest DR version, but VS 2022 might work in most cases too. RDTSC runtime check.</span></figcaption></figure><p><strong>Result:</strong> As long as you do not do foolish things, such as insert too much code at runtime or instrument a large loop inside the target application, DR is usually fast enough to avoid detection. Of course, this depends on the kind of instrumentation you do and on how aggressive the timer is set. DR usually adds a delay of between 2 – 10 times that of the original execution time.&nbsp;</p><p>Test case: Large loops</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/fig19.png" class="kg-image" alt="" loading="lazy" width="1750" height="476" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/fig19.png 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/fig19.png 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/fig19.png 1600w, https://blog.talosintelligence.com/content/images/2025/10/fig19.png 1750w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 19. Large loop test.</span></figcaption></figure><p><strong>Result:</strong> Similar to the above, you don’t want to instrument something inside this loop, but anything outside is no problem.</p><h3 id="test-case-self-modifying-code">Test case: Self-modifying code</h3><p>In our self-modifying code, we are doing multiple things:</p><ul><li>Pre-patching code: This means we patch the code soon before it is executed.</li><li>Post-patching code: This means we patch the code after it is executed, and the next time this function is called the patch will be executed instead of the original code.</li><li>Interleave jumps: We jump in between the bytes of an instruction, which converts the bytes of the instruction into another instruction. In our case a “mov” instruction becomes a “jmp” instruction. This not only changes the instruction, but also the control flow graph (CFG) at runtime. We want to verify if this has an impact on the Basic Block and Trace Cache mentioned above.</li></ul><p>First, let’s have a closer look at the self-modifying code which we are using. Here you can see the pre-patch code. It converts the original “jmp end_label” instruction to a “mov rax,3” instruction. Once again, it is not only the instruction that is being changed; the control flow graph (CFG) is also being modified.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/fig20.png" class="kg-image" alt="" loading="lazy" width="1827" height="1554" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/fig20.png 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/fig20.png 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/fig20.png 1600w, https://blog.talosintelligence.com/content/images/2025/10/fig20.png 1827w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 20. Self modifying code: Pre-patch code.</span></figcaption></figure><p>The next one is the post-patch, which is similar to the pre-patch and overwrites a “mov rax,1234” with a “mov rax,1”, but this modification is done after the code was executed. This means when the function is called the next time, the values in rax and rbx are not equal anymore, the comparison later fails, and the jump is not taken.&nbsp;</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/fig21.png" class="kg-image" alt="" loading="lazy" width="2000" height="1130" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/fig21.png 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/fig21.png 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/fig21.png 1600w, https://blog.talosintelligence.com/content/images/size/w2400/2025/10/fig21.png 2400w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 21. Self modifying code: Post-patch code.</span></figcaption></figure><p>Last but not least, in the middle of the function, we do the interleave trick. The “test rax,rax” will set ZF=0 (RAX = 3) which means the “jz” will not be taken and the “jnz” will be taken. Some static disassemblers get confused by this and disassemble the byte starting with “048h, 0C7h, …” to a “mov rax, 0FFFFFFFF90900CEB”, because they do not realize that these bytes are never executed.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/fig22.png" class="kg-image" alt="" loading="lazy" width="2000" height="1125" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/fig22.png 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/fig22.png 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/fig22.png 1600w, https://blog.talosintelligence.com/content/images/size/w2400/2025/10/fig22.png 2400w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 22.Self-modifying code: Interleave trick (part 1).</span></figcaption></figure><p>Only after manually converting it, the disassembler shows the jmp (= EB 0C), in other words the byte we jnz’ed to. Again, we want to see if DR’s code cache generator or dispatcher gets confused by this.&nbsp;</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/fig23.png" class="kg-image" alt="" loading="lazy" width="2000" height="1123" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/fig23.png 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/fig23.png 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/fig23.png 1600w, https://blog.talosintelligence.com/content/images/size/w2400/2025/10/fig23.png 2400w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 23. Self-modifying code: Interleave trick (part 2).</span></figcaption></figure><p><strong>Result:</strong> The self-modifications are working as expected. DR executes everything like it would on a real CPU. These self modifications were no problem for DR.&nbsp;</p><p>The screenshot below is from the simple_client3 DR client run against the anti-x target application mentioned above, which is doing a code trace over the self modifying function. We deleted all messages from the client output, except the instruction related output.</p><p>The left side is the instruction trace showing when the self modifying function was called the first time. The right side is the second call of the self modifying function.&nbsp;</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://blog.talosintelligence.com/content/images/2025/10/fig24.png" class="kg-image" alt="" loading="lazy" width="2000" height="1028" srcset="https://blog.talosintelligence.com/content/images/size/w600/2025/10/fig24.png 600w, https://blog.talosintelligence.com/content/images/size/w1000/2025/10/fig24.png 1000w, https://blog.talosintelligence.com/content/images/size/w1600/2025/10/fig24.png 1600w, https://blog.talosintelligence.com/content/images/size/w2400/2025/10/fig24.png 2400w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 24. Self modifying code: Result.</span></figcaption></figure><h2 id="summary">Summary</h2><p>DR offers a wide range of built-in capabilities to counter common malware anti-analysis techniques. However, some methods can still detect or circumvent DR; these were intentionally excluded from this blog to avoid aiding malware authors. In this post, we introduced how to use DR for malware analysis and demonstrated how it can help bypass typical anti-analysis measures with minimal effort. We hope this helps readers get started with DR and encourages you to contribute to our GitHub project. Have fun exploring DBI and DynamoRIO!</p><p></p><p></p>
