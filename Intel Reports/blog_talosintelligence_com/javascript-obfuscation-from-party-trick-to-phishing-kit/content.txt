    <h1 class="text-center">JavaScript obfuscation: From party trick to phishing kit</h1>

    <div class="text-center m-1">
        <div class="post-author">
            <span>By </span>
                <a href="https://blog.talosintelligence.com/author/james-hodgkinson/">James Hodgkinson</a>
        </div>

        <br/>
        <time class="post-datetime" datetime="August 27, 2026 06:00">
            Thursday, August 27, 2026 06:00
        </time>

        <div class="m-3">
                        <a href="https://blog.talosintelligence.com/category/tool-talk/" class="category primary-category">
                            Tool Talk
                        </a>
                            </div>
    </div>

    <section class="post-content-wrapper mt-5">
        <div class="post-content" id="post-content">
            <p>We open a JavaScript artifact hoping for code, and instead get string arrays, strangely named functions, encoded URLs, runtime decoders, and eval statements. That is the point where “reading the script” stops being enough. Obfuscated JavaScript is still code, but it is code with the useful context stripped out, the names ruined, the strings hidden, and the real behavior pushed into runtime. It shows up in phishing pages, malware loaders, sketchy browser scripts, and occasionally in legitimate software protection that has wandered into suspicious-looking territory.&nbsp;</p><p>Over the last few years, I’ve spent a fair amount of time pulling apart suspicious JavaScript from phishing kits, malware packages, compromised sites, and other places where the readable source has been deliberately buried. I might not be a world-class JavaScript reverser, but I’ve learned enough useful tricks to make the mess explain itself.&nbsp;</p><p>In this post I’ll be running through what obfuscation is, why we would try to get past it, and some ways to approach the problem.&nbsp;</p><p>Warning: lots of code (and entirely contrived examples) ahead.</p><h2 id="before-touching-the-weird-code">Before touching the weird code&nbsp;</h2><p>Before doing any of this, assume the sample is hostile. Work on a copy, preserve the original, and do not run unknown JavaScript on your normal machine, in your normal browser profile, or anywhere useful credentials, clipboard contents, SSH agents, npm tokens, cloud credentials, or corporate proxy details are available.&nbsp;</p><p>That includes AI-assisted analysis. AI tools are useful here, and this whole workflow leans on them, but they are not a sandbox and they are not an evidence source by themselves. Use them on isolated snippets, decoded artifacts, and recovered payloads you are comfortable sharing with the tool in front of you. The goal is not to avoid AI; it is to avoid feeding hostile or sensitive material into places you do not control.&nbsp;</p><p>The useful questions are boring, which is why they work:&nbsp;</p><ul><li>What does it read?&nbsp;</li><li>What does it write?&nbsp;</li><li>Where does it connect?&nbsp;</li><li>What code does it generate?&nbsp;</li><li>What conditions change its behavior?&nbsp;</li><li>What happens to a real user, developer, or build runner?&nbsp;</li></ul><h2 id="what-counts-as-obfuscation">What counts as obfuscation?&nbsp;</h2><p>Let's make some important definitions:&nbsp;</p><ul><li><strong>Minification</strong> reduces raw code size by shortening identifiers and removing whitespace.&nbsp;</li><li><strong>Packing</strong> compresses or encodes code and reconstructs it at runtime.&nbsp;</li><li><strong>Encoding </strong>hides strings or payloads until decoded; <strong>encryption </strong>does the same with a key involved.&nbsp;</li><li><strong>Anti-analysis</strong> tries to punish, detect, or mislead the analyst and their tools.&nbsp;</li><li><strong>Obfuscation</strong> is an overall term for when code is transformed to preserve execution while obscuring intent.&nbsp;</li></ul><p>Not all obfuscation is malicious, but it can be a reason to look more closely. Examples of benign uses include performance bundling/minification, IP protection and anti-tamper controls.&nbsp;</p><p>Examples of suspicious uses are:&nbsp;</p><ul><li>Hiding phishing credential exfiltration&nbsp;</li><li>Malware loaders&nbsp;</li><li>Browser extension abuse&nbsp;</li><li>npm package install scripts&nbsp;</li><li>Compromised website injections&nbsp;</li><li>Fake CAPTCHA and update flows</li></ul><h2 id="why-beautifying-is-not-enough">Why beautifying is not enough&nbsp;</h2><p>Beautifying code is useful, but it is not deobfuscation. Tools like <a href="https://biomejs.dev/" rel="noreferrer noopener"><u>Biome</u></a> or <a href="https://prettier.io/" rel="noreferrer noopener"><u>Prettier</u></a> can restore indentation line breaks and basic readability, so they are usually a sensible first step. What they cannot do is restore original variable names, recover intent, rebuild removed structure, decode runtime strings, or turn a dispatcher loop back into normal logic.&nbsp;</p><p>Beautifying makes the code easier to look at. It does not necessarily make it easier to understand.&nbsp;</p><h2 id="minification-and-packing">Minification and packing&nbsp;</h2><p>Minification takes identifiers like <code>myVeryImportantBusinessFunction</code> and renames them to <code>m</code>. Great for saving bytes; less great when the original name was the only obvious clue about what the function did.&nbsp;</p><p>Packing goes further: Compress or encode the real code, then reconstruct and execute it at runtime. <code>eval()</code> does not care whether the input started life as readable JavaScript, Base64, gzip output, or a custom string table.&nbsp;</p><p>The usual move is to find the unpacking step and capture what comes out. Do not spend too long admiring the wrapper. Replace the execution sink, log the payload, decode the next layer, and keep going.</p><h2 id="a-practical-catalog-of-nonsense">A practical catalog of nonsense&nbsp;</h2><p>Most JavaScript obfuscation is not one grand technique. It is a collection of smaller tricks stacked together until the useful behavior disappears under ceremony.&nbsp;</p><p>I normally group the tricks into a few buckets:&nbsp;</p><ul><li>Hiding strings and identifiers&nbsp;</li><li>Hiding which APIs are being called&nbsp;</li><li>Generating code at runtime&nbsp;</li><li>Making the control flow hostile&nbsp;</li><li>Detecting or punishing analysis&nbsp;</li><li>Adding noise without changing behavior&nbsp;</li></ul><p>Once you can classify the trick, the next move is usually obvious: Decode it, rename it, replace the action-taking functionality, then run it in a controlled harness — or ignore it because it does not affect behavior.&nbsp;</p><h3 id="static-hiding">Static hiding&nbsp;</h3><p>This is obfuscation that makes the code harder to understand <em>before it runs</em>, usually by disguising strings, identifiers, API names, or structure so simple reading and searching become less useful.&nbsp;</p><p><strong>String hiding and encoding</strong>&nbsp;</p><p>If strings are hidden, the author probably cares about what simple scanning would find. This is especially useful when they need to include things like URLs, authentication tokens, common functions, or other interesting indicators.&nbsp;</p><p>All these lines evaluate into the string "eval":</p>
<!--kg-card-begin: html-->
<pre>// Splitting strings 
> 'e'+"va"+'l' 
< 'eval' 
// Hex encoding 
> "\x65\x76\x61\x6c" 
< 'eval' 
// Character-code reconstruction 
> String.fromCharCode(101, 118, 97, 108) 
< 'eval' 
// Base64 encoding 
> atob('ZXZhbA==') 
< 'eval' 
// Unicode encoding 
> "\u0065\u0076\u0061\u006C" 
< 'eval'</pre>
<!--kg-card-end: html-->
<p>Another option is arrays of strings joined together. It hides from simple searches but is transparent at runtime. This example turns into `"https://"`, which means a basic string search for URLs may miss it.</p>
<!--kg-card-begin: html-->
<pre>> ["ht", "tps", "://"].join("") 
< "https://"</pre>
<!--kg-card-end: html-->
<p>Unicode escaping can also be used to refer to a function — we're doing <code>eval(1+2)</code> here:</p>
<!--kg-card-begin: html-->
<pre>> \u0065\u0076\u0061\u006C(0x01+2) 
< 3 
// set the variable 'eeee' equal to 1 
> const \u0065\u0065\u0065\u0065=1; 
> eeee 
1</pre>
<!--kg-card-end: html-->
<p>Combine a few of these methods and you get code that hides in plain sight from simple searches, but not from execution. Small blocks like this are also where AI tools can help: decode the string, rename the variables, and explain the resulting behavior.&nbsp;</p><p><strong>Lookup tables and decoder functions&nbsp;</strong></p><p>A common pattern is using identifiers that start with <code>_0x</code>, which makes the code harder to scan quickly. Here's an example:</p>
<!--kg-card-begin: html-->
<pre>
const _0x1234 = ["fetch", "password", "https://example.com"]; 
// javascript has a load of different syntaxes for creating functions 
_0xabc = (i) => { 
  return _0x1234[i - 0x10]; 
} 
\u0065\u0076\u0061\u006C(`${_0xabc(16)}(\"${_0xabc(18)}?${_0xabc(17)}\")`) 
</pre>
<!--kg-card-end: html-->
<p>If you want to do it by hand, the first quick move is renaming things:</p>
<!--kg-card-begin: html-->
<pre>const ourSneakyItems = ["fetch", "password", "https://example.com"]; 
function lookup(i) { 
  return ourSneakyItems[i - 16]; 
} 
eval(`${lookup(16)}(\"${lookup(18)}?${lookup(17)}\")`) 
</pre>
<!--kg-card-end: html-->
<p>Then you can collapse the lookups into their values:</p>
<!--kg-card-begin: html-->
<pre>
eval(`fetch("https://example.com?password")`) 
</pre>
<!--kg-card-end: html-->
<p>Modern IDEs are very handy here. Formatting makes the code less awful to read, and refactoring tools make repeated renaming less error-prone. AI tools can also do this well, assuming you pass in small blocks without stripping away the context needed to understand them.&nbsp;</p><p><strong>Dynamic property access</strong>&nbsp;</p><p>JavaScript gives you several ways to refer to the same property:</p>
<!--kg-card-begin: html-->
<pre>> window.document.cookie 
> window["document"].cookie 
> window["doc" + "ument"]["coo" + "kie"] 
</pre>
<!--kg-card-end: html-->
<p>This is great for hiding references to sensitive APIs from simple text searches.&nbsp;</p><p><strong>Dead code and noise</strong>&nbsp;</p><p>Dead code and distracting noise are common in JavaScript obfuscation. The code may contain fake branches that can never execute, unused functions with dramatic names, pointless arithmetic that always resolves to the same value, bogus conditionals that pretend to make decisions, random strings that look like domains or keys, and helper functions whose only real job is to make you scroll.&nbsp;</p><p>None of it has to be clever. It just has to be annoying enough that you spend time proving it does not matter.</p><h3 id="runtime-hiding">Runtime hiding&nbsp;</h3><p>This is obfuscation that only reveals the interesting behavior <em>while the code is running</em>, often by decoding payloads, generating code, checking the environment, or changing behavior based on timers, domains, browsers, or sandbox conditions.&nbsp;</p><p><strong>Runtime code generation</strong>&nbsp;</p><p>This is where the code stops merely hiding strings and starts constructing executable behavior at runtime. Packing and encoding often rely on this pattern, because the sample begins with string-like data and then asks the runtime to execute whatever gets reconstructed.</p><p>Generated code may come from embedded strings, downloaded payloads, runtime assembly, or less obvious sources such as DOM state or image data. The useful move is to replace execution sinks with logging: Turn <code>eval(payload)</code> into <code>console.log(payload)</code>, capture the intermediate code, and analyze that next layer separately.</p>
<!--kg-card-begin: html-->
<pre>eval(<insert code here>) 
Function(<insert code here>) 
setTimeout("<insert code here>")</pre>
<!--kg-card-end: html-->
<p><strong>Control-flow flattening</strong>&nbsp;</p><p>Another common trick is turning normal program flow into a state machine or dispatcher loop. Instead of reading top-to-bottom as “do this, then that,” the code jumps through numbered states, lookup tables, and artificial branches until the original intent is buried under plumbing. The result is technically readable in the same way a wiring diagram is readable: All the parts are there, but the meaning has been made deliberately hostile. Beautifying makes this neater, but it does not recover the original flow.</p>
<!--kg-card-begin: html-->
<pre>
let state = 0; 
let data = {}; 
while (state !== 3) { 
  state = [ 
    () => { 
      data["p"] = "hunter2"; 
      return 1; 
    }, 
    () => { 
      console.log("Sending password:", data["p"]); 
      return 3; 
    } 
  ][state](); 
} 
</pre>
<!--kg-card-end: html-->
<p>What that really was:</p>
<!--kg-card-begin: html-->
<pre>console.log("Sending password:", "hunter2"); </pre>
<!--kg-card-end: html-->
<p><strong>Anti-debugging and anti-analysis</strong>&nbsp;</p><p>Some obfuscated JavaScript is less interested in being unreadable and more interested in being inconvenient to inspect. It may drop debugger statements into loops, so DevTools keeps tripping over itself, check whether DevTools is open, compare timing differences to spot breakpoints, or look for headless-browser fingerprints such as <code>navigator.webdriver</code>. It may refuse to run outside an expected domain, alter or replace <code>console.log</code> so useful output disappears, probe for sandbox artifacts, or delay execution long enough that a quick scan sees nothing interesting. These tricks are not magic and they are not unbeatable, but they change the analyst’s workload.&nbsp;&nbsp;</p><p>The code may not be trying to hide forever. It may only be trying to outlast the first five minutes of analysis.</p><h2 id="jsfuck-punctuation-soup-with-consequences">JSFuck: Punctuation soup with consequences&nbsp;</h2><p>Inspired by <a href="https://esolangs.org/wiki/BrainFuck" rel="noreferrer"><u>BrainFuck</u></a>, <a href="https://esolangs.org/wiki/JSFuck" rel="noreferrer noopener"><u>JSFuck</u></a> is valid JavaScript written using only six characters: <code>[</code><strong> </strong><code>]</code><strong> </strong><code>(</code> <code>)</code> <code>!</code> <code>+</code>.&nbsp;</p><p>It relies on JavaScript type <a href="https://www.w3schools.com/js/js_type_coercion.asp" rel="noreferrer noopener"><u>coercion</u></a> to build values like false, true, undefined, numbers, strings, and eventually executable code. The result looks ridiculous, but it is still valid JavaScript.</p><p>Tricks for handling this breed of nonsense:</p><ul><li>Don’t manually decode it by staring at it.</li><li>Recognize it, then use a decoder or controlled runtime capture.</li><li>Look for what it produces, not how elaborate the construction is.</li></ul><p>For more complicated samples, I’ve had success using headless Chrome in a debugging harness and pulling the real code out of runtime state. It’s messy, but it beats treating the punctuation as the interesting part.</p><h2 id="javascript-obfuscator-the-practical-nuisance">javascript-obfuscator: the practical nuisance&nbsp;</h2><p>You are less likely to meet a hand-crafted masterpiece of JavaScript weirdness and more likely to meet output from tools like the npm package “javascript-obfuscator” or “obfuscator[.]io”.&nbsp;</p><p>These tools automate the usual techniques: identifier renaming, string-array extraction, string encoding, string rotation, control-flow flattening, dead-code injection, debug protection, self-defending code, domain locks, and console output disablement.&nbsp;</p><p>The result is not necessarily sophisticated, but it is practical and repeatable. Rather than understanding every trick individually, a phishing kit author or malware operator can run the code through a tool and produce something that is slower to read, harder to search, more annoying to debug, and more likely to survive casual inspection.&nbsp;</p><h2 id="when-the-browser-is-not-the-victim">When the browser is not the victim&nbsp;</h2><p>The npm version is more serious because the browser is no longer the only execution environment. Package scripts can run during install, so preinstall, postinstall, build hooks, and even test scripts become interesting places to hide behavior.&nbsp;</p><p>In Node, obfuscated JavaScript can reach <code>process.env</code>, the file system, child processes, home directories, npm tokens, GitHub tokens, SSH keys, and CI variables. Browser-only assumptions break badly here: “What does it read?” stops meaning cookies and form fields, and starts meaning, “What secrets did the build runner have lying around?”</p><h2 id="the-shape-of-the-workflow">The shape of the workflow&nbsp;</h2><p>The full workflow deserves its own article, because this is where tooling starts to matter. The short version is:&nbsp;</p><ol><li>Preserve the original.&nbsp;</li><li>Make a safe working copy.&nbsp;</li><li>Beautify only as a first pass.&nbsp;</li><li>Extract strings.&nbsp;</li><li>Identify execution sinks.&nbsp;</li><li>Capture generated payloads.&nbsp;</li><li>Observe behavior in a controlled environment.&nbsp;</li><li>Repeat until the code stops hiding behind ceremony.&nbsp;</li></ol><p>That process is boring on purpose. Obfuscation wants you to improvise, stare at weird bits, and get dragged into fake complexity. A repeatable workflow turns the mess into smaller jobs: Decode this, rename that, log this sink, compare these strings, explain this branch, prove whether this behavior actually runs.&nbsp;</p><p>AI helps inside that loop. It can explain an isolated decoder, rename variables, collapse a lookup table, summarize a recovered payload, compare variants, or help document the analysis — but it is not a magic malware oracle, and it is <em>definitely </em>not a sandbox.&nbsp;</p><p>That applies whether the sample is a phishing page, a malicious npm package, a compromised dependency, or a JavaScript loader handing work off to WASM. The shapes change, but the job is the same: Turn hidden behavior into observable behavior.&nbsp;</p>
