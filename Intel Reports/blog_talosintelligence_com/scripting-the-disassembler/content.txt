    <h1 class="text-center">Scripting the disassembler: Local agentic reverse engineering through vbdec’s live COM object model</h1>

    <div class="text-center m-1">
        <div class="post-author">
            <span>By </span>
                <a href="https://blog.talosintelligence.com/author/david-zimmer/">David Zimmer</a>
        </div>

        <br/>
        <time class="post-datetime" datetime="June 18, 2026 06:00">
            Thursday, June 18, 2026 06:00
        </time>

        <div class="m-3">
                        <a href="https://blog.talosintelligence.com/category/tool-talk/" class="category primary-category">
                            Tool Talk
                        </a>
                                            <a href="https://blog.talosintelligence.com/category/ai/" class="category primary-category">
                            AI
                        </a>
                            </div>
    </div>

    <section class="post-content-wrapper mt-5">
        <div class="post-content" id="post-content">
            <ul><li>Analysis tools do not need AI built in to support agentic workflows; they simply need to expose their data through an external scripting interface.&nbsp;</li><li>Even traditional&nbsp;graphical user interface (GUI)&nbsp;applications can be made AI-accessible by publishing their internal object models, allowing agents to query and automate analysis without&nbsp;modifying&nbsp;the core application.&nbsp;</li><li>This approach can often be implemented with surprisingly little engineering effort,&nbsp;leveraging&nbsp;existing scripting technologies and&nbsp;application&nbsp;data structures.&nbsp;</li><li>By exposing structured data rather than adding predefined AI features, users can extend a&nbsp;tool's&nbsp;capabilities through prompts, turning new analyses into workflows instead of product feature requests.&nbsp;</li><li>The application becomes both an interactive viewer and a persistent data server, enabling local data to be parsed once and queried repeatedly across multiple agent sessions while keeping analyst-controlled data local.</li></ul><hr><h2 id="the-problem-with-vb6-binaries">The&nbsp;problem with VB6&nbsp;binaries&nbsp;</h2><p>VB6 binaries are laid out as a complex file format with embedded metadata. Recovering&nbsp;advanced data embeddings means reimplementing VB6s’&nbsp;internal file format: the VB header, the object table,&nbsp;and&nbsp;the P-code layout. This is a highly specialized task that takes dedicated tools to do accurately, but not every tool exposes an equivalent programmatic library. The technique in this&nbsp;blog shows&nbsp;how AI agents can automate existing tools and reach deep into the result set.</p><h2 id="the-recipe">The&nbsp;recipe&nbsp;</h2><p>The whole technique&nbsp;comprises&nbsp;three pieces. Any one of them in isolation is interesting, but&nbsp;together they are a new working mode.&nbsp;</p><h3 id="the-live-model">The&nbsp;live&nbsp;model&nbsp;</h3><p><a href="https://sandsprite.com/vbdec/" rel="noreferrer noopener"><u>vbdec</u></a>&nbsp;does not keep its parsed model locked behind its GUI. When a binary is loaded and remote scripting is enabled (Help → Options → Enable Remote Scripting),&nbsp;vbdec&nbsp;registers its central&nbsp;<code>CVBProject</code>&nbsp;object and its main form in the Windows&nbsp;<a href="https://github.com/dzzie/tests/blob/master/rot_test_3/CRemotelyScriptable.cls" rel="noreferrer noopener"><u>Running Object Table</u></a>&nbsp;(ROT)&nbsp;under the monikers&nbsp;<code>vbdec.vbp</code>&nbsp;and&nbsp;<code>vbdec.frmMain</code>. The ROT is a system-wide directory of live&nbsp;Component Object Model (COM)&nbsp;objects; any process can look an object up by moniker and receive a reference to the running instance. From a script, that is a single line:</p>
<!--kg-card-begin: html-->
<pre>Set o = GetObject("vbdec.vbp")</pre>
<!--kg-card-end: html-->
<p>The variable&nbsp;<code>o</code>&nbsp;can now access the entire parsed project: every form, class, module, declared API, P-code body, control, and string, presented as a navigable object graph. The script is driving the disassembler itself.&nbsp;</p><p><strong>Note:</strong>&nbsp;For VB6&nbsp;host applications in particular, this capability can even be forcefully added&nbsp;<a href="https://www.gendigital.com/blog/insights/research/scripting-arbitrary-vb6-applications" rel="noreferrer noopener"><u>without source code access</u></a>.</p><h3 id="the-contract">The&nbsp;contract&nbsp;</h3><p>A live model is useless to an agent that does not know its shape.&nbsp;vbdec&nbsp;now includes an AI agent&nbsp;<a href="https://sandsprite.com/vbdec/vbdec_ai.zip" rel="noreferrer noopener"><u>support package</u></a>&nbsp;that helps bridge this gap. The first is the&nbsp;operator briefing (“_claude_vbdec_ai_instructions.txt”) — a short markdown file that tells the agent what&nbsp;vbdec&nbsp;is, how to bind to the ROT,&nbsp;and&nbsp;how the object model is shaped. The second is the&nbsp;proto folder&nbsp;—&nbsp;90&nbsp;auto-generated&nbsp;class&nbsp;definitions covering every public class and form&nbsp;vbdec&nbsp;exposes. The agent treats these as the authoritative reference for member names and types. (The original&nbsp;IntelliSensesupport files were also usable for this&nbsp;task.)</p><h3 id="the-local-agent">The&nbsp;local&nbsp;agent&nbsp;</h3><p>The third piece is the agent.&nbsp;In this blog,&nbsp;Talos used&nbsp;Claude Code, run locally on the workstation. The user opens a terminal, points the AI at the briefing and prototypes, and simply describes what they would like analyzed. Claude Code then runs multiple&nbsp;.vbs&nbsp;files with&nbsp;cscript&nbsp;and&nbsp;explores the data through iterations. There is no preselected AI integration embedded in&nbsp;vbdec, no upload for the analyst’s binary,&nbsp;and&nbsp;no glue to be&nbsp;maintained&nbsp;as a separate codebase. The agent and disassembler share a machine and file&nbsp;system; analysis occurs locally, with only the model inference requests leaving the workstation.&nbsp;&nbsp;</p><p>Whatever capability the agent adds next&nbsp;extends&nbsp;vbdec&nbsp;without any new code in the tool itself,&nbsp;and users are free to select whichever model they prefer.</p><h2 id="what-the-analyst-actually-does">What the&nbsp;analyst&nbsp;actually&nbsp;does&nbsp;</h2><p>Next are a couple examples tested against a&nbsp;P-code version of PDFStreamDumper.</p><h3 id="decompile-a-function">Decompile a&nbsp;function&nbsp;</h3><p>The analyst names a function and asks for a source code reconstruction. The agent pulls the P-code, walks the VB-VM opcode stream, maps each construct to its VB6 equivalent, and produces a source level equivalent with inline comments.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/2026/06/claude_decompile_pcode.png" class="kg-image" alt="" loading="lazy" width="1341" height="711" srcset="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w600/2026/06/claude_decompile_pcode.png 600w, https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w1000/2026/06/claude_decompile_pcode.png 1000w, https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/2026/06/claude_decompile_pcode.png 1341w" sizes="(min-width: 720px) 720px"><figcaption><i><em class="italic" style="white-space: pre-wrap;">Figure 1.</em></i> <i><em class="italic" style="white-space: pre-wrap;">Example output</em></i> <i><em class="italic" style="white-space: pre-wrap;">(right)</em></i> <i><em class="italic" style="white-space: pre-wrap;">compared to the original source function</em></i> <i><em class="italic" style="white-space: pre-wrap;">(left).</em></i></figcaption></figure><p>The reconstruction is not byte-identical, but the control flow is&nbsp;substantially recovered&nbsp;with agent comments added in.&nbsp;It is also interesting to note that the AI went into the subfunctions&nbsp;on its own, determined their purpose, and gave them reasonable names to complete its task decompiling the parent.&nbsp;This is usable reverse-engineering output that a human would spend&nbsp;substantial time producing, now&nbsp;scalable and&nbsp;generated in seconds.</p><h3 id="build-a-call-graph">Build a&nbsp;call&nbsp;graph&nbsp;</h3><p>The analyst picks a function and asks for its callees as a&nbsp;Graphviz&nbsp;DOT file. The agent walks each&nbsp;<code>CCodeBody.Disasm</code>, picks out the call opcodes (<code>ImpAdCallI2</code>,&nbsp;<code>VCallHresult</code>,&nbsp;<code>LateMemCall</code>, and others) and emits the DOT graph with depth tracking.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/2026/06/AI-tool.jpg" class="kg-image" alt="" loading="lazy" width="2000" height="1887" srcset="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w600/2026/06/AI-tool.jpg 600w, https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w1000/2026/06/AI-tool.jpg 1000w, https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w1600/2026/06/AI-tool.jpg 1600w, https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w2400/2026/06/AI-tool.jpg 2400w" sizes="(min-width: 720px) 720px"><figcaption><i><em class="italic" style="white-space: pre-wrap;">Figure 2. Example output for a target in</em></i> <i><em class="italic" style="white-space: pre-wrap;">PDFStreamDumper.</em></i></figcaption></figure><h3 id="dump-every-function-to-sql">Dump&nbsp;every&nbsp;function to SQL&nbsp;</h3><p>To test a real automation-heavy use,&nbsp;the agent&nbsp;was next asked&nbsp;to&nbsp;enumerate&nbsp;every function in the binary and dump&nbsp;stats&nbsp;to a SQLite database&nbsp;including&nbsp;address, size, module, instruction count, callees, and external API calls. The agent did this in a single&nbsp;<code>cscript</code>&nbsp;pass over&nbsp;<code>o.CodeObjects</code>, classifying calls with the same rules used in the graph task. For&nbsp;PDFStreamDumper&nbsp;the result is a 600+-row database. Now the database can be explored with simple queries such as:</p>
<!--kg-card-begin: html-->
<pre>SELECT display_name FROM functions WHERE api_calls LIKE '%RtlMoveMemory%';</pre>
<!--kg-card-end: html-->
<p>The binary has been transformed from something you must click through into something you can simply query. Whole-program questions that would be impractical by hand become single-line requests.&nbsp;&nbsp;</p><p>The three tasks above — decompile, graph, export — used to be features that a tool vendor would have to design, build, and ship as menu items. They are now&nbsp;prompts&nbsp;a user can add on themselves.&nbsp;The capability surface of the tool has decoupled from the feature list of the tool.</p><h3 id="build-an-opcode-reference-database">Build an&nbsp;opcode&nbsp;reference&nbsp;database&nbsp;</h3><p>The same recipe scales beyond single analyses to producing reference data. In the next&nbsp;example&nbsp;the agent was tasked with building a complete opcode database for the VB6 P-code interpreter (MSVBVM60.dll;&nbsp;1,165 dispatch slots). Two tools were coordinated.&nbsp;Vbdec&nbsp;was again used over the ROT to search and analyze actual examples of every opcode from a real binary (PDFStreamDumper). The results were then bolstered&nbsp;utilizing&nbsp;the&nbsp;idalib MCP server to read the actual runtime handler functions in VB&nbsp;runtime itself&nbsp;to&nbsp;verify what each opcode does at the dispatch level.&nbsp;</p><p>The results were combined into a SQLite database that includes operand decoding, handler-verified semantics, alias relationships, corpus statistics, and written descriptions for every opcode.&nbsp;Resources such as this could now be fed back into AI agents to produce better P-code&nbsp;decompilation.&nbsp;This corpus of knowledge would be impractical to build by&nbsp;hand, yet was agentically synthesized in a matter of hours.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img style="white-space: pre-wrap;">and IDA.</em></i></figcaption></figure><h3 id="application-testing">Application&nbsp;testing</h3><p>The same mechanism can also be used to test the outputs of the tool itself. An agent pointed at the briefing and prototypes will exercise the real COM surface against actual data. With COM in&nbsp;particular&nbsp;this means there is no mock, no&nbsp;proxy,&nbsp;and no UI automation layers to debug in between.&nbsp;&nbsp;</p><p>Method signature drift, type regressions, malformed objects, edge-case P-code, missing members are all easily exposed. The proto files and the briefing get tested alongside the API implementation itself.</p><h2 id="what-this-makes-possible">What&nbsp;this&nbsp;makes&nbsp;possible&nbsp;</h2><p>This design pattern generalizes cleanly.&nbsp;Any analysis tool that publishes its internal model to the&nbsp;ROT&nbsp;and&nbsp;ships an&nbsp;operator briefing with prototypes can become a substrate for local agentic automation.&nbsp;The interactive GUI&nbsp;remains&nbsp;available for exploration; the agent handles everything that&nbsp;benefits&nbsp;from being repeatable, exhaustive, or fast.&nbsp;</p><p>The architectural move is the part worth carrying away. The author of an analysis tool that holds structured data behind a UI does not have to predict the analyses their users will want.&nbsp;&nbsp;</p><p>Publish the model, write the briefing, and hand the keys over to the user. Every user wish list idea now collapses into the same answer:&nbsp;Ask the agent. Tedious analysis can be easily automated.&nbsp;&nbsp;</p><p>The local part is valuable as well. Sensitive binaries do not leave the analyst’s machine. There is no API key in the&nbsp;product&nbsp;and there is no service that can be&nbsp;discontinued. The agent is whichever agent the analyst already has.&nbsp;The contract between agent and tool is text files on a file&nbsp;system.</p><h2 id="conclusion">Conclusion&nbsp;</h2><p>While analysis tools commonly include internal scripting, exposing the application to external automation is what opens them to AI agents. ROT-published COM objects are well-suited to this because they are&nbsp;language-agnostic, process-agnostic, synchronous, and discoverable.&nbsp;Turning the analysis tool into a data server has&nbsp;additional&nbsp;benefits,&nbsp;such as allowing repeat query sessions without itself having to reload and reparse the data set.&nbsp;&nbsp;</p><p>While the specific design in this paper was COM-based, any&nbsp;<a href="https://hex-rays.com/blog/interacting-with-ida-through-ipc-channels" rel="noreferrer noopener"><u>IPC communication protocol</u></a>&nbsp;could be used. COM and&nbsp;IDispatch&nbsp;are particularly useful here because they are inherently scriptable without requiring&nbsp;additional&nbsp;marshaling or synchronization layers.&nbsp;&nbsp;</p><p>Another aspect of this design&nbsp;that&nbsp;is&nbsp;easy to overlook is the utility of having a full GUI for data exploration at the forefront. Data can be explored and verified&nbsp;manually&nbsp;and then scripts written against it for bulk operations. While plugin frameworks have been the traditional solution to automation needs, plugin development is&nbsp;generally quite&nbsp;bulky in practice and often bound to a specific program version.</p><p>With this paradigm, the disassembler stops being a place you look at a&nbsp;binary, and&nbsp;becomes a service you ask questions of.</p>
