    <h1 class="text-center">Inside KeyDrift: Analyzing historical UAT-11473 activity on Cisco SD-WAN</h1>

    <div class="text-center m-1">
        <div class="post-author">
            <span>By </span>
                <a href="https://blog.talosintelligence.com/author/cisco/">Cisco Talos</a>
        </div>

        <time class="post-datetime" datetime="October 28, 2026 17:32">

        </time>

        <div class="m-3">
                        <a href="https://blog.talosintelligence.com/category/threat-advisory/" class="category primary-category">

                        </a>
                                            <a href="https://blog.talosintelligence.com/category/apt/" class="category primary-category">

    <section class="post-content-wrapper mt-5">
        <div class="post-content" id="post-content">
            <ul><li>Cisco Talos has identified UAT-11473, a highly sophisticated advanced persistent threat (APT) actor, who exploited <a href="https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-sdwan-rpa-EHchtZk">CVE-2026-20127</a>, an authentication bypass vulnerability in Cisco SD-WAN Catalyst Controller instances to bypass authentication and gain unauthorized access to affected systems.</li><li>UAT-11473 then installed a custom malware framework we track as “KeyDrift” consisting of multiple components geared towards collecting sensitive keying information, acting as backdoors and intermediate command-and-control (C2) hosts.</li><li>Observed targeting spans across space and satellite services, defense and aerospace technology, and policy research.</li></ul><hr><p>Talos assesses with high confidence that UAT-11473’s operating infrastructure overlaps considerably with <a href="https://www.lumen.com/blog/en-us/silent-train-volt-typhoon-operational-framework" rel="noreferrer">Volt Typhoon’s “Silent Train” covert access network</a>.</p><p>KeyDrift is a custom malware framework that is designed to operate in Cisco SD-WAN controller environments. Talos assesses with high confidence that the framework is designed to provide long-term persistent access and automated exfiltration of sensitive keying material. KeyDrift operates inside SD-WAN control-plane processes and is capable of intercepting decrypted control traffic, extracting control-session metadata and data-plane keying material, and staging or transmitting the collected material using encrypted records.</p><p>The framework's primary component is PolyFlame, a memory-resident module deployed through modified runit service paths. PolyFlame is injected into legitimate running vdaemon processes, and it can also masquerade as a packed “aaamgrd” loader variant. Once resident, PolyFlame interposes socket, DTLS, and runtime-linker behavior through functions such as recvfrom, sendto, getpeername, dlopen, dlsym, mprotect, and “/proc/%d/maps” parsing. This gives KeyDrift access to SD-WAN control-plane traffic from inside legitimate controller daemon execution rather than through a conventional endpoint beacon.</p><p>LittleFilch, another component of the KeyDrift framework, provides the collection and exfiltration capability identified in the framework. The module hooks “SSL_read” inside vdaemon, inspects decrypted control-plane buffers, extracts keying material for a list of predefined edge nodes, and stages the data locally in encrypted format for exfiltration.</p><p>Talos assesses with high confidence that KeyDrift's intended operational purpose is Cisco SD-WAN control-plane collection: persistent controller residence, in-band traffic access, key-material extraction from decrypted control messages, and encrypted staging or exfiltration of the recovered material. Observed variations of the KeyDrift modules and deployment mechanisms suggest active development of the framework’s capabilities.</p><h2 id="keydrift-analysis">KeyDrift analysis</h2><p>KeyDrift uses Cisco SD-WAN runit service paths as its primary execution anchor. In the PolyFlame sshd deployment, the actor modifies the service run script, remounts /rootfs.rw executable, launches a malicious script “conf_sshd” in the background, and then starts the legitimate sshd service. The loader script enumerates running vdaemon PIDs, records them in “/tmp/system-vdaemon”, and invokes the injector component “rsshd” to inject PolyFlame (“libdssl.so”) into each process.</p><p>Recovered conf_sshd logic uses the same control flow across reviewed samples:</p><figure class="kg-card kg-image-card kg-card-hascaption"><img 720px"><figcaption><span style="white-space: pre-wrap;">Figure 1. conf_sshd control flow logic.</span></figcaption></figure><h3 id="runit-launchers">Runit launchers</h3><p>The observed sshd runit launcher preserves normal Cisco SD-WAN sshd startup logic while adding two malicious lines before service execution, which remount “/rootfs.rw” executable and background execution of conf_sshd, which then drives rsshd injection into vdaemon.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/2026/10/data-src-image-52ca1586-b9e0-4a7c-8767-e8f362f8371a.png" class="kg-image" alt="" loading="lazy" 720px"><figcaption><span style="white-space: pre-wrap;">Figure 2. conf_sshd execution logic.</span></figcaption></figure><p>The recovered aaamgr runit launcher from an affected vBond appliance uses a parallel service-wrapper pattern, but it executes the packed aaamgrd PolyFlame loader directly. The deletion of the writable-overlay PAM configurations for sshd and login before remounting “/rootfs.rw” executable if part of the legitimate script, along with the invocation of the aaamgrd daemon via Python:</p><figure class="kg-card kg-image-card kg-card-hascaption"><img src="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/2026/10/data-src-image-7c670c4f-818e-478d-aa59-705b8c657f16.png" class="kg-image" alt="" loading="lazy" width="937" height="479" srcset="https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/size/w600/2026/10/data-src-image-7c670c4f-818e-478d-aa59-705b8c657f16.png 600w, https://storage.ghost.io/c/af/a0/afa04ee3-414f-4481-8d23-7e7c146f192e/content/images/2026/10/data-src-image-7c670c4f-818e-478d-aa59-705b8c657f16.png 937w" sizes="(min-width: 720px) 720px"><figcaption><span style="white-space: pre-wrap;">Figure 3. aamgrd daemon launch.</span></figcaption></figure><h3 id="polyflame">PolyFlame</h3><p>PolyFlame is the primary operational module in the KeyDrift framework. PolyFlame operates at the socket and DTLS control-plane layer. PolyFlame serves two primary purposes:</p><ul><li>Command execution via a TinyShell-styled backdoor</li><li>Intermediate C2 that can forward commands to and from the C2 to other peers</li></ul><p>PolyFlame is primarily injected into the vdaemon process, providing operational obfuscation and access to all in-process state: DTLS session keys, vEdge topology, OMP routes, and policy tables. No hardcoded IPv4 addresses, binding ports, callback domains, URLs, host headers, or polling interval were recovered from the analyzed PolyFlame samples. PolyFlame is designed for in-band control or tasking over Cisco SD-WAN control-plane traffic rather than a conventional fixed external beacon.</p><p>This implant is meant to serve as a hook of the recvfrom() API call. The original recvfrom is replaced by a malicious subroutine in the vdaemon process. When recvfrom is called in the vdaemon process, the malicious subroutine will first execute the real/legitimate recvfrom() API to obtain the C2 IP address info for communicating with it in the future.</p><p><strong>PolyFlame’s time check</strong></p><p>The recvd data from the C2 consists of the MD5 value of a specific DATE. PolyFlame will calculate the local time on the device in format “%Y-%m-%d" and calculate its MD5 hash. If the MD5 calculated by the device does not match with the one sent by the C2, the implant will stop further execution. Otherwise, the implant then uses an “administrative code” from the C2 and performs an action.</p><p><strong>PolyFlame’s tasking</strong></p><p>PolyFlame contains an administrative mode that processes the admin code sent by the C2, that defines operations — it's one of the first flags checked in the backdoor:</p><ul><li>Code = 1: Generate random bytes and send to C2. This is likely a check-in beacon or heartbeat for the C2.</li><li>Code = 2: Set implant type to backdoor (TinyShell) or intermediate C2.</li><li>Code = 3: Set up the command handler for the intermediate C2.</li><li>Any other code value: Check the implant type flag currently set. Based on the implant type flag, either send the accompanying data to TinyShell or the intermediate C2 component for processing.</li></ul><p><strong>PolyFlame’s command execution</strong></p><p>PolyFlame contains a backdoor that matches the capabilities of TinyShell: file read, file write, and arbitrary command execution, but not interactive shell. This backdoor component’s implementation is quite similar to TinyShell, but the command codes differ. PolyFlame handles the following command codes:</p><ul><li>Code = 0x100: Execute command using “/bin/sh -c &lt;command&gt;”</li><li>Code = 0x200: Write file to disk.</li><li>Code = 0x300: Read file from disk and send to the C2.</li></ul><p><strong>PolyFlame as an intermediate C2 component</strong></p><p>The intermediate C2 component is a one-to-many handler (somewhat like a one-to-many multiplexer) — meaning the implant can connect to only one C2 but can connect to many peers who can be served by the intermediate C2 component. Similar to the TinyShell-backdoor component, the intermediate C2 component also accepts and processes specific command codes from the C2:</p><ul><li>Code = 0x403: Create a thread to connect to the specified peer IP. Make a new connection and keep socket alive until specified.</li><li>Code = 0x404: Send data recvd from the C2 to a connected peer.</li><li>Code = 0x405: Remove a peer from the list of active connections.</li><li>Code = 0x407: Send a response recvd from a peer, back to the C2.</li><li>Code = 0x408: Set a specific value in memory.</li></ul><p><strong>PolyFlame variant: aaamgrd</strong></p><p>&nbsp;Talos has observed a distinct PolyFlame variant that masquerades as the aaamgr service. The legitimate Cisco aaamgr component is a Python package; it does not normally appear as a compiled ELF runit service. This PolyFlame variant is executed by a malicious runit service under “/etc/sv/aaamgr/” with aaamgrd and a modified run launcher.</p><p>aaamgrd is a statically linked ELF64 executable with no section headers, a single RWE loader segment, and an RC4-encrypted embedded ELF payload.
