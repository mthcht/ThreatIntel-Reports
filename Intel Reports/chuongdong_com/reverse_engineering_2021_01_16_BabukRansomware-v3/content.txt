    <h1 id="babuk-ransomware-v3">Babuk Ransomware v3</h1>

<h2 id="overview">Overview</h2>

<p>This is a short report for the latest Babuk ransomware sample. This sample is marked as version 3 based on the run-once mutex string.</p>

<p>For this new version, the malware author keeps most of the old functionalities the same except for the encryption scheme and the multithreading approach.</p>

<p>Since I have covered Babuk old sample <a href="http://chuongdong.com/reverse%20engineering/2021/01/03/BabukRansomware/">here</a>, I will only discuss the new changes in this report.</p>

<p>For encryption, Babuk uses ChaCha20 encryption, but the Elliptic-curve Diffie–Hellman (ECDH) key generation and exchange algorithm is changed from <strong>NIST K-571</strong> to <a href="https://en.wikipedia.org/wiki/Curve25519">Curve25519</a>, one of the fastest ECDH curves.</p>

<h2 id="iocs">IOCS</h2>

<p>Babuk v3 comes in the form of a 32-bit <em>.exe</em> file.</p>

<p><strong>MD5</strong>: 8b9a0b44b738c7884e6a14f4cb18afff</p>

<p><strong>SHA256</strong>: 704a0fa7de19564bc743fb68aa0652e38bf86e8ab694bc079b15f945c85f4320</p>

<p><strong>Sample</strong>: https://bazaar.abuse.ch/sample/704a0fa7de19564bc743fb68aa0652e38bf86e8ab694bc079b15f945c85f4320/</p>

<h2 id="new-changes">New Changes</h2>

<h3 id="run-once-mutex">Run-Once Mutex</h3>

<p>In the beginning, Babuk checks if a mutex with the name <strong>“babuk_v3”</strong> exists through the call to <strong>OpenMutexA</strong>. If it already exists, the malware exits immediately.</p>

<p>This is commonly used by malware to prevent themselves from having multiple instances running at once.</p>

<p><img src="/uploads/babukv3_1.PNG" alt="alt text"></p>

<p><em>Figure 3: Babuk checking for mutex</em></p>

<h3 id="command-line-arguments">Command-line Arguments</h3>

<p>Babuk can work with or without command line parameters.</p>

<p>The new command line parameters are <strong>“lanfirst”</strong>, <strong>“nolan”</strong>, and <strong>“shares”</strong>.</p>

<p><img src="/uploads/babukv3_2.PNG" alt="alt text"></p>

<p><em>Figure 4: Babuk checking for mutex</em></p>

<h3 id="multithreading">Multithreading</h3>

<p>The multithreading implementation has been changed a lot since the first version. I guess they really tried to improve it after reading what I had to say in the last blog post <img class="emoji" title=":relieved:" alt=":relieved:" src="https://github.githubassets.com/images/icons/emoji/unicode/1f60c.png" height="20" width="20"></p>

<p><img src="/uploads/babukv3_3.PNG" alt="alt text"></p>

<p><em>Figure 5: Babuk team’s friendly response to my analysis!</em></p>

<p>The steps taken to improve the ransomware’s threading functionalities are in the right direction since they do increase the encryption speed by quite a bit.</p>

<p>Babuk uses a structure similar to a circular queue (Ring Buffer) backed by an array to store file names to encrypt. The queue size is double the number of processors on the system, which is the same amount of child threads being spawned.</p>

<p><img src="/uploads/babukv3_4.PNG" alt="alt text"></p>

<p><em>Figure 6: Queue initialization</em></p>

<p>This queue is shared and used by child threads.</p>

<p>The parent thread will recursively crawl through directories and enqueue the file names it finds to the head of the queue. The child threads will start dequeuing them at the tail of the queue to begin encryption.</p>

<p><img src="/uploads/babukv3_5.PNG" alt="alt text"></p>

<p><em>Figure 7: Babuk’s circular queue illustration</em></p>

<p>First, Babuk will spawn child threads. The number of threads being spawned is double the number of processors. This is clearly <a href="https://docs.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createthread#remarks">not a good amount</a> so I have no idea why they still use it similar to the previous version.</p>

<p><img src="/uploads/babukv3_6.PNG" alt="alt text"></p>

<p><em>Figure 8: Spawning child threads</em></p>

<p>The Babuk parent thread then proceeds to traverse through an entire drive by checking whether it has encountered a directory or a file.</p>

<p>Upon finding a directory, it will call that function again and go down another layer to recursively traverse that directory.</p>

<p>Upon finding a file, it will enqueue that file to the head of the queue and move on.</p>

<p><img src="/uploads/babukv3_7.PNG" alt="alt text"></p>

<p><em>Figure 9: Babuk parent thread traversing through directories and enqueuing files</em></p>

<p>Each child thread will dequeue a file at the tail of the queue and encrypt it.</p>

<p><img src="/uploads/babukv3_8.PNG" alt="alt text"></p>

<p><em>Figure 10: Babuk child threads dequeuing and encrypting files</em></p>

<p>Here is the implementation for enqueuing and dequeuing files.</p>

<p><img src="/uploads/babukv3_9.PNG" alt="alt text"></p>

<p><em>Figure 11: Function to enqueue files</em></p>

<p><img src="/uploads/babukv3_10.PNG" alt="alt text"></p>

<p><em>Figure 12: Function to dequeue files</em></p>

<p>As we can see, Babuk uses a file queue backed by an array. By keeping track of the head and tail indices, adding and removing file names from the queue take a constant time and are really fast.</p>

<p>With all of these new changes to the implementation, this new version of Babuk is much faster than the original one. Unfortunately, there is still a lot more room for improvement since it is nowhere near <strong>Conti</strong> and other ransomware in terms of speed and efficiency.</p>

<p>With an array-backed queue, space is limited. As we can see in the enqueue function, there is no check to see if the queue is full before adding more files onto it. In the theoretical case where all the threads are busy encrypting files and the queue is full, the parent thread will continue adding more files. Since this is a circular queue, this will result in files being overwritten with new ones before the child threads have a chance to encrypt them if the parent thread is fast enough.</p>

<p>Moreover, the malware author still sticks with the old recursive approach to traversing files. With only the parent thread traversing entire drives, there will be an extreme amount of overhead from the stack frame since there will be too many recursion layers. This essentially makes the total encryption time dependent on the time it takes for one thread to traverse the entire system.</p>

<h3 id="encryption">Encryption</h3>

<p>Encryption scheme remains the same from the original version. However, there is a slight change in the ChaCha20 key generation.</p>

<p>For every file, a random buffer of 32 bytes is generated using <strong>CryptGenRandom</strong>.</p>

<p><img src="/uploads/babukv3_11.PNG" alt="alt text"></p>

<p><em>Figure 13: Generating random buffer</em></p>

<p>Next, using the this exact piece of <a href="https://github.com/agl/curve25519-donna/blob/master/curve25519-donna.c">Curve25519 implementation</a>, Babuk will generate a public key for the victim from the random buffer using ECDH.</p>

<p>It will also generate a shared secret using its hard-coded public key and the random buffer. This shared secret is eventually used as the ChaCha20 key to encrypt the file.</p>

<p><img src="/uploads/babukv3_12.PNG" alt="alt text"></p>

<p><em>Figure 14: Public key and shared secret generation</em></p>

<p>Finally, the victim’s public key is then written to the end of the file to be used for decryption if the victim decides to pay.</p>

<p><img src="/uploads/babukv3_13.PNG" alt="alt text"></p>

<p><em>Figure 15: Victim’s public key being written to the end of file</em></p>

<p>Not sure if this was intended, but I believe the Babuk group has messed up the public key generation phase.</p>

<p>According to <a href="https://cr.yp.to/djb.html">Dan Bernstein</a> who was the author of this Diffie-Hellman function, here is the procedure of generating a public key using Curve25519.</p>

<p><img src="/uploads/babukv3_14.PNG" alt="alt text"></p>

<p><em>Figure 16: Curve25519 Public Key Generation</em></p>

<p>Instead of using 9 followed by all zeroes, Babuk uses an array of all 9 values.</p>

<p><img src="/uploads/babukv3_15.PNG" alt="alt text"></p>

<p><em>Figure 17: Babuk’s basepoint constant</em></p>

<p>Unless the malware author has modified the math in the Curve25519 source code to accommodate for this (which is unlikely), this basepoint constant might not generate a correct public key.</p>

<p>With an incorrect public key, it’s impossible for the malware author to generate the correct shared secret to decrypt files.</p>

<h2 id="key-findings">Key Findings</h2>

<p>The new version of Babuk has been improved to encrypt files at a much faster rate using a better multithreading approach. Despite still having a lot to improve, Babuk has been really effective in attacking many corporations using ChaCha20 encryption as well as Elliptic-curve Diffie–Hellman algorithm.</p>

<p>As suspected, the Babuk team probably uses spear phishing attacks, VPN 0-days, and vulnerable RDP setup to target certain companies. They have dropped this sample specifically targeting a mechanical contractor in Austria according to the ransom note and the conversation with the victim on their website.</p>

<p><img src="/uploads/babukv3_16.PNG" alt="alt text"></p>
