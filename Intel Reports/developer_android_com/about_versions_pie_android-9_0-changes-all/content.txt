<p>Android 9 (API level 28) introduces a number of changes to the Android system.
The following behavior changes apply to <em>all apps</em> when they
run on the Android 9 platform, regardless of the API level that they
are targeting. All developers should review these changes and modify
their apps to support them properly, where applicable to the app.</p>

<p>For changes that only affect apps that target API level 28 or higher, see
<a href="/about/versions/pie/android-9.0-changes-28">Behavior changes: apps targeting API Level
28+</a>.</p>

<h2 id="power" data-text="Power management" tabindex="-1">Power management</h2>

<p>Android 9 introduces new features to improve device power
management. These changes, along with features that were already present before
Android 9, help to ensure that system resources are made available to the apps
that need them the most.</p>

<p>For details, see <a href="/about/versions/pie/power">Power management</a>.</p>

<h2 id="privacy-changes-all" data-text="Privacy changes" tabindex="-1">Privacy changes</h2>

<p>To enhance user privacy, Android 9 introduces several behavior
changes, such as limiting background apps&#39; access to device sensors, restricting
information retrieved from Wi-Fi scans, and new permission rules and permission
groups related to phone calls, phone state, and Wi-Fi scans.</p>

<p>These changes affect all apps running on Android 9, regardless of target SDK
version.</p>

<h4 id="bg-sensor-access" data-text="Limited access to sensors in background" tabindex="-1">Limited access to sensors in background</h4>

<p>Android 9 limits the ability for background apps to access user input and
sensor data. If your app is running in the background on a device running
Android 9, the system applies the following restrictions to your app:</p>

<ul>
<li>Your app cannot access the microphone or camera.</li>
<li>Sensors that use the
<a href="https://source.android.com/devices/sensors/report-modes#continuous">continuous</a>
reporting mode, such as accelerometers and gyroscopes, don&#39;t receive events.</li>
<li>Sensors that use the
<a href="https://source.android.com/devices/sensors/report-modes#on-change">on-change</a>
or <a href="https://source.android.com/devices/sensors/report-modes#one-shot">one-shot</a>
reporting modes don&#39;t receive events.</li>
</ul>

<p>If your app needs to detect sensor events on devices running Android 9, use a
<a href="/guide/components/services#Foreground">foreground service</a>.</p>

<h4 id="restrict-access-call-logs" data-text="Restricted access to call logs" tabindex="-1">Restricted access to call logs</h4>

<p>Android 9 introduces the
<a href="/reference/android/Manifest.permission_group#CALL_LOG"><code translate="no" dir="ltr">CALL_LOG</code></a> <a href="/guide/topics/permissions/overview#perm-groups">permission
group</a> and moves the
<a href="/reference/android/Manifest.permission#READ_CALL_LOG"><code translate="no" dir="ltr">READ_CALL_LOG</code></a>,
<a href="/reference/android/Manifest.permission#WRITE_CALL_LOG"><code translate="no" dir="ltr">WRITE_CALL_LOG</code></a>, and
<a href="/reference/android/Manifest.permission#PROCESS_OUTGOING_CALLS"><code translate="no" dir="ltr">PROCESS_OUTGOING_CALLS</code></a>
permissions into this group. In previous versions of Android, these permissions
were located in the <code translate="no" dir="ltr">PHONE</code> permission group.</p>

<p>This <code translate="no" dir="ltr">CALL_LOG</code> permission group gives users better control and visibility to
apps that need access to sensitive information about phone calls, such as
reading phone call records and identifying phone numbers.</p>

<p>If your app requires access to call logs or needs to process outgoing calls, you
must explicitly request these permissions from the
<a href="/reference/android/Manifest.permission_group#CALL_LOG"><code translate="no" dir="ltr">CALL_LOG</code></a> permission
group. Otherwise, a
<a href="/reference/java/lang/SecurityException"><code translate="no" dir="ltr">SecurityException</code></a> occurs.</p>

<div class="note">
  <p><b>Note: </b>Because these permissions have changed groups and are granted
  at runtime, it's possible for the user to deny your app access to phone call
  logs information. In this case, your app should be able to handle the lack of
  access to information gracefully.</p>
  <p>If your app is already following
  <a href="/distribute/best-practices/develop/runtime-permissions">runtime
  permissions best practices</a>, it can handle the change in permission group.
  </p>
</div>

<h4 id="restrict-access-phone-numbers" data-text="Restricted access to phone numbers" tabindex="-1">Restricted access to phone numbers</h4>

<p>Apps running on Android 9 cannot read phone numbers or phone state without
first acquiring the
<a href="/reference/android/Manifest.permission#READ_CALL_LOG"><code translate="no" dir="ltr">READ_CALL_LOG</code></a>
permission, in addition to the other permissions that your app&#39;s use cases
require.</p>

<p>Phone numbers associated with incoming and outgoing calls are visible in the
<a href="/reference/android/telephony/TelephonyManager#action_phone_state_changed">phone state
broadcast</a>,
such as for incoming and outgoing calls and are accessible from the
<a href="/reference/android/telephony/PhoneStateListener"><code translate="no" dir="ltr">PhoneStateListener</code></a> class.
Without the
<a href="/reference/android/Manifest.permission#READ_CALL_LOG"><code translate="no" dir="ltr">READ_CALL_LOG</code></a>
permission, however, the phone number field that&#39;s provided in
<code translate="no" dir="ltr">PHONE_STATE_CHANGED</code> broadcasts and through <code translate="no" dir="ltr">PhoneStateListener</code> is empty.</p>

<p>To read phone numbers from phone state, update your app to request the necessary
permissions based on your use case:</p>

<ul>
<li>To read numbers from the <code translate="no" dir="ltr">PHONE_STATE</code> <a href="/guide/topics/manifest/action-element">intent
action</a>, you need both the
<a href="/reference/android/Manifest.permission#READ_CALL_LOG"><code translate="no" dir="ltr">READ_CALL_LOG</code></a>
permission and the
<a href="/reference/android/Manifest.permission#READ_PHONE_STATE"><code translate="no" dir="ltr">READ_PHONE_STATE</code></a>
permission.</li>
<li>To read numbers from
<a href="/reference/android/telephony/PhoneStateListener#oncallstatechanged"><code translate="no" dir="ltr">onCallStateChanged()</code></a>,
you need the
<a href="/reference/android/Manifest.permission#READ_CALL_LOG"><code translate="no" dir="ltr">READ_CALL_LOG</code></a>
permission only. You don&#39;t need the
<a href="/reference/android/Manifest.permission#READ_PHONE_STATE"><code translate="no" dir="ltr">READ_PHONE_STATE</code></a>
permission.</li>
</ul>

<h4 id="restricted_access_to_wi-fi_location_and_connection_information" data-text="Restricted access to Wi-Fi location and connection information" tabindex="-1">Restricted access to Wi-Fi location and connection information</h4>

<p>In Android 9, the permission requirements for an app to perform Wi-Fi
scans are more strict than in previous versions. For details, see
<a href="/guide/topics/connectivity/wifi-scan#wifi-scan-restrictions">Wi-Fi scanning restrictions</a>.</p>

<p>Similar restrictions also apply to the
<a href="/reference/android/net/wifi/WifiManager#getConnectionInfo()"><code translate="no" dir="ltr">getConnectionInfo()</code></a>
method, which returns a <a href="/reference/android/net/wifi/WifiInfo"><code translate="no" dir="ltr">WifiInfo</code></a>
object describing the current Wi-Fi connection. You can only use this object&#39;s
methods to retrieve SSID and BSSID values if the calling app has the following
permissions:</p>

<ul>
<li>ACCESS_FINE_LOCATION <strong>or</strong> ACCESS_COARSE_LOCATION</li>
<li>ACCESS_WIFI_STATE</li>
</ul>

<p>Retrieving the SSID or BSSID also requires location services to be enabled on
the device (under <strong>Settings &gt; Location</strong>).</p>

<h4 id="information_removed_from_wi-fi_service_methods" data-text="Information removed from Wi-Fi service methods" tabindex="-1">Information removed from Wi-Fi service methods</h4>

<p>In Android 9, the following events and broadcasts don&#39;t receive information
about the user&#39;s location or personally identifiable data:</p>

<ul>
<li>The
<a href="/reference/android/net/wifi/WifiManager#getScanResults()"><code translate="no" dir="ltr">getScanResults()</code></a>
and <a href="/reference/android/net/wifi/WifiManager#getConnectionInfo()"><code translate="no" dir="ltr">getConnectionInfo()</code></a>
methods from <code translate="no" dir="ltr">WifiManager</code>.</li>
<li>The <a href="/reference/android/net/wifi/p2p/WifiP2pManager#discoverServices(android.net.wifi.p2p.WifiP2pManager.Channel,%20android.net.wifi.p2p.WifiP2pManager.ActionListener)"><code translate="no" dir="ltr">discoverServices()</code></a>
and <a href="/reference/android/net/wifi/p2p/WifiP2pManager#addServiceRequest(android.net.wifi.p2p.WifiP2pManager.Channel,%20android.net.wifi.p2p.nsd.WifiP2pServiceRequest,%20android.net.wifi.p2p.WifiP2pManager.ActionListener)"><code translate="no" dir="ltr">addServiceRequest()</code></a>
methods from <code translate="no" dir="ltr">WifiP2pManager</code>.</li>
<li>The <a href="/reference/android/net/wifi/WifiManager#NETWORK_STATE_CHANGED_ACTION"><code translate="no" dir="ltr">NETWORK_STATE_CHANGED_ACTION</code></a> broadcast.</li>
</ul>

<p>The <a href="/reference/android/net/wifi/WifiManager#NETWORK_STATE_CHANGED_ACTION"><code translate="no" dir="ltr">NETWORK_STATE_CHANGED_ACTION</code></a>
system broadcast from Wi-Fi no longer contains SSID (previously EXTRA_SSID),
BSSID (previously EXTRA_BSSID), or connection information (previously
EXTRA_NETWORK_INFO). If your app needs this information, call
<a href="/reference/android/net/wifi/WifiManager#getConnectionInfo()"><code translate="no" dir="ltr">getConnectionInfo()</code></a>
instead.</p>

<h4 id="telephony_information_now_relies_on_device_location_setting" data-text="Telephony information now relies on device location setting" tabindex="-1">Telephony information now relies on device location setting</h4>

<p>If the user has <a href="https://support.google.com/accounts/answer/3467281?hl=en">disabled device
location</a> on a device
running Android 9, the following methods don&#39;t provide results:</p>

<ul>
<li><a href="/reference/android/telephony/TelephonyManager#getAllCellInfo()"><code translate="no" dir="ltr">getAllCellInfo()</code></a></li>
<li><a href="/reference/android/telephony/TelephonyManager#listen(android.telephony.PhoneStateListener,%20int)"><code translate="no" dir="ltr">listen()</code></a></li>
<li><a href="/reference/android/telephony/TelephonyManager#getCellLocation()"><code translate="no" dir="ltr">getCellLocation()</code></a></li>
<li><a href="/reference/android/telephony/TelephonyManager#getNeighboringCellInfo()"><code translate="no" dir="ltr">getNeighboringCellInfo()</code></a></li>
</ul>

<h2 id="compat" data-text="Restrictions on use of non-SDK interfaces" tabindex="-1">Restrictions on use of non-SDK interfaces</h2>

<p>To help ensure app stability and compatibility, the platform restricts the use of
some non-SDK methods and fields; these restrictions apply whether you
attempt to access these methods and fields directly, via reflection, or using
JNI. In Android 9, your app can continue to access these restricted
interfaces; the platform uses toasts and log entries to bring them to your attention.
If your app shows such a toast, it is important that you pursue an
implementation strategy other than the restricted interface. If you feel
that no alternative strategy is feasible, you may file
<a href="https://issuetracker.google.com/issues/new?component=328403&amp;template=1027267">a bug</a>
to request reconsideration of the restriction.</p>

<p><a href="/about/versions/pie/restrictions-non-sdk-interfaces">Restrictions on Non-SDK Interfaces</a>
contains further important information. You should review it to ensure that your
app continues to function properly.</p>

<h2 id="security-changes" data-text="Security behavior changes" tabindex="-1">Security behavior changes</h2>

<h3 id="device-security-changes" data-text="Device security changes" tabindex="-1">Device security changes</h3>

<p>Android 9 adds several capabilities that improve your app&#39;s
security, regardless of which version your app targets.</p>

<h4 id="tls-impl-changes" data-text="TLS implementation changes" tabindex="-1">TLS implementation changes</h4>

<p>The system&#39;s TLS implementation has undergone several changes in Android 9:</p>

<ul>
<li>If an instance of <a href="/reference/javax/net/ssl/SSLSocket"><code translate="no" dir="ltr">SSLSocket</code></a> fails
to connect while it&#39;s being created, the system throws an
<a href="/reference/java/io/IOException"><code translate="no" dir="ltr">IOException</code></a> instead of a
<a href="/reference/java/lang/NullPointerException"><code translate="no" dir="ltr">NullPointerException</code></a>.</li>
<li>The <a href="/reference/javax/net/ssl/SSLEngine"><code translate="no" dir="ltr">SSLEngine</code></a> class cleanly
handles any <code translate="no" dir="ltr">close_notify</code> alerts that occur.</li>
</ul>

<p>To learn more about making secure web requests in an Android app, see <a href="/training/articles/security-ssl#HttpsExample">An HTTPS
example</a>.</p>

<h4 id="seccomp-filter" data-text="Stricter SECCOMP filter" tabindex="-1">Stricter SECCOMP filter</h4>

<p>Android 9 further restricts the system calls that are available to apps. This
behavior is an extension of the <a href="/about/versions/oreo/android-8.0-changes#security-all">SECCOMP filter that Android 8.0 (API level 26)
includes</a>.</p>
<aside class="note"><strong>Note:</strong><span> This change only affects apps that use privileged syscalls.</span></aside>
<h3 id="crypto-changes" data-text="Cryptographic changes" tabindex="-1">Cryptographic changes</h3>

<p>Android 9 introduces several changes to the implementation and
handling of cryptographic algorithms.</p>

<h4 id="conscrypt_implementations_of_parameters_and_algorithms" data-text="Conscrypt implementations of parameters and algorithms" tabindex="-1">Conscrypt implementations of parameters and algorithms</h4>

<p>Android 9 provides additional implementations of algorithm parameters in
<a href="https://github.com/google/conscrypt" class="external-link">Conscrypt</a>. These
parameters include: AES, DESEDE, OAEP, and EC. The
<a href="https://www.bouncycastle.org/" class="external-link">Bouncy Castle</a> versions of
these parameters and many algorithms have been deprecated as of Android 9.</p>
<aside class="note"><strong>Note:</strong><span> Conscrypt&#39;s implementation of the EC parameter only supports named curves.</span></aside>
<p>If your app targets Android 8.1 (API level 27) or lower, you receive a warning
when requesting the Bouncy Castle implementation of one of these deprecated
algorithms. If you target Android 9, however, these requests each throw a
<a href="/reference/java/security/NoSuchAlgorithmException"><code translate="no" dir="ltr">NoSuchAlgorithmException</code></a>.</p>

<h4 id="other_changes" data-text="Other changes" tabindex="-1">Other changes</h4>

<p>Android 9 introduces several other changes related to cryptography:</p>

<ul>
<li>When using PBE keys, if Bouncy Castle is expecting an initialization vector
(IV) and your app doesn’t supply one, you receive a warning.</li>
<li>The Conscrypt implementation of the ARC4 cipher allows you to specify either
<strong>ARC4/ECB/NoPadding</strong> or <strong>ARC4/NONE/NoPadding</strong>.</li>
<li>The Crypto Java Cryptography Architecture (JCA) provider has been removed. As
a result, if your app calls <code translate="no" dir="ltr">SecureRandom.getInstance(&quot;SHA1PRNG&quot;, &quot;Crypto&quot;)</code>, a
<a href="/reference/java/security/NoSuchProviderException"><code translate="no" dir="ltr">NoSuchProviderException</code></a>
occurs.</li>
<li>If your app parses RSA keys from buffers that are larger than the key
structure, an exception no longer occurs.</li>
</ul>

<p>To learn more about using Android&#39;s cryptographic capabilities, see
<a href="/guide/topics/security/cryptography">Cryptography</a>.</p>

<h3 id="asec" data-text="Android secure encrypted files are no longer supported" tabindex="-1">Android secure encrypted files are no longer supported</h3>

<p>Android 9 completely removes support for Android secure
encrypted files (ASECs).</p>

<p>In Android 2.2 (API level 8), Android introduced ASECs to support
apps-on-SD-card functionality. On Android 6.0 (API level 23), the platform
introduced an <a href="/about/versions/marshmallow/android-6.0#adoptable-storage">adoptable storage
device</a> technology
that developers can use in place of ASECs.</p>

<h2 id="icu" data-text="Updates to the ICU libraries" tabindex="-1">Updates to the ICU libraries</h2>

<p>Android 9 uses version 60 of the ICU library. Android 8.0 (API
level 26) and Android 8.1 (API level 27) use ICU 58.</p>

<p>ICU is used to provide public APIs beneath the <code translate="no" dir="ltr">android.icu package</code>
and is used internally in the Android platform for internationalization support.
For example, it is used to implement Android classes in <code translate="no" dir="ltr">java.util</code>, <code translate="no" dir="ltr">java.text</code>,
and <code translate="no" dir="ltr">android.text.format</code>.</p>

<p>The update to ICU 60 contains many small but useful changes, including Emoji 5.0
data support and improved date/time formats, as documented in the ICU 59 and ICU
60 release notes.</p>

<p>Notable changes in this update:</p>

<ul>
  <li>The way the platform handles time zones has changed.
    <ul>
      <li>The platform handles GMT and UTC better; UTC is no longer a synonym for
        GMT.
        <p>
      ICU now provides translated zone names for GMT and UTC. This change
      affects <code translate="no" dir="ltr">android.icu</code> formatting and parsing behavior for
      zones like "GMT", "Etc/GMT", "UTC", "Etc/UTC", and "Zulu".
        </p>
      </li>
      <li><code translate="no" dir="ltr">java.text.SimpleDateFormat</code> now uses ICU to
      provide display names for UTC /GMT, meaning:
        <ul>
          <li>Formatting <code translate="no" dir="ltr">zzzz</code> generates a long localized string
          for many locales. Previously, it
          produced "UTC" for UTC and strings like "GMT+00:00" for GMT.</li>
          <li>Parsing <code translate="no" dir="ltr">zzzz</code> recognizes strings like "Universal
            Coordinated Time", and "Greenwich Mean Time".</li>
          <li>Apps may encounter compatibility problems if they assume
            that "UTC" or "GMT+00:00" are output for
            <code translate="no" dir="ltr">zzzz</code> in all languages.</li>
        </ul>
      </li>
      <li>The behavior of
        <code translate="no" dir="ltr">java.text.DateFormatSymbols.getZoneStrings()</code> has changed:
        <ul>
          <li>As with <code translate="no" dir="ltr">SimpleDateFormat</code>, UTC and GMT now have
            long names. DST variants of time zone names for the UTC zone, such
            as "UTC", "Etc/UTC", and "Zulu", become GMT+00:00, which is
            the standard fallback when there are no names available,
            rather than the hard-coded string <code translate="no" dir="ltr">UTC</code>.</li>
          <li>Some zone IDs are correctly recognized as synonyms for other
            zones, so that Android finds strings for
            archaic zone IDs, such as <code translate="no" dir="ltr">Eire</code>, that previously could
            not be resolved.</li>
        </ul>
      </li>
      <li>Asia/Hanoi is no longer a recognized zone. For this reason
        <code translate="no" dir="ltr">java.util.TimeZones.getAvailableIds()</code> does not return this
        value, and <code translate="no" dir="ltr">java.util.TimeZone.getTimeZone()</code> does not
        recognize it. This behavior is consistent with the
        existing <code translate="no" dir="ltr">android.icu</code> behavior.
      </li>
    </ul>
  </li>
<li>The
  <code translate="no" dir="ltr">android.icu.text.NumberFormat.getInstance(ULocale, PLURALCURRENCYSTYLE).parse(String)</code>
  method may throw a <code translate="no" dir="ltr">ParseException</code> even when parsing legitimate
  currency text. Avoid this problem by using
  <code translate="no" dir="ltr">NumberFormat.parseCurrency</code>, available since Android 7.0 (API
  level 24), for <code translate="no" dir="ltr">PLURALCURRENCYSTYLE</code>-style currency text.
  </li>
  </ul>

<h2 id="android-test-changes" data-text="Android Test changes" tabindex="-1">Android Test changes</h2>

<p>Android 9 introduces several changes to the Android Test framework&#39;s library
and class structure. These changes help developers use framework-supported,
public APIs, but the changes also allow for more flexibility in building and
running tests using third-party libraries or custom logic.</p>

<h4 id="testing-libs-removed" data-text="Libraries removed from framework" tabindex="-1">Libraries removed from framework</h4>

<p>Android 9 reorganizes the JUnit-based classes into three libraries:
<strong>android.test.base</strong>, <strong>android.test.runner</strong>, and <strong>android.test.mock</strong>.
This change allows you to run tests against a version of JUnit that works best
with your project&#39;s dependencies. This version of JUnit might be different than
the one that <code translate="no" dir="ltr">android.jar</code> provides.</p>

<p>To learn more about how the JUnit-based classes are organized into these
libraries, as well as how to prepare your app&#39;s project for writing and running
tests, see <a href="/training/testing/set-up-project">Set up project for Android Test</a>.</p>

<h4 id="test-suite-build" data-text="Test suite build changes" tabindex="-1">Test suite build changes</h4>

<p>The <code translate="no" dir="ltr">addRequirements()</code> method in the
<a href="/reference/android/test/suitebuilder/TestSuiteBuilder"><code translate="no" dir="ltr">TestSuiteBuilder</code></a>
class has been removed, and the <code translate="no" dir="ltr">TestSuiteBuilder</code> class itself been deprecated.
The <code translate="no" dir="ltr">addRequirements()</code> method had required developers to supply arguments whose
types are hidden APIs, making the API invalid.</p>

<h2 id="decoder" data-text="Java UTF decoder" tabindex="-1">Java UTF decoder</h2>

<p>UTF-8 is the default charset in Android. A UTF-8 byte sequence can be decoded
by a <code translate="no" dir="ltr">String</code> constructor, such as <code translate="no" dir="ltr">String(byte[] bytes)</code>.</p>

<p>The UTF-8 decoder in Android 9 follows the Unicode standards
more strictly than in previous versions. The changes include the following:</p>

<ul>
<li>The non-shortest form of UTF-8, such as <code translate="no" dir="ltr">&lt;C0, AF&gt;</code>, is treated as ill-formed.</li>
<li>The surrogate form of UTF-8, such as <code translate="no" dir="ltr">U+D800</code>..<code translate="no" dir="ltr">U+DFFF</code>, is treated as
ill-formed.</li>
<li>The maximal subpart is replaced by a single <code translate="no" dir="ltr">U+FFFD</code>. For example, in the byte
sequence &quot;<code translate="no" dir="ltr">41 C0 AF 41 F4 80 80 41</code>,&quot; the maximal subparts are &quot;<code translate="no" dir="ltr">C0</code>,&quot; &quot;<code translate="no" dir="ltr">AF</code>,&quot;
and &quot;<code translate="no" dir="ltr">F4 80 80</code>.&quot; &quot;<code translate="no" dir="ltr">F4 80 80</code>&quot; can be the initial subsequence of
&quot;<code translate="no" dir="ltr">F4 80 80 80</code>&quot;, but &quot;<code translate="no" dir="ltr">C0</code>&quot; can&#39;t be the initial subsequence of any well-formed
code unit sequence. Thus, the output should be &quot;<code translate="no" dir="ltr">A\ufffd\ufffdA\ufffdA</code>.&quot;</li>
<li>To decode a modified UTF-8 / CESU-8 sequence in Android 9 or higher, use the
<a href="https://developer.android.com/reference/java/io/DataInputStream.html#readUTF()"><code translate="no" dir="ltr">DataInputStream.readUTF()</code></a>
method or the <code translate="no" dir="ltr">NewStringUTF()</code> JNI method.</li>
</ul>

<h2 id="certificate-common-name" data-text="Hostname verification using a certificate" tabindex="-1">Hostname verification using a certificate</h2>

<p><a href="https://tools.ietf.org/html/rfc2818%7D%7B:%20.external-link">RFC 2818</a> describes two
methods to match a domain name against a certificate&mdash;using the available
names within the <code translate="no" dir="ltr">subjectAltName</code> (<code translate="no" dir="ltr">SAN</code>) extension, or in the absence of a
<code translate="no" dir="ltr">SAN</code> extension, falling back to the <code translate="no" dir="ltr">commonName</code> (<code translate="no" dir="ltr">CN</code>).</p>

<p>However, the fallback to the <code translate="no" dir="ltr">CN</code> was deprecated in RFC 2818. For this reason,
Android no longer falls back to using the <code translate="no" dir="ltr">CN</code>. To verify a hostname, the server
must present a certificate with a matching <code translate="no" dir="ltr">SAN</code>. Certificates that don&#39;t
contain a <code translate="no" dir="ltr">SAN</code> matching the hostname are no longer trusted.</p>

<h2 id="network-address-strictmode" data-text="Network address lookups can cause network violations" tabindex="-1">Network address lookups can cause network violations</h2>

<p>Network address lookups that require name resolution can involve network I/O and
are therefore considered blocking operations. Blocking operations on the main
thread can cause pauses or jank.</p>

<p>The <code translate="no" dir="ltr"><a href="/reference/android/os/StrictMode">StrictMode</a></code> class is a development tool that helps
developers to detect problems in their code.</p>

<p>In Android 9 and higher, <code translate="no" dir="ltr">StrictMode</code> detects network
violations caused by network address lookups that require name resolution.</p>

<p>You should not ship your apps with <code translate="no" dir="ltr">StrictMode</code> enabled. If you do, then your
apps can experience exceptions, such as
<code translate="no" dir="ltr"><a href="/reference/android/os/NetworkOnMainThreadException">NetworkOnMainThreadException</a></code> when using the
<code translate="no" dir="ltr"><a href="/reference/android/os/StrictMode.ThreadPolicy.Builder#detectNetwork()">detectNetwork()</a></code> or
<code translate="no" dir="ltr"><a href="/reference/android/os/StrictMode.ThreadPolicy.Builder#detectAll()">detectAll()</a></code> methods to get a
policy that detects network violations.</p>

<p>Resolving a numeric IP address isn&#39;t considered a blocking operation. Numeric IP
address resolution works the same as in versions before Android 9.</p>

<h2 id="trafficstats-setthreadstatstag" data-text="Socket tagging" tabindex="-1">Socket tagging</h2>

<p>In platform versions lower than Android 9, if a socket is
tagged using the
<code translate="no" dir="ltr"><a href="/reference/android/net/TrafficStats#setThreadStatsTag(int)">setThreadStatsTag()</a></code> method,
the socket is untagged when it&#39;s sent to another process using
<a href="https://source.android.com/devices/architecture/hidl/binder-ipc#ipc">binder IPC</a>
with a <code translate="no" dir="ltr"><a href="/reference/android/os/ParcelFileDescriptor">ParcelFileDescriptor</a></code> container.</p>

<p>In Android 9 and higher, the socket tag is kept when it’s sent to another
process using binder IPC. This change can affect network traffic statistics, for
example, when using the
<code translate="no" dir="ltr"><a href="/reference/android/app/usage/NetworkStatsManager#queryDetailsForUidTag(int, java.lang.String, long, long, int, int)">queryDetailsForUidTag()</a></code> method.</p>

<p>If you want to retain the behavior of the previous versions, which untags a
socket that is sent to another process, you can call
<code translate="no" dir="ltr"><a href="/reference/android/net/TrafficStats#untagSocket(java.net.Socket)">untagSocket()</a></code> before sending the
socket.</p>

<h2 id="socketimpl-shutdowninput" data-text="Reported amount of available bytes in socket" tabindex="-1">Reported amount of available bytes in socket</h2>

<p>The <code translate="no" dir="ltr"><a href="/reference/java/net/SocketImpl#available()">available()</a></code> method returns <code translate="no" dir="ltr">0</code> when it&#39;s called
after invoking the <code translate="no" dir="ltr"><a href="/reference/java/net/SocketImpl#shutdownInput()">shutdownInput()</a></code> method.</p>

<h2 id="network-capabilities-vpn" data-text="More detailed network capabilities reporting for VPNs" tabindex="-1">More detailed network capabilities reporting for VPNs</h2>

<p>In Android 8.1 (API level 27) and lower, the
<code translate="no" dir="ltr"><a href="/reference/android/net/NetworkCapabilities">NetworkCapabilities</a></code> class only reported a limited set of
information for VPNs, such as
<code translate="no" dir="ltr"><a href="/reference/android/net/NetworkCapabilities#TRANSPORT_VPN">TRANSPORT_VPN</a></code>, but omitting
<code translate="no" dir="ltr"><a href="/reference/android/net/NetworkCapabilities#NET_CAPABILITY_NOT_VPN">NET_CAPABILITY_NOT_VPN</a></code>. This limited
information made it difficult to determine if using a VPN would result in charges
to the app&#39;s user. For example, checking
<code translate="no" dir="ltr"><a href="/reference/android/net/NetworkCapabilities#NET_CAPABILITY_NOT_METERED">NET_CAPABILITY_NOT_METERED</a></code> would not
determine whether the underlying networks were metered or not.</p>

<p>In Android 9 and higher, when a VPN calls the
<code translate="no" dir="ltr"><a href="/reference/android/net/VpnService#setUnderlyingNetworks(android.net.Network[])">setUnderlyingNetworks()</a></code>
method, the Android system merges the transports and capabilities of any
underlying networks and returns the result as the effective network capabilities
of the VPN network.</p>

<p>In Android 9 and higher, apps that already check for
<code translate="no" dir="ltr">NET_CAPABILITY_NOT_METERED</code> receive the network capabilities of the VPN and the
underlying networks.</p>

<h2 id="qtaguid-nolonger-accessible" data-text="Files in xt_qtaguid folder are no longer available to apps" tabindex="-1">Files in xt_qtaguid folder are no longer available to apps</h2>

<p>Beginning with Android 9, apps are not allowed to have direct
read access to files in the <code translate="no" dir="ltr">/proc/net/xt_qtaguid</code> folder. The reason is to
ensure consistency with some devices that don&#39;t have these files at all.</p>

<p>The public APIs that rely on these files, <code translate="no" dir="ltr"><a href="/reference/android/net/TrafficStats">TrafficStats</a></code> and
<code translate="no" dir="ltr"><a href="/reference/android/app/usage/NetworkStatsManager">NetworkStatsManager</a></code>, continue to work as intended.
However, the unsupported
<a href="https://android.googlesource.com/platform/system/core/+/master/libcutils/include/cutils">cutils</a>
functions, such as
<a href="https://android.googlesource.com/platform/system/core/+/master/libcutils/include/cutils/qtaguid.h#29"><code translate="no" dir="ltr">qtaguid_tagSocket()</code></a>,
may not work as expected&mdash;or at all&mdash; on different devices.</p>

<h2 id="fant-required" data-text="FLAG_ACTIVITY_NEW_TASK requirement is now enforced" tabindex="-1">FLAG_ACTIVITY_NEW_TASK requirement is now enforced</h2>

<p>With Android 9, you cannot start an activity from a
non-activity context unless you pass the intent flag
<a href="/reference/android/content/Intent#FLAG_ACTIVITY_NEW_TASK"><code translate="no" dir="ltr">FLAG_ACTIVITY_NEW_TASK</code></a>.
If you attempt to start an activity without passing this flag, the
activity does not start, and the system prints a message to the log.</p>
<aside class="note"><strong>Note:</strong><span> The flag requirement has always been the intended behavior, and was
enforced on versions lower than Android 7.0 (API level 24). A bug in Android
7.0 prevented the flag requirement from being enforced.</span></aside>
<h2 id="screen-rotation-changes" data-text="Screen rotation changes" tabindex="-1">Screen rotation changes</h2>

<p>Beginning with Android 9, there are significant changes to the
<strong>portrait</strong> rotation mode. In Android 8.0 (API level 26), users could toggle
between <strong>auto-rotate</strong> and <strong>portrait</strong> rotation modes using a Quicksettings
tile or Display settings. The portrait mode has been renamed <strong>rotation lock</strong>
and it is active when auto-rotate is toggled off. There are no changes to 
auto-rotate mode.</p>

<p>When the device is in rotation lock mode, users can lock their screen to any
rotation supported by the top, visible Activity. An Activity should not assume
it will always be rendered in portrait. If the top Activity can be rendered in
multiple rotations in auto-rotate mode, the same options should be available in
rotation locked mode, with some exceptions based on the Activity&#39;s
<code translate="no" dir="ltr">screenOrientation</code> setting (see the table below).</p>

<p>Activities that request a specific orientation (for example,
<code translate="no" dir="ltr">screenOrientation=landscape</code>) ignore the user lock preference and behave
the same way as in Android 8.0.</p>

<p>The screen orientation preference can be set at the Activity level in the <a href="/reference/android/R.attr#screenOrientation">Android
Manifest</a>, or programmatically
with <a href="/reference/android/app/Activity#setRequestedOrientation(int)">setRequestedOrientation()</a>.</p>

<p>The rotation lock mode works by setting the user rotation preference which the
WindowManager uses when handling Activity rotation. The user rotation preference
might be changed in the following cases. Note that there is a bias to return to
the device&#39;s natural rotation, which is normally portrait for phone form factor
devices:</p>

<ul>
<li>When the user accepts a rotation suggestion the rotation preference changes to the suggestion.</li>
<li>When the user switches to a forced portrait app (including the lock screen or the launcher) the rotation preference changes to portrait.</li>
</ul>

<p>The following table summarizes rotation behavior for the common screen
orientations:</p>

<table>
<thead>
<tr>
<th>Screen Orientation</th>
<th>Behavior</th>
</tr>
</thead>

<tbody>
<tr>
<td>unspecified, user</td>
<td>In auto-rotate and rotation lock the Activity can be rendered in portrait or landscape (and the reverse). Expect to support both portrait and landscape layouts.</td>
</tr>
<tr>
<td>userLandscape</td>
<td>In auto-rotate and rotation lock the Activity can be rendered in either landscape or reverse landscape. Expect to support only landscape layouts.</td>
</tr>
<tr>
<td>userPortrait</td>
<td>In auto-rotate and rotation lock the Activity can be rendered in either portrait or reverse portrait. Expect to support only portrait layouts.</td>
</tr>
<tr>
<td>fullUser</td>
<td>In auto-rotate and rotation lock the Activity can be rendered in portrait or landscape (and the reverse). Expect to support both portrait and landscape layouts.<br><br>Rotation lock users will be given the option to lock to reverse portrait, often 180º.</td>
</tr>
<tr>
<td>sensor, fullSensor, sensorPortrait, sensorLandscape</td>
<td>The rotation lock mode preference is ignored and is treated as if auto-rotate is active. Only use this in exceptional circumstances with very careful UX consideration.</td>
</tr>
</tbody>
</table>

<h2 id="apache-nonp" data-text="Apache HTTP client deprecation affects apps with non-standard ClassLoader" tabindex="-1">Apache HTTP client deprecation affects apps with non-standard ClassLoader</h2>

<p>With Android 6.0,
<a href="/about/versions/marshmallow/android-6.0-changes#behavior-apache-http-client">we removed support for the Apache HTTP client</a>.
This change has no effect on the great majority of apps that do not target
Android 9 or higher. However, the change can affect certain apps that
use a nonstandard <a href="/reference/java/lang/ClassLoader"><code translate="no" dir="ltr">ClassLoader</code></a> structure,
even if the apps do not target Android 9 or higher.</p>

<p>An app can be affected if it uses a non-standard <code translate="no" dir="ltr">ClassLoader</code> that explicitly
delegates to the system <code translate="no" dir="ltr">ClassLoader</code>. These apps need to delegate to the <em>app</em>
<code translate="no" dir="ltr">ClassLoader</code> instead when looking for classes in <code translate="no" dir="ltr">org.apache.http.*</code>. If they
delegate to the system <code translate="no" dir="ltr">ClassLoader</code>, the apps will fail on Android 9 or higher
with a <a href="/reference/java/lang/NoClassDefFoundError"><code translate="no" dir="ltr">NoClassDefFoundError</code></a>,
because those classes are no longer known to the system <code translate="no" dir="ltr">ClassLoader</code>. To
prevent similar problems in the future, apps should in general load classes
through the app <code translate="no" dir="ltr">ClassLoader</code> rather than accessing the system <code translate="no" dir="ltr">ClassLoader</code>
directly.</p>

<h2 id="multi-camera" data-text="Enumerating cameras" tabindex="-1">Enumerating cameras</h2>

<p>Apps running on Android 9 devices can discover every available camera by calling
<a href="/reference/android/hardware/camera2/CameraManager#getCameraIdList()"><code translate="no" dir="ltr">getCameraIdList()</code></a>.
An app should not assume that the device has only a single back camera or only a
single front camera.</p>

<p>For example, if your app has a button to switch between the front and back
cameras, there may be more than one front or back camera to choose from. You
should walk the camera list, examine each camera&#39;s characteristics, and decide
which cameras to expose to the user.</p>
