Feb 14, 2026 </time> </span> <span> Updated <time data-ts="1773612082" data-df="ll" data-bs-toggle="tooltip" data-bs-placement="bottom" > Mar 15, 2026 </time> </span><div class="d-flex justify-content-between"> <span> By <em> <a href="https://github.com/dmpdump">dmpdump</a> </em> </span><div> <span class="readtime" data-bs-toggle="tooltip" data-bs-placement="bottom" title="1102 words" > <em>6 min</em> read</span></div></div></div></header><div class="content"><p>In early March, <a href="https://x.com/malwrhunterteam">MalwareHunterTeam</a> shared a hash associated with a Linux backdoor with 0 detection in VirusTotal. It is well known that AV engines in VirusTotal do not implement the full capability of AV solutions, however, the presence of obviously malicious unobfuscated code made it an interesting finding. The backdoor has been in VirusTotal since January 27, 2026 with 2 distinct submissions, one from the US and another from Vietnam.</p><p>The backdoor is contained within a tar file named <code class="language-plaintext highlighter-rouge">out_linux.tar</code>. The tar file contains 2 files, <code class="language-plaintext highlighter-rouge">netd</code> and <code class="language-plaintext highlighter-rouge">netd.lck</code>.</p><ul><li><code class="language-plaintext highlighter-rouge">out_linux.tar</code>: 8e4f33722c16a5e922a81a4be61db804bbf2e899d89902085e854b7f0a0d587f<li><code class="language-plaintext highlighter-rouge">netd</code>: be0f36ee071a9c0c200dcdaed98fce7fadc31305d0a5f24a244a3af7833d21dd<li><code class="language-plaintext highlighter-rouge">netd.lck</code>: 78e145fcc9f099a1dec49f9001bfbb06366fcf30f66a7cc9e6605b36019dfac4</ul><p><a href="/assets/images/linuxbackdoor/tarcontent.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/tarcontent.png" alt="sshot" loading="lazy"></a></p><h1 id="backdoor-analysis">Backdoor Analysis</h1><p><code class="language-plaintext highlighter-rouge">netd</code> is a 64-bit ELF backdoor. It is statically linked, and not stripped. <code class="language-plaintext highlighter-rouge">netd.lck</code>, on the other hand, is an encrypted configuration file used by the backdoor. This configuration file can be retrieved and updated remotely by the threat actor via backdoor commands.</p><p>When the backdoor is initialized, it implements the <code class="language-plaintext highlighter-rouge">lock_process</code> and a <code class="language-plaintext highlighter-rouge">load_config</code> functions.</p><p><a href="/assets/images/linuxbackdoor/lock_conf.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/lock_conf.png" alt="sshot" loading="lazy"></a></p><p><code class="language-plaintext highlighter-rouge">lock_process</code> uses a named semaphore (<code class="language-plaintext highlighter-rouge">KoqiItPtTbsntsoTspaltsT</code>) that acts as a mutex to prevent repeated execution of the backdoor. This lock can be bypassed by running the backdoor with the <code class="language-plaintext highlighter-rouge">skip</code> argument.</p><p><a href="/assets/images/linuxbackdoor/semaphore.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/semaphore.png" alt="sshot" loading="lazy"></a></p><p>The <code class="language-plaintext highlighter-rouge">load_config</code> function reads the configuration file from <code class="language-plaintext highlighter-rouge">&lt;backdoor_path&gt;.lck</code>. The backdoor expects the .lck file to exist in its same path and have the same file name as the backdoor, so it is retrieved by parsing the backdoor path, retrieving the backdoor file name, and appending the .lck extension, resulting in <code class="language-plaintext highlighter-rouge">netd.lck</code>. The backdoor reads 810 bytes (the size of <code class="language-plaintext highlighter-rouge">netd.lck</code>) and decrypts the first byte with XOR key <code class="language-plaintext highlighter-rouge">0x38</code>. The rest of the configuration file is XOR decrypted with key <code class="language-plaintext highlighter-rouge">0x384E65296D662467273B2B3D3474316B2D334E79634D4557662C414F496B6E7433776E5566674B644646746E4C2C53643569</code>.</p><p>After decryption, we can see 2 domains:</p><ul><li><code class="language-plaintext highlighter-rouge">chopaw.camdvr[.]org</code><li><code class="language-plaintext highlighter-rouge">drawpin.accesscam[.]org</code></ul><p><a href="/assets/images/linuxbackdoor/decryptedconfig.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/decryptedconfig.png" alt="sshot" loading="lazy"></a></p><p>The backdoor has an additional default hard-coded C2:</p><ul><li><code class="language-plaintext highlighter-rouge">mefng.giize[.]com:443</code></ul><p><a href="/assets/images/linuxbackdoor/configdefc2.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/configdefc2.png" alt="sshot" loading="lazy"></a></p><p>After locking the process and loading the configuration, the backdoor forks to daemonize itself, acquiring a new session. Within the daemon, it allocates a PTY pair via <code class="language-plaintext highlighter-rouge">forkPty</code>. It then forks again. The child executes an interactive shell (<code class="language-plaintext highlighter-rouge">$SHELL</code> or <code class="language-plaintext highlighter-rouge">/bin/sh -i</code>) and the parent spawns <code class="language-plaintext highlighter-rouge">recv_thread</code> as a thread to manage RC4-encrypted C2 communication.</p><p><a href="/assets/images/linuxbackdoor/forks.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/forks.png" alt="sshot" loading="lazy"></a></p><p>Previously initialized shell:</p><p><a href="/assets/images/linuxbackdoor/shell.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/shell.png" alt="sshot" loading="lazy"></a></p><p>Execution of the interactive shell: <a href="/assets/images/linuxbackdoor/shellexec.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/shellexec.png" alt="sshot" loading="lazy"></a></p><p>The <code class="language-plaintext highlighter-rouge">recv_thread</code> function initializes the connection to the C2 and handles the operator’s commands. The 2 main functions within <code class="language-plaintext highlighter-rouge">recv_thread</code> are <code class="language-plaintext highlighter-rouge">connect_peer</code> and <code class="language-plaintext highlighter-rouge">main_proc</code>.</p><p><a href="/assets/images/linuxbackdoor/connectmainproc.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/connectmainproc.png" alt="sshot" loading="lazy"></a></p><p>The <code class="language-plaintext highlighter-rouge">connect_peer</code> function implements an interesting function named <code class="language-plaintext highlighter-rouge">resolve_name</code>. This function uses the Google DNS (8.8.8.8), it makes a DNS request to <code class="language-plaintext highlighter-rouge">www.google.com</code>, likely a decoy, and then makes a DNS request against the C2 to retrieve its IP address using <code class="language-plaintext highlighter-rouge">getaddress()</code>. The retrieved IP address is subsequently XOR decrypted with key <code class="language-plaintext highlighter-rouge">0xC7852752</code>. The domains used in this backdoor (<code class="language-plaintext highlighter-rouge">camdvr[.]org</code>, <code class="language-plaintext highlighter-rouge">accesscam[.]org</code>, <code class="language-plaintext highlighter-rouge">giize[.]com</code>) are associated with the <code class="language-plaintext highlighter-rouge">Dynu Systems</code> Dynamic DNS service, so the IP that is XOR decrypted can be updated dynamically by the threat actor.</p><p><a href="/assets/images/linuxbackdoor/resolve_name.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/resolve_name.png" alt="sshot" loading="lazy"></a></p><p>Once the IP address is retrieved and decrypted, a TCP socket connection is established via <code class="language-plaintext highlighter-rouge">connect_ex</code>. The connection is followed by a custom RC4 challenge-response protocol implemented in a function named <code class="language-plaintext highlighter-rouge">auth_response</code>:</p><p><a href="/assets/images/linuxbackdoor/connsequence.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/connsequence.png" alt="sshot" loading="lazy"></a></p><p>The <code class="language-plaintext highlighter-rouge">auth_response</code> function implements the following challenge-response mechanism:</p><ul><li>It generates 100 random bytes to be sent to the C2.<li>The bytes to be sent are random, but one specific byte is set to <code class="language-plaintext highlighter-rouge">0x7C</code> (offset 23 based on static analysis).<li>The random bytes are encrypted using RC4 with the following key: <code class="language-plaintext highlighter-rouge">0x5D84EFD639604BB295FC270E715883EA</code>.<li>A response from the C2 is received and decrypted with the same RC4 key.<li>A byte is checked for the presence of value <code class="language-plaintext highlighter-rouge">0xC7</code> at a specific offset (offset 77 based on static analysis).<li>A new request is made to the C2, using the previously checked byte with value <code class="language-plaintext highlighter-rouge">0xC7</code>.</ul><p>If the byte with value <code class="language-plaintext highlighter-rouge">0xC7</code> is received at the expected offset, a new request with fresh random bytes is sent to the C2 with byte value <code class="language-plaintext highlighter-rouge">0xC7</code> explicitly set at the same hardcoded offset.</p><p><a href="/assets/images/linuxbackdoor/challengeresponse.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/challengeresponse.png" alt="sshot" loading="lazy"></a></p><p>The backdoor commands are handled in a command dispatcher function named <code class="language-plaintext highlighter-rouge">main_proc</code>. Before implementing the command dispatching capabilities, the backdoor sends victim information to the C2. All the traffic between the victim and the C2 is RC4 encrypted with the key referenced before. Before implementing the command dispatching capabilities, the backdoor sends system information to the C2 with a function appropriately named <code class="language-plaintext highlighter-rouge">send_systeminfo</code>. The information is sent with the following format:</p><p><code class="language-plaintext highlighter-rouge">generated_uid|hostname|connection_state|unknown_value|sysname|nodename|release|version|machine|domain name|</code></p><p>The uid generated for each victim will be based on the mac address. If the mac address cannot be obtained, a random per-victim uid is generated. The majority of the system information is retrieved from the <a href="https://man7.org/linux/man-pages/man2/uname.2.html">utsname</a> struct, as can be seen below:</p><p><a href="/assets/images/linuxbackdoor/systeminfo.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/systeminfo.png" alt="sshot" loading="lazy"></a></p><p>The following interactive commands are implemented by this backdoor:</p><div class="table-wrapper"><table><thead><tr><th>Command<th>Function Name<th>Capability<tbody><tr><td>0<td>do_upload<td>C2 to victim file transfer<tr><td>1<td>do_download<td>Victim to C2 file transfer<tr><td>2<td>popen<td>Execute arbitrary shell command<tr><td>3<td>do_dir<td>Directory listing<tr><td>4<td>do_rm_file<td>Delete file (rm -f)<tr><td>5<td>N/A<td>Interactive shell input<tr><td>7<td>N/A<td>Sleep<tr><td>8<td>N/A<td>‘continue’. Possible keepalive<tr><td>9<td>N/A<td>Self-delete / cleanup by setting connection state to 6<tr><td>0xA<td>request_config<td>Send current configuration to the C2<tr><td>0xB<td>update_config<td>Receive a new configuration from the C2<tr><td>0xC<td>do_get_process<td>Process list (ps -eo pid,ppid,command)<tr><td>0xD<td>do_kill_process<td>Kill process (kill -9 pid)</table></div><p>Excerpt from <code class="language-plaintext highlighter-rouge">main_proc</code> implementing the <code class="language-plaintext highlighter-rouge">send_systeminfo</code> function and the command dispatcher:</p><p><a href="/assets/images/linuxbackdoor/dispatcher.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/dispatcher.png" alt="sshot" loading="lazy"></a></p><p>The following connection states are implemented in the backdoor:</p><div class="table-wrapper"><table><thead><tr><th>Connection State<th>Description<tbody><tr><td>2<td>Send system info<tr><td>3<td>Receive commands<tr><td>4<td>error / default<tr><td>5<td>sleep<tr><td>6<td>self-destroy</table></div><p>For self-deletion purposes, when command 9 is received, the connection state is set to 6. This state is associated with the removal of the backdoor and the configuration file:</p><p><a href="/assets/images/linuxbackdoor/selfdestroy.png" class="popup img-link shimmer"><img src="/assets/images/linuxbackdoor/selfdestroy.png" alt="sshot" loading="lazy"></a></p><h1 id="possible-c2-ip">Possible C2 IP</h1><p>Based on the <code class="language-plaintext highlighter-rouge">resolve_name</code> address resolution, the actual C2 IP address will be retrieved from the domain used by the backdoor (e.g. <code class="language-plaintext highlighter-rouge">mefng.giize[.]com:443</code>), and it will be subsequently XOR decrypted with key <code class="language-plaintext highlighter-rouge">0xC7852752</code>.
