href="https://x.com/500mk500">@500mk500</a> and a related sample by <a href="https://x.com/malwrhunterteam">@malwrhunterteam</a>, I found quite a few similarities with the Adaptix Agent using the adaptix_gopher protocol.</p><p>In early July 2026, <a href="https://x.com/malwrhunterteam">MalwareHunterTeam</a> shared an interesting ELF named <code class="language-plaintext highlighter-rouge">gregbfdah.png</code> with minimal detection in VirusTotal. The ELF was uploaded to VirusTotal on 2026-06-16 and it still has very low detection. The file was delivered from the following AWS domain: <code class="language-plaintext highlighter-rouge">https://zapier-logos.s3.amazonaws[.]com/gregbfdah.png</code>. That URL was first submitted to VirusTotal from India on 2026-06-11.</p><p>The file in question is a statically-linked x86-64 Linux ELF backdoor/C2 implant written in C++, possibly still in development. When executed, the backdoor:</p><ul><li>Implements a classic double fork for daemonization.<li>Redirects its standard streams to <code class="language-plaintext highlighter-rouge">/dev/null</code>.<li>Changes directories to <code class="language-plaintext highlighter-rouge">/tmp</code>.<li>Checks if it was executed with the <code class="language-plaintext highlighter-rouge">-nodel</code> argument. If it was, it executes the main backdoor logic. If not, it self-deletes.</ul><p><a href="/assets/images/linbdoor/main.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/main.png" alt="sshot" loading="lazy"></a></p><h2 id="configuration-decryption"><span class="me-2">Configuration Decryption</span><a href="#configuration-decryption" class="anchor text-muted"><i class="fas fa-hashtag"></i></a></h2><p>The implant uses the <a href="https://msgpack.org/index.html"><code class="language-plaintext highlighter-rouge">MessagePack</code></a> binary serialization format for its configuration and C2 communication. The main function of the malware starts by retrieving, decrypting, and parsing its configuration.</p><p>The following attributes are parsed from the configuration:</p><ul><li><code class="language-plaintext highlighter-rouge">type</code><li><code class="language-plaintext highlighter-rouge">banner_size</code><li><code class="language-plaintext highlighter-rouge">conn_timeout</code><li><code class="language-plaintext highlighter-rouge">conn_count</code><li><code class="language-plaintext highlighter-rouge">sleep_delay</code><li><code class="language-plaintext highlighter-rouge">jitter</code><li><code class="language-plaintext highlighter-rouge">addresses</code></ul><p><a href="/assets/images/linbdoor/config1.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/config1.png" alt="sshot" loading="lazy"></a></p><p>The configuration is embedded in the .data section and is encrypted with AES-128 in GCM mode. </pre></table></code></div></div><p>Decrypted and parsed configuration for this backdoor:</p><p><a href="/assets/images/linbdoor/decryptedconfig.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/decryptedconfig.png" alt="sshot" loading="lazy"></a></p><p>Next, the agent generates a per-host ID (a “fingerprint”) using SHA1. The fingerprint is comprised of the following elements:</p><ul><li>The <code class="language-plaintext highlighter-rouge">nginx</code> string. This does not change.<li>The machine id from <code class="language-plaintext highlighter-rouge">/etc/machine-id</code>. If that fails, it tries with <code class="language-plaintext highlighter-rouge">/proc/sys/kernel/random/boot_id</code>.<li>The username (via the <code class="language-plaintext highlighter-rouge">$USER</code> and <code class="language-plaintext highlighter-rouge">$LOGNAME</code> environment variables).<li>The MAC address, enumerating interfaces under <code class="language-plaintext highlighter-rouge">/sys/class/net</code>, searching for the first non-loopback interface.<li>The <code class="language-plaintext highlighter-rouge">reverse</code> static string. This does not change.</ul><p><a href="/assets/images/linbdoor/agentid.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/agentid.png" alt="sshot" loading="lazy"></a></p><p><a href="/assets/images/linbdoor/agentid2.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/agentid2.png" alt="sshot" loading="lazy"></a></p><p>Only the first 4 bytes of the SHA1 digest are extracted as the agent ID, with <code class="language-plaintext highlighter-rouge">_byteswap_ulong</code> applied for endian conversion.</p><h2 id="key-generation-and-system-profiling"><span class="me-2">Key Generation and System Profiling</span><a href="#key-generation-and-system-profiling" class="anchor text-muted"><i class="fas fa-hashtag"></i></a></h2><p>Next, the ‘agent’ generates a new random AES-128 session key and retrieves the key from the configuration (for further use).</p><p><a href="/assets/images/linbdoor/sessionkey.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/sessionkey.png" alt="sshot" loading="lazy"></a></p><p>After generating the session key, the agent starts profiling the infected host. The following items are retrieved:</p><ul><li>The process name that the agent is running as by checking <code class="language-plaintext highlighter-rouge">/proc/self/exe</code>. If it cannot be retrieved, it falls back to <code class="language-plaintext highlighter-rouge">agent</code>.<li>The PID (process ID).<li>The username by first getting the user ID and looking it up in <code class="language-plaintext highlighter-rouge">/etc/passwd</code>. Fallbacks include the <code class="language-plaintext highlighter-rouge">$USER</code> environment variable, the <code class="language-plaintext highlighter-rouge">$LOGNAME</code> environment variable, or <code class="language-plaintext highlighter-rouge">unknown</code> if everything else fails.<li>The hostname by retrieving the nodename via the <code class="language-plaintext highlighter-rouge">uname</code> syscall.<li>The IP address is retrieved by creating a UDP socket (using <code class="language-plaintext highlighter-rouge">8.8.8.8</code> as a dummy address), calling connect to trigger a routing table lookup, and retrieving the local IP address via <code class="language-plaintext highlighter-rouge">getsockname</code>. It falls back to 127.0.0.1.<li>Validates if it is running as root by comparing the uid to 0.<li>The OS type is always set to “linux”.<li>OS information by parsing <code class="language-plaintext highlighter-rouge">/etc/os-release</code> and parsing <code class="language-plaintext highlighter-rouge">NAME=</code>, <code class="language-plaintext highlighter-rouge">VERSION=</code>, and <code class="language-plaintext highlighter-rouge">VERSION_ID=</code>. This check falls back to running <code class="language-plaintext highlighter-rouge">uname</code>, or <code class="language-plaintext highlighter-rouge">"Linux"</code> if everything else fails.</ul><p>Process name retrieval and fallback to <code class="language-plaintext highlighter-rouge">agent</code>:</p><p><a href="/assets/images/linbdoor/procname.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/procname.png" alt="sshot" loading="lazy"></a></p><p>Username retrieval:</p><p><a href="/assets/images/linbdoor/username.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/username.png" alt="sshot" loading="lazy"></a></p><p>Hostname retrieval:</p><p><a href="/assets/images/linbdoor/hostcheck.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/hostcheck.png" alt="sshot" loading="lazy"></a></p><p>IP retrieval:</p><p><a href="/assets/images/linbdoor/ipcheck.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/ipcheck.png" alt="sshot" loading="lazy"></a></p><p>OS type and OS information:</p><p><a href="/assets/images/linbdoor/oschecks.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/oschecks.png" alt="sshot" loading="lazy"></a></p><h2 id="beacon-registration"><span class="me-2">Beacon Registration</span><a href="#beacon-registration" class="anchor text-muted"><i class="fas fa-hashtag"></i></a></h2><p>After profiling the system, the agent builds a beacon to register to the C2. The beacon includes a combination of configuration settings and system profiling information. The registration beacon is serialized using the MessagePack format. The registration MessagePack has an outer map and an inner map.</p><p>The inner map contains: the process name, the pid, the user, the hostname, the ip address, whether or not the implant is running as root, the os, the os version, the encryption key (the previously generated session key), the sleep delay, and the jitter. In addition to these values, which were observed before in the system profiling and configuration, additional values are sent:</p><ul><li>acp<li>oem<li>rootkit_scheme</ul><p>All three are set to 0, and not modified. While I did not see a clear explanation for these fields in the implant, a hypothesis is that there may be versions of the agent that support Windows. <code class="language-plaintext highlighter-rouge">acp</code> could potentially refer to the <code class="language-plaintext highlighter-rouge">GetACP</code> function (to obtain the current ANSI Code Page), and <code class="language-plaintext highlighter-rouge">oem</code> could refer to <code class="language-plaintext highlighter-rouge">GetOEMCP</code>, associated with the OEM code page. However, this is just a hypothesis. I could not correlate these settings with anything within this specific implant.</p><p>Inner map:</p><p><a href="/assets/images/linbdoor/innermap.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/innermap.png" alt="sshot" loading="lazy"></a></p><p>The outer map contains the ID, previously generated via the SHA1 hash, the type, from the configuration, and the data, which is the inner map data.</p><p><a href="/assets/images/linbdoor/outermap.png" class="popup img-link shimmer"><img src="/assets/images/linbdoor/outermap.png" alt="sshot" loading="lazy"></a></p><p>The registration beacon with the inner and outer maps is encrypted with the AES-128 key from the implant configuration (previously decrypted). This has to be known by the C2 to decrypt the registration information. This initial beacon includes the random session key.</p><p>After sending the registration beacon, the agent enters a loop to receive encrypted instructions from the C2. The commands received from the C2 are decrypted with the session key and deserialized with MessagePack unpacking. A <code class="language-plaintext highlighter-rouge">type</code> and an <code class="language-plaintext highlighter-rouge">object</code> are parsed from the response.
