When it is loaded, its malicious logic is executed via the <code class="language-plaintext highlighter-rouge">execute_python_entrypoint</code> exported function. There is a second exported function , <code class="language-plaintext highlighter-rouge">simple_print</code>, but this one returns without doing anything.</p><p>The DLL uses <code class="language-plaintext highlighter-rouge">GetModuleFileNameW</code> to get a path to the executable loading it (the path to <code class="language-plaintext highlighter-rouge">calibre.exe</code>). Then, it creates/checks a mutex named <code class="language-plaintext highlighter-rouge">Global\\LightshotsService32</code> to avoid duplicate execution. If the mutex does not exist, it creates a RunOnce registry persistence entry in the following path: <code class="language-plaintext highlighter-rouge">HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnce\ /v LightshotsService</code>. The <code class="language-plaintext highlighter-rouge">LightshotService</code> value has the previously retrieved path to the executable loading the DLL.</p><p>After setting persistence, 3 routines with the core functionality are executed: The first one decrypts the configuration, the second one builds a beacon to the C2, and the third one contacts the C2 and retrieves additional payload.</p><p><a href="/assets/images/downloaderru/mainlogic.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/mainlogic.png" alt="Main logic" loading="lazy"></a> <em>Figure 5: Main logic in side-loaded DLL.</em></p><p>The stager configuration is decrypted using AES in CTR mode. The DLL retrieves and parses an embedded blob which has the AES key, the IV, and the encrypted configuration.</p><p><a href="/assets/images/downloaderru/codedecrypt.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/codedecrypt.png" alt="Main logic" loading="lazy"></a> <em>Figure 6: Decryption calls and embedded blob.</em></p><p>The embedded blob includes the size of the key, the IV, and the encrypted configuration, all preceded by their corresponding sizes.</p><ul><li>IV size: 0x10 (16 bytes)<li>IV: 54e62fc69ea8ca6c5ecaa61a31be5337<li>Key size: 0x10 (16 bytes)<li>Key: 4c88525415a13f21796fc24fdf6bb228<li>Encrypted configuration size: 0xE7 (231 bytes)<li>Encrypted configuration: 0f6bc57d867507cc4cd70b99fd812c9253a5dd95b6982af029db1d21a1de9d8172c92b9566e9c35d2c28cdf731099e40ab227e3d863964e2c970f32d3b8f5bbd3e6f396c71a155b34dfc514bbcf8b40b024928b06df72c5bccf6bd2c0f2a538a30270288f3a919f97135c16e61bb85fe9f241c35b7426853f144366dc1bc4d75bdddefc24d824badafb11142c6625772471ab13f88b0f31b5aeae13560d8fe6be3142f46cbef7d7f13372f5a75f74d90cff70399615eae5c65c8a4671a43403d3d37d50b2ba5bfdeda546ad2cbf887665d13ec1ea731a4c92fcae8a9be7d9b6dc34d18ca844549</ul><p><a href="/assets/images/downloaderru/blob.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/blob.png" alt="Main logic" loading="lazy"></a> <em>Figure 7: Embedded configuration.</em></p><p>Decrypting the embedded blob with the parameters above reveals an RSA key and the C2 domain - The <code class="language-plaintext highlighter-rouge">Cookie:SESSION=</code> string is XOR decrypted, so the encrypted/encoded beacon is sent to the C2 as a “session cookie” in the request header.</p><p><code class="language-plaintext highlighter-rouge">Cookie:SESSION=&lt;BASE64_ENCODED_RSA_ENCRYPTED_PROFILING_INFORMATION&gt;</code></p><p>Next, a C2 polling function is implemented via a loop that switches from a GET request to a POST request. The stager first makes a GET request to the C2, reading the response back. The request embeds the RSA-encrypted beacon in the header. The connection to the C2 is implemented via the WINHTTP API, and it is proxy aware. For proxy discovery purposes, the implant attempts WPAD automatic discovery. If that fails, it attempts to use the proxy configured for Internet Explorer via <code class="language-plaintext highlighter-rouge">WinHttpGetIEProxyConfigForCurrentUser</code>.</p><p><a href="/assets/images/downloaderru/proxydiscovery.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/proxydiscovery.png" alt="Proxy Discovery" loading="lazy"></a> <em>Figure 9: Proxy discovery attempts.</em></p><p>The stager authenticates the C2 via a derived key challenge. When the beacon is generated, the stager generates a random 16-byte seed, derives an HMAC key from it using SHA-256, and transmits the seed to the C2 inside the registration beacon. The C2 RSA decrypts the beacon (it has the private key), recovers the seed, and derives the same HMAC key. On each GET request, the C2 must prove it holds this key. The C2 computes HMAC-SHA256 over 4 bytes of encrypted payload using the derived key and returns the first 12 bytes of the result in the response. The stager computes HMAC-SHA256 over the same 4 bytes using its locally held key and compares the first 12 bytes of the result against what the C2 provided. If they match, the C2 is authenticated and the implant switches to the POST method to retrieve a task.</p><p><a href="/assets/images/downloaderru/c2auth.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/c2auth.png" alt="C2 Auth" loading="lazy"></a> <em>Figure 10: C2 Authentication via HMAC SHA256.</em></p><p>The loop uses a separate routine to send POST requests to the C2, receive tasks, AES decrypt them, and execute them.</p><p><a href="/assets/images/downloaderru/taskhandler.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/taskhandler.png" alt="Task Handler" loading="lazy"></a> <em>Figure 11: Function responsible for handling C2 tasks.</em></p><p>This function creates a new thread to execute the decrypted tasks received from the C2. The tasks allow the DLL to act as a stager, delivering additional payloads. The downloaded payload is written to the previously created file.</p><p><a href="/assets/images/downloaderru/download2.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/download2.png" alt="Download" loading="lazy"></a> <em>Figure 13: Payload download.</em></p><p>The downloaded files may or may not have an ‘execute’ flag. When the ‘execute’ flag is set, the downloaded file is executed using the <code class="language-plaintext highlighter-rouge">CreateProcessW</code> API.</p><p><a href="/assets/images/downloaderru/execute.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/execute.png" alt="Execute" loading="lazy"></a> <em>Figure 14: Payload execution.</em></p><p>The stager uses a the <code class="language-plaintext highlighter-rouge">Baby::</code> namespace for deserialization purposes. This is a namespace that I have not seen used in malware before, and looks fairly unique - at least in the limited telemetry that I have. I could not find related samples using that namespace.</p><p><a href="/assets/images/downloaderru/baby.png" class="popup img-link shimmer"><img src="/assets/images/downloaderru/baby.png" alt="Baby"
