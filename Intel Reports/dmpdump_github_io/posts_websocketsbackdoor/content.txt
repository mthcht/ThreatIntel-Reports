class="post-meta text-muted"> <span> Posted <time data-ts="1791936000" data-df="ll" data-bs-toggle="tooltip" data-bs-placement="bottom" > Oct 14, 2026 </time> </span> <span> Updated <time data-ts="1792013478" data-df="ll" data-bs-toggle="tooltip" data-bs-placement="bottom" > Oct 14, 2026 </time> </span><div class="d-flex justify-content-between"> <span> By <em> <a href="https://github.com/dmpdump">dmpdump</a> </em> </span><div> <span class="readtime" data-bs-toggle="tooltip" data-bs-placement="bottom" title="1467 words" > <em>8 min</em> read</span></div></div></div></header><div class="content"><p>On September 29 2026, <a href="https://x.com/malwrhunterteam">@MalwareHunterTeam</a> shared a suspicious low detection file named <code class="language-plaintext highlighter-rouge">document.exe</code>, uploaded to VirusTotal from Iraq on that same day. The sample has minimal detection in VirusTotal:</p><p><a href="/assets/images/websockbdoor/lowdetection.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/lowdetection.png" alt="lowdetection" loading="lazy"></a> <em>Figure 1: Low Detection in VirusTotal.</em></p><p>The first thing that stands out in the sample is an interesting PDB path:<br /> <code class="language-plaintext highlighter-rouge">L:\1-The-Last-Versions\sendingto-costumers-version2\TAHVILAT\mehr\DP-version 2.1.0\Dpr-Vor-Cpp -final - Copy\x64\Release\Dp.pdb</code></p><p>Some of the interesting things in the PDB path include:</p><ul><li>The misspelling of <code class="language-plaintext highlighter-rouge">customers</code> as <code class="language-plaintext highlighter-rouge">costumers</code>, suggesting the malware developer is not a native English speaker.<li>The <code class="language-plaintext highlighter-rouge">TAHVILAT</code> folder, which may refer to <code class="language-plaintext highlighter-rouge">deliveries</code> in Persian.<li>The <code class="language-plaintext highlighter-rouge">mehr</code> folder. <code class="language-plaintext highlighter-rouge">Mehr</code> is the month of September/October in the Persian calendar.</ul><p>The references to Persian words in the PDB path suggest with low confidence a potential Iranian origin of the malware developer. That Iranian origin could be consistent with a possible target in Iraq, based on the submission geolocation. There are <a href="https://dreamgroup.com/blog/darkblinders-inside-an-active-espionage-campaign">recent reports</a> indicating Iran-nexus threat activity targeting the Kurdistan region of Iraq. However, additional indicators are needed for a higher confidence attribution.</p><h2 id="documentexe-downloader"><span class="me-2">Document.exe Downloader</span><a href="#documentexe-downloader" class="anchor text-muted"><i class="fas fa-hashtag"></i></a></h2><p>A review of <code class="language-plaintext highlighter-rouge">document.exe</code> revealed a downloader compiled using MSVC. The downloader first performs API resolution by walking the PEB to locate the base address of <code class="language-plaintext highlighter-rouge">kernel32.dll</code>. It then locates <code class="language-plaintext highlighter-rouge">LoadLibraryA</code> by computing its FNV-1a hash and walking kernel32’s export table directly, avoiding the use of <code class="language-plaintext highlighter-rouge">GetProcAddress</code>. <code class="language-plaintext highlighter-rouge">LoadLibraryA</code> is then called to load additional DLLs, and their exports are also resolved via FNV-1a export table walking. Resolved APIs are stored as function pointers for further calling in subsequent functions.</p><p><a href="/assets/images/websockbdoor/fnv1a1.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/fnv1a1.png" alt="fnv1a1" loading="lazy"></a> <em>Figure 2: LoadLibraryA Resolution.</em></p><p><a href="/assets/images/websockbdoor/fnv1a2.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/fnv1a2.png" alt="fnv1a2" loading="lazy"></a> <em>Figure 3: Sample Creation of API Function Pointer.</em></p><p>Function pointers are created for multiple APIs for capabilities consistent with downloader malware:</p><ul><li>CreateToolhelp32Snapshot<li>Process32FirstW<li>Process32NextW<li>CreateDirectoryA<li>CreateProcessA<li>GetTempPathA<li>Sleep<li>DeleteFileA<li>CopyFileA<li>FindFirstFileA<li>CreateFileA<li>WriteFile<li>CloseHandle<li>CreateMutexA<li>GetLastError<li>ExitProcess<li>ReleaseMutex<li>SetConsoleCtrlHandler<li>CreateThread<li>WaitForSingleObject<li>WaitForMultipleObjects<li>ShowWindow<li>GetConsoleWindow<li>GetUserNameA<li>ShellExecuteA<li>WinHttpOpen<li>WinHttpCloseHandle<li>WinHttpConnect<li>WinHttpOpenRequest<li>WinHttpSendRequest<li>WinHttpReceiveResponse<li>WinHttpReadData<li>WinHttpQueryHeaders<li>WinHttpAddRequestHeaders<li>WinHttpSetTimeouts</ul><p>The downloader XOR decrypts relevant strings with key <code class="language-plaintext highlighter-rouge">0x5A</code>. This reveals the infrastructure used to host the next stage payload and the name of the downloaded files (both on the remote server and locally on the victim’s disk).</p><ul><li>The next stage payload is downloaded from <code class="language-plaintext highlighter-rouge">153.75.247[.]94</code>.<li>The files have image extensions on the attacker infrastructure (e.g. .jpg), but are saved to disk with their actual extension (e.g. .dll).<li>The payload is downloaded to the <code class="language-plaintext highlighter-rouge">AppData\Roaming\Microsoft\Protect\NV</code> folder.</ul><p><a href="/assets/images/websockbdoor/stringdecrypt.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/stringdecrypt.png" alt="string decryption" loading="lazy"></a> <em>Figure 4: Sample String Decryption.</em></p><p>The downloader checks if it is the first run and if mutex <code class="language-plaintext highlighter-rouge">Global\\NvCDIr_U54321</code> is present.</p><p><a href="/assets/images/websockbdoor/mutex.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/mutex.png" alt="mutex check" loading="lazy"></a> <em>Figure 5: Mutex check</em></p><p>The downloader also checks if <code class="language-plaintext highlighter-rouge">AppData\Roaming\Microsoft\Protect\NV\nvcontainer.exe</code> already exists. If it does not, it continues with the download logic. First, it makes a ‘lazy’ connectivity check by creating a connection object using <code class="language-plaintext highlighter-rouge">google.com</code> as the host name. However, it never makes a request to it.</p><p><a href="/assets/images/websockbdoor/lazycheck.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/lazycheck.png" alt="lazy check" loading="lazy"></a> <em>Figure 6: Creation of Connection Object Without Connection</em></p><p>Finally, it performs the file downloads in a function I renamed to <code class="language-plaintext highlighter-rouge">fn_file_download</code>.</p><p><a href="/assets/images/websockbdoor/filecheckanddownload.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/filecheckanddownload.png" alt="file check and download" loading="lazy"></a> <em>Figure 7: File Check and Download</em></p><p>The file download function creates the destination folder <code class="language-plaintext highlighter-rouge">AppData\Roaming\Microsoft\Protect\NV</code> and creates a new thread to download the next stage files. The download sequence includes a HEAD request to check the length of the response body and a GET request to download the files using the WinHttp API.</p><p>The HEAD request checks the <code class="language-plaintext highlighter-rouge">WINHTTP_QUERY_CONTENT_LENGTH</code> InfoLevel flag via <code class="language-plaintext highlighter-rouge">WinHttpQueryHeaders</code>, which retrieves the size of the resource in bytes. The integer ‘5’ for the content length can be validated in the <a href="https://doxygen.reactos.org/dd/d59/winhttp_8h.html#a0a4cca98682a3aef78338072e4698110">ReactOS documentation</a>. This request uses the <code class="language-plaintext highlighter-rouge">Mozilla/5.0 (Windows NT 10.0; Win64; x64)</code> user-agent string. The retrieved length is passed as an argument to function that downloads files via GET requests.</p><p><a href="/assets/images/websockbdoor/downloadthread.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/downloadthread.png" alt="download thread" loading="lazy"></a> <em>Figure 8: Download Thread</em></p><p><a href="/assets/images/websockbdoor/headrequest.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/headrequest.png" alt="HEAD request" loading="lazy"></a> <em>Figure 9: Header check</em></p><p>A different user-agent string is used for the GET requests that retrieve the payload: <code class="language-plaintext highlighter-rouge">Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36</code>.</p><p><a href="/assets/images/websockbdoor/filedownload.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/filedownload.png" alt="GET" loading="lazy"></a> <em>Figure 10: File Download</em></p><p>The payload downloaded from <code class="language-plaintext highlighter-rouge">153.75.247[.]94</code> includes <code class="language-plaintext highlighter-rouge">nvcontainer.exe</code>, the next stage implant, as well as supporting libraries and a cacert.pem CA certificate bundle. The following table shows the names of the files in the staging server and the names of the files on the victim’s disk.</p><div class="table-wrapper"><table><thead><tr><th>File on server<th>Saved as<tbody><tr><td>cacert.jpg<td>cacert.pem<tr><td>libcrypto-3-x64.jpg<td>libcrypto-3-x64.dll<tr><td>libssl-3-x64.jpg<td>libssl-3-x64.dll<tr><td>nvcontainer.png<td>nvcontainer.exe<tr><td>ucrtbased.jpg<td>ucrtbased.dll<tr><td>vcruntime140D.jpg<td>vcruntime140D.dll<tr><td>websockets.jpg<td>websockets.dll</table></div><p><a href="/assets/images/websockbdoor/downloadedfiles.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/downloadedfiles.png" alt="file check and download" loading="lazy"></a> <em>Figure 11: Downloaded Files</em></p><p>Finally, <code class="language-plaintext highlighter-rouge">nvcontainer.exe</code> is executed. Before executing it, the downloader attempts to delete the Mark of the Web by calling the <code class="language-plaintext highlighter-rouge">DeleteFileA</code> API to delete the zone identifier from the Alternate Data Stream (<code class="language-plaintext highlighter-rouge">nvcontainer.exe:Zone.Identifier</code>).</p><p><a href="/assets/images/websockbdoor/motwremoval.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/motwremoval.png" alt="zone identifier removal" loading="lazy"></a> <em>Figure 12: Zone Identifier Removal</em></p><p>The execution of <code class="language-plaintext highlighter-rouge">nvcontainer.exe</code> has multiple fallback modes. First, the downloader tries to copy all the downloaded files to <code class="language-plaintext highlighter-rouge">%temp%\cr_nv_run</code> and it attempts to execute <code class="language-plaintext highlighter-rouge">nvcontainer.exe</code> with <code class="language-plaintext highlighter-rouge">CreateProcessA</code>, falling back to the use of the <code class="language-plaintext highlighter-rouge">ShellExecuteA</code> API. If that fails, it attempts to execute the file from the original location using different methods: via the <code class="language-plaintext highlighter-rouge">CreateProcessA</code> API and via the <code class="language-plaintext highlighter-rouge">ShellExecuteA</code> API.</p><h2 id="nvcontainerexe-backdoor"><span class="me-2">Nvcontainer.exe Backdoor</span><a href="#nvcontainerexe-backdoor" class="anchor text-muted"><i class="fas fa-hashtag"></i></a></h2><p><code class="language-plaintext highlighter-rouge">nvcontainer.exe</code> is a backdoor that communicates with its C2 using Websockets. As observed in the downloaded files, the websockets communication relies on <code class="language-plaintext highlighter-rouge">websockets.dll</code>, a <a href="https://libwebsockets.org/">libwebsockets</a> implementation. The backdoor starts by performing a sandbox check and creates mutex <code class="language-plaintext highlighter-rouge">MyUniqueClientAppMutex</code>. The backdoor uses its own implementation of <code class="language-plaintext highlighter-rouge">GetModuleHandle</code> and <code class="language-plaintext highlighter-rouge">GetProcAddress</code>.</p><p><a href="/assets/images/websockbdoor/nvmutex.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/nvmutex.png" alt="nvmutex" loading="lazy"></a> <em>Figure 13: Backdoor Mutex</em></p><p><a href="/assets/images/websockbdoor/gmhimplementation.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/gmhimplementation.png" alt="getmodulehandleimplementation" loading="lazy"></a> <em>Figure 14: GetModuleHandle Implementation</em></p><p><a href="/assets/images/websockbdoor/gpaimplementation.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/gpaimplementation.png" alt="getprocaddressimplementation" loading="lazy"></a> <em>Figure 15: GetProcAddress Implementation</em></p><p>After creating the mutex, the backdoor establishes persistence via the common <code class="language-plaintext highlighter-rouge">HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run</code> run key, using <code class="language-plaintext highlighter-rouge">MyClientApp</code> as the value and the path to <code class="language-plaintext highlighter-rouge">nvcontainer.exe</code> as the value data. The backdoor uses debug messages indicating the success or error of specific actions omitting vowels in a seemingly random manner. For example, the creation of the registry persistence has the following debug messages:</p><ul><li><code class="language-plaintext highlighter-rouge">Staate/openode: %ld\n</code>: Possibly indicating <code class="language-plaintext highlighter-rouge">State/open mode: %ld\n</code><li><code class="language-plaintext highlighter-rouge">Sled Cde: %ld\n</code>: Possibly indicating <code class="language-plaintext highlighter-rouge">SetValue Error Code: %ld\n</code><li><code class="language-plaintext highlighter-rouge">Sup Prucceully: %ls\n</code>: Possibly indicating <code class="language-plaintext highlighter-rouge">Startup Successfully %ls\n</code></ul><p><a href="/assets/images/websockbdoor/persistence.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/persistence.png" alt="persistencecreation" loading="lazy"></a> <em>Figure 16: Persistence Creation via the Registry Run Key</em></p><p>The backdoor checks if it is the first run by checking the <code class="language-plaintext highlighter-rouge">Activated</code> value in the <code class="language-plaintext highlighter-rouge">HKCU\SOFTWARE\Microsoft\MyApp</code> registry key. If the marker does not exist, it displays a fake activation message: <code class="language-plaintext highlighter-rouge">"The program has been activated."</code> and creates the registry key/value.</p><p><a href="/assets/images/websockbdoor/fakeactivation.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/fakeactivation.png" alt="fakeactivation" loading="lazy"></a> <em>Figure 17: Fake Activation Message</em></p><p>The backdoor creates the websockets <a href="https://libwebsockets.org/lws-api-doc-main/html/group__client.html#ga8387abdc3dc5d97beaa71d391f1e74c2">lws_client_connect_info</a> structure to set up the connection to the C2. In that structure, we can see that the C2 address is <code class="language-plaintext highlighter-rouge">www.xionamiconm[.]com:8050/ws/</code>.</p><p><a href="/assets/images/websockbdoor/wsstructure.png" class="popup img-link shimmer"><img src="/assets/images/websockbdoor/wsstructure.png" alt="wsstructure" loading="lazy"></a> <em>Figure 18: Websockets Structure</em></p><p>The protocol handler (callback function) registered under the protocol name <code class="language-plaintext highlighter-rouge">ws-protocol</code> reveals the backdoor’s capabilities.</p><p>The following commands are supported by the backdoor:</p><div class="table-wrapper"><table><thead><tr><th>Command<th>Capability<tbody><tr><td>[HB_OK]<td>Updates pong timestamp<tr><td>[PING]<td>Client sends [PONG] response<tr><td>[CAL]<td>Cancels upload<tr><td>[DIS]<td>Disconnects<tr><td>[CONFIRMED] and [CON]<td>C2 confirms a file has been uploaded. Deletes the staged file + .vortexstamp file<tr><td>[RESUME_OFFSET] + offset<td>Resumes a file upload to the C2 from a specific offset<tr><td>PPPP + path<td>Prepare file for exfiltration<tr><td>DDDD + url + destination<td>Downloads a file via <code class="language-plaintext highlighter-rouge">URLDownloadToFileW</code><tr><td>1<td>List logical drives<tr><td>2<td>Detailed drive enumeration<tr><td>cd + path<td>Directory listing</table></div><p>The capabilities of the backdoor focus primarily on drive reconnaissance and data exfiltration, suggesting that the primary purpose is likely espionage. For instance, when an operator runs command <code class="language-plaintext highlighter-rouge">2</code>, the backdoor responds with the following detailed drive information:</p><p>========== DRIVE LIST WITH DETAILED TYPE DETECTION ==========</p><ul><li>Enumerates drives with the <code class="language-plaintext highlighter-rouge">GetLogicalDriveStringsW</code> API. For each drive:<li>It uses the <code class="language-plaintext highlighter-rouge">GetDriveTypeW</code> API (to determine if it’s removable, fixed, network, CD ROM, or RAM).<li>Uses the <code class="language-plaintext highlighter-rouge">GetVolumeInformationW</code> API:<ul><li>Then it checks keywords in volume name such as “USB”, “Flash”, and “SD”.<ul><li>Checks for words such as “SSD”, “SOLID”.<li>A FAT/exFAT drive with an unusual name (blank space) is assessed as a possibly encrypted volume.</ul></ul></ul><p>The <code class="language-plaintext highlighter-rouge">PPPP + path</code> command prepares a file for exfiltration. Files that are greater than or equal to 64 MB are streamed directly to the C2 server. Smaller files are compressed into ZIP archives before exfiltration. Directories can also be compressed and exfiltrated.<br /> The developer implemented a caching mechanism to avoid re-compressing files that have not changed since they were last archived. Upon completion of the compression process, a <code class="language-plaintext highlighter-rouge">.vortexstamp</code> file is created for each ZIP archive, containing a fingerprint of the source file, including its hash, size, and timestamps. When PPPP receives a request for the same path, the implant reads the corresponding .vortexstamp file and compares the recorded metadata against the current source file. If the source file remains unchanged, the existing ZIP archive is reused.
