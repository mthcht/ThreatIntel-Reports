</svg></div><p>Back to blog</p></a></div><div class="margin-bottom margin-mid-medium"><div class="max-width-medium"><h1 class="heading-style-h2">Fantastic payloads and where we find them</h1></div></div><div class="margin-bottom margin-medium"><p>March 30, 2020</p></div><div class="author-holder"><div class="author-image-wrapper"><img src="https://cdn.prod.website-files.com/6a1dde3fab071067432aca09/6a207970f658ff95148a4182_Placeholder%20Image%20-%20Landscape.svg" loading="lazy" alt="" class="author-image w-dyn-bind-empty"/></div><div class="text-side-space"><p class="text-size-medium text-weight-medium author font-display">Written by</p><p class="text-size-medium text-weight-medium author font-display">Michael Kajiloti</p></div></div></div><div id="w-node-_2ce6fd2a-3472-60ab-7050-6d1fd451f9a5-224f9669" class="mainblogheader-image-wrapper image-on-top"><img src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a6c48f11a41d684c34f192b_6a2cf888b79970e94d33f805_shutterstock_1098524594-1.jpeg" loading="lazy" alt="" class="mainblogbody_-image"/></div></div></div></div></div></div></div><div class="section_mainbodyblog"><div class="padding-global sectiontop"><div class="container-large"><div class="padding-section-large padding-bottom"><div class="mainbodyblogheader_component"><div class="mainblogbody"><div class="mainbodyblog-left"><style>.text-rich-text figure img { width: 100%; height: auto; } .text-rich-text figure { width: 100%; max-width: 100%; } .text-rich-text pre { overflow-x: auto; max-width: 100%; } .text-rich-text table { display: block; overflow-x: auto; max-width: 100%; } .mainbodyblog-left { min-width: 0; }</style><div fs-toc-offsettop="7.5rem" fs-toc-element="contents" class="text-rich-text helper w-richtext"><p>Attackers have long used evasion features in their malware to avoid detection by security products and analysis systems. One of the most common anti-analysis tricks we have seen in today’s Windows malware is the use of <strong>packers</strong>. Packers often complicate the analysis and detection of binary files by hiding the malware’s real code and data; often referred to as the <strong>payload</strong>.</p><p>The most common solution to overcome packing is the use of <strong>dynamic analysis</strong> (sandboxes) and emulation systems. However, as these solutions have become more mainstream, packers have started to incorporate new <strong>anti-analysis</strong> methods to both detect and evade these systems.</p><p>One such anti-analysis method which is becoming increasingly popular is the malformation or complete removal of the Windows PE header from unpacked malicious payloads. This can make both finding the malware payload and properly analyzing its code more challenging.</p><p>While removal of Windows PE headers from malicious payloads is not an entirely new method, we are seeing some of the most popular and sophisticated crimeware families fully incorporate this approach into their packers. Below we will present some examples that demonstrate this trend through our Genetic Malware Analysis platform, Intezer Analyze.</p><p><strong>On packers and payloads</strong><br/>When we investigate a packed malware file, the malware (payload) itself is encrypted or encoded and therefore we can’t access its real code and data. Typically, in order to analyze the malware’s code, we must execute the file in a sandboxed environment, let it unpack itself, and then grab the payload from memory.</p><p>While various malware and packers operate in different ways, an abstraction of a typical unpacking flow looks like this:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12718f3aa6f7b1a31286_6a2cf8105182a5b586aa4e66_intezer-1024x377.png"/></div></figure><p>In this flow we can see that the packer will decode and execute a shellcode component that will in turn decode and execute the real payload. This is just a common scenario; some packers will not use a shellcode loader and instead they will unpack the payload directly. It’s worth noting that unlike the packer’s code, which is designed to be obfuscated and appear random, we have observed that these shellcode components are often reused. This means that these components generally have more value than the packer itself when investigating them with code reuse analysis. Therefore, detecting and analyzing this component’s code can be worthwhile for us.</p><p>With that said, finding and analyzing the malware module itself is by far the most effective way to properly detect and classify packed malware. The most common way to identify malware payloads in memory is to search for PE header artifacts. Knowing this, many attackers try to stay undetected by removing these artifacts from the PE Header of the payload, or by using no PE header at all, as we’ll see soon in the examples presented in this article.</p><p><strong>The many faces of Emotet<br/></strong><a href="https://intezer.com/blog/emotet-evolves-but-code-remains-mostly-the-same/">Emotet is one of the most widespread malware</a> in the crimeware ecosystem which has undergone a number of updates since its inception. In particular, we have noticed that this malware is constantly evolving and adapting, both in the malware code itself, and in the packers it uses. While switching the packer is relatively inexpensive for the attacker and happens frequently, modifying the malware’s code is much more costly and happens rarely.</p><p>An interesting example of this can be seen when we compare the following Emotet samples:</p><ul><li>Emotet sample from June 2019: <a href="https://analyze.intezer.com/#/analyses/f5619f98-3552-440e-b7f9-fdf0a5bc0111" target="_blank">8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb</a></li><li>Emotet sample from December 2019: <a href="https://analyze.intezer.com/#/analyses/5edfe909-6c21-4d7a-badc-c6d95756cfe3" target="_blank">3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef</a></li></ul><p>When looking at the code of the packed files themselves, we can see just how different these samples are, showing no apparent connections to one another:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a3128d_6a2cf811810063a433606087_intezer1-1024x200.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/f5619f98-3552-440e-b7f9-fdf0a5bc0111" target="_blank">Packer (June 2019) - 8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb</a></p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="intezer platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a312af_6a2cf8123f9feeabc2cbee2f_intezer2-1024x479.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/5edfe909-6c21-4d7a-badc-c6d95756cfe3" target="_blank">Packer (December 2019) - 3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef</a></p><p>But if we look at the unpacked memory module payloads after undergoing dynamic analysis, we can see that they are nearly identical from a binary code perspective:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="intezer platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a312a9_6a2cf8135377018dfdf388f4_intezer3-1024x368.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/f5619f98-3552-440e-b7f9-fdf0a5bc0111/sub/7804422f-75c6-4904-b69d-25b6a2b38acb" target="_blank">Payload (June 2019) - 8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb</a></p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a31296_6a2cf879172fd222e5ed5671_intezer4-1024x373.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/5edfe909-6c21-4d7a-badc-c6d95756cfe3/sub/e4019d81-86b9-4b45-8e1e-a85645f0dd8b" target="_blank">Payload (December 2019) - 3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef</a></p><p>There is one notable exception: in the December 2019 sample, the payload memory module has a <strong>“malformed header”</strong> tag. In this case, this indicates that the packer loaded the module with a PE Header that’s missing certain PE artifacts, such as the “MZ” magic or other PE Header constants. This is usually done in an attempt to make it more difficult to find these modules in memory, since the most common method of finding PE memory modules is by scanning for these artifacts.</p><p>It is worth mentioning that in Intezer Analyze we repair the malformed header as part of our analysis process. Downloading and examining the memory module will reveal that it has a full PE header.</p><p>It is also important to note that even in the instance of a constantly evolving threat such as Emotet, when the attacker modifies the code of the malware itself, there are still parts that remain unchanged. Therefore, when Intezer Analyze executes the malware, finds its payload, and then analyzes its code, we can still detect those traces to Emotet’s code that have not been modified.</p><p>This can be observed when we investigate a recent sample of Emotet from March 2020. Looking at the packer’s code, we can see that it is different yet again, and has no relations to any code we have seen previously:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a3129c_6a2cf87b3f9feeabc2cbfb94_intezer5-1024x237.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/48b36b5c-4cea-40bf-b3b5-a0d2dfec4cda" target="_blank">Packer (March 2020) - C6684aa4af41685ffc584c1b1bb78855c894b3dae7f6fae4fb572bc02525102f</a></p><p>However, when we look at the memory module payload itself, we can see that some of the code is new and has been modified from previous versions. Most importantly, a substantial part of the code has been reused from previous Emotet variants that we have seen before:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a31290_6a2cf87cb835d8b66945a4e4_intezer6-1024x301.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/48b36b5c-4cea-40bf-b3b5-a0d2dfec4cda/sub/0d3943b2-eae2-496c-acce-20381f23b17b" target="_blank">Payload (March 2020) - C6684aa4af41685ffc584c1b1bb78855c894b3dae7f6fae4fb572bc02525102f</a></p><p><strong>When less is more</strong><br/>While using a malformed PE Header is a relatively simple trick, using no PE header at all is a more sophisticated and complicated affair. It takes more than just removing a few unused magic constants from the header in order to conceal it. This method requires loading and executing the payload just like shellcode.</p><p>When malware authors write and compile the malware payload itself, it is usually compiled and built into the form of standard PE files, not position independent shellcode. Directly converting a sophisticated malware’s codebase such as Dridex or TrickBot to run like shellcode can be complicated.</p><p>Most malware authors choose a simpler option, using a packer that unpacks and loads the payload module without using its PE Header at load time. These packers typically store the relevant information from the PE header, such as API import and relocations data, in a custom structure during packing time. The packer then uses that structure during the unpacking process in order to properly load the malware code.</p><p><strong>Same Dridex, new tricks</strong><br/>An example of a popular malware that has recently adopted such a packer is the Dridex banking trojan. Let's compare two recent Dridex samples from February 2020:</p><ul><li><a href="https://analyze.intezer.com/#/analyses/9fdbb152-275f-4cb3-beaa-4acc33a28a52" target="_blank">9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a</a></li><li><a href="https://analyze.intezer.com/#/analyses/66328685-405d-4445-9437-2942e125aed4" target="_blank">45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb</a></li></ul><p>Similar to Emotet, these packed files are very different from one another at the code level, showing no resemblance:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a31293_6a2cf87d1ad72d3a0d011e40_intezer7-1024x277.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/9fdbb152-275f-4cb3-beaa-4acc33a28a52" target="_blank">Packer - 9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a</a></p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a31299_6a2cf87f2243172b566592bf_intezer8-1024x226.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/66328685-405d-4445-9437-2942e125aed4" target="_blank">Packer - 45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb</a></p><p>However, when we look at the payloads themselves, we can see again that they are actually very similar:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12708f3aa6f7b1a31277_6a2cf880a77c1ee08c5156c7_intezer9-1024x489.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/9fdbb152-275f-4cb3-beaa-4acc33a28a52/sub/d47a060e-c241-42c5-8f20-ea00a849a042" target="_blank">Payload - 9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a</a></p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12718f3aa6f7b1a31283_6a2cf8814b1c2550e5e802f3_intezer10-1024x440.png"/></div></figure><p><a href="https://analyze.intezer.com/#/analyses/66328685-405d-4445-9437-2942e125aed4/sub/cd707392-6139-4d9a-bded-253719d943da" target="_blank">Payload - 45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb</a></p><p>There is one notable exception here as well, but in this case it is much more substantial. In the second payload we can see the <strong>“fileless_code” </strong>tag, which indicates this module has no PE header. Downloading and examining this module will make it known that it is indeed a binary file with no structure.</p><p>Intezer Analyze detects these modules during dynamic analysis and analyzes their code even though no PE Header is present. It will also detect any other shellcode pieces that are used by the malware.</p><p><strong>Look ma! No heads!<br/></strong>To demonstrate how prevalent this trend is, let’s look at the analyses of recent samples of the <a href="https://analyze.intezer.com/#/analyses/b166869f-beda-4010-bf28-d50717750df9" target="_blank">Ursnif</a> and <a href="https://analyze.intezer.com/#/files/26d61225f07e39d9e35880631c5043626eb8e3846a526a44015d3a5d03642d55" target="_blank">TrickBot</a> malware. When looking at the dynamic analysis modules, we see several different malicious modules that are detected and analyzed:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a312b4_6a2cf8833f65f5442c14c471_Intezer11.png"/></div></figure><p>If we review them more closely, we will see that all of them — minus copies of the original packer file — have the <strong>“fileless_code” </strong>tag, indicating that they are all shellcode-style modules with no PE header:</p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a3129f_6a2cf8847b5b078875109a9b_intezer12-1024x209.png"/></div></figure><p><a href="https://analyze.intezer.com/#/files/26d61225f07e39d9e35880631c5043626eb8e3846a526a44015d3a5d03642d55/sub/3d431957-aae3-42b6-8582-0b214f0f824d" target="_blank">TrickBot - 26d61225f07e39d9e35880631c5043626eb8e3846a526a44015d3a5d03642d55</a></p><figure class="w-richtext-figure-type-image" data-rt-align="" data-rt-type="image"><div><img alt="Intezer Platform" loading="lazy" src="https://cdn.prod.website-files.com/6a246004d4c8e03752caba5a/6a2d12728f3aa6f7b1a312ac_6a2cf8857d66a66d9a73962d_intezer13-1024x368.png"/></div></figure><p><strong>Conclusion</strong><br/>The use of pure shellcode and shellcode-style components in modern malware seems to be a growing trend, one that is being adopted by some of the most successful malware developers. At the same time, when we identify and analyze these components using code reuse analysis, we can see that they are mostly just a different version of the same thing.
