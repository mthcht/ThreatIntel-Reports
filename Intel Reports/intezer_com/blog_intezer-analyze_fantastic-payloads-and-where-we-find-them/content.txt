by security products and analysis systems. One of the most common anti-analysis
tricks we have seen in today’s Windows malware is the use of packers. Packers
often complicate the analysis and detection of binary files by hiding the
malware’s real code and data; often referred to as the payload.</p><p>The most common solution to overcome packing is the use of <strong>dynamic analysis</strong>
(sandboxes) and emulation systems. However, as these solutions have become more
mainstream, packers have started to incorporate new <strong>anti-analysis</strong> methods
to both detect and evade these systems.</p><p>One such anti-analysis method which is becoming increasingly popular is the
malformation or complete removal of the Windows PE header from unpacked
malicious payloads. This can make both finding the malware payload and properly
analyzing its code more challenging.</p><p>While removal of Windows PE headers from malicious payloads is not an entirely
new method, we are seeing some of the most popular and sophisticated crimeware
families fully incorporate this approach into their packers. Below we will
present some examples that demonstrate this trend through our Genetic Malware
Analysis platform, Intezer Analyze.</p><h2>On packers and payloads<span class="hx:absolute hx:-mt-20" id=on-packers-and-payloads></span>
<a href=#on-packers-and-payloads class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>When we investigate a packed malware file, the malware (payload) itself is
encrypted or encoded and therefore we can’t access its real code and data.
Typically, in order to analyze the malware’s code, we must execute the file in
a sandboxed environment, let it unpack itself, and then grab the payload from
memory.</p><p>While various malware and packers operate in different ways, an abstraction of
a typical unpacking flow looks like this:</p><p><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig1.png alt loading=lazy></p><p>In this flow we can see that the packer will decode and execute a shellcode
component that will in turn decode and execute the real payload. This is just a
common scenario; some packers will not use a shellcode loader and instead they
will unpack the payload directly. It’s worth noting that unlike the packer’s
code, which is designed to be obfuscated and appear random, we have observed
that these shellcode components are often reused. This means that these
components generally have more value than the packer itself when investigating
them with code reuse analysis. Therefore, detecting and analyzing this
component’s code can be worthwhile for us.</p><p>With that said, finding and analyzing the malware module itself is by far the
most effective way to properly detect and classify packed malware. The most
common way to identify malware payloads in memory is to search for PE header
artifacts. Knowing this, many attackers try to stay undetected by removing
these artifacts from the PE Header of the payload, or by using no PE header at
all, as we’ll see soon in the examples presented in this article.</p><h2>The many faces of Emotet<span class="hx:absolute hx:-mt-20" id=the-many-faces-of-emotet></span>
<a href=#the-many-faces-of-emotet class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>Emotet is one of the most widespread malware in the crimeware ecosystem which
has undergone a number of updates since its inception. In particular, we have
noticed that this malware is constantly evolving and adapting, both in the
malware code itself, and in the packers it uses. While switching the packer is
relatively inexpensive for the attacker and happens frequently, modifying the
malware’s code is much more costly and happens rarely.</p><p>An interesting example of this can be seen when we compare the following Emotet
samples:</p><ul><li>Emotet sample from June 2019:
<code>8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb</code></li><li>Emotet sample from December 2019:
<code>3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef</code></li></ul><p>When looking at the code of the packed files themselves, we can see just how
different these samples are, showing no apparent connections to one another:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig2.png title="Packer (June 2019) – 8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb" alt loading=lazy><figcaption>Packer (June 2019) – 8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb</figcaption></figure></p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig3.png title="Packer (December 2019) – 3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef" alt loading=lazy><figcaption>Packer (December 2019) – 3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef</figcaption></figure></p><p>But if we look at the unpacked memory module payloads after undergoing dynamic
analysis, we can see that they are nearly identical from a binary code
perspective:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig4.png title="Payload (June 2019) – 8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb" alt loading=lazy><figcaption>Payload (June 2019) – 8e5089260064a955819a92ebccc43d05520e32d234dd3c176bed5f6d0665ebdb</figcaption></figure></p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig5.png title="Payload (December 2019) – 3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef" alt loading=lazy><figcaption>Payload (December 2019) – 3e8a273f80575ab6079d6512008bb6355b59de978fabc2a9a66c0ed148b94fef</figcaption></figure></p><p>There is one notable exception: in the December 2019 sample, the payload memory
module has a &ldquo;<strong>malformed header</strong>&rdquo; tag. In this case, this indicates that the
packer loaded the module with a PE Header that’s missing certain PE artifacts,
such as the &ldquo;MZ&rdquo; magic or other PE Header constants. This is usually done in an
attempt to make it more difficult to find these modules in memory, since the
most common method of finding PE memory modules is by scanning for these
artifacts.</p><p>It is worth mentioning that in Intezer Analyze we repair the malformed header
as part of our analysis process. Downloading and examining the memory module
will reveal that it has a full PE header.</p><p>It is also important to note that even in the instance of a constantly evolving
threat such as Emotet, when the attacker modifies the code of the malware
itself, there are still parts that remain unchanged. Therefore, when Intezer
Analyze executes the malware, finds its payload, and then analyzes its code, we
can still detect those traces to Emotet’s code that have not been modified.</p><p>This can be observed when we investigate a recent sample of Emotet from March
2020. Looking at the packer’s code, we can see that it is different yet again,
and has no relations to any code we have seen previously:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig6.png title="Packer (March 2020) – C6684aa4af41685ffc584c1b1bb78855c894b3dae7f6fae4fb572bc02525102f" alt loading=lazy><figcaption>Packer (March 2020) – C6684aa4af41685ffc584c1b1bb78855c894b3dae7f6fae4fb572bc02525102f</figcaption></figure></p><p>However, when we look at the memory module payload itself, we can see that some
of the code is new and has been modified from previous versions. Most
importantly, a substantial part of the code has been reused from previous
Emotet variants that we have seen before:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig7.png title="Payload (March 2020) – C6684aa4af41685ffc584c1b1bb78855c894b3dae7f6fae4fb572bc02525102f" alt loading=lazy><figcaption>Payload (March 2020) – C6684aa4af41685ffc584c1b1bb78855c894b3dae7f6fae4fb572bc02525102f</figcaption></figure></p><h2>When less is more<span class="hx:absolute hx:-mt-20" id=when-less-is-more></span>
<a href=#when-less-is-more class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>While using a malformed PE Header is a relatively simple trick, using no PE
header at all is a more sophisticated and complicated affair. It takes more
than just removing a few unused magic constants from the header in order to
conceal it. This method requires loading and executing the payload just like
shellcode.</p><p>When malware authors write and compile the malware payload itself, it is
usually compiled and built into the form of standard PE files, not position
independent shellcode. Directly converting a sophisticated malware’s codebase
such as Dridex or TrickBot to run like shellcode can be complicated.</p><p>Most malware authors choose a simpler option, using a packer that unpacks and
loads the payload module without using its PE Header at load time. These
packers typically store the relevant information from the PE header, such as
API import and relocations data, in a custom structure during packing time. The
packer then uses that structure during the unpacking process in order to
properly load the malware code.</p><h2>Same Dridex, new tricks<span class="hx:absolute hx:-mt-20" id=same-dridex-new-tricks></span>
<a href=#same-dridex-new-tricks class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>An example of a popular malware that has recently adopted such a packer is the
Dridex banking trojan. Let’s compare two recent Dridex samples from February
2020:</p><ul><li><code>9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a</code></li><li><code>45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb</code></li></ul><p>Similar to Emotet, these packed files are very different from one another at
the code level, showing no resemblance:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig8.png title="Packer – 9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a" alt loading=lazy><figcaption>Packer – 9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a</figcaption></figure></p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig9.png title="Packer – 45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb" alt loading=lazy><figcaption>Packer – 45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb</figcaption></figure></p><p>However, when we look at the payloads themselves, we can see again that they
are actually very similar:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig10.png title="Payload – 9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a" alt loading=lazy><figcaption>Payload – 9b6ffb05ec826b3fbff7db04ebd187e2f956a5730af1d36e10a9f56ee1bb767a</figcaption></figure></p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig11.png title="Payload – 45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb" alt loading=lazy><figcaption>Payload – 45e0408d3ae2647cb9be835a5277eb7de41c83d8e473d22d5b3772c2f65305fb</figcaption></figure></p><p>There is one notable exception here as well, but in this case it is much more
substantial. In the second payload we can see the &ldquo;<strong>fileless_code</strong>&rdquo; tag,
which indicates this module has no PE header. Downloading and examining this
module will make it known that it is indeed a binary file with no structure.</p><p>Intezer Analyze detects these modules during dynamic analysis and analyzes
their code even though no PE Header is present. It will also detect any other
shellcode pieces that are used by the malware.</p><h2>Look ma! No heads!<span class="hx:absolute hx:-mt-20" id=look-ma-no-heads></span>
<a href=#look-ma-no-heads class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>To demonstrate how prevalent this trend is, let’s look at the analyses of
recent samples of the Ursnif and TrickBot malware. When looking at the dynamic
analysis modules, we see several different malicious modules that are detected
and analyzed:</p><p><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig12.png alt loading=lazy></p><p>If we review them more closely, we will see that all of them — minus copies of
the original packer file — have the &ldquo;fileless_code&rdquo; tag, indicating that they
are all shellcode-style modules with no PE header:</p><p><figure><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig13.png title="TrickBot – 26d61225f07e39d9e35880631c5043626eb8e3846a526a44015d3a5d03642d55" alt loading=lazy><figcaption>TrickBot – 26d61225f07e39d9e35880631c5043626eb8e3846a526a44015d3a5d03642d55</figcaption></figure></p><p><img src=/blog/2020/03/fantastic-payloads-and-where-we-find-them/images/fig14.png alt loading=lazy></p><h2>Conclusion<span class="hx:absolute hx:-mt-20" id=conclusion></span>
<a href=#conclusion class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>The use of pure shellcode and shellcode-style components in modern malware
seems to be a growing trend, one that is being adopted by some of the most
successful malware developers. At the same time, when we identify and analyze
these components using code reuse analysis, we can see that they are mostly
just a different version of the same thing.</p></div><div class=hx:mt-16></div><div class="hx:mb-8 hx:flex hx:items-center hx:border-t hx:pt-8 hx:border-gray-200 hx:dark:border-neutral-800
