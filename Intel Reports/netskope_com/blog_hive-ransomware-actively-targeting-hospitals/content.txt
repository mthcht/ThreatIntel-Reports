  (function () {
    let pagefind;
    let debounceTimer;

    async function loadPagefind() {
      if (pagefind) return pagefind;
      try {
        pagefind = await import('/pagefind/pagefind.js');
        await pagefind.init();
      } catch {
        pagefind = null;
      }
      return pagefind;
    }

    function initSearch() {
      const overlay = document.getElementById('search-overlay');
      const openBtn = document.getElementById('search-open');
      const closeBtn = document.getElementById('search-close');
      const input = document.getElementById('search-input');
      const results = document.getElementById('search-results');

      function openModal() {
        overlay?.classList.remove('hidden');
        overlay?.classList.add('flex');
        input?.focus();
        loadPagefind();
      }

      function closeModal() {
        overlay?.classList.add('hidden');
        overlay?.classList.remove('flex');
        if (input) input.value = '';
        if (results) results.innerHTML = '';
      }

      openBtn?.addEventListener('click', openModal);
      closeBtn?.addEventListener('click', closeModal);
      overlay?.addEventListener('click', (e) => {
        if (e.target === overlay) closeModal();
      });
      document.addEventListener('keydown', (e) => {
        if (e.key === 'Escape') closeModal();
        if ((e.metaKey || e.ctrlKey) && e.key === 'k') {
          e.preventDefault();
          openModal();
        }
      });

      input?.addEventListener('input', () => {
        clearTimeout(debounceTimer);
        debounceTimer = setTimeout(runSearch, 200);
      });

      async function runSearch() {
        const query = input?.value.trim() ?? '';
        if (!results) return;
        if (!query) {
          results.innerHTML = '';
          return;
        }

        const pf = await loadPagefind();
        if (!pf) {
          results.innerHTML = `<p class="p-4 text-sm text-(--text-secondary)">Search is unavailable in development. It runs against the built site.</p>`;
          return;
        }

        const search = await pf.search(query);
        if (search.results.length === 0) {
          results.innerHTML = `<p class="p-4 text-sm text-(--text-secondary)">No results for "${query}".</p>`;
          return;
        }

        const items = await Promise.all(search.results.slice(0, 8).map((r) => r.data()));
        results.innerHTML = items
          .map(
            (item) => `
            <a href="${item.url}" class="block px-4 py-3 border-b border-(--border-subtle) last:border-0 hover:bg-(--bg-tertiary) transition-colors">
              <p class="font-medium text-(--text-primary) text-sm mb-1">${item.meta?.title ?? item.url}</p>
              <p class="text-xs text-(--text-secondary) line-clamp-2">${item.excerpt}</p>
            </a>
          `,
          )
          .join('');
      }
    }

    // Initialize on page load and after Astro view transitions
    document.addEventListener('astro:page-load', initSearch);
  })();

bg-(--bg-primary)"><div class="prose max-w-none"><h2 id="summary">Summary</h2>
<p>Most ransomware groups operating in the RaaS (Ransomware-as-a-Service) model have an internal code of ethics that includes avoiding breaching some specific sectors, such as hospitals or critical infrastructure, thus avoiding great harm to society and consequently drawing less attention from law enforcement. For example, the <a href="/blog/2021/08/netskope-threat-coverage-blackmatter">BlackMatter</a> ransomware states they are not willing to attack hospitals, critical infrastructure, defense industry, non-profit companies, and oil and gas industry targets, having learned from the mistakes of other groups, such as <a href="/blog/2021/05/netskope-threat-coverage-darkside">DarkSide</a>, who shut down its operations after the Colonial Pipeline attack.</p>
<p>However, this code of ethics is not always adopted by attackers, as is the case with <a href="/library/malware/hive" class="threat-link">Hive</a>, a new family of ransomware discovered in <a href="https://twitter.com/fbgwls245/status/1408632067181604865">June 2021</a>. On August 15, 2021, Hive ransomware was responsible for an <a href="https://www.bleepingcomputer.com/news/security/hive-ransomware-attacks-memorial-health-system-steals-patient-data/">attack against the Memorial Health System</a>, a non-profit integrated health system with three hospitals in Ohio and West Virginia (Marietta Memorial Hospital, Selby General Hospital, and Sistersville General Hospital), causing <a href="https://mhsystem.org/cyberattack">radiology exams and surgical cases to be canceled</a>. According to the <a href="https://www.ic3.gov/Media/News/2021/210825.pdf">FBI</a>, the group uses phishing emails with malicious attachments to gain access into networks, allowing the attackers to move laterally over the network to steal data and infect more machines.</p>
<h2 id="hiveleaks">HiveLeaks</h2>
<p>In addition to encrypting files, Hive also steals sensitive data from networks, threatening to publish everything in their HiveLeak website, hosted on the deep web, which is a common practice among ransomware working in this double extortion scheme.</p>
<p>There are two websites maintained by the group, the first one is protected by username and password, accessible only by the victims who obtain the credentials in the ransom note.</p>
<p><img src="/_astro/hive-1.BVHnPO7y_Z2ohU0b.webp" alt loading="lazy" decoding="async" width="612" height="512"></p>
<p>Figure 01. Hive ransomware private website</p>
<p>Once authenticated, the victim can see:</p>
<ol>
<li>The name of the infected organization;</li>
<li>A live chat, where the victim can interact with the attackers;</li>
<li>A file upload system, where the victim can send files to the attackers;</li>
<li>A link to <a href="/library/malware/hive" class="threat-link">Hive</a>’s decryption software, if the ransom is paid by the victims.</li>
</ol>
<p><img src="/_astro/hive-2-updated-1024x672.C8J-OynI_ZkIIPJ.webp" alt loading="lazy" decoding="async" width="1024" height="672"></p>
<p>Figure 02. Victim’s private website by Hive ransomware</p>
<p>The second website, “HiveLeaks,” is where the attackers publish data about their targets and is publicly accessible.</p>
<p><img src="/_astro/hive-3.ChqRgsDT_10fTJn.webp" alt loading="lazy" decoding="async" width="264" height="198"></p>
<p>Figure 03. “HiveLeaks” logo.</p>
<p>For each target, you can see the name, a small description, the website, the revenue, and the number of employees at the company. Also, you can see two dates, when the files were encrypted and when the attack was made public. Curiously enough, there are also two social media buttons where you can share this information.</p>
<p><img src="/_astro/hive-4-1024x354.CFORfwYg_ZltsFS.webp" alt loading="lazy" decoding="async" width="1024" height="354"></p>
<p>Figure 04. Information about the infected company on the “HiveLeaks” website.</p>
<p>If any data is published by the attackers, you will also find a link where the files can be downloaded. Hive uses common file-sharing services for this purpose, such as PrivatLab, AnonFiles, MEGA, UFile, SendSpace, and Exploit.in, as shown in Figure 05.</p>

<h2 id="memorial-health-system-attack">Memorial Health System Attack</h2>
<p>The Hive ransomware infected the <a href="https://www.mhs.net/">Memorial Health System (MHS)</a> on August 15, 2021. The attackers claim to have stolen patient data including names, social security numbers, dates of birth, addresses and phone numbers, and medical histories for 200,000 patients, and an additional 1.2 TB of other data.</p>
<p>MHS tried to appeal to the attackers to provide the decrypter for free but ultimately ended up paying 1.8M, divided equally into two Bitcoin wallets. The attackers moved the Bitcoins to another wallet just a few minutes after the transaction was made by MHS.</p>
<p>Aside from the decryptor, the attackers also promise a security report, a file tree describing all stolen data, and the logs proving that they had erased everything from their servers.</p>
<h2 id="analysis">Analysis</h2>
<p>The ransomware was written in Go, an open-source programming language that allows cross-compilation, meaning that the same source code can be compiled to different OS, such as Linux, Windows, and macOS.</p>
<p>Although we have only seen Windows versions in the wild at this point, we have strong indications that the group is able to infect other systems such as Linux, as well as the Hypervisor ESXi, as we will demonstrate later in the analysis.</p>
<p>We have analyzed two different samples, being 32 and 64-bit Windows versions of the malware. Both of them are packed with <a href="https://upx.github.io/">UPX</a>, which is an open-source executable packer.</p>
<p><img src="/_astro/hive-6.DLXctCB7_Z1WaKsc.webp" alt loading="lazy" decoding="async" width="630" height="311"></p>
<p>Figure 06. Main Hive ransomware payload, packed with UPX.</p>
<p>The first thing we noticed is that both samples we analyzed had a command line interface (CLI), accepting parameters and also showing log messages throughout the malware execution.</p>
<p>The <strong>64-bit</strong> sample accepts two parameters:</p>
<ul>
<li><strong>kill:</strong> Kill processes specified as value (case insensitive regex)</li>
<li><strong>stop:</strong> Stop services specified as value (case insensitive regex)</li>
</ul>
<p><img src="/_astro/hive-7.Dw7iYdDW_ZaQ9mx.webp" alt loading="lazy" decoding="async" width="775" height="230"></p>
<p>Figure 07. Parameters accepted by the 64-bit sample of Hive.</p>
<p>On the other hand, the <strong>32-bit</strong> sample offers three more options:</p>
<ul>
<li><strong>kill:</strong> Kill processes specified as value (case insensitive regex)</li>
<li><strong>no-clean:</strong> Do not clean disk space (described later in this analysis)</li>
<li><strong>skip:</strong> Files that the attacker doesn’t want to encrypt (case insensitive regex)</li>
<li><strong>skip-before:</strong> Skips files created before the specified date.</li>
</ul>
<p><strong>stop:</strong> Stop services specified as value (case insensitive regex)</p>
<p><img src="/_astro/hive-8.CKTWiB_P_ZxkRDi.webp" alt loading="lazy" decoding="async" width="964" height="272"></p>
<p>Figure 08. Parameters accepted by the 32-bit sample of Hive.</p>
<p>Aside from the parameters above, the attacker can also specify the path containing the files that need to be encrypted. If this path isn’t specified, the ransomware will list all the files in the machine, skipping the ones specified in the <strong>“-skip”</strong> and <strong>“-skip-before”</strong> parameters.</p>
<p>For analysis purposes, we have created a folder named <strong>“C:\to_encrypt”</strong>, containing three different pictures. Once executed, the ransomware starts printing out log messages throughout the whole encryption process.</p>
<p><img src="/_astro/hive-9.xrTjzeiO_ZLzC04.webp" alt loading="lazy" decoding="async" width="553" height="307"></p>
<p>Figure 09. 32-bit Hive ransomware execution.</p>
<p>The log messages show pretty much everything the malware is doing, however, let’s take a look at each one of the aspects being printed out.</p>
<p>Analyzing this 32-bit sample closely, we can see some of the function names parsed by the disassembler, from a package the attackers named as “google.com”, perhaps as an attempt to deceive the analyst.</p>
<p><img src="/_astro/hive-10.bed1se8g_1Q1VSH.webp" alt loading="lazy" decoding="async" width="356" height="500"></p>
<p>Figure 10. 32-bit Hive function names.</p>
<p>First, the malware calls a function <strong>encryptor</strong>.<strong>NewApp().</strong></p>
<p><img src="/_astro/hive-11.DC4g3tBX_2rNu9E.webp" alt loading="lazy" decoding="async" width="335" height="118"></p>
<p>Figure 11. “NewApp” Hive function.</p>
<p>Simply put, this function initializes some important data used by the ransomware, such as the primary key.</p>
<p><img src="/_astro/hive-12.DOyV_6g__Zeo7TS.webp" alt loading="lazy" decoding="async" width="734" height="390"></p>
<p>Figure 12. “NewApp” function flow.</p>
<p>The function <strong>keys.NewPrimaryKey()</strong> generates a 10 MB random key used in the encryption process.</p>
<p><img src="/_astro/hive-13.cnnVGS5N_Z28lNxx.webp" alt loading="lazy" decoding="async" width="283" height="159"></p>
<p>Figure 13. 10 MB key generated by Hive.</p>
<p>Once the key is generated, the ransom note and a batch script are loaded into memory, which will be eventually saved to the disk during the process.</p>
<p>After this setup is completed, the ransomware calls a function named <strong>App.Run()</strong>, which starts the flow we saw in the log messages.</p>
<p><img src="/_astro/hive-14.BnNzp26q_ZT63Bp.webp" alt loading="lazy" decoding="async" width="406" height="228"></p>
<p>Figure 14. Hive “Run” function.</p>
<p>The first function called inside <strong>App.Run()</strong> is <strong>App.ExportKey()</strong>.</p>
<p><img src="/_astro/hive-15.BUdgppb1_19iIi5.webp" alt loading="lazy" decoding="async" width="458" height="209"></p>
<p>Figure 15. “ExportKey” function.</p>
<p>This function is responsible for encrypting the 10 MB key generated by <strong>keys.NewPrimaryKey().</strong></p>
<p><img src="/_astro/hive-16.BRk5b19f_Z1Wr0ro.webp" alt loading="lazy" decoding="async" width="606" height="363"></p>
<p>Figure 16. Main flow of “ExportKey” function.</p>
<p>Hive contains 100 public RSA keys embedded in the binary, which are used to encrypt the key generated previously. They are all parsed through the function <strong>ParsePKCS1PublicKey</strong> from the <a href="https://golang.org/src/crypto/x509/pkcs1.go">pkcs1.go</a> library.</p>
<p><img src="/_astro/hive-17.GRBTj_SH_2sxryn.webp" alt loading="lazy" decoding="async" width="391" height="65"></p>
<p>Figure 17. Hive ransomware loading public RSA keys.</p>
<p>The malware then encrypts the data using the <strong>EncryptOAEP</strong> function from the <a href="https://golang.org/src/crypto/rsa/rsa.go">rsa.go</a> library.</p>
<p><img src="/_astro/hive-18.DAJq3n9q_Zo3pNj.webp" alt loading="lazy" decoding="async" width="285" height="58"></p>
<p>Figure 18. Hive encrypting the key using RSA.</p>
<p>The encrypted key is then saved into a file that ends with “.key.hive” extension (or “key.&lt;random&gt;” for the 64-bit version). This is the file that is eventually loaded by the decryptor to retrieve the encryption key used in the process.</p>
<p><img src="/_astro/hive-19.COejqD0-_Z2s09a4.webp" alt loading="lazy" decoding="async" width="221" height="28"></p>
<p>Figure 19. Key file saved by Hive during the process.</p>
<p>After creating the encrypted key, the malware calls two functions named <strong>App.KillProcesses()</strong> and <strong>App.StopServices()</strong>.</p>
<p><img src="/_astro/hive-20.B0bO8nzL_Z1aNOqX.webp" alt loading="lazy" decoding="async" width="504" height="116"></p>
<p>Figure 20. Hive functions to kill processes and stop services.</p>
<p>The name of these functions are self-explanatory, and the full list of default values for stopped processes and services can be found in our <a href="https://github.com/netskopeoss/NetskopeThreatLabsIOCs/tree/main/Hive/IOCs">GitHub repository</a>.</p>
<p>Next, Hive executes the functions <strong>App.RemoveItself()</strong> and <strong>App.RemoveShadowCopies()</strong>.</p>
<p><img src="/_astro/hive-21.DcGx3Sqi_wBuPl.webp" alt loading="lazy" decoding="async" width="536" height="114"></p>
<p>Figure 21. Next two functions executed by the “Run”.</p>
<p>The first one is responsible for creating a batch script that was loaded into memory by the function <strong>encryptor</strong>.<strong>NewApp().</strong> The purpose of this script is to delete the ransomware payload once this process is done.</p>
<p><img src="/_astro/hive-22.CWZwBLvl_Z2de7hs.webp" alt="Figure 27. Batch script created by Hive to delete the payload from disk" loading="lazy" decoding="async" width="358" height="112"></p>
<p>Figure 22. Batch script created by Hive to delete the payload from disk</p>
<p>The second function creates another batch script in disk that is responsible for deleting Windows Shadow Copies, to prevent any file restoration.</p>
<p><img src="/_astro/hive-23.C-Ui743u_1AOb9z.webp" alt loading="lazy" decoding="async" width="367" height="76"></p>
<p>Figure 23. “shadow.bat” script created by the 32-bit Hive.</p>
<p>Here, we have a big difference between the two samples we have analyzed. Instead of creating a batch script, the 64-bit version we found uses several commands to delete not only the Windows Shadow Copies, but also to stop services, including Windows Defender.</p>
<p><img src="/_astro/hive-24.DJkWI7Uh_Z1deoIt.webp" alt loading="lazy" decoding="async" width="964" height="111"></p>
<p>Figure 24. Commands executed by the 64-bit Hive sample we analyzed.</p>
<p>The full list of commands executed by the 64-bit version can be found in our <a href="https://github.com/netskopeoss/NetskopeThreatLabsIOCs/tree/main/Hive/IOCs">GitHub repository</a>.</p>
<p>Next in the flow, we have two important functions:</p>
<p><img src="/_astro/hive-25.BmLiyJzI_Z2fYx4f.webp" alt loading="lazy" decoding="async" width="504" height="100"></p>
<p>Figure 30. “ScanFiles” and “EncryptFiles” functions of Hive.</p>
<p><strong>App.ScanFiles()</strong> is responsible for fetching all the files that will be encrypted by the ransomware. Also, this function creates the ransom note in disk, which was already loaded in memory previously.</p>
<p><strong>App.EncryptFiles()</strong> does exactly what the name describes. Within that function, the code is calling another two, respectively <strong>encryptFilesGroup()</strong> and <strong>EncryptFile()</strong>, loading the contents of the targeted file in memory, encrypting the data with what seems to be a custom algorithm created by Hive developers. Then, the encrypted file is written into disk, using the extension “.hive”.</p>
<p><img src="/_astro/hive-26.DXkVrGZ3_ZCee4B.webp" alt loading="lazy" decoding="async" width="693" height="164"></p>
<p>Figure 26. Files encrypted by Hive ransomware.</p>
<p>Following the file encryption, we have another two functions executed by <strong>App.Run()</strong>.</p>
<p><img src="/_astro/hive-27.HuHF55K6_Z4XQMK.webp" alt loading="lazy" decoding="async" width="504" height="100"></p>
<p>Figure 27. “EraseKey” and “Notify” functions.</p>
<p>The function <strong>App.EraseKey()</strong> accesses the memory location where the 10 MB primary key was stored by Hive and replaces all its bytes with random data.</p>
<p><img src="/_astro/hive-28.CwWOyXkM_ZpX5nv.webp" alt loading="lazy" decoding="async" width="965" height="288"></p>
<p>Figure 28. Before and after the “EraseKey” function</p>
<p><strong>App.Notify()</strong> creates the ransom note in disk, which is redundant since this file is also created by the function <strong>App.ScanFiles()</strong>.</p>
<p>Last but not least, we have a curious function executed by the ransomware if the flag <strong>“-no-clean”</strong> wasn’t specified, named <strong>App.CleanSpace()</strong>.</p>
<p><img src="/_astro/hive-29.48Jrz8Vr_25mLvg.webp" alt loading="lazy" decoding="async" width="463" height="129"></p>
<p>Figure 29. “CleanSpace” function.</p>
<p>Simply put, if executed, this code creates several files with 1GB+ each until the disk is full. Then, these newly created files are deleted.</p>
<p><img src="/_astro/hive-30.4PixeS-t_Z1GM60o.webp" alt loading="lazy" decoding="async" width="461" height="192"></p>
<p>Figure 30. Files created by the “CleanSpace” function.</p>
<p>Since Hive deletes files that have been encrypted, this process is likely performed to overwrite any bytes on disk that could potentially be restored to their original state, creating new files to replace deleted ones.</p>
<p><img src="/_astro/hive-31.MlN-sMmq_Z2r0jSM.webp" alt loading="lazy" decoding="async" width="681" height="243"></p>
<p>Figure 31. Disk space while the “CleanSpace” function is being executed.</p>
<p>Different from other ransomware families, Hive doesn’t change the user background, the only message available to the victim is the ransom note.</p>
<p><img src="/_astro/hive-32.DAtyve6F_Zl1y4g.webp" alt loading="lazy" decoding="async" width="782" height="651"></p>
<p>Figure 32. Hive ransom note.</p>
<p>According to the note, if the user deletes the file that has the “.key” extension, the data will be undecryptable, which leads us to the next part of this blog.</p>
<h2 id="decryptor"><a href="/library/malware/decryptor" class="threat-link">Decryptor</a></h2>
<p>Hive provides decryptors for ESXi, Linux, and Windows (32 / 64-bit).</p>
<p><img src="/_astro/hive-33.CqeO4vLk_1mHLzz.webp" alt loading="lazy" decoding="async" width="446" height="174"></p>
<p>Figure 33. Hive ransomware decryptors for MHS.</p>
<p>Although we only found Windows versions of Hive in the wild, this is a strong indication that they have payloads for other systems, aligning with the fact that the whole code was built in Go language, which is multi-platform.</p>
<p>When it comes to the decryption process, the file first loads the encrypted key from disk, which is why the ransom note states that you can’t delete this file.</p>
<p><img src="/_astro/hive-34.DipNxr0u_Z17VTlC.webp" alt loading="lazy" decoding="async" width="832" height="224"></p>
<p>Figure 34. Hive decryption process</p>
<p>Once the key is loaded and decrypted, Hive scans all directories searching for encrypted files, and then proceeds with the decryption process.</p>
<h2 id="conclusion">Conclusion</h2>
<p>Hive is yet another ransomware group that is likely operating in the RaaS model. However, the process used to encrypt the files is quite unusual.</p>
<p>Usually, the encryption process implemented by ransomware in the wild is to generate a unique symmetric key for each file, that is eventually encrypted and stored along with the encrypted data, so it can be recovered later. Instead, Hive creates a unique key that is eventually encrypted and written into disk, making the decryption process irreversible if this file is deleted by accident. Furthermore, this ransomware contains functionalities that make the execution slow, such as “wiping” the disk until it’s full to avoid file restoration.</p>
<p>Regardless of these points, we consider Hive a dangerous threat, as it’s already causing damage to people and organizations, combined with the fact that the threat is multi-platform.</p>
