<h2 class="wp-block-heading">Key Points</h2>



<ul class="wp-block-list">
<li><strong>A Chinese-speaking actor is now targeting Brazil.</strong>&nbsp;Check Point Research has uncovered a sustained campaign against Brazilian organizations, primarily government and educational institutions since mid-2025. We dubbed this group Gambling Goblin: a Chinese-speaking cybercrime cluster connected to a previously documented group, Earth Berberoka, that targeted gambling sites across Asia. It marks a shift from Brazil’s usual home-grown banking-trojan threats to a foreign operator moving in</li>



<li><strong>Compromised web servers turned into stealthy proxies.</strong>&nbsp;The attackers compile and install malicious Apache modules on victim servers that silently reverse-proxy visitors to attacker-controlled phishing pages, while the traffic still appears to originate from the legitimate domain, with the site’s own security headers stripped so injected content runs freely.</li>



<li><strong>Large-scale SEO manipulation.</strong>&nbsp;The phishing pages pose as trusted app stores such as Google Play, Microsoft Store, and Amazon. Behind that facade, they push online gambling and sports betting, and they chain together compromised high-reputation domains, many of them Brazilian government sites, to inflate search rankings and hijack traffic at scale.</li>



<li><strong>A broad, heavily obfuscated Linux toolkit.</strong>&nbsp;Once inside a host, the group deploys custom tools &#8211; downloader (<strong>DownPro</strong>), multiple backdoors including the modular&nbsp;<strong>AlphaAgent</strong>&nbsp;and the&nbsp;<strong>oRAT</strong>&nbsp;RAT, a 3snake-based credential stealer, an SSH brute-forcer, and a plugin-driven reconnaissance agent. Most of them are wrapped in packing and virtualization layers to slow analysis and evade detection.</li>



<li><strong>The operation reaches well beyond Brazil.</strong>&nbsp;We identified parallel phishing networks localized in Vietnamese, Spanish, and English, alongside infrastructure that generates fresh domains daily &#8211; evidence the model is built to scale and be exported to new regions.</li>



<li><strong>One step from direct malware delivery.</strong>&nbsp;Because the pages already mimic app-download destinations, the same infrastructure sits a single configuration change away from pushing malware straight to victims, a latent escalation risk beyond the current search-fraud scheme.</li>
</ul>



<h2 class="wp-block-heading">Introduction</h2>



<p class="wp-block-paragraph">Since mid-2025, Check Point Research has tracked a sustained campaign against Brazilian organizations. The tradecraft points to a Chinese-speaking cybercrime group connected to Earth Berberoka, an actor first&nbsp;<a href="https://www.trendmicro.com/en_us/research/22/d/new-apt-group-earth-berberoka-targets-gambling-websites-with-old.html">documented</a>&nbsp;targeting gambling sites across Asia.</p>



<p class="wp-block-paragraph">Once inside a victim, the group deploys a broad Linux toolkit: a custom downloader, several backdoors, and familiar offensive utilities. Most of it arrives heavily obfuscated &#8211; wrapped in layered virtualization and packing to slow analysis and evade detection.</p>



<p class="wp-block-paragraph">The purpose becomes clear at the network layer. The attackers install custom Apache modules that quietly proxy visitors to a sprawling set of phishing pages. Many of those pages sit on Brazilian government domains that appear to have been compromised and repurposed without their owners’ knowledge.</p>



<p class="wp-block-paragraph">The reach extends beyond Brazil. We uncovered a second phishing network run by the same actor; this one is built for Vietnamese victims.</p>



<p class="wp-block-paragraph">The likely goal is SEO manipulation at scale. By hijacking trusted, high-reputation domains, many of them Brazilian government sites, the operators borrow that reputation to push their own content up the search rankings and hijack the traffic that follows. But the same infrastructure could serve a more dangerous end: the phishing pages impersonate app-download destinations such as Google Play, the Microsoft Store, and Amazon, which leaves the operators one step from pushing malware straight to victims.</p>

<h2 class="wp-block-heading">Initial Access</h2>



<p class="wp-block-paragraph">We have not directly observed this group’s initial access, but a revealing artifact surfaced on one of their servers: an exposed open directory hosting an ELF binary written in Go that bundles numerous reconnaissance and scanning plugins. The toolset reads like a complete attack-surface-mapping pipeline for internet-facing targets.</p>



<p class="wp-block-paragraph">The group refers to this agent as “<code>cluster-asset-mapping</code>”, or “<code>cam-agent</code>” for short. It runs with a handful of flags:</p>



<ul class="wp-block-list">
<li><strong>default</strong>&nbsp;&#8211; long-lived worker session for orchestrated task dispatch</li>



<li><strong>f</strong>&nbsp;&#8211; foreground mode without logging</li>



<li><strong>flog</strong>&nbsp;&#8211; enable logging (use with&nbsp;<code>f</code>)</li>



<li><strong>h</strong>&nbsp;&#8211; show help</li>



<li><strong>v</strong>&nbsp;&#8211; show version</li>
</ul>


<div class="wp-block-image">
<figure class="aligncenter size-large"><img decoding="async" width="1024" height="430" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image16-1024x430.png" alt="" class="wp-image-33530" srcset="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image16-1024x430.png 1024w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image16-300x126.png 300w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image16-768x323.png 768w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image16.png 1309w" sizes="(max-width: 1024px) 100vw, 1024px" /><figcaption class="wp-element-caption">Figure 2 &#8211; Cam-agent help message</figcaption></figure>
</div>


<p class="wp-block-paragraph">The agent carries a configuration that includes:</p>



<ul class="wp-block-list">
<li>worker_endpoint</li>



<li>server_id</li>



<li>project</li>



<li>agent_token</li>



<li>embedded PEM certificates and keys for the server and agent</li>



<li>a plugin list</li>



<li>report policies</li>
</ul>



<p class="wp-block-paragraph">It logs to&nbsp;<code>payload-run.log</code>&nbsp;under the default directory of&nbsp;<code>/tmp/asset-scan</code>. The agent reads the JSON report policies to decide how to run its scan. The policies are driven by the following fields:</p>



<ul class="wp-block-list">
<li>common web ports</li>



<li>batch_size</li>



<li>retry_count</li>



<li>retry_backoff_seconds</li>



<li>level</li>
</ul>


<div class="wp-block-image">

<p class="wp-block-paragraph">The agent communicates with its server over gRPC, authenticating with the certificates and keys from its own configuration. It uses many known open-source pentesting tools as modules:</p>



<ul class="wp-block-list">
<li><strong>dirprobe</strong>&nbsp;&#8211; takes URLs and a directory list or profile, sends HTTP requests, and records the status code, response length, and title for each probed path.</li>



<li><strong>httpx</strong>&nbsp;&#8211; takes URLs, ports, and HTTP options, then collects the status code, response length, title, protocol, TLS details, and banners from each target.</li>

<li><strong>subfinder</strong>&nbsp;&#8211; takes root domains, resolvers, and a depth, then enumerates subdomains via DNS brute force, certificate transparency, and passive sources, returning the discovered subdomains.</li>



<li><strong>whatweb</strong>&nbsp;&#8211; a Wappalyzer-style fingerprinter that issues HTTP requests to each target and applies rules to identify web servers, frameworks, CMS platforms, JavaScript libraries, and more.</li>
</ul>



<h2 class="wp-block-heading">Stealth phishing structure</h2>



<h3 class="wp-block-heading">Apache Modules</h3>



<p class="wp-block-paragraph">The group automates deployment of its malicious Apache module through a Bash installer. The script first confirms it is running as root, then fingerprints the host as either Debian/Ubuntu or CentOS/RedHat and pulls in the matching Apache development packages so the module can be compiled on the victim itself. It downloads the module’s C source,&nbsp;<code>opsproxy.c</code>, from a hardcoded staging server and, notably, patches the source on the fly to insert a missing macro definition so the code compiles cleanly. This is a small touch that shows the operators built the module to run across a range of victim configurations.</p>



<p class="wp-block-paragraph">Compilation and installation are handled in a single step via Apache’s own&nbsp;<code>apxs</code>&nbsp;tooling, which also wires the module into the server’s configuration. What follows is a deliberate effort to hide the intrusion: the script deletes the source and all build artifacts, then timestomps the resulting&nbsp;<code>.so</code>&nbsp;and its load-configuration files to match legitimate, pre-existing Apache modules such as&nbsp;<code>mod_ssl</code>&nbsp;or&nbsp;<code>mod_suexec</code>, so the malicious files blend in during a casual review. It then enables the stock proxy, headers, and rewrite modules the malicious module depends on, tests the configuration, and restarts Apache to bring everything live.</p>



<p class="wp-block-paragraph">Throughout, the script’s status messages are written in Chinese and decorated with emoji, a style that may point to AI-assisted development.</p>


<div class="wp-block-image">
<figure class="aligncenter size-full"><img loading="lazy" decoding="async" width="795" height="738" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image17.png" alt="" class="wp-image-33535" srcset="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image17.png 795w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image17-300x278.png 300w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image17-768x713.png 768w" sizes="auto, (max-width: 795px) 100vw, 795px" /><figcaption class="wp-element-caption">Figure 4 &#8211; Checking the URL by the Apache module</figcaption></figure>
</div>


<p class="wp-block-paragraph">The source file,&nbsp;<code>opsproxy.c</code>, reveals a purpose-built reverse proxy that quietly grafts attacker-controlled content onto a compromised web server. The module registers itself at Apache’s name-translation stage and inspects every incoming request for one of a small set of hardcoded URL prefixes which in our samples,&nbsp;<code>/wps</code>,&nbsp;<code>/bmw</code>, and&nbsp;<code>/card</code>. When a request matches, the module rewrites it into a reverse-proxy request to a corresponding upstream server hardcoded into the source, silently relaying the visitor to attacker infrastructure while the request still appears, to the outside world, to come from the legitimate compromised domain.</p>



<p class="wp-block-paragraph">To make that relayed content render without interference, the module strips the upstream site’s Content-Security-Policy headers. It replaces them with a deliberately permissive policy that allows inline and dynamically evaluated scripts, third-party assets, and&nbsp;<code>data:</code>&nbsp;and&nbsp;<code>blob:</code>&nbsp;sources. This removes the restrictions a browser’s CSP normally enforces, allowing injected or externally hosted scripts to execute freely.</p>


<div class="wp-block-image">
<figure class="aligncenter size-large"><img loading="lazy" decoding="async" width="1024" height="522" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image18-1024x522.png" alt="" class="wp-image-33538" srcset="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image18-1024x522.png 1024w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image18-300x153.png 300w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image18-768x392.png 768w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image18-1536x783.png 1536w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image18-2048x1044.png 2048w" sizes="auto, (max-width: 1024px) 100vw, 1024px" /><figcaption class="wp-element-caption">Figure 5 &#8211; CSP stripping so injected scripts can run</figcaption></figure>
</div>


<p class="wp-block-paragraph">The module also forwards the original&nbsp;<code>Host</code>&nbsp;header and adds standard proxy headers so the upstream sees a convincing request. The effect is a compromised, reputable server acting as a stealthy front door: certain paths transparently serve attacker content, and the browser protections that would ordinarily block foreign scripts are switched off for exactly those paths.</p>


<div class="wp-block-image">
<figure class="aligncenter size-large"><img loading="lazy" decoding="async" width="1024" height="354" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image19-1024x354.png" alt="" class="wp-image-33539" srcset="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image19-1024x354.png 1024w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image19-300x104.png 300w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image19-768x265.png 768w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image19-1536x531.png 1536w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image19-2048x707.png 2048w" sizes="auto, (max-width: 1024px) 100vw, 1024px" /><figcaption class="wp-element-caption">Figure 6 &#8211; How the compromised .gov site relays attacker content to visitors</figcaption></figure>

<p class="wp-block-paragraph">A second ELF Apache module used by the group disguises itself as a basic filter module while registering request and response hooks that examine visitor headers, URI paths, referrers, and client IPs. It carries a static configuration, decrypts it with RC4, and parses it into two rule types:</p>



<ol class="wp-block-list">
<li><strong>rule1</strong>&nbsp;&#8211; an array of matching rules (path, referrer, or User-Agent, paired with a proxy URL)</li>



<li><strong>rule3</strong>&nbsp;&#8211; an optional response-filtering or injection configuration</li>
</ol>


<div class="wp-block-image">
<figure class="aligncenter"><img decoding="async" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image5.png" alt="Figure 7 - JSON struct example"/><figcaption class="wp-element-caption">Figure 7 &#8211; JSON struct example</figcaption></figure>

<p class="wp-block-paragraph">Using a compiled-in regex for&nbsp;<code>&lt;body.*?&gt;</code>&nbsp;to locate its injection point, the module expands placeholders such as&nbsp;<code>{host}</code>,&nbsp;<code>{hip}</code>,&nbsp;<code>{url}</code>, and&nbsp;<code>{name}</code>, fetches remote content with libcurl, and writes that content into Apache responses via&nbsp;<code>ap_rwrite</code>&nbsp;and bucket manipulation. This gives a remote service control over what selected visitors and crawlers see on the compromised server. This is a behavior consistent with SEO cloaking and content-injection malware.</p>

<h2 class="wp-block-heading">The Attacker’s Arsenal</h2>



<p class="wp-block-paragraph">Across these intrusions, the group draws on two kinds of tooling: well-known offensive utilities that any attacker might reach for, such as&nbsp;<code>netcat</code>,&nbsp;<code>fscan</code>, and&nbsp;<code>pwnkit</code>, and a broad set of custom tools written by the operators themselves: a downloader, several backdoors, a credential stealer, and purpose-built reconnaissance scripts. The sections below focus on that custom toolkit, which is where the group’s tradecraft shows.</p>



<h3 class="wp-block-heading">DownPro</h3>



<p class="wp-block-paragraph">A downloader written in Go, referred to internally as&nbsp;<strong>DownPro</strong>. Its job is to pull the rest of the toolkit onto a freshly compromised host and launch it.</p>



<p class="wp-block-paragraph">The binary is driven by a handful of flags, and a telling detail stands out immediately: their help strings are written in both English and Chinese. The flags are:</p>



<ul class="wp-block-list">
<li><code>u</code>&nbsp;&#8211; URL of the main backdoor to download</li>



<li><code>id</code>&nbsp;&#8211; URL of the ChUser payload</li>



<li><code>up</code>&nbsp;&#8211; URL of the&nbsp;<code>unix_updates</code>&nbsp;payload (the PasswordHarvester)</li>



<li><code>j</code>&nbsp;&#8211; offline URL encryptor mode: it takes a plaintext URL via&nbsp;<code>u</code>&nbsp;and outputs the ciphertext to use as the flag value in real runs</li>



<li><code>logs</code>&nbsp;&#8211; where to write logs</li>
</ul>



<p class="wp-block-paragraph">The values passed to these flags are AES-GCM encrypted with a hardcoded key and Base64-encoded, so the operator supplies pre-encrypted URLs at runtime rather than leaving them in the clear.</p>



<p class="wp-block-paragraph"><strong>DownPro</strong>&nbsp;then decides where to drop its payload based on its effective UID, preparing two sets of candidate destination paths: one for root, one for non-root. Running as root, it selects one of:</p>



<ul class="wp-block-list">
<li><code>/usr/local/bin/systemd-udevd</code></li>



<li><code>/usr/local/bin/rsync-tsl</code></li>



<li><code>/usr/local/bin/tcp-tsl</code></li>



<li><code>/usr/local/bin/snapd-ext</code></li>



<li><code>/usr/local/bin/fsck-disk</code></li>



<li><code>/usr/local/bin/nftables-init</code></li>
</ul>



<p class="wp-block-paragraph">These names are chosen to blend into a Linux server environment, either mimicking legitimate system components or looking like ordinary utility and network helpers. Running without root, it instead generates one of two temp-style names designed to pass as routine disk clutter:</p>



<ul class="wp-block-list">
<li><code>/tmp/php_sess_&lt;32_hex_chars&gt;</code>&nbsp;&#8211; mimicking a PHP session file</li>



<li><code>/tmp/private-tmp-&lt;5_alnum_chars&gt;</code>&nbsp;&#8211; looking like an ephemeral temp artifact</li>
</ul>



<p class="wp-block-paragraph">With the destination chosen, it downloads the file from the&nbsp;<code>-u</code>&nbsp;URL and executes it with the argument&nbsp;<code>-si</code>.</p>


<div class="wp-block-image">
<figure class="aligncenter size-large"><img loading="lazy" decoding="async" width="1024" height="519" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image20-1024x519.png" alt="" class="wp-image-33559" srcset="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image20-1024x519.png 1024w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image20-300x152.png 300w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image20-768x390.png 768w, https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image20.png 1102w" sizes="auto, (max-width: 1024px) 100vw, 1024px" /><figcaption class="wp-element-caption">Figure 13 &#8211; DownPro main logic</figcaption></figure>
</div>


<p class="wp-block-paragraph">The two optional payloads are handled separately. When the&nbsp;<code>-id</code>&nbsp;flag is set,&nbsp;<strong>DownPro</strong>&nbsp;downloads a file to&nbsp;<code>/usr/bin/chuser</code>, sets its permissions to&nbsp;<code>0755</code>, changes its owner to root, and timestomps it to match&nbsp;<code>/bin/ls</code>&nbsp;and turning it into a setuid helper that serves as a persistent local privilege-escalation backdoor. When the&nbsp;<code>-up</code>&nbsp;flag is set, it downloads a file to&nbsp;<code>/usr/sbin/unix_updates</code>&nbsp;and runs it with&nbsp;<code>-v FuckMe#988</code>, then strips the setuid bit from&nbsp;<code>/usr/bin/pkexec</code>.</p>



<h3 class="wp-block-heading">ChUser</h3>



<p class="wp-block-paragraph">A simple backdoor that masquerades as a&nbsp;<code>chuser</code>&nbsp;utility. It executes commands passed through the&nbsp;<code>-c</code>&nbsp;flag, but only after passing one of two activation checks:</p>



<ol class="wp-block-list">
<li><strong>Remote HTTP activation</strong>&nbsp;&#8211; the backdoor builds a&nbsp;<code>curl</code>&nbsp;command using the&nbsp;<code>-x &lt;version&gt;</code>&nbsp;flag and runs it. Activation succeeds only if the command’s output matches the expected value,&nbsp;<code>chuser no version</code>.</li>



<li><strong>Local MD5-based activation</strong>&nbsp;&#8211; the backdoor concatenates a user-supplied secret (from the&nbsp;<code>-s &lt;secret&gt;</code>&nbsp;flag) with a hardcoded salt,&nbsp;<code>FuCkMe#</code>, computes the MD5 of&nbsp;<code>secret + salt</code>, and compares it against a hardcoded target hash. Activation succeeds only on a match.</li>
</ol>



<h3 class="wp-block-heading">PasswordHarvester</h3>



<p class="wp-block-paragraph">A credential stealer based on&nbsp;<a href="https://github.com/blendin/3snake">3snake</a>&nbsp;that monitors newly executed authentication programs, including&nbsp;<code>sshd</code>,&nbsp;<code>sudo</code>,&nbsp;<code>su</code>,&nbsp;<code>doas</code>,&nbsp;<code>ssh</code>,&nbsp;<code>ssh-add</code>,&nbsp;<code>passwd</code>,&nbsp;<code>kinit</code>, and&nbsp;<code>login</code>.</p>



<p class="wp-block-paragraph">On startup, it sets a clean&nbsp;<code>PATH</code>&nbsp;environment variable and installs signal handlers so the daemon can log and exit cleanly. It runs only as root, exiting otherwise, and gates execution behind a covert activation switch: the CRC32 of the&nbsp;<code>-v</code>&nbsp;argument must match a hardcoded value.</p>


<div class="wp-block-image">
<figure class="aligncenter"><img decoding="async" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image14.png" alt="Figure 14: CRC32 gate"/><figcaption class="wp-element-caption">Figure 14: CRC32 gate</figcaption></figure>
</div>


<p class="wp-block-paragraph">Once the CRC gate passes, the stealer resolves the host’s name and IPv4 addresses, then daemonizes by forking, calling&nbsp;<code>umask(0)</code>&nbsp;so it can freely control file permissions, changing its working directory to&nbsp;<code>/tmp</code>, and redirecting stdout and stderr to a file.</p>



<p class="wp-block-paragraph">To hide itself, it picks at random from roughly 29 fake process names, such as:</p>



<ul class="wp-block-list">
<li><code>[kworker/1:2]</code></li>



<li><code>[ksoftirqd/0]</code></li>



<li><code>[watchdog/0]</code></li>



<li><code>[systemd]</code></li>



<li><code>[dbus-daemon]</code></li>



<li><code>[journald]</code></li>



<li><code>[migration/0]</code></li>



<li><code>[ksmd]</code></li>
</ul>



<p class="wp-block-paragraph">It overwrites the original&nbsp;<code>argv</code>&nbsp;with the chosen name and calls&nbsp;<code>prctl</code>&nbsp;to change the kernel-visible task name to match.</p>



<p class="wp-block-paragraph">The core logic then opens a netlink socket and subscribes to process events (<code>PROC_CN_MCAST_LISTEN</code>). On every process execution or UID change event, it checks whether the process name or command line matches one of the target programs listed above. When a match falls outside the expected path prefixes, it enters the interceptor flow: it attaches to the target with&nbsp;<code>ptrace</code>, reads the credential buffers, and exfiltrates them to its C2, RC4-encrypted and Base64-encoded.</p>



<h3 class="wp-block-heading">AlphaAgent</h3>



<p class="wp-block-paragraph">A modular backdoor written in Go, built to land quietly, blend into a busy host, take orders over an encrypted channel, and hand its operator everything they need to work through a network.</p>



<p class="wp-block-paragraph">On launch, AlphaAgent first checks whether it was invoked to finish an upgrade, so an in-progress self-update can complete cleanly. It then parses its command-line flags, validates its configured role and transport, and generates a Device ID from either the victim’s MAC address or the username combined with a hardcoded salt (<code>e*f#1%0d$6&amp;5=6</code>). After checking its debug flags (<code>DEBUG</code>,&nbsp;<code>VERBOSE</code>, or neither), it decrypts its configuration strings using AES-GCM with a hardcoded key.</p>



<p class="wp-block-paragraph">[Figure 19 &#8211; Device ID generation](Gaming the system how a Chinese-speaking actor tur/image_(4)</p>



<p class="wp-block-paragraph">The configuration holds the region blocklist, the transport role and mode, the C2 domain, the TLS SNI camouflage value used for the certificates, and the directory, filename, and loader names for the rootkit.</p>



<p class="wp-block-paragraph">With its configuration in hand, the agent goes to ground. It renames its own process to pass as a kernel thread or a system daemon, choosing the disguise from its configuration profile and applying it by rewriting&nbsp;<code>argv[0]</code>&nbsp;or calling&nbsp;<code>prctl</code>. The profiles are:</p>



<ul class="wp-block-list">
<li><strong>aws</strong>&nbsp;→&nbsp;<code>/usr/sbin/amazon-master</code>&nbsp;or&nbsp;<code>/usr/local/sbin/amazon-proxy</code></li>



<li><strong>google</strong>&nbsp;→&nbsp;<code>/usr/bin/google_user_agent</code>&nbsp;or&nbsp;<code>/usr/bin/google_proxy_agent</code></li>



<li><strong>aliyun</strong>&nbsp;→&nbsp;<code>rsyslogd</code></li>



<li><strong>general</strong>&nbsp;→ one of a set of kernel-thread-style names:</li>
</ul>



<pre class="EnlighterJSRAW" data-enlighter-language="generic" data-enlighter-theme="" data-enlighter-highlight="" data-enlighter-linenumbers="" data-enlighter-lineoffset="" data-enlighter-title="" data-enlighter-group="">"dbus-daemon -n%d"
"scsi_eh_%d"
"[migration/%d]"
"[cpuhp/%d]"
"[kworker/u%d:1]"
"[watchdog/%d]"
"[kswapd%d]"</pre>



<ul class="wp-block-list">
<li>When not running as root, it falls back to&nbsp;<code>php-fpm: pool www</code>&nbsp;or&nbsp;<code>nginx: worker process</code>.</li>
</ul>



<p class="wp-block-paragraph">AlphaAgent then detaches into the background and writes a PID lock file under an innocuous path so that only one copy runs. It sleeps for a randomized interval which is long enough to outlast a quick sandbox detonation, and checks where it is running: if the host’s country matches the operators’ blocklist (China, in the samples we analyzed), the agent simply exits. Only after clearing that geofence does it enter its connect-and-retry loop and reach out to the server.</p>



<p class="wp-block-paragraph">Finally, if the&nbsp;<code>-r</code>&nbsp;flag is set at execution, AlphaAgent checks whether the rootkit’s kernel module is already loaded. If it is not, the agent installs it; the rootkit ships embedded inside the binary via Go’s&nbsp;<code>embed.FS</code>&nbsp;API. In all the samples we analyzed, we haven’t found any rootkits, only placeholders.</p>



<p class="wp-block-paragraph">Once connected, the agent enrolls, starts a heartbeat, and subscribes for jobs. How it talks to its server is a build-time choice, and each option is designed to look like something benign.</p>



<p class="wp-block-paragraph">The primary channel is&nbsp;<strong>gRPC over HTTPS</strong>. The agent’s gRPC transport is built as a publish/subscribe service. The agent subscribes to receive jobs and publishes results back, and on top of that base, it opens dedicated streams for each interactive function rather than multiplexing everything through one pipe. There are separate streams for the web terminal, for uploads, for downloads, and for keepalive pings, and each exists in two directions an operator-facing set and an agent-facing set. That separation keeps a live terminal session responsive while a large file transfer runs in parallel.</p>



<p class="wp-block-paragraph">Three design choices make this channel hard to spot on the wire:</p>



<ul class="wp-block-list">
<li><strong>uTLS fingerprint mimicry.</strong>&nbsp;The agent uses a library that forges the TLS handshake of a real browser, so fingerprint-based detection (JA3/JA4-style) sees a normal Chrome-like client, not a Go program.</li>



<li><strong>Google and Cloudflare camouflage.</strong>&nbsp;It presents&nbsp;<code>api.google.com</code>&nbsp;as its server name, serves a&nbsp;<code>.google.com</code>&nbsp;certificate, and dresses its HTTPS heartbeats as Google traffic with decoy cookies (<code>NID</code>,&nbsp;<code>SID</code>, and similar) plus a custom proof scheme carried in Cloudflare-style parameters (<code>_cf_auth_ts</code>,&nbsp;<code>_cf_auth_nonce</code>,&nbsp;<code>_cf_auth_method</code>). The heartbeat side exposes handler paths like&nbsp;<code>/agent/heartbeat</code>&nbsp;and&nbsp;<code>/notifications/v1/push</code>&nbsp;to complete the illusion of a Google notification service.</li>



<li><strong>Encryption beneath the encryption.</strong>&nbsp;Job and result messages are themselves AES-GCM encrypted before they travel inside the TLS session. Even an analyst who terminates the TLS still faces an encrypted payload.</li>
</ul>

Here the same commands travel inside DNS queries: each job is encrypted, Base32-encoded, and split across DNS labels, then exchanged as TXT-style traffic on port 53. Many environments scrutinize outbound web sessions but wave DNS through<strong>,</strong>&nbsp;which is exactly the point. A separate variant of the toolkit keeps things simpler still, tunneling its protocol over a plain HTTP connection with certificate checks disabled.</p>

<p class="wp-block-paragraph">Whichever channel it uses, the agent bootstraps through public DoH and GeoIP providers such as Cloudflare, Google, ipinfo, and others, both to resolve its server and to run the geofence check described above.</p>



<p class="wp-block-paragraph">At the center of the agent is a single job dispatcher. The server sends a numbered command; the dispatcher routes it to the matching handler. That design keeps the protocol compact and makes the feature set easy to summarize. The sections below cover the ones that matter most.</p>



<ul class="wp-block-list">
<li><strong>Remote shell and interactive terminal</strong>&nbsp;&#8211; The workhorse is remote command execution. A shell job is joined into a single string and run through&nbsp;<code>/bin/sh -c</code>, and the combined output is captured and returned to the operator. The agent takes care to keep this quiet. It sets&nbsp;<code>HISTFILE=/dev/null</code>&nbsp;so commands leave no shell history behind. For interactive work, the agent goes beyond one-shot commands. It can allocate a real pseudo-terminal, launch a shell inside it, and stream that terminal to the operator as a browser-based “webtty” session. This gives an attacker a live, interactive shell with full terminal behavior, not just fire-and-forget commands, which is what you want for hands-on-keyboard operations.</li>



<li><strong>File Operations</strong>&nbsp;&#8211; File handling is complete in both directions. The agent can download files to the host and upload files from it, with both direct and streamed transfer paths for larger data transfers. Alongside transfer, a file browser lets the operator list directories and walk the filesystem interactively before deciding what to take. Together, these turn the backdoor into a remote file manager for the compromised host.</li>



<li><strong>Tunneling and pivoting &#8211;</strong>&nbsp;This is where the agent shows its intent to move laterally. It bundles a SOCKS5 proxy, a yamux-based multiplexer, and a Ligolo-style relay, turning the compromised host into a pivot point for the operators’ traffic. A dedicated relay mode lets the agent listen for inbound connections and forward them, so one foothold can open a path into the rest of an internal network. In the tunneling paths, certificate verification is deliberately turned off to keep the relay flexible.</li>



<li><strong>Relay Tunneling</strong>&nbsp;&#8211; AlphaAgent can also be deployed not as an implant but as a&nbsp;<strong>relay node</strong>. The agent validates a configured role at startup, and, in its tunnel-edge role, starts a listener and forwards traffic upstream to the command-and-control server on a different port, preserving the same gRPC streams. It uses its own embedded node token to identify itself in this mode. In other words, the operators can seed both endpoints &#8211; victims that call home and relay nodes that concentrate and forward that traffic &#8211; from one codebase. One build even carries a tag pointing to a specific tunnel geography (<strong>[dns-hktun / Hong Kong]</strong>), suggesting the relay tier is planned around location.</li>



<li><strong>Discovery and collection &#8211;</strong>&nbsp;The reconnaissance is aimed squarely at spreading. Beyond a standard host and network inventory: hostname, users, running services, active network connections, interface addresses, and virtualization hints, the agent reads login history from&nbsp;<code>wtmp</code>,&nbsp;<code>utmp</code>, and the system authentication logs, and enumerates current SSH sessions. It can then archive a victim’s&nbsp;<code>.ssh</code>&nbsp;directory and&nbsp;<code>.bash_history</code>&nbsp;into a compressed bundle for exfiltration. Read who logged in, grab their keys and history, and use the tunnel to reach the next host: the collection features are built to feed lateral movement, not just to profile a single machine. Worth flagging: the host inventory the agent sends home includes a&nbsp;<strong>virtualization role</strong>&nbsp;field, meaning the agent reports back whether it believes it is running inside a virtual machine or sandbox. That gives the operators a chance to abandon or lie low on analysis systems before doing anything noisy.</li>



<li><strong>AI Plugin</strong>&nbsp;&#8211; The newest build we found, introduces something the earlier versions do not have: an AI plugin execution path. The evidence is currently limited to internal strings. The agent logs executing AI plugins when it runs one and recovers from failures through an AI plugin panic handler, so we can confirm the capability exists and is guarded like a first-class feature, but the sample does not reveal what the plugin is or does. In the code AlphaAgent gets scripts probably written by an AI orchestrator on the server side named “<code>ai_plugin_%s.sh</code>”, runs them and sends the result to the C2.</li>



<li><strong>Evasions</strong>&nbsp;&#8211; The agent invests heavily in remaining unseen. It renames its process to impersonate legitimate kernel threads and services entries like&nbsp;<code>[kworker/...]</code>,&nbsp;<code>[kswapd...]</code>,&nbsp;<code>nginx: worker process</code>, or&nbsp;<code>rsyslogd</code>&nbsp;and overwrites its own command-line arguments so tools that read them see the disguise too. It suppresses its own output to&nbsp;<code>/dev/null</code>&nbsp;and detaches as a daemon. Some builds go further and hide the process outright. On command, the agent can bind-mount over its own&nbsp;<code>/proc</code>&nbsp;entry, making itself invisible to anything that reads the process table &#8211; a lightweight but effective trick that needs no kernel module. Other builds do carry a kernel-module component, controlled through custom device commands, that hides processes and network connections at the kernel level and can stage an additional loader fetched from the operator. The encrypted configuration and the traffic camouflage described earlier round out an evasion posture that spans disk, process table, and network. One variant is packaged to defeat analysis itself. It is wrapped in a protector that strips the file’s structure, unpacks the real payload only in memory, obfuscates its internals, and watches for a debugger, popping a decoy error and exiting the moment it detects one. Same feature set underneath, hardened against the analyst.</li>
</ul>

<h3 class="wp-block-heading">oRAT</h3>



<p class="wp-block-paragraph">oRAT is a Go-based Linux remote access trojan built for full remote administration of a compromised host.</p>



<p class="wp-block-paragraph">It starts with decrypting the configuration baked into the binary that contains: the C2 address, the install paths, the process disguise, and the hiding flags all live inside one encrypted blob and are only unpacked in memory.</p>



<p class="wp-block-paragraph">Unless told to skip it, the agent then runs its preparation routine, and this is where most of the damage is done before any traffic leaves the box. It configures logging to&nbsp;<code>/dev/null</code>&nbsp;by default, daemonizes, disables SELinux enforcement (<code>setenforce 0</code>), installs itself to a persistent location, registers a service, writes a GUID, takes a file lock so only one copy runs, deletes its original on-disk copy if it was relocated, and optionally hides its own process. Only after all of that does it enter its main loop of communication.</p>



<p class="wp-block-paragraph">The agent’s communication routine supports three transports, selected by config:</p>



<ul class="wp-block-list">
<li><strong>tcp</strong>&nbsp;&#8211; a raw TCP connection</li>



<li><strong>stcp</strong>&nbsp;&#8211; TLS over TCP</li>



<li><strong>sudp</strong>&nbsp;&#8211; QUIC over UDP, using the quic-go library</li>
</ul>



<p class="wp-block-paragraph">On top of whichever transport it picks, oRAT layers a multiplexed session and speaks HTTP through it. It uses a standard Go HTTP client, but rewrites the client’s dialer so every request is carried inside the established oRAT session instead of hitting the network directly. The agent registers with the server by posting a join request to&nbsp;<code>/join</code>, then serves operator commands as REST-style routes over that same tunnel.</p>



<p class="wp-block-paragraph">Because oRAT exposes its capabilities as HTTP routes, its feature set reads almost like API documentation. The operator API includes:</p>



<figure class="wp-block-table"><table class="has-fixed-layout"><thead><tr><th>Route</th><th>Capability</th></tr></thead><tbody><tr><td><code>/agent/info</code></td><td>Report host details (distribution, kernel, and more)</td></tr><tr><td><code>/agent/ping</code></td><td>Liveness check</td></tr><tr><td><code>/agent/exec</code></td><td>Run an operator-supplied command</td></tr><tr><td><code>/agent/upload</code></td><td>Write an uploaded file to a chosen path</td></tr><tr><td><code>/agent/download</code></td><td>Retrieve a file from the host</td></tr><tr><td><code>/agent/screenshot</code></td><td>Capture and return a screen image</td></tr><tr><td><code>/agent/zip</code>&nbsp;·&nbsp;<code>/agent/unzip</code></td><td>Archive or extract chosen paths</td></tr><tr><td><code>/agent/portscan</code></td><td>Scan hosts and ports from the victim</td></tr><tr><td><code>/agent/proxy</code></td><td>Open a SOCKS proxy through the host</td></tr><tr><td><code>/agent/net</code></td><td>Forward a raw TCP connection to any target</td></tr><tr><td><code>/agent/ssh</code></td><td>Reach an embedded SSH / SFTP server</td></tr><tr><td><code>/agent/upgrade</code></td><td>Replace the running binary</td></tr><tr><td><code>/agent/kill-self</code></td><td>Delete the agent and exit</td></tr></tbody></table></figure>



<p class="wp-block-paragraph">oRAT offers two paths to run commands, and the second is the more interesting.</p>



<p class="wp-block-paragraph">The direct path is a command route that hands operator input to&nbsp;<code>sh -c</code>&nbsp;and returns the output, standard RAT behavior.</p>



<p class="wp-block-paragraph">The richer path is a fully&nbsp;<strong>embedded SSH server</strong>. oRAT builds its own SSH service into the agent, complete with a hardcoded RSA host key, password authentication, port-forwarding, and an SFTP handler. When an operator connects, the agent spawns an interactive shell: trying&nbsp;<code>zsh</code>, then&nbsp;<code>bash</code>, then&nbsp;<code>sh</code>&nbsp;with proper pseudo-terminal handling. In practice, the operator gets a real SSH session and SFTP file access on the target, tunneled through the C2 channel rather than exposed on a listening port.</p>



<p class="wp-block-paragraph">oRAT’s persistence is quiet and well chosen. It installs itself to&nbsp;<code>/usr/local/bin/xtables-addons</code>&nbsp;and registers a systemd service named&nbsp;<code>xtables-addons</code>, wired into the standard multi-user target so it starts on boot as root.&nbsp;<code>xtables-addons</code>&nbsp;is a real netfilter/iptables extension package, so an administrator glancing at the process list or the service table sees what looks like legitimate firewall tooling. If the agent lacks the privileges for a system-wide install, it falls back to per-user persistence through a user service and a cron entry.</p>



<p class="wp-block-paragraph">It also hides its identity in an unexpected place. The agent stores its GUID by appending a&nbsp;<code># GUID: &lt;uuid&gt;</code>&nbsp;comment line to&nbsp;<code>/etc/protocols</code>, a legitimate system file no one thinks to check. Its lock file sits at&nbsp;<code>/tmp/.lock</code>.</p>



<p class="wp-block-paragraph">The evasion posture is layered and Linux-native:</p>



<ul class="wp-block-list">
<li><strong>Process masquerade.</strong>&nbsp;The agent sets its process name to&nbsp;<code>sshd: root@pts/0</code>, so it reads in the process table as an interactive root SSH session. One build reinforces this by spoofing its executable path as&nbsp;<code>/usr/sbin/sshd</code>.</li>



<li><strong>Procfs hiding.</strong>&nbsp;When its mount mode is enabled, the agent bind-mounts over its own&nbsp;<code>/proc/&lt;pid&gt;</code>&nbsp;entry, disrupting inspection of the running process through the proc filesystem.</li>



<li><strong>Silent by default.</strong>&nbsp;Logging goes to&nbsp;<code>/dev/null</code>&nbsp;unless a specific debug environment variable is set.</li>
</ul>



<p class="wp-block-paragraph">Together, these span the process table, the filesystem, the security policy, and the kernel’s view of the process, a broad effort to make the agent hard to notice and harder to inspect.</p>



<h3 class="wp-block-heading">BruteForcer</h3>



<p class="wp-block-paragraph">An SSH credential-checking and brute-force utility. It reads target IP addresses (<code>-f</code>&nbsp;flag), usernames (<code>-u</code>&nbsp;flag), passwords (<code>-p</code>&nbsp;flag), or pre-combined&nbsp;<code>user:pass</code>&nbsp;pairs (<code>-up</code>&nbsp;flag) from operator-supplied files, then attempts concurrent SSH logins against each target.</p>



<p class="wp-block-paragraph">Successful credentials are printed and appended in plaintext to a local results file,&nbsp;<code>res.txt</code>. The binary has no hardcoded C2 infrastructure or persistence mechanism and its sole purpose is credential access against remote SSH services.</p>



<h3 class="wp-block-heading">Recon Scripts</h3>



<p class="wp-block-paragraph">In some of the attacks we observed a number of Bash scripts with Chinese-language comments used by the attackers.</p>



<p class="wp-block-paragraph">The first,&nbsp;<code>info.sh</code>, proceeds in four stages. It first pulls recent login activity to profile who uses the box. It then walks every user’s home directory, including root’s, to inventory&nbsp;<code>.ssh</code>&nbsp;folders, flag any files containing private keys, and comb&nbsp;<code>.bash_history</code>&nbsp;for sensitive commands involving SSH, SCP, database clients, cloud tooling, credentials, and&nbsp;<code>kubectl</code>, a fast way to harvest reusable secrets and understand the victim’s workflows. The third stage is the most refined: a storage analysis that hunts for remote network mounts (NFS, CIFS/Samba, WebDAV, cloud FUSE) and Docker volumes while deliberately filtering out overlay, tmpfs, and container-ID noise, so the operator sees only genuine lateral-movement targets rather than local container clutter &#8211; a sign the author iterated on the tool to cut false positives. Finally, it gathers classic lateral-movement intelligence:&nbsp;<code>/etc/hosts</code>&nbsp;entries, local listening TCP ports, and the ARP neighbor table to reveal adjacent hosts on the network.</p>


<div class="wp-block-image">
<figure class="aligncenter"><img decoding="async" src="https://research.checkpoint.com/wp-content/uploads/2026/09/BYNYGPOQAT-image15.png" alt="Figure 20 - Third stage of info.sh"/><figcaption class="wp-element-caption">Figure 15 &#8211; Third stage of info.sh</figcaption></figure>
</div>


<p class="wp-block-paragraph">The second script,&nbsp;<code>findweb.sh</code>, surveys a compromised host’s web-server landscape and maps out every site it serves. It first detects which web servers are running (Nginx, Apache, or httpd) using several fallback methods, and extends the check to containerized deployments by inspecting Docker for web-server images and any containers publishing ports 80 or 443 to the host. Where possible, it reports the ports each server listens on. It then parses the server configurations directly: for Nginx it walks the common configuration directories, resolving symbolic links and de-duplicating by real path, then extracts each virtual host’s domain (<code>server_name</code>), web root, and any&nbsp;<code>proxy_pass</code>&nbsp;upstreams; for Apache and httpd it does the equivalent, pulling&nbsp;<code>DocumentRoot</code>,&nbsp;<code>ServerName</code>, and&nbsp;<code>ServerAlias</code>&nbsp;from every&nbsp;<code>VirtualHost</code>&nbsp;block across the standard Debian, RedHat, and common control-panel configuration paths.</p>



<p class="wp-block-paragraph">The result is a concise inventory of every domain hosted on the machine, where each site’s files live on disk, and where any existing reverse-proxy rules already point. In the context of this campaign, that inventory is exactly what an operator needs to weaponize a compromised server: it reveals which trusted domains are available to abuse, the exact web roots to plant content in, and where to graft the malicious proxy module so that attacker pages are served under a legitimate site’s name.</p>



<h2 class="wp-block-heading"><strong>Attribution and links to prior work</strong></h2>



<p class="wp-block-paragraph">We assess with medium-to-high confidence that&nbsp;<strong>Gambling Goblin</strong>&nbsp;is tied to&nbsp;<strong>Earth Berberoka &#8211;</strong>&nbsp;a Chinese-speaking threat cluster first documented by&nbsp;<a href="https://www.trendmicro.com/en_us/research/22/d/new-apt-group-earth-berberoka-targets-gambling-websites-with-old.html">Trend Micro</a>&nbsp;in 2022. Earth Berberoka is known for targeting online gambling platforms that serve Chinese-speaking users and operators, and for working across Windows, Linux, and macOS with a mix of aged commodity RATs and purpose-built tooling. Our assessment rests on three independent overlaps: the malware, the operator artifacts, and the network infrastructure.</p>



<p class="wp-block-paragraph"><strong>Tooling.</strong>&nbsp;The group’s use of oRAT is the clearest link. oRAT was tied to Earth Berberoka in 2022, and the variant we analyzed shares the same&nbsp;<code>orat/cmd/agent</code>&nbsp;codebase and REST-style operator routes. The connection extends to the group’s custom malware: one of the AlphaAgent samples we recovered was uploaded in the same archive as other tools previously attributed to Earth Berberoka, placing AlphaAgent directly alongside the group’s known toolset rather than merely resembling it.</p>



<p class="wp-block-paragraph"><strong>Operator artifacts.</strong>&nbsp;The focus on the online gambling sector and the Chinese-language strings scattered across this campaign’s tooling (dual-language flag descriptions, Chinese script comments, and Chinese-language page artifacts) align with operator fingerprints seen in the group’s past campaigns.</p>



<p class="wp-block-paragraph"><strong>Infrastructure.</strong>&nbsp;The group has a documented habit of registering domains that impersonate trusted platforms. Trend Micro reported&nbsp;<code>github[.]wiki</code>&nbsp;as an Earth Berberoka domain while the infrastructure behind Gambling Goblin follows the same playbook: lookalike domains such as&nbsp;<code>github[.]la</code>&nbsp;and&nbsp;<code>gitlab[.]bet</code>&nbsp;closely mirror that tradecraft. Reinforcing the link, many of the C2 servers in this campaign are hosted on the same Amazon ASN (<strong>AS16509</strong>) the group has relied on before.</p>



<h2 class="wp-block-heading">Conclusion</h2>



<p class="wp-block-paragraph">This campaign marks a shift in who targets Brazil, and why. For years, the threats facing Brazilian users came mostly from home grown banking trojan crews. Brazil is a natural target for this kind of operator. It has become one of the world’s fastest-growing online-betting markets, with a vast base of mobile users accustomed to installing apps on the spot, which is exactly the audience a gambling-driven fraud operation wants to reach. For a Chinese-speaking group that has spent a decade monetizing the gambling sector, the money now runs through Brazil, and the infrastructure to exploit it is often trusted but under-secured. A vast base of mobile users conditioned to install apps on sight, and a sprawl of trusted but under-secured web servers, most of them on government&nbsp;<code>.gov.br</code>&nbsp;domains whose search reputation is exactly what a large-scale SEO-fraud operation needs. Compromise those servers, graft on a malicious Apache module, and the attacker turns a nation’s legitimate infrastructure into a distribution network for gambling pages and fake app stores. That is the notable part: this is not opportunistic crime but patient, industrialized abuse of reputation, and it is run with espionage-grade Linux tooling in the service of financially motivated fraud, blurring the line between cybercrime and APT.</p>



<p class="wp-block-paragraph">We expect the operation to grow rather than fade. The same infrastructure that inflates search rankings today is one configuration change away from serving malware tomorrow: the phishing pages already impersonate Google Play, the Microsoft Store, and Amazon, putting the operators a single step from pushing malicious apps straight to Brazilian victims. The Vietnamese, Spanish, and English pages we uncovered show the model is being exported, and the daily domain generators show it is built to scale. Countries should expect more of this, aimed higher, not only at customers and banking credentials, but at the government institutions whose domains lend the campaign its trust. None of it depends on novel exploits. It runs on unpatched internet-facing services, weak SSH credentials, and Apache modules that no one thinks to watch. If organizations, and public-sector operators in particular, do not close those gaps &#8211; patching exposed services, auditing Apache and SSH configurations, and hunting for rogue modules and masqueraded processes, then this actor and the wider wave of global cybercrime it represents, will keep finding an open door.</p>

function loadImg(element){
    var bg = '';
	switch (screenW) {
		case  'mobile':
			bg = element.getAttribute('data-bg-mobile');
			if(bg)
				break; 
		case 'tablet':
			bg = element.getAttribute('data-bg-tablet');
			if(bg)
				break; 
		case 'laptop':
			bg = element.getAttribute('data-bg-laptop');
			if(bg)
				break; 
		default: 
			bg = element.getAttribute('data-bg');
	}
	if(bg)
		element.style.backgroundImage = 'url(' + bg + ')';	
}

function calcScreenW(){
	var screenC = false;
	curentW= jQuery(window).width();	
	if ( curentW > 1450 ) { 
		if (screenW != 'desktop'){
			screenW = 'desktop';	
			screenC = true;
		}
	} else if (curentW > 973){
		if (screenW != 'laptop'){
			screenW = 'laptop';	
			screenC = true;
		}		
	} else if (curentW >767){
		if (screenW != 'tablet'){
			screenW = 'tablet';	
			screenC = true;
		}		
	} else {
		if (screenW != 'mobile'){
			screenW = 'mobile';	
			screenC = true;
		}		
	}
	if (screenC) {
		jQuery('.bg-change-done').removeClass('bg-change-done');
		screenC = false;
		animate_elems();
	}
}

var $elems = jQuery('.responsive-bg');

	animate_elems();

function animate_elems() {
	wintop = jQuery(window).scrollTop(); // calculate distance from top of window
	// loop through each item to check when it animates
	$elems.each(function(){
		$elm = jQuery(this);
		if($elm.hasClass('lazyload')|| $elm.hasClass('bg-change-done')) { return true; } // if already animated skip to the next item

		topcoords = $elm.offset().top; // element's distance from top of page in pixels

		if(wintop > (topcoords - (winheight))) {			
			$elm.addClass('bg-change-done');		
			loadImg($elm[0]);
		} 
	});	
}
