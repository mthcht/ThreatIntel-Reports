		<div class="entry-meta">
			<span class="posted-on"><a href="https://thedfirreport.com/2025/11/17/cats-got-your-files-lynx-ransomware/" rel="bookmark"><time class="entry-date published" datetime="2025-11-17T13:00:28+00:00">November 17, 2025</time></a></span>		</div><!-- .entry-meta -->

<h2 class="wp-block-heading">Key Takeaways</h2>



<ul class="wp-block-list">
<li>The intrusion began with a successful RDP login using already-compromised credentials, likely obtained via an infostealer, data breach reuse, or an initial access broker.</li>



<li>Within minutes, the threat actor moved laterally to a domain controller using a separate compromised domain admin account, created multiple impersonation-style accounts, and added them to privileged groups.</li>



<li>The threat actor mapped out virtualization infrastructure and file shares, conducted additional enumeration, and created one more look-alike account before pausing activity.</li>



<li>Sensitive files from multiple network shares were collected, compressed using 7-Zip, and exfiltrated via temporary file-sharing service <code>temp.sh</code> .</li>



<li>The threat actor connected to backup servers, deleted backup jobs, and deployed Lynx ransomware across multiple backup and file servers via RDP. The overall Time to Ransomware (TTR) was ~178 hours across nine days.</li>
</ul>

<h2 id="case-summary" class="wp-block-heading"><a href="#case-summary">Case Summary</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The intrusion began in early March 2025 with a single successful Remote Desktop Protocol (RDP) logon to an internet-exposed system. Notably, there was no evidence of credential stuffing, brute forcing, or other failed authentication attempts from the source IP, indicating the threat actor likely possessed valid credentials before the activity occurred. Although the original source of the credentials could not be determined, they are commonly acquired through credential-stealing malware, reused passwords from prior data breaches, or purchased through initial access brokers.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Immediately after logging in, the threat actor began reconnaissance using the command prompt and standard Windows utilities. They then expanded their activity to network-wide enumeration by deploying SoftPerfect Network Scanner (netscan).</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Just ten minutes after the initial logon, the threat actor identified a domain controller and moved laterally to it via RDP. For this activity, they authenticated using a different account with domain administrator privileges. In the absence of any evidence of on-host privilege escalation or credential dumping, we assess that these domain admin credentials were also compromised prior to the intrusion. The threat actor&#8217;s possession of multiple valid accounts, spanning both standard and privileged access, further supports the likelihood that an initial access broker was the source of their entry into the environment.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Once on the domain controller, the threat actor used Active Directory Users and Computers (dsa.msc) to create two new accounts: one named “administratr” and another designed to mimic an existing domain account, altered by a single character to blend in. Both accounts were promptly added to privileged security groups, including Domain Administrators. To establish persistence, the threat actor installed the AnyDesk remote access client on the domain controller. Although, this AnyDesk access was never used during the remainder of the intrusion.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>The threat actor then searched the environment for signs of virtualization infrastructure and browsed several network file shares. Afterward, they created one additional look-alike account and concluded their first round of hands-on activity.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Six days after the initial access, the threat actor returned via RDP from the same source IP address and using the same hostname. They resumed reconnaissance by running netscan, then downloaded NetExec through a web browser and conducted a password spray attack over port 445. Afterward, they again browsed multiple file shares. These shares were then targeted for collection; the actor compressed the contents into archives and exfiltrated them to the temporary file-sharing service temp[.]sh. This activity marked the end of their operations for the day.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Around nine hours after the exfiltration activity, the threat actor returned via RDP from a new source IP address but using the same hostname observed earlier in the intrusion. Notably, both IP addresses involved were associated with Railnet LLC, a company previously identified as a front for Virtualine, which is known to operate infrastructure tied to IP ranges reportedly leveraged by criminal networks. Further details on this attribution are available in the Intrinsec blog. [<a href="https://www.intrinsec.com/en/from-espionage-to-psyops-tracking-operations-and-bulletproof-providers-of-uac/" target="_blank" rel="noreferrer noopener">link</a>]</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>During this period, the threat actor connected to several additional domain controllers and hypervisor systems via RDP. On these hosts, they executed various discovery commands and interacted with the Microsoft Management Console (MMC), specifically the Local Users and Groups snap-in, to enumerate and review user accounts and permissions. Leveraging their earlier netscan results, they also identified additional network infrastructure and attempted to access these systems by launching browser sessions directly from within netscan.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Approximately 24 hours later, on the ninth day of the intrusion, the threat actor returned for the final time. They initiated one last round of network scanning with netscan on the beachhead host before connecting via RDP to a backup server, where they proceeded to delete existing backup jobs. Following this, they deployed and executed Lynx ransomware on the backup server. The threat actor then repeated this ransomware deployment across multiple additional backup and file servers accessed via RDP.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>The Time to Ransomware (TTR) for this intrusion was just under 178 hours, spanning nine calendar days.</p>

<h2 id="initial-access" class="wp-block-heading"><a href="#initial-access">Initial Access</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The first instance of unauthorized access by the threat actor was a successful RDP logon to the beachhead host, a publicly exposed RDP server. The logon was performed using valid credentials, and there was no indication of brute force or password spraying occurring, indicating these credentials were obtained prior to the intrusion.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>The threat actor was also observed using credentials for a second account with domain administrator privileges to pivot from the beachhead host without performing any credential access activities, indicating these credentials were also obtained prior to initial access.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>The logon originated from IP address 195.211.190[.]189 and can be observed in Windows Security Log Event ID 4624 logon type 3 followed by logon type 10 indicating a successful RDP logon. </p>
<p><a href="https://thedfirreport.com/wp-content/uploads/2025/11/34936_001.png"><img fetchpriority="high" decoding="async" class="aligncenter size-full wp-image-50007" src="https://thedfirreport.com/wp-content/uploads/2025/11/34936_001.png" alt="" width="1392" height="272" srcset="https://thedfirreport.com/wp-content/uploads/2025/11/34936_001.png 1392w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_001-300x59.png 300w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_001-1024x200.png 1024w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_001-768x150.png 768w" sizes="(max-width: 1392px) 100vw, 1392px" /></a></p>

<h2 id="execution" class="wp-block-heading"><a href="#execution">Execution</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Due to the primary method of access being Remote Desktop Protocol (RDP), the threat actor conducted most post-compromise activity through RDP sessions. This was evidenced by processes consistently spawning under <code>explorer.exe</code>, indicating interactive use aligned with RDP behavior.</p>
<p><a href="https://thedfirreport.com/wp-content/uploads/2025/11/34936_003_1.png"><img decoding="async" class="aligncenter size-full wp-image-50189" src="https://thedfirreport.com/wp-content/uploads/2025/11/34936_003_1.png" alt="" width="1363" height="761" srcset="https://thedfirreport.com/wp-content/uploads/2025/11/34936_003_1.png 1363w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_003_1-300x167.png 300w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_003_1-1024x572.png 1024w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_003_1-768x429.png 768w" sizes="(max-width: 1363px) 100vw, 1363px" /></a></p>
<!-- /wp:paragraph -->

<!-- wp:image -->
<figure class="wp-block-image"></figure>
<!-- /wp:image -->

<!-- wp:paragraph -->
<p>Throughout the intrusion, the threat actor used Windows Command Shell (<code>cmd.exe</code>) and PowerShell to execute commands on compromised hosts during hands-on-keyboard activity. These tools were primarily used to run Living Off The Land Binaries (LOLBins), largely for discovery purposes.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>SoftPerfect NetScan was used extensively during the intrusion. While the configuration deployed by the threat actor is detailed in the Discovery section, it’s clear the tool played a role in automating portions of their activity. Notably, evidence from <code>Security Event ID 4688</code> logs showed <code>mstsc.exe /v:&lt;IP address&gt;</code> being launched by <code>netscan.exe</code>, confirming the use of NetScan’s Remote Desktop functionality.</p>

<h2 id="persistence" class="wp-block-heading"><a href="#persistence">Persistence</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>In the first hour of the compromise, the threat actor leveraged already-known high-privileged account credentials to connect to a domain controller via RDP.</p>

<!-- wp:paragraph -->
<p>On the domain controller, they used the &#8220;Active Directory Users and Computers&#8221; snap-in (dsa.msc) to create three users for persistence. All of the newly created accounts have usernames that mimic legitimate accounts already present in the environment. For the rest of the report we will refer to these accounts as: &#8220;administratr&#8221;, &#8220;Lookalike 1&#8221;, and &#8220;Lookalike 2&#8221;.</p>

<h2 id="privilege-escalation" class="wp-block-heading"><a href="#privilege-escalation">Privilege Escalation</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>After having created the three domain accounts, the threat actor added them to several high-privilege domain groups.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>First, they added two of the accounts, namely &#8220;administratr&#8221; and &#8220;Lookalike 1&#8221;, to the Domain Admins group. The &#8220;administratr&#8221; account was also added to the Group Policy Creator Owners, giving it capabilities to create, for example, new GPOs. Afterward, the threat actor added &#8220;Lookalike 2&#8221; to a high-privilege group specific to the domain in question.</p>

<h2 id="defense-evasion" class="wp-block-heading"><a href="#defense-evasion">Defense Evasion</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Other than creating new accounts to blend in to the environment, the threat actor did not take other actions to really obscure their activity.</p>
<!-- /wp:paragraph -->

<!-- wp:heading -->
<h2 id="credential-access" class="wp-block-heading"><a href="#credential-access">Credential Access</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>The attacker was able to get into the environment through a successful Remote Desktop Protocol (RDP) connection. What’s interesting is that there were no signs of brute force or password spraying, so this wasn’t a case of someone hammering away at login attempts until they got in. Instead, it looks like the credentials were already valid, which points to a few likely scenarios:</p>
<!-- /wp:paragraph -->

<!-- wp:list -->
<ul class="wp-block-list"><!-- wp:list-item -->
<li><strong>Third-Party Access Broker:</strong> These are threat actors who specialize in selling access to compromised systems. They don’t always do the hacking themselves, instead, they collect or buy credentials and then resell them to others who want to get into networks without doing the initial legwork.</li>
<!-- /wp:list-item --></ul>
<!-- /wp:list -->

<!-- wp:list -->
<ul class="wp-block-list"><!-- wp:list-item -->
<li><strong>Info Stealer Malware:</strong> This type of malware is designed to quietly grab saved credentials, browser cookies, and other sensitive data from infected machines. Once stolen, that data often ends up for sale or trade on dark web marketplaces, where attackers can use it to log in.</li>
<!-- /wp:list-item --></ul>
<!-- /wp:list -->

<!-- wp:list -->
<ul class="wp-block-list"><!-- wp:list-item -->
<li><strong>Credential Dump Leaks:</strong> These are large sets of usernames and passwords that get exposed during breaches of unrelated services. If users reuse passwords across platforms (which is still pretty common), attackers can test those credentials elsewhere and find systems where they still work.</li>
<!-- /wp:list-item --></ul>
<!-- /wp:list -->

<!-- wp:paragraph -->
<p>Given the clean nature of the logins seen throughout this incident, it’s reasonable to assume the threat actor used credentials obtained through one of these indirect methods rather than trying to force their way in.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>Within this incident, there were no signs of additional reconnaissance or attempts to escalate access by harvesting more credentials. This suggests the attacker may have had a specific goal or was operating with limited scope.</p>
<!-- /wp:paragraph -->

<h2 id="lateral-movement" class="wp-block-heading"><a href="#lateral-movement">Lateral Movement</a></h2>
<p><a href="https://thedfirreport.com/wp-content/uploads/2025/11/34936_033.jpg"><img loading="lazy" decoding="async" class="aligncenter size-full wp-image-49975" src="https://thedfirreport.com/wp-content/uploads/2025/11/34936_033.jpg" alt="" width="789" height="1362" srcset="https://thedfirreport.com/wp-content/uploads/2025/11/34936_033.jpg 789w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_033-174x300.jpg 174w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_033-593x1024.jpg 593w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_033-768x1326.jpg 768w" sizes="auto, (max-width: 789px) 100vw, 789px" /></a></p>

<!-- wp:heading --><!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Throughout the intrusion, the threat actor used the beachhead host as a central point to access and move laterally across the network via RDP. The threat actor relied heavily on SoftPerfect Network Scanner to identify and enumerate targets for lateral movement, running scans each time they accessed the network.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>On day one of the intrusion, after running initial discovery commands and netscan.exe, the threat actor was observed connecting to a domain controller via RDP using Domain Admin credentials. <h2 id="impact" class="wp-block-heading"><a href="#impact">Impact</a></h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p><strong>Ransomware deployment</strong></p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>On the ninth day of the intrusion, the threat actor moved laterally to several backup servers and file servers via RDP from the beachhead.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>On these servers, they dropped the Lynx ransomware payload &#8220;w.exe&#8221; on the Desktop folder of the compromised Domain Administrator account.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>On one occasion &#8220;w.exe&#8221; was also dropped on the root folder of an E drive, likely by mistake.</p>
<p><a href="https://thedfirreport.com/wp-content/uploads/2025/11/34936_053.png"><img loading="lazy" decoding="async" class="aligncenter size-full wp-image-49955" src="https://thedfirreport.com/wp-content/uploads/2025/11/34936_053.png" alt="" width="1553" height="223" srcset="https://thedfirreport.com/wp-content/uploads/2025/11/34936_053.png 1553w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_053-300x43.png 300w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_053-1024x147.png 1024w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_053-768x110.png 768w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_053-1536x221.png 1536w" sizes="auto, (max-width: 1553px) 100vw, 1553px" /></a></p>
<!-- /wp:paragraph -->

<!-- wp:image -->
<figure class="wp-block-image"></figure>
<!-- /wp:image -->

<!-- wp:paragraph -->
<p>The threat actor then executed &#8220;w.exe&#8221; on each server using cmd, as shown below.</p>
<p><a href="https://thedfirreport.com/wp-content/uploads/2025/11/34936_054.png"><img loading="lazy" decoding="async" class="aligncenter size-full wp-image-49954" src="https://thedfirreport.com/wp-content/uploads/2025/11/34936_054.png" alt="" width="1638" height="223" srcset="https://thedfirreport.com/wp-content/uploads/2025/11/34936_054.png 1638w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_054-300x41.png 300w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_054-1024x139.png 1024w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_054-768x105.png 768w, https://thedfirreport.com/wp-content/uploads/2025/11/34936_054-1536x209.png 1536w" sizes="auto, (max-width: 1638px) 100vw, 1638px" /></a></p>
<!-- /wp:paragraph -->

<!-- wp:image -->
<figure class="wp-block-image"></figure>
<!-- /wp:image -->

<!-- wp:paragraph -->
<p>It is interesting to note that in almost all the command lines the order of the passed parameters differs. In one case, the threat actor also mistyped the command by forgetting to specify a flag.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>In general, the ransomware was executed with the following arguments:</p>
<!-- /wp:paragraph -->

<!-- wp:preformatted -->
<pre class="wp-block-preformatted">w.exe --dir E:\ --mode fast --verbose --noprint
</pre>
<!-- /wp:preformatted -->

<!-- wp:paragraph -->
<p>As detailed in a blog post from <a href="https://www.group-ib.com/blog/cat-s-out-of-the-bag-lynx-ransomware/" target="_blank" rel="noreferrer noopener">Group-IB</a>, the arguments passed can be summed up as follows:</p>
<!-- /wp:paragraph -->

<!-- wp:list -->
<ul class="wp-block-list"><!-- wp:list-item -->
<li><code>--dir E:\</code> specifies the folder to encrypt, in this case the E drive.</li>
<!-- /wp:list-item -->

<!-- wp:list-item -->
<li><code>--mode fast</code> specifies the percentage of file to encrypt, in this case 5%.</li>
<!-- /wp:list-item -->

<!-- wp:list-item -->
<li><code>--verbose</code> enables output verbosity.</li>
<!-- /wp:list-item -->

<!-- wp:list-item -->
<li><code>--noprint</code> disables printing out the ransom note on connected printers.</li>
<!-- /wp:list-item --></ul>
<!-- /wp:list -->

<!-- wp:paragraph -->

<p><strong>Inhibit system recovery</strong></p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>While connected via RDP to the backup servers to deploy the ransomware payload, the threat actor also interacted with the backup software application present on these hosts.</p>
<!-- /wp:paragraph -->

<!-- wp:paragraph -->
<p>In particular, the RDP bitmap cache of the beachhead host shows the threat actor opening the Veeam Backup &amp; Replication console.</p>
