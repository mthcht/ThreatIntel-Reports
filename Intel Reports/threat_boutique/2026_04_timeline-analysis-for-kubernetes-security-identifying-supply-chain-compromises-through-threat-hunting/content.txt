                            <h1 class="title-post" itemprop="name">Timeline Analysis for Kubernetes Security: Identifying Supply Chain Compromises Through Threat Hunting</h1>
                    <div class="date">
            <span itemprop="datePublished"><a href="https://threat.boutique/archive/2026-04" title="Show all posts made on this month">05 April 2026</a></span>
            - Posted in            <span itemprop="articleSection"><a href="https://threat.boutique/category/incident-response">Incident Response</a></span> by            <span itemprop="author"><a href="https://threat.boutique/author/b3vSclAuunBMsdt">Jok3r</a></span> -
            <span><a href="https://threat.boutique/2026/04/timeline-analysis-for-kubernetes-security-identifying-supply-chain-compromises-through-threat-hunting" rel="permalink">Permalink</a></span>
        </div>
                    <div class="featured-image">
                <a href="https://threat.boutique/2026/04/timeline-analysis-for-kubernetes-security-identifying-supply-chain-compromises-through-threat-hunting"><img src="https://threat.boutique/content/images/20260405120904-d5XjK.jpg" alt="Timeline Analysis for Kubernetes Security: Identifying Supply Chain Compromises Through Threat Hunting"/></a>
            </div>
                                        <div class="post-body post-1775376125" itemprop="articleBody">
            <p><strong>Background:</strong>
As we continue our journey through action reconstruction in Kubernetes, we have already discussed one of the forensic methods for supply chain attack investigation at the pod level. Now, let's look into another important part of every investigation, which is highly valuable. The name of this metadata is Timeline.</p>

<p><strong><em>Method:</em></strong>
It is no secret that a well-constructed timeline can provide a strong forensic approach to narrow down our search. To obtain these results using kubectl, simply use the describe command to retrieve valuable metadata and insights.</p>

<pre><code>kubectl describe pods -n  YOURNAMESPACE
</code></pre>

<p>Because a pod can contain multiple containers, you should examine the Containers section in the output . This will be the key to your investigation.</p>

<p><img src="https://threat.boutique/content/images/20260405121922-123REMOVE.png" alt="enter image description here" /></p>

<p>Inside the Containers section, you can see two important fields for each container:</p>

<ul>
<li>Started At – shows exactly when the current container instance was started.</li>
<li>Restart Count – indicates how many times the container has been restarted.</li>
</ul>

<p>These values are key to answering the critical forensic questions:
“When did the process(pod creation) actually started?” and “How many times was this container restarted before the current instance?”</p>

<p><img src="https://threat.boutique/content/images/20260405122339-1234REMOVE.png" alt="enter image description here" /></p>

<p>We have already mentioned that a pod can contain multiple containers. Now, let’s check when the pod itself — as the parent Kubernetes object — was started.
This information can be found at the top level of the kubectl describe pod command output, under the State section. Look for the Start Time field, which shows the exact timestamp when the pod was created and started by the Kubernetes control plane.</p>

<p><img src="https://threat.boutique/content/images/20260405122818-TEST001.png" alt="enter image description here" /></p>

<p><strong>Conclusion:</strong>
If you want to solve the puzzle and accurately reconstruct the sequence of activities in Kubernetes, the timeline of when the pod, node, and other Kubernetes objects were started is extremely important. It helps you narrow down the scope of your threat hunt.</p>

<p>For example, if you know that a particular solution or image was a victim of a supply chain attack during a specific time range, this approach allows you to quickly check whether your environment was impacted and verify the exact timing of events.</p>
