That sentence shouldn&#x27;t be exciting, but it is. For most of the past decade, this slice of telemetry simply didn&#x27;t exist as a customer-accessible log stream. Microsoft Graph Activity Logs (the modern <em>graph.microsoft.com</em> surface) went GA in April 2024. The legacy graph.windows.net surface, the one adversary tooling actually hits, stayed dark until early 2026.</p>
<p>This post walks the loop end-to-end. Why visibility matters, how to ingest the logs into Elastic, how to generate realistic recon manually and with ROADrecon, and how to hunt the result in ES|QL. Everything below was validated against a live tenant.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="key-takeaways" class="absolute -top-32"></span>Key takeaways</h2>
<ul>
<li>
<p>AAD Graph Activity Logs ride into Elastic through the <a href="https://www.elastic.co/docs/reference/integrations/azure">Azure integration</a> and land in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">logs-azure.aadgraphactivitylogs-*</code> with full ECS extraction.</p>
</li>
<li>
<p>ROADtools, AADInternals, and friends have been operating in a visibility gap for years. Defenders weren&#x27;t capturing the calls.</p>
</li>
<li>
<p>AAD Graph is &quot;deprecated&quot; but still queryable in most tenants. The 1.61-internal API version still returns data that Microsoft Graph won&#x27;t.</p>
</li>
<li>
<p>ECS fields land typed (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.action</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.outcome</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">http.request.method</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">source.ip</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">user.id</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">user_agent.original</code>). Dataset extras stay queryable under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">azure.aadgraphactivitylogs.properties.*</code>.</p>
</li>
<li>
<p>Five hunts reliably catch the activity: tooling user-agents, endpoint breadth, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">*-internal</code> API misuse, FOCI client-ID mismatches, and 4xx surges.</p>
</li>
</ul>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="a-short-history-of-defender-visibility" class="absolute -top-32"></span>A short history of defender visibility</h2>
<p>Defenders have spent years on sign-ins, conditional access, role assignments, and OAuth consent grants. Very little content covers the <em>underlying</em> directory APIs that adversary tooling actually hits. The reason is structural: customer-accessible logs for those APIs didn&#x27;t exist. Microsoft Graph Activity Logs landed first (preview October 2023, GA April 2024). AzureADGraphActivityLogs finally showed up in early 2026.</p>
<p>For most of the past decade, AAD Graph enumeration was invisible to SOCs, not because the telemetry was hidden, but because it didn&#x27;t exist. ROADtools, AADInternals, MSOLSpray, Microburst. None of them produced data that anyone could capture, even with a perfect logging configuration.</p>
<p>That changes the day AzureADGraphActivityLogs start landing in your platform-logs index.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="aad-graph-is-deprecated-but-still-very-much-alive" class="absolute -top-32"></span>AAD Graph is “deprecated” but still very much alive</h2>
<p>Quick refresher. Azure AD Graph is the legacy REST API for Entra ID directory objects, hosted at <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">https://graph.windows.net/{tenantId}/{objecttype}</code> with API versions like <em>1.5</em>, <em>1.6</em>, and <em>1.61-internal</em>. Microsoft has been telling everyone to migrate to Microsoft Graph since 2019, and the retirement date has slipped several times.</p>
<p>Deprecation isn’t gone. In 2026, AAD Graph can still answer requests in environments where legacy access paths remain available or where applications have not been explicitly blocked from using it. A few reasons it sticks around as an attacker target:</p>
<ul>
<li>
<p>Adversary tooling hasn&#x27;t been ported. ROADrecon still uses it for <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">gather</code>. AADInternals has dozens of cmdlets wrapping it.</p>
</li>
<li>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">*-internal</code> API versions return more data. <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">1.61-internal</code> exposes <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">strongAuthenticationDetail</code> inline on the user object during a normal directory walk. The Microsoft Graph equivalent lives behind a separate /authentication/methods endpoint gated by <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">UserAuthenticationMethod.Read.All</code>. That asymmetry is exactly what bulk enumeration tooling exploits.</p>
</li>
<li>
<p>The block isn&#x27;t a single toggle. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">blockAzureADGraphAccess</code> control lives per-app on <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">application.authenticationBehaviors</code>, so blocking tenant-wide means iterating every app registration. Most environments haven&#x27;t done that because some legacy automation still depends on the API. Microsoft&#x27;s phased retirement enforcement does the work on Microsoft&#x27;s timeline, not the defender&#x27;s.</p>
</li>
<li>
<p>Visibility did not exist, thus red teamers and adversaries could hammer the API endpoints for relevant information.</p>
</li>
</ul>
<p>Legitimate AAD Graph traffic is dominated by a handful of first-party Microsoft callers. In our test tenant, the order, by volume, was <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Microsoft.OData.Client</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Microsoft Azure Graph Client Library</code>, an empty-UA tail from first-party AppIds, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Microsoft ADO.NET Data Services</code>, and the Azure portal (Chrome UAs against the portal app ID). Anything outside that recognisable set is either internal tooling or unauthorized activity. That makes it a solid threat hunting/detection dataset. If you&#x27;re capturing it.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="setting-up-the-ingestion-pipeline" class="absolute -top-32"></span>Setting up the ingestion pipeline</h2>
<p>If you&#x27;re already running the Elastic Azure <a href="https://www.elastic.co/docs/reference/integrations/azure">integration</a> with diagnostic settings forwarding to an event hub, skim this section. You probably just need to enable one extra log category. From scratch, it&#x27;s about a 20-minute path.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="step-1-a-stack-to-receive-the-logs" class="absolute -top-32"></span>Step 1: A stack to receive the logs</h4>
<p>Any Elastic deployment works. An Elastic Cloud trial is the lowest-friction option for prototyping. Another option is the <a href="https://github.com/peasead/elastic-container">Elastic Container Project</a> for getting started. The Azure integration already handles AzureADGraphActivityLogs once it&#x27;s enabled.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="step-2-add-the-azure-integration" class="absolute -top-32"></span>Step 2: Add the Azure integration</h4>
<p>In Kibana, Integrations &gt; Azure Logs &gt; Add Azure Logs. Plug in your Event Hub connection string, the Event Hub name, and a Storage account for offset checkpointing, all on an event hub in the same subscription as your tenant.</p>
<p>Enable the Azure logs v2 data stream specifically. That&#x27;s the entry point for AAD Graph Activity Logs. The events router matches <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">category == &quot;AzureADGraphActivityLogs&quot;</code> and reroutes documents to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">logs-azure.aadgraphactivitylogs-*</code>, where the dataset pipeline applies full ECS extraction.</p>
<p></p>
<p>We&#x27;ve also broken Azure AD Graph Activity Logs out into its own integration item, so you can search for &quot;Azure AD Graph Activity Logs&quot; and install via the policy template directly.</p>
<p></p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="step-3-enable-diagnostic-settings-on-entra-id" class="absolute -top-32"></span>Step 3: Enable diagnostic settings on Entra ID</h4>
<p>This is the step most defenders miss. AzureADGraphActivityLogs as a diagnostic-settings category is newer. Even if your Entra ID diagnostic settings have been configured for a while now, the new category needs a fresh tick. Otherwise, the data lives and dies in Microsoft&#x27;s tenant boundary.</p>
<p>In the Azure portal:</p>
<ol>
<li>Entra ID &gt; Monitoring &gt; Diagnostic settings &gt; + Add diagnostic setting.</li>
<li>Name it.</li>
<li>Under Logs, check AzureADGraphActivityLogs. While you&#x27;re there, MicrosoftGraphActivityLogs, SignInLogs, and AuditLogs are worth turning on if they aren&#x27;t already. The integration handles all of them.</li>
<li>Under Destination details, Stream to an event hub (the same one from step 2).</li>
<li>Save.</li>
</ol>
<p></p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="step-4-verify-data-is-flowing" class="absolute -top-32"></span>Step 4: Verify data is flowing</h4>
<p>Within a few minutes, you should start seeing events. Fastest sanity check:</p>
<pre><code>FROM logs-azure.aadgraphactivitylogs-*
| LIMIT 20</code></pre>
<p>If documents come back with a populated <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.action</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">http.request.method</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">zure.aadgraphactivitylogs.properties.*</code> fields, you&#x27;re good. If nothing shows up, the usual suspects are a forgotten event hub permission, a typo in the connection string, or the AAD Graph category just not being ticked.</p>
<p>To force a few events, sign in to the Azure portal and click around Users or Applications. The portal still calls AAD Graph internally for some object details. If that doesn&#x27;t generate anything, this curl loop will:</p>
<pre><code>TOKEN=$(az account get-access-token --resource https://graph.windows.net --query accessToken -o tsv)
TID=$(az account show --query tenantId -o tsv)
for obj in users groups servicePrincipals applications tenantDetails; do
  curl -sS -o /dev/null -H &quot;Authorization: Bearer $TOKEN&quot; \
    &quot;https://graph.windows.net/$TID/$obj?api-version=1.6&amp;\$top=5&quot;
done</code></pre>
<p></p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="field-shape" class="absolute -top-32"></span>Field shape</h2>
<p>Once data is flowing, properties land as typed, top-level fields. The ones that matter for hunting:</p>
<ul>
<li><a href="https://www.elastic.co/docs/reference/ecs">ECS</a>, populated directly: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.action</code> (a semantic verb derived from method + collection, e.g., <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">users-read, batch-execute</code>), <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.outcome</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.duration</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">http.request.method</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">http.response.status_code, source.ip</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">source.geo.*, user.id, user_agent.original</code> (plus parsed sub-fields), <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">url.path, azure.tenant_id, cloud.service.name = &quot;Azure AD Graph&quot;</code>.</li>
<li>Dataset-specific under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">zure.aadgraphactivitylogs.properties.*: app_id,</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">app_id</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">api_version</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">actor_type</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">roles</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">scopes</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">wids</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">identity_provider</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">client_auth_method</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">sign_in_activity_id</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">token_issued_at</code>.</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">related.user</code> gets both <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">user.id</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">properties.app_id</code>, so pivots on the OAuth-client dimension work alongside the user pivot.</li>
</ul>
<p>Raw JSON stays in <em>event.original</em> for forensic replay. You shouldn&#x27;t need to reach into it for normal hunting. If you do, ES|QL&#x27;s <a href="https://www.elastic.co/docs/reference/query-languages/esql/functions-operators/string-functions/json_extract"><em>JSON_EXTRACT()</em></a> is the lever.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="aad-graph-enumeration-with-roadrecon" class="absolute -top-32"></span>AAD Graph enumeration with ROADrecon</h2>
<p>To know what to hunt, you need to know what the activity looks like. The two toolkits below are the most common sources of AAD Graph traffic in red team and security research workflows. I ran both against our testing tenant.</p>
<p>Note: I take no responsibility for misuse of this code. Run these tools only against tenants you own or have explicit written authorization to test.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="roadrecon-bulk-enumeration-test" class="absolute -top-32"></span>ROADrecon: Bulk enumeration test</h3>
<p>ROADrecon is the data-collection module of <a href="https://github.com/dirkjanm/ROADtools">ROADtools</a>, Dirk-jan Mollema&#x27;s Entra ID research framework. Highly recommended if you haven&#x27;t used it. <em>gather</em> walks every interesting object type in the directory (users, groups, service principals, applications, devices, directory roles, role assignments, eligible role assignments, OAuth2 permission grants, administrative units) and writes the result to SQLite.</p>
<p>Setup is the standard workflow:</p>
<pre><code>pip install roadrecon
roadrecon auth --device-code -c 04b07795-8ddb-461a-bbee-02f9e1bf7b46 -r https://graph.windows.net</code></pre>
<p>The device-code flow hands you a URL and a code. We use the Microsoft Azure CLI as the default (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">1b730954-1685-4b74-9bfd-dac224a7b894</code> - AAD PowerShell), which returned 403s in our tenant. After signing in:</p>
<pre><code>roadrecon gather</code></pre>
<p>Running <em>roadrecon gather</em> with the resulting token completed cleanly. From the tenant&#x27;s perspective, the run produced just over ~2,000 AAD Graph calls and logs in roughly 1 minute. Bulk enumeration across every object type ROADrecon knows.</p>
<p></p>
<p></p>
<p>From this, we can form some initial detections to start flagging these anomalies.</p>

<h2 class="font-bold text-2xl md:text-4xl relative"><span id="detection-and-prevention" class="absolute -top-32"></span>Detection and prevention</h2>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="detection" class="absolute -top-32"></span>Detection</h3>
<p>The prerequisite for any AAD Graph detection is having the logs in the first place. The <em>AzureADGraphActivityLogs</em> diagnostic category needs to be enabled in Entra ID and routed to a destination you can query (at minimum a Log Analytics workspace, ideally also forwarded to an event hub for Elastic ingestion as described in the setup section above). Until that&#x27;s done, the calls described in this post happen entirely off-camera, and none of the hunts below will fire.</p>
<p>If you can&#x27;t ingest into Elastic right now, enable the diagnostic setting anyway and send to Log Analytics. The KQL equivalents of the hunts below are straightforward, and the data accumulates with retention even without further processing.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="prevention" class="absolute -top-32"></span>Prevention</h3>
<p>There&#x27;s no single tenant-wide AAD Graph kill-switch in the portal. The actual application-layer control is:</p>
<ul>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">application.authenticationBehaviors.blockAzureADGraphAccess</code></li>
</ul>
<p>A per-app Boolean on the application resource (Microsoft Graph beta, <a href="https://learn.microsoft.com/en-us/graph/api/resources/authenticationbehaviors">docs</a>). Blocking at scale means walking through every app registration and flipping it manually or programmatically. Microsoft&#x27;s own phased retirement is doing this on their timeline regardless. The further along that gets, the less surface there is to defend.</p>
<p>Defenders can move on the same axes in the meantime:</p>
<ul>
<li>
<p>Audit applications in your tenant that still hold tokens for <em>graph.windows.net</em>. Set <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">blockAzureADGraphAccess = true</code> on the ones that don&#x27;t need it. Anything still depending on AAD Graph breaks loudly, which surfaces legacy automation you didn&#x27;t know you had.</p>
</li>
<li>
<p>Apply Conditional Access with Azure AD Graph as a target resource. The Azure AD Graph service principal (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">00000002-0000-0000-c000-000000000000</code>) doesn&#x27;t show in the standard CA app picker, but it&#x27;s covered by <em>All resources</em> policies and is individually targetable via the <a href="https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-cloud-apps#protect-directory-information">custom security attribute filter approach</a>. Microsoft&#x27;s <a href="https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-cloud-apps#new-conditional-access-behavior-when-an-all-resources-policy-has-a-resource-exclusion">March 2026 enforcement change</a> makes this more practical: low-privilege scopes (<em>User.Read</em>, <em>People.Read</em>, etc.) that used to be auto-excluded from CA enforcement are now treated as AAD Graph access, so <em>all resource</em> policies actually gate them. CA evaluates at token issuance, so already-valid tokens keep working until expiry.</p>
</li>
<li>
<p>Apply CA to the FOCI clients adversary tooling rides on (Microsoft Teams, Microsoft Office, OneDrive, Azure PowerShell, etc.). Require managed and compliant devices. The swap path collapses if the underlying client can&#x27;t sign in.</p>
</li>
<li>
<p>For service-principal callers, <a href="https://learn.microsoft.com/en-us/entra/identity/conditional-access/workload-identity">Workload Identities Premium</a> adds CA scoped to service principals. Conditions are limited to location, Identity Protection risk, and authentication context; the only grant control is Block. Useful for collapsing external- and risky-context paths, not for scoping an SP to specific cloud apps the way user CA does.</p>
</li>
<li>
<p>Disable device-code flow for users who don&#x27;t need it. <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">roadrecon auth --device-code</code> is the path of least resistance into the entire pipeline above and is extremely common in OAuth phishing.</p>
</li>
</ul>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="behavior-detection" class="absolute -top-32"></span>Behavior detection</h3>
<p>We shipped detection rules covering the AAD Graph recon shapes documented above. Each lives in the <a href="https://github.com/elastic/detection-rules">Elastic detection-rules</a> repository and runs natively against the parsed <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">logs-azure.aadgraphactivitylogs-*</code> data stream.</p>
<p><a href="https://github.com/elastic/detection-rules/blob/31d1fa31152c208dfde4feeb6737ca06e030ae53/rules/integrations/azure/discovery_aad_graph_suspicious_user_agent.toml">Azure AD Graph Access with Suspicious User-Agent</a> - KQL match rule. Triggers when AAD Graph receives traffic from user-agent strings matching offensive tooling families (Python, aiohttp, curl, Go-http-client, axios, AzureHound, BloodHound, AADIntenals, etc.). Solid baseline signal because no first-party Microsoft component identifies as any of these, while default tooling does. </p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/df0396ea4a3b0fb25529444166c36c430941d3a6/rules/integrations/azure/discovery_aad_graph_high_4xx_ratio_by_user.toml">Azure AD Graph High 4xx Error Ratio from User</a> - ES|QL aggregation. Triggers when a single caller produces an unusually high ratio of 4xx responses against AAD Graph in a short window. Recon and brute-force token usage leave a tail of 403s and 404s as tools walk endpoints they don&#x27;t have permission for, ask for object IDs they don&#x27;t have, or use a client ID unauthorized for AAD Graph. </p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/0c15c6c581780d962b33972a8a83263b75fb2d79/rules/integrations/azure/discovery_aad_graph_unusual_client_for_user.toml">Azure AD Graph Access with Unusual Client and User</a> - KQL new_terms rule, medium severity. Fires when a (calling OAuth client, signed-in user) pair appears on AAD Graph for the first time in the prior 14 days. Catches FOCI swaps, phished refresh tokens redeemed for clients the user doesn&#x27;t normally use, and stolen tokens used under unfamiliar clients. Ignores known first-party applications that were commonly observed interacting with Azure AD that are backend owned by Microsoft.</p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/6f933e04ddbe720898c9ea9c4bae234700a822fe/rules/integrations/azure/initial_access_aad_graph_unusual_asn.toml">Azure AD Graph Access with Unusual User and ASN</a> - KQL match rule. Excludes the common Microsoft / AWS / GCP / Akamai / Cloudflare ASN organisations and flags AAD Graph traffic originating outside that set. Adversary tooling typically rides on residential ISPs, VPS providers, or anonymising networks that produce a different ASN distribution than legitimate first-party callers. Tunable per tenant by adjusting the excluded ASN list.</p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/4256409e8925a8da016448d1378bc669c2333961/rules/integrations/azure/discovery_aad_graph_roadrecon_aiohttp_enumeration.toml">Azure AD Graph Potential Enumeration (ROADrecon)</a> - ES|QL aggregation, <strong>high severity</strong>. Requires both an <em>aiohttp</em> user-agent and a burst of 500+ AAD Graph requests from a single identity. ROADrecon&#x27;s <em>gather</em> command uses aiohttp by default and walks every directory object type, so the combination is essentially a tool fingerprint. Higher severity than the generic non-Microsoft UA rule because the additional burst requirement removes the developer-prototype false-positive class.</p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/6a946179e66c7a952e55a33741c160d6bd83f3b8/rules/integrations/azure/credential_access_device_code_signin_aad_graph_enum.toml">Entra ID OAuth Device Code Sign-in to Azure AD Graph Enumeration</a> - EQL sequence, <strong>high severity</strong>. Joins a successful device-code sign-in to the legacy AAD Graph audience (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">00000002-0000-0000-c000-000000000000</code>) on an unmanaged device with directory enumeration against <em>graph.windows.net</em> by the same user within five minutes. Device-code phishing lands an OAuth token without touching the user&#x27;s password or MFA, so immediate Graph reads of users, service principals, applications, role assignments, policies, or tenant details under that token are the compromised identity being driven by the attacker. Cross-data-stream sequence removes the single-event false-positive class that the other AAD Graph rules carry.</p>
<p></p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="aad-graph-visibility-what-comes-next" class="absolute -top-32"></span>AAD Graph visibility: what comes next</h2>
<p>For most of the past decade, AAD Graph activity was the telemetry equivalent of dark matter. We knew it was there because adversary tooling kept pointing at it, but customers had no diagnostic stream to subscribe to and no logs to query. Microsoft Graph Activity Logs closed half the gap when they went GA in April 2024. <em>AzureADGraphActivityLogs</em> finally closed the other half in early 2026.</p>
<p>Now that the data exists, the rest is on us. Add the new diagnostic setting, point it at an event hub, ingest into your stack, turn detections on (or create your own) and get to monitoring.</p>
<p>The detections in this post are a starting point. Once you have AAD Graph traffic landing in your stack and a baseline of what normal looks like in your tenant, the same patterns generalize. Legitimate first-party Microsoft callers form a small, recognisable set, and anything outside that set deserves a closer look.</p>
<p>The activity was always there. The visibility finally is too.</p>
<p>Happy hunting!</p>

The 1.61-internal API version still returns data that Microsoft Graph won't.\n\n- ECS fields land typed (`event.action`, `event.outcome`, `http.request.method`, `source.ip`, `user.id`, `user_agent.original`). Dataset extras stay queryable under `azure.aadgraphactivitylogs.properties.*`.\n\n- Five hunts reliably catch the activity: tooling user-agents, endpoint breadth, `*-internal` API misuse, FOCI client-ID mismatches, and 4xx surges.\n\n## A short history of defender visibility\n\nDefenders have spent years on sign-ins, conditional access, role assignments, and OAuth consent grants. Very little content covers the _underlying_ directory APIs that adversary tooling actually hits. The reason is structural: customer-accessible logs for those APIs didn't exist. Microsoft Graph Activity Logs landed first (preview October 2023, GA April 2024). AzureADGraphActivityLogs finally showed up in early 2026.\n\nFor most of the past decade, AAD Graph enumeration was invisible to SOCs, not because the telemetry was hidden, but because it didn't exist. ROADtools, AADInternals, MSOLSpray, Microburst. None of them produced data that anyone could capture, even with a perfect logging configuration.\n\nThat changes the day AzureADGraphActivityLogs start landing in your platform-logs index.\n\n\n## AAD Graph is “deprecated” but still very much alive\n\nQuick refresher. Azure AD Graph is the legacy REST API for Entra ID directory objects, hosted at `https://graph.windows.net/{tenantId}/{objecttype}` with API versions like _1.5_, _1.6_, and _1.61-internal_. Microsoft has been telling everyone to migrate to Microsoft Graph since 2019, and the retirement date has slipped several times.\n\nDeprecation isn’t gone. In 2026, AAD Graph can still answer requests in environments where legacy access paths remain available or where applications have not been explicitly blocked from using it. A few reasons it sticks around as an attacker target:\n\n- Adversary tooling hasn't been ported. ROADrecon still uses it for `gather`. AADInternals has dozens of cmdlets wrapping it.\n\n- The `*-internal` API versions return more data. `1.61-internal` exposes `strongAuthenticationDetail` inline on the user object during a normal directory walk. The Microsoft Graph equivalent lives behind a separate /authentication/methods endpoint gated by `UserAuthenticationMethod.Read.All`. That asymmetry is exactly what bulk enumeration tooling exploits.\n\n- The block isn't a single toggle. The `blockAzureADGraphAccess` control lives per-app on `application.authenticationBehaviors`, so blocking tenant-wide means iterating every app registration. Most environments haven't done that because some legacy automation still depends on the API. Microsoft's phased retirement enforcement does the work on Microsoft's timeline, not the defender's.\n\n- Visibility did not exist, thus red teamers and adversaries could hammer the API endpoints for relevant information.\n\nLegitimate AAD Graph traffic is dominated by a handful of first-party Microsoft callers. In our test tenant, the order, by volume, was `Microsoft.OData.Client`, `Microsoft Azure Graph Client Library`, an empty-UA tail from first-party AppIds, `Microsoft ADO.NET Data Services`, and the Azure portal (Chrome UAs against the portal app ID). Anything outside that recognisable set is either internal tooling or unauthorized activity. That makes it a solid threat hunting/detection dataset. If you're capturing it.\n\n## Setting up the ingestion pipeline\n\nIf you're already running the Elastic Azure [integration](https://www.elastic.co/docs/reference/integrations/azure) with diagnostic settings forwarding to an event hub, skim this section. You probably just need to enable one extra log category. From scratch, it's about a 20-minute path.\n\n\n#### Step 1: A stack to receive the logs\n\nAny Elastic deployment works. An Elastic Cloud trial is the lowest-friction option for prototyping. Another option is the [Elastic Container Project](https://github.com/peasead/elastic-container) for getting started. The Azure integration already handles AzureADGraphActivityLogs once it's enabled.\n\n\n#### Step 2: Add the Azure integration\n\nIn Kibana, Integrations \u003e Azure Logs \u003e Add Azure Logs. Plug in your Event Hub connection string, the Event Hub name, and a Storage account for offset checkpointing, all on an event hub in the same subscription as your tenant.\n\nEnable the Azure logs v2 data stream specifically. That's the entry point for AAD Graph Activity Logs. The events router matches `category == \"AzureADGraphActivityLogs\"` and reroutes documents to `logs-azure.aadgraphactivitylogs-*`, where the dataset pipeline applies full ECS extraction.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/collect-azure-logs.png)\n\nWe've also broken Azure AD Graph Activity Logs out into its own integration item, so you can search for \"Azure AD Graph Activity Logs\" and install via the policy template directly.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/azure-graph.png)\n\n#### Step 3: Enable diagnostic settings on Entra ID\n\nThis is the step most defenders miss. AzureADGraphActivityLogs as a diagnostic-settings category is newer. Even if your Entra ID diagnostic settings have been configured for a while now, the new category needs a fresh tick. Otherwise, the data lives and dies in Microsoft's tenant boundary.\n\nIn the Azure portal:\n\n1. Entra ID \u003e Monitoring \u003e Diagnostic settings \u003e + Add diagnostic setting.\n2. Name it.\n3. Under Logs, check AzureADGraphActivityLogs. While you're there, MicrosoftGraphActivityLogs, SignInLogs, and AuditLogs are worth turning on if they aren't already. The integration handles all of them.\n4. Under Destination details, Stream to an event hub (the same one from step 2).\n5. Save.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/diagnostic-setting.png)\n\n#### Step 4: Verify data is flowing\n\nWithin a few minutes, you should start seeing events. Fastest sanity check:\n\n```sql\nFROM logs-azure.aadgraphactivitylogs-*\n| LIMIT 20\n```\n\nIf documents come back with a populated `event.action`, `http.request.method`, and `zure.aadgraphactivitylogs.properties.*` fields, you're good. If nothing shows up, the usual suspects are a forgotten event hub permission, a typo in the connection string, or the AAD Graph category just not being ticked. \n\nTo force a few events, sign in to the Azure portal and click around Users or Applications. The portal still calls AAD Graph internally for some object details. If that doesn't generate anything, this curl loop will:\n\n```sh\nTOKEN=$(az account get-access-token --resource https://graph.windows.net --query accessToken -o tsv)\nTID=$(az account show --query tenantId -o tsv)\nfor obj in users groups servicePrincipals applications tenantDetails; do\n  curl -sS -o /dev/null -H \"Authorization: Bearer $TOKEN\" \\\n    \"https://graph.windows.net/$TID/$obj?api-version=1.6\u0026\\$top=5\"\ndone\n```\n![](/assets/images/aad-graph-activity-logs-threat-detection/verify-data-flowing.png)\n\n## Field shape\n\nOnce data is flowing, properties land as typed, top-level fields. The two toolkits below are the most common sources of AAD Graph traffic in red team and security research workflows. I ran both against our testing tenant.\n\nNote: I take no responsibility for misuse of this code. Run these tools only against tenants you own or have explicit written authorization to test.\n\n### ROADrecon: Bulk enumeration test\n\nROADrecon is the data-collection module of [ROADtools](https://github.com/dirkjanm/ROADtools), Dirk-jan Mollema's Entra ID research framework. Highly recommended if you haven't used it. _gather_ walks every interesting object type in the directory (users, groups, service principals, applications, devices, directory roles, role assignments, eligible role assignments, OAuth2 permission grants, administrative units) and writes the result to SQLite.\n\nSetup is the standard workflow:\n\n```sh\npip install roadrecon\nroadrecon auth --device-code -c 04b07795-8ddb-461a-bbee-02f9e1bf7b46 -r https://graph.windows.net\n```\nThe device-code flow hands you a URL and a code. We use the Microsoft Azure CLI as the default (`1b730954-1685-4b74-9bfd-dac224a7b894` - AAD PowerShell), which returned 403s in our tenant. After signing in:\n\n```sh\nroadrecon gather\n```\nRunning _roadrecon gather_ with the resulting token completed cleanly. From the tenant's perspective, the run produced just over \\~2,000 AAD Graph calls and logs in roughly 1 minute. Bulk enumeration across every object type ROADrecon knows.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/roaddrecon.png)\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/roaddrecon2.png)\n\nFrom this, we can form some initial detections to start flagging these anomalies.\n\n## Key fields for AAD Graph threat detection\n\nBefore the hunts, here are some solid starting fields for detecting anomalies.\n\n| Field | Description | What you can find |\n|---------|-------------|-------------------|\n| `event.action` | Semantic verb (HTTP method + collection, e.g.,`users-read, batch-execute) | A cheap filter to isolate AAD Graph activity by intent |\n| `http.request.method` | GET, POST, PATCH`, DELETE | Reads (recon) vs writes (modification, credential injection, persistence) |\n| `http.response.status_code` | HTTP status returned | Successful vs blocked recon; bursts of 4xx indicate permission-probing or brute-forcing |\n| `user.id` | Calling user's directory object ID | Identity attribution; pivot to that user's other activity in SignInLogs / AuditLogs |\n| `user_agent.original` | Full UA string of the caller | Whether the caller is a first-party Microsoft library, a developer tool (curl, Python aiohttp), or known offensive tooling |\n| `url.path` | Resource path (/users, /policies, /servicePrincipals, ...) | Which directory object types are being touched; breadth across distinct paths indicates bulk enumeration |\n| `azure.aadgraphactivitylogs.properties.app_id` | OAuth client ID that issued the token | Whether traffic comes from a legitimate first-party client or from a FOCI-swap-style abuse path |\n| `azure.aadgraphactivitylogs.properties.api_version` | 1.5, 1.6, 1.61-internal, etc. | Whether the caller is asking for internal-only fields (strongAuthenticationDetail, full CAP set) that adversary tooling specifically targets |\n| `azure.aadgraphactivitylogs.properties.actor_type` | User, Application, ServicePrincipal | Human caller vs service-principal / app-only flow |\n| `azure.aadgraphactivitylogs.properties.roles` / `wids` | Directory role display names and well-known role template GUIDs held by the caller | Whether a privileged role (Global Admin, Application Administrator, etc.) is being exercised at the moment of the call |\n| `azure.aadgraphactivitylogs.properties.scopes` | OAuth scopes on the calling token | Which directory permissions the token actually grants the caller |\n| `azure.aadgraphactivitylogs.properties.client_auth_method` | How the client authenticated (PRT, certificate, secret, ...) | Fingerprints for PRT abuse, device-PRT exploitation, or stolen client-credential use |\n| `azure.aadgraphactivitylogs.properties.sign_in_activity_id` | Correlation ID to the originating sign-in | Pivot from an AAD Graph call back to the sign-in event that produced the calling token |\n| `azure.aadgraphactivitylogs.properties.token_issued_at` | Timestamp the token was minted | Token-age analysis; calls riding on a token issued days ago can indicate stale-token / refresh-token abuse |\n\n## Detection and prevention\n\n### Detection\nThe prerequisite for any AAD Graph detection is having the logs in the first place. The _AzureADGraphActivityLogs_ diagnostic category needs to be enabled in Entra ID and routed to a destination you can query (at minimum a Log Analytics workspace, ideally also forwarded to an event hub for Elastic ingestion as described in the setup section above). Until that's done, the calls described in this post happen entirely off-camera, and none of the hunts below will fire.\n\nIf you can't ingest into Elastic right now, enable the diagnostic setting anyway and send to Log Analytics. The KQL equivalents of the hunts below are straightforward, and the data accumulates with retention even without further processing.\n\n### Prevention\n\nThere's no single tenant-wide AAD Graph kill-switch in the portal. The actual application-layer control is:\n\n- `application.authenticationBehaviors.blockAzureADGraphAccess`\n\nA per-app Boolean on the application resource (Microsoft Graph beta, [docs](https://learn.microsoft.com/en-us/graph/api/resources/authenticationbehaviors)). Blocking at scale means walking through every app registration and flipping it manually or programmatically. Microsoft's own phased retirement is doing this on their timeline regardless. The further along that gets, the less surface there is to defend.\n\nDefenders can move on the same axes in the meantime:\n\n- Audit applications in your tenant that still hold tokens for _graph.windows.net_. Set `blockAzureADGraphAccess = true` on the ones that don't need it. Anything still depending on AAD Graph breaks loudly, which surfaces legacy automation you didn't know you had.\n\n- Apply Conditional Access with Azure AD Graph as a target resource. The Azure AD Graph service principal (`00000002-0000-0000-c000-000000000000`) doesn't show in the standard CA app picker, but it's covered by _All resources_ policies and is individually targetable via the [custom security attribute filter approach](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-cloud-apps#protect-directory-information). Microsoft's [March 2026 enforcement change](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-conditional-access-cloud-apps#new-conditional-access-behavior-when-an-all-resources-policy-has-a-resource-exclusion) makes this more practical: low-privilege scopes (_User.Read_, _People.Read_, etc.) that used to be auto-excluded from CA enforcement are now treated as AAD Graph access, so _all resource_ policies actually gate them. CA evaluates at token issuance, so already-valid tokens keep working until expiry.\n\n- Apply CA to the FOCI clients adversary tooling rides on (Microsoft Teams, Microsoft Office, OneDrive, Azure PowerShell, etc.). Require managed and compliant devices. The swap path collapses if the underlying client can't sign in.\n\n- For service-principal callers, [Workload Identities Premium](https://learn.microsoft.com/en-us/entra/identity/conditional-access/workload-identity) adds CA scoped to service principals. Conditions are limited to location, Identity Protection risk, and authentication context; the only grant control is Block. Useful for collapsing external- and risky-context paths, not for scoping an SP to specific cloud apps the way user CA does.\n\n- Disable device-code flow for users who don't need it. `roadrecon auth --device-code` is the path of least resistance into the entire pipeline above and is extremely common in OAuth phishing.\n\n### Behavior detection\n\nWe shipped detection rules covering the AAD Graph recon shapes documented above. Each lives in the [Elastic detection-rules](https://github.com/elastic/detection-rules) repository and runs natively against the parsed `logs-azure.aadgraphactivitylogs-*` data stream.\n\n[Azure AD Graph Access with Suspicious User-Agent](https://github.com/elastic/detection-rules/blob/31d1fa31152c208dfde4feeb6737ca06e030ae53/rules/integrations/azure/discovery_aad_graph_suspicious_user_agent.toml) - KQL match rule. Triggers when AAD Graph receives traffic from user-agent strings matching offensive tooling families (Python, aiohttp, curl, Go-http-client, axios, AzureHound, BloodHound, AADIntenals, etc.). Solid baseline signal because no first-party Microsoft component identifies as any of these, while default tooling does. \n\n![](/assets/images/aad-graph-activity-logs-threat-detection/azuread-graph-suspicious-user-agent.png)\n\n[Azure AD Graph High 4xx Error Ratio from User](https://github.com/elastic/detection-rules/blob/df0396ea4a3b0fb25529444166c36c430941d3a6/rules/integrations/azure/discovery_aad_graph_high_4xx_ratio_by_user.toml) - ES|QL aggregation. Triggers when a single caller produces an unusually high ratio of 4xx responses against AAD Graph in a short window. Recon and brute-force token usage leave a tail of 403s and 404s as tools walk endpoints they don't have permission for, ask for object IDs they don't have, or use a client ID unauthorized for AAD Graph. \n\n![](/assets/images/aad-graph-activity-logs-threat-detection/azure-ad-graph-high-error-ratio-user.png)\n\n[Azure AD Graph Access with Unusual Client and User](https://github.com/elastic/detection-rules/blob/0c15c6c581780d962b33972a8a83263b75fb2d79/rules/integrations/azure/discovery_aad_graph_unusual_client_for_user.toml) - KQL new\\_terms rule, medium severity. Fires when a (calling OAuth client, signed-in user) pair appears on AAD Graph for the first time in the prior 14 days. Catches FOCI swaps, phished refresh tokens redeemed for clients the user doesn't normally use, and stolen tokens used under unfamiliar clients. Ignores known first-party applications that were commonly observed interacting with Azure AD that are backend owned by Microsoft.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/azure-unusual-client-user.png)\n\n[Azure AD Graph Access with Unusual User and ASN](https://github.com/elastic/detection-rules/blob/6f933e04ddbe720898c9ea9c4bae234700a822fe/rules/integrations/azure/initial_access_aad_graph_unusual_asn.toml) - KQL match rule. Excludes the common Microsoft / AWS / GCP / Akamai / Cloudflare ASN organisations and flags AAD Graph traffic originating outside that set. Adversary tooling typically rides on residential ISPs, VPS providers, or anonymising networks that produce a different ASN distribution than legitimate first-party callers. Tunable per tenant by adjusting the excluded ASN list.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/3.png)\n\n[Azure AD Graph Potential Enumeration (ROADrecon)](https://github.com/elastic/detection-rules/blob/4256409e8925a8da016448d1378bc669c2333961/rules/integrations/azure/discovery_aad_graph_roadrecon_aiohttp_enumeration.toml) - ES|QL aggregation, **high severity**. Requires both an _aiohttp_ user-agent and a burst of 500+ AAD Graph requests from a single identity. ROADrecon's _gather_ command uses aiohttp by default and walks every directory object type, so the combination is essentially a tool fingerprint. Higher severity than the generic non-Microsoft UA rule because the additional burst requirement removes the developer-prototype false-positive class.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/graph-potential.png)\n\n[Entra ID OAuth Device Code Sign-in to Azure AD Graph Enumeration](https://github.com/elastic/detection-rules/blob/6a946179e66c7a952e55a33741c160d6bd83f3b8/rules/integrations/azure/credential_access_device_code_signin_aad_graph_enum.toml) - EQL sequence, **high severity**. Joins a successful device-code sign-in to the legacy AAD Graph audience (`00000002-0000-0000-c000-000000000000`) on an unmanaged device with directory enumeration against _graph.windows.net_ by the same user within five minutes. Device-code phishing lands an OAuth token without touching the user's password or MFA, so immediate Graph reads of users, service principals, applications, role assignments, policies, or tenant details under that token are the compromised identity being driven by the attacker. Cross-data-stream sequence removes the single-event false-positive class that the other AAD Graph rules carry.\n\n![](/assets/images/aad-graph-activity-logs-threat-detection/id-oauth.png)\n\n## AAD Graph visibility: what comes next\n\nFor most of the past decade, AAD Graph activity was the telemetry equivalent of dark matter.
