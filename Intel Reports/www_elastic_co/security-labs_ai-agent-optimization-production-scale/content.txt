<p>We run 14 AI agents in the Elastic InfoSec security operations pipeline. They were producing correct verdicts and taking up to 19 large language model (LLM) calls to do work that needed 8, at thousands of input tokens per call. At hundreds of runs per day, that compounds fast. We built a five-step optimization loop to measure, diagnose, and fix exactly this. On the same workload, LLM call counts dropped to 7–9. Every step applies to any <a href="https://www.elastic.co/docs/explore-analyze/ai-features/elastic-agent-builder">Elastic Agent Builder</a> agent, and the instruction-revision step works with any AI assistant your team already uses.</p>
<p>We needed a repeatable process for identifying what was wrong with each agent rather than guessing at prompt edits and hoping the numbers moved in the right direction. The loop works on any Agent Builder agent: fully automated triage pipelines, analyst-led chat assistants, single-purpose enrichment agents, or anything in between.</p>
<p>At Elastic, our InfoSec team operates as Customer Zero. We run the newest versions of <a href="https://www.elastic.co/guide/en/security/current/">Elastic Security</a> and Agent Builder in our production environment, often before they reach general availability, across a globally distributed fleet of laptops, servers, and cloud workloads. We’re the first and most demanding user of every feature we ship. The agents we’re optimizing run against real alerts from our production detection rules, so the numbers matter.</p>
<p>This post focuses on the optimization process itself, which applies to any agent regardless of purpose. The companion posts (<a href="https://www.elastic.co/security-labs/alert-triage-agentic-soc-elastic-workflows">Part 1</a>, <a href="https://www.elastic.co/security-labs/agentic-soc-token-budget-architecture">Part 2</a>) describe the pipeline we apply this methodology to.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="why-agent-optimization-is-different-from-prompt-engineering" class="absolute -top-32"></span>Why agent optimization is different from prompt engineering</h2>
<p><em>Prompt engineering</em> focuses on getting a model to produce the right answer. <em>Agent optimization</em> focuses on getting an agent to produce the right answer consistently, thousands of times, at a predictable cost. These are different problems that require different approaches.</p>
<p>The dominant cost driver in an agentic workflow isn&#x27;t the length of the system prompt. It&#x27;s the number of LLM calls the agent makes to complete its work. Cost scales with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls × input_tokens_per_call</code>, and input tokens per call grow as the conversation accumulates more context. In our own measurements, average input tokens per LLM call ranged from roughly 10,000 for narrowly scoped specialized agents to roughly 36,000 for skills-based agents with broader toolsets. The conversation history carrying forward each LLM call was the dominant weight, regardless of system prompt size. An agent that makes six extra LLM calls to finish work it could have completed earlier isn&#x27;t slightly more expensive; trimming the prompt by a third wouldn&#x27;t recover the same cost.</p>
<blockquote>
<p><strong>A note on terminology.</strong> The Agent Builder consumption API exposes two related metrics: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">round_count</code> (the number of user-agent turns) and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls</code> (the total LLM API invocations across those turns). For automated workflow agents that handle one alert per invocation, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">round_count</code> is always 1, so the cost lever is <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls</code>. For analyst-led interactive agents where a conversation can run multiple messages, both matter. This post uses &quot;LLM calls&quot; as the primary unit, except when quoting verbatim from a system prompt that uses &quot;rounds.&quot;</p>
</blockquote>
<p>Three things are worth optimizing separately:</p>
<ul>
<li><strong>LLM call count:</strong> The single biggest factor to reduce. An agent that makes 14 LLM calls when 8 are sufficient costs roughly 75% more per run, before considering context-growth overhead on the later calls.</li>
<li><strong>Tool-call discipline:</strong> Redundant queries, schema-exploration calls, and requerying data that was already retrieved earlier in the conversation are all avoidable once you see them in a trace.</li>
<li><strong>Behavioral consistency:</strong> The same input should produce the same investigation path on every run. High variance in token count across similar inputs is a signal that the agent is deciding what to do at runtime rather than following a prescribed methodology.</li>
</ul>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="the-five-step-agent-optimization-loop" class="absolute -top-32"></span>The five-step agent optimization loop</h2>
<p>The process has five steps. Each is described in its own section below.</p>
<ol>
<li><strong>Measure the baseline:</strong> Capture LLM call count and token usage for the agent in its current state before changing anything.</li>
<li><strong>Capture representative test conversations:</strong> Run the agent against a curated set of inputs under your own credentials so the full conversation bodies are available for analysis.</li>
<li><strong>Analyze conversation traces for inefficiency patterns:</strong> Compare the agent&#x27;s actual behavior in those conversations against a checklist of known cost drivers.</li>
<li><strong>Revise and verify:</strong> Use the analysis to produce revised instructions, apply them in a QA environment, and measure again to confirm improvement.</li>
<li><strong>Monitor for drift:</strong> Run the measurement step on a schedule in production so emerging inefficiencies surface before they grow expensive.</li>
</ol>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="step-1-measure-the-baseline" class="absolute -top-32"></span>Step 1: Measure the baseline</h2>
<p>Before touching the prompt, record how the agent is performing today. The <a href="https://www.elastic.co/docs/api/doc/kibana/operation/operation-post-agent-builder-agents-agent-id-consumption">Agent Builder consumption endpoint</a> returns per-conversation token usage, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">round_count</code> for a given agent, across all users in the space:</p>
<pre><code>curl -X POST \
  -H &quot;Authorization: ApiKey ${KIBANA_API_KEY}&quot; \
  -H &#x27;kbn-xsrf: true&#x27; \
  -H &#x27;Content-Type: application/json&#x27; \
  &quot;${KIBANA_URL}/s/${KIBANA_SPACE}/api/agent_builder/agents/${AGENT_ID}/consumption&quot; \
  -d &#x27;{
    &quot;size&quot;: 100,
    &quot;sort_field&quot;: &quot;updated_at&quot;,
    &quot;sort_order&quot;: &quot;desc&quot;
  }&#x27;</code></pre>
<p>Replace <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">${KIBANA_URL}</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">${KIBANA_API_KEY}</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">${KIBANA_SPACE}</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">${AGENT_ID}</code> with your Kibana URL, API key, space name, and target agent ID.</p>
<p>The API uses cursor-based pagination. If you have more than 100 conversations in the window, pass the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">search_after</code> value from each response into the next request body until the results array is empty.</p>
<p>Four things to track:</p>
<ul>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls</code>: Total LLM API invocations across the conversation. <strong>For automated agents, this is the primary cost lever.</strong> Each LLM call pays the full and growing conversation-history cost.</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">round_count</code>: The number of user-agent turns. For automated workflow agents that handle one alert per invocation, this is always 1. For analyst-led interactive agents, it grows with the conversation; watch it for those agents.</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">token_usage.total_tokens</code>: The total cost for that conversation. Record the median across conversations, not the mean. A single runaway conversation on an unusual alert can skew the mean significantly.</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Run-to-run variance</code>: If similar inputs produce a 2–3× spread in token counts, the agent isn&#x27;t following a consistent investigation path. Variance is as meaningful a signal as the median.</li>
</ul>
<p>Capture these numbers for a representative time window (the last 14 days is usually sufficient for high-volume agents) before you make any changes. Without a baseline, you cannot tell whether a subsequent prompt edit helped or hurt.</p>
<blockquote>
<p><strong>Note:</strong> The consumption API aggregates across all users in the space, so it reflects real-world usage across analysts and automated workflows alike. The individual conversation bodies are per-user access-controlled (see Step 2), but the token statistics are fleet-wide.</p>
</blockquote>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="step-2-capture-representative-test-conversations" class="absolute -top-32"></span>Step 2: Capture representative test conversations</h2>
<p>Each conversation in Agent Builder is readable only by the user who created it. A request for another user&#x27;s conversation returns 404, regardless of role. This means conversations that analysts generate in the Kibana UI under their own credentials aren&#x27;t available to optimization scripts running under a separate API key.</p>
<p>The solution is to generate test conversations under your own credentials before running the trace analysis. Use the <a href="https://www.elastic.co/docs/api/doc/kibana/operation/operation-post-agent-builder-converse">Converse API</a> to submit test inputs to the agent:</p>
<pre><code>curl -X POST \
  -H &quot;Authorization: ApiKey ${KIBANA_API_KEY}&quot; \
  -H &#x27;kbn-xsrf: true&#x27; \
  -H &#x27;Content-Type: application/json&#x27; \
  &quot;${KIBANA_URL}/s/${KIBANA_SPACE}/api/agent_builder/converse&quot; \
  -d &#x27;{
    &quot;agent_id&quot;: &quot;&lt;your_agent_id&gt;&quot;,
    &quot;input&quot;: &quot;&lt;representative test input&gt;&quot;
  }&#x27;</code></pre>
<p>The response includes a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">conversation_id</code>. Poll <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">GET /api/agent_builder/conversations/{conversation_id}</code> until the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">status</code> field returns <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">completed</code>, and then retrieve the full conversation for analysis.</p>
<p>A few guidelines for selecting test inputs:</p>
<ul>
<li>Cover the distinct input types your agent handles. For a triage agent, include an endpoint alert, a cloud alert, and a software as a service (SaaS) alert. For a domain-specific agent, cover the alert variants it handles most often.</li>
<li>Include at least one input where you suspect the current prompt performs poorly (where it runs long, misses steps, or produces variable output). That&#x27;s the signal the analysis step needs.</li>
<li>Avoid inputs that your environment closes or suppresses before the agent runs. They produce short, uninformative conversations that don&#x27;t reflect the agent&#x27;s actual investigation behavior.</li>
</ul>
<p>Aim for two to four conversations per agent before the analysis step. You don&#x27;t need a large sample. You&#x27;re looking for patterns in behavior, not statistical significance.</p>

<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="a-concrete-example-textual-budgets-versus-stopping-checklists" class="absolute -top-32"></span>A concrete example: Textual budgets versus stopping checklists</h3>
<p>One of the most common and fixable issues is an ineffective budget instruction. Before we applied this loop to one of our forensics agents, the system prompt included the following instruction:</p>
<pre><code>Target 5–10 rounds for this investigation. Hard cap: 12 rounds.</code></pre>
<p>In practice, the agent consistently made 14–19 LLM calls on the same class of alert. It found another thing to check at the end of every LLM call, each one individually justifiable. The textual budget was not actionable. There was no mechanism to stop.</p>
<p>We replaced it with a concrete stopping checklist:</p>
<pre><code>Complete your investigation in this order:
1. Retrieve process context for the alerting process
2. Trace one hop of process ancestry
3. Run the entity behavioral correlation check
After completing these three steps, emit your verdict. Do not continue investigating remaining hypotheses.</code></pre>
<p>The specific steps will differ for every agent. These are ours. The pattern is the same: a named, ordered list that ends with an explicit &quot;emit verdict&quot; instruction.</p>
<p>The same class of alert that previously took 14-19 LLM calls came in at 7-9 after this change. The prompt didn&#x27;t get shorter; the stopping criterion got specific enough that the agent could follow it.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="a-second-pattern-redundant-queries-against-enrichment-context" class="absolute -top-32"></span>A second pattern: Redundant queries against enrichment context</h3>
<p>A related issue appears in agents that receive a pre-enrichment block at the start of a conversation (a workflow step that injects Elasticsearch Query Language [ES|QL] query results before the agent runs). The agent frequently requeries the same entities in subsequent LLM calls because the prompt doesn&#x27;t say not to.</p>
<p>Adding one explicit rule eliminates this: <em>&quot;Do not requery any entity or field that is already present in the enrichment context you received at the start of this conversation. Reference that data in your reasoning; do not call a tool to retrieve it again.&quot;</em></p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="auditing-the-instructions-for-ambiguity-and-contradictions" class="absolute -top-32"></span>Auditing the instructions for ambiguity and contradictions</h3>
<p>Beyond trace analysis, it&#x27;s also worth reviewing the prompt itself for structural issues that don&#x27;t always show up in conversation traces:</p>
<ul>
<li>Logical contradictions between instructions.</li>
<li>Ambiguous wording that leaves the agent guessing at runtime.</li>
<li>Excessive nested conditions that increase cognitive load.</li>
<li>Missing coverage for error cases (<em>&quot;What happens if this step fails?&quot;</em>).</li>
</ul>
<p>These issues often explain why a prompt behaves inconsistently even when the conversation trace looks normal. Reading the prompt with those specific questions in mind (<em>&quot;Where is this ambiguous?&quot;</em>, <em>&quot;Does any instruction contradict another?&quot;</em>) surfaces a different class of problems than trace analysis does.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="step-4-revise-and-verify" class="absolute -top-32"></span>Step 4: Revise and verify</h2>
<p>Two options exist for producing revised instructions: write the changes directly or use an AI assistant to analyze and rewrite them.</p>
<ol>
<li>
<p><strong>Write the changes directly.</strong> If the trace analysis points to a small number of clear issues (a missing stopping criterion, a redundant query instruction, a field name typo), edit the system prompt directly. Small, targeted changes are easy to review and understand. They&#x27;re also easier to isolate as the cause if something regresses.</p>
</li>
<li>
<p><strong>Use an AI assistant to analyze and rewrite.</strong> For agents with more complex issues, or where the trace suggests several overlapping problems, pairing with an AI coding assistant can produce a more thorough revision. What matters most is giving the assistant the right inputs: the current instructions, a compact conversation summary, and the optimization guidelines.</p>
<p>The compact summary doesn&#x27;t need to be the full raw conversation JSON. Extract the number of LLM calls, the tool names and call counts, the approximate payload size of each result, any error messages, and short excerpts from the agent&#x27;s reasoning steps where those are visible. This keeps the assistant&#x27;s context small and focused on behavioral patterns rather than raw data.</p>
<p>Here&#x27;s the analyzer prompt template we use at Elastic InfoSec, adapted for any AI coding assistant or chat interface:</p>
</li>
</ol>
<pre><code>You are analyzing an AI agent&#x27;s system prompt and recent conversation behavior to identify
inefficiencies and produce a revised version of the instructions.

You will receive:
1. The agent&#x27;s current instructions
2. A compact conversation summary (LLM calls, tool calls, payload sizes, errors, reasoning excerpts)

Your task: Identify inefficiencies based on the patterns below, then output a full revised
version of the agent&#x27;s instructions. Output only the revised instructions: no issue list,
no commentary, no wrapper text. The output should be ready to replace the current instructions.

---

Optimization patterns to apply:

1. Excessive data retrieval: If the agent retrieves full documents but uses only 1–2 fields,
   add explicit field projections (e.g. KEEP clauses in ES|QL) so only the needed fields return.

2. Redundant lookups: If data retrieved in an early step is re-queried later, add an explicit
   rule: &quot;Do not re-query [entity]: use the [entity] value from the earlier step.&quot;

3. Post-filtering waste: If many records are fetched then filtered in text, move the filter
   into the query.

4. Schema exploration: If the agent calls get_mapping or runs a LIMIT 1 query to discover
   available fields, list those fields directly in the instructions so discovery is unnecessary.

5. Textual call budgets: If the instructions say &quot;complete in N rounds&quot; or &quot;target N–M rounds&quot;
   (or any vague numeric budget), replace with a named, ordered list of steps to take before
   emitting a final answer.

6. Missing final answer: If conversations end without a verdict or conclusion, add near the top
   of the instructions: &quot;After completing your investigation, emit a final answer even if some
   hypotheses remain uninvestigated.&quot;

7. Time window defaults: If queries use a long default range when only recent data is needed,
   specify the window: &quot;Restrict [query type] to the last [N] hours unless instructed otherwise.&quot;

8. Case-sensitive comparisons: If queries fail on case mismatches, add: &quot;Use case-insensitive
   comparisons for all name and string fields.&quot;

9. High-volume entity noise: If the agent traces ancestry or queries raw events for known
   high-volume processes (common shells, IDE tools, build agents, system services), add a named
   skip list with instruction to log and proceed rather than query.

10. Missing output constraints: If the final output includes raw identifiers (UUIDs, entity IDs,
    internal index names), add a rule specifying human-readable labels in the final response.

---

Current instructions:
[PASTE CURRENT AGENT INSTRUCTIONS HERE]

Conversation summary:
[PASTE COMPACT SUMMARY HERE]</code></pre>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="how-to-verify-an-ai-agent-optimization-actually-worked" class="absolute -top-32"></span>How to verify an AI agent optimization actually worked</h3>
<p>Apply the revised prompt in a QA environment (not production) and rerun the same test inputs from Step 2. Use the consumption endpoint with a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">--since</code> filter on the post-change window, and compare median <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">total_tokens</code> against your Step 1 baseline.</p>
<p>Two things to check before promoting to production:</p>
<ol>
<li>The target metrics improved. LLM call count dropped, token count dropped, or token variance narrowed, whichever pattern you were targeting.</li>
<li>The output quality held. The agent still reaches a coherent conclusion, covers the expected investigation steps, and doesn’t skip something it was previously doing correctly.</li>
</ol>
<p>If the output quality regressed while the metrics improved, the revised instructions are too constraining. The stopping checklist is likely cutting off necessary steps. Loosen it and retest before deploying.</p>
<blockquote>
<p><strong>Note:</strong> See the <a href="https://www.elastic.co/docs/explore-analyze/ai-features/elastic-agent-builder">Agent Builder documentation</a> for version-specific feature availability, including the consumption API.</p>
</blockquote>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="step-5-monitor-for-drift" class="absolute -top-32"></span>Step 5: Monitor for drift</h2>
<p>Deploying an optimized prompt isn&#x27;t the end of the process. The inputs an agent receives in the real world evolve. New detection rules fire, data sources change format, and an agent that was well tuned for last quarter&#x27;s alert mix can drift as the environment around it changes. The same measurement step that established the baseline becomes the monitoring step; run it on a schedule.</p>
<p>Metrics to watch after a prompt change:</p>
<div class="table-container"><table style="width:100%;table-layout:fixed;word-wrap:break-word"><thead><tr><th>Metric</th><th>Threshold to investigate</th><th>What it usually means</th></tr></thead><tbody><tr><td><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">avg_total</code> tokens per conversation</td><td>&gt;20% above your baseline</td><td>New tool calls or growing context injections from upstream workflow changes</td></tr><tr><td><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">avg_llm_calls</code> per conversation</td><td>Rising steadily over 1–2 weeks</td><td>The agent is entering reasoning loops or spending more LLM calls deliberating</td></tr><tr><td><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">max_total</code> spike on a single conversation</td><td>Single outlier well above the median</td><td>One alert type is triggering a runaway path; pull that conversation and apply Step 3 to it</td></tr><tr><td><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">llm_calls</code> variance</td><td>2–3× spread reappears after being tight</td><td>New input variation the current stopping criterion doesn’t handle</td></tr></tbody></table></div>
<p>A useful pattern for identifying the source of a spike: Run the consumption endpoint with a short <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">--since</code> window covering only the elevated period, and then retrieve and summarize the top-N most expensive conversations from that window. One alert type usually dominates. Once you identify the pattern, you have everything you need for another pass through the loop.</p>
<p>A drift signal isn’t a failure. It means new inputs have surfaced a case that the current instructions don’t handle well. Return to Step 2, generate test conversations for the new case type, and run the loop again. Each pass through the loop narrows the gap between what the prompt expects and what the real world sends.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="the-four-part-discipline-behind-agent-optimization-at-scale" class="absolute -top-32"></span>The four-part discipline behind agent optimization at scale</h2>
<p>The five-step loop is the process we run across all 14 Agent Builder agents in the Elastic InfoSec fleet. It isn&#x27;t a one-time optimization exercise. It’s closer to a maintenance discipline. Each time a detection rule changes significantly or a new class of alert enters high volume, the agents that handle it are candidates for another pass.</p>
<p>The process isn’t specific to any use case, architecture, or AI model. The core discipline has four parts:</p>
<ol>
<li>Measure before you change anything.</li>
<li>Analyze the actual conversation behavior rather than reading the instructions in isolation.</li>
<li>Verify improvements before deploying them.</li>
<li>Watch the metrics after.</li>
</ol>
<p>Those habits apply to any agent that runs at production volume.</p>

An agent that makes six extra LLM calls to finish work it could have completed earlier isn't slightly more expensive; trimming the prompt by a third wouldn't recover the same cost.\n\n\u003e **A note on terminology.** The Agent Builder consumption API exposes two related metrics: `round_count` (the number of user-agent turns) and `llm_calls` (the total LLM API invocations across those turns). For automated workflow agents that handle one alert per invocation, `round_count` is always 1, so the cost lever is `llm_calls`. For analyst-led interactive agents where a conversation can run multiple messages, both matter. This post uses \"LLM calls\" as the primary unit, except when quoting verbatim from a system prompt that uses \"rounds.\"\n\nThree things are worth optimizing separately:\n\n- **LLM call count:** The single biggest factor to reduce. An agent that makes 14 LLM calls when 8 are sufficient costs roughly 75% more per run, before considering context-growth overhead on the later calls.  \n- **Tool-call discipline:** Redundant queries, schema-exploration calls, and requerying data that was already retrieved earlier in the conversation are all avoidable once you see them in a trace.  \n- **Behavioral consistency:** The same input should produce the same investigation path on every run. High variance in token count across similar inputs is a signal that the agent is deciding what to do at runtime rather than following a prescribed methodology.\n\n## The five-step agent optimization loop\n\nThe process has five steps. Each is described in its own section below.\n\n1. **Measure the baseline:** Capture LLM call count and token usage for the agent in its current state before changing anything.  \n2. **Capture representative test conversations:** Run the agent against a curated set of inputs under your own credentials so the full conversation bodies are available for analysis.  \n3. **Analyze conversation traces for inefficiency patterns:** Compare the agent's actual behavior in those conversations against a checklist of known cost drivers.  \n4. **Revise and verify:** Use the analysis to produce revised instructions, apply them in a QA environment, and measure again to confirm improvement.  \n5. **Monitor for drift:** Run the measurement step on a schedule in production so emerging inefficiencies surface before they grow expensive.\n\n## Step 1: Measure the baseline\n\nBefore touching the prompt, record how the agent is performing today. The [Agent Builder consumption endpoint](https://www.elastic.co/docs/api/doc/kibana/operation/operation-post-agent-builder-agents-agent-id-consumption) returns per-conversation token usage, `llm_calls`, and `round_count` for a given agent, across all users in the space:\n\n```shell\ncurl -X POST \\\n  -H \"Authorization: ApiKey ${KIBANA_API_KEY}\" \\\n  -H 'kbn-xsrf: true' \\\n  -H 'Content-Type: application/json' \\\n  \"${KIBANA_URL}/s/${KIBANA_SPACE}/api/agent_builder/agents/${AGENT_ID}/consumption\" \\\n  -d '{\n    \"size\": 100,\n    \"sort_field\": \"updated_at\",\n    \"sort_order\": \"desc\"\n  }'\n```\n\nReplace `${KIBANA_URL}`, `${KIBANA_API_KEY}`, `${KIBANA_SPACE}`, and `${AGENT_ID}` with your Kibana URL, API key, space name, and target agent ID.\n\nThe API uses cursor-based pagination. If you have more than 100 conversations in the window, pass the `search_after` value from each response into the next request body until the results array is empty.\n\nFour things to track:\n\n- `llm_calls`: Total LLM API invocations across the conversation. **For automated agents, this is the primary cost lever.** Each LLM call pays the full and growing conversation-history cost.  \n- `round_count`: The number of user-agent turns. For automated workflow agents that handle one alert per invocation, this is always 1\\. For analyst-led interactive agents, it grows with the conversation; watch it for those agents.  \n- `token_usage.total_tokens`: The total cost for that conversation. Record the median across conversations, not the mean. A single runaway conversation on an unusual alert can skew the mean significantly.  \n- `Run-to-run variance`: If similar inputs produce a 2–3× spread in token counts, the agent isn't following a consistent investigation path. Variance is as meaningful a signal as the median.\n\nCapture these numbers for a representative time window (the last 14 days is usually sufficient for high-volume agents) before you make any changes. Without a baseline, you cannot tell whether a subsequent prompt edit helped or hurt.\n\n\u003e **Note:** The consumption API aggregates across all users in the space, so it reflects real-world usage across analysts and automated workflows alike. The individual conversation bodies are per-user access-controlled (see Step 2), but the token statistics are fleet-wide.\n\n## Step 2: Capture representative test conversations\n\nEach conversation in Agent Builder is readable only by the user who created it. A request for another user's conversation returns 404, regardless of role. This means conversations that analysts generate in the Kibana UI under their own credentials aren't available to optimization scripts running under a separate API key.\n\nThe solution is to generate test conversations under your own credentials before running the trace analysis. Use the [Converse API](https://www.elastic.co/docs/api/doc/kibana/operation/operation-post-agent-builder-converse) to submit test inputs to the agent:\n\n```shell\ncurl -X POST \\\n  -H \"Authorization: ApiKey ${KIBANA_API_KEY}\" \\\n  -H 'kbn-xsrf: true' \\\n  -H 'Content-Type: application/json' \\\n  \"${KIBANA_URL}/s/${KIBANA_SPACE}/api/agent_builder/converse\" \\\n  -d '{\n    \"agent_id\": \"\u003cyour_agent_id\u003e\",\n    \"input\": \"\u003crepresentative test input\u003e\"\n  }'\n```\nThe response includes a `conversation_id`. Poll `GET /api/agent_builder/conversations/{conversation_id}` until the `status` field returns `completed`, and then retrieve the full conversation for analysis.\n\nA few guidelines for selecting test inputs:\n\n- Cover the distinct input types your agent handles. For a triage agent, include an endpoint alert, a cloud alert, and a software as a service (SaaS) alert. For a domain-specific agent, cover the alert variants it handles most often.  \n- Include at least one input where you suspect the current prompt performs poorly (where it runs long, misses steps, or produces variable output). That's the signal the analysis step needs.  \n- Avoid inputs that your environment closes or suppresses before the agent runs. They produce short, uninformative conversations that don't reflect the agent's actual investigation behavior.\n\nAim for two to four conversations per agent before the analysis step. You don't need a large sample. You're looking for patterns in behavior, not statistical significance.\n\n| Symptom in trace | Likely cause | Prompt-level fix |\n|---|---|---|\n| `llm_calls` consistently \u003e 12 | No concrete stopping criterion | Replace text budget with a specific checklist: \"After completing [named steps], emit your verdict regardless of remaining hypotheses\" |\n| Same tool called 2–3× in one investigation | Agent requerying to \"confirm\" results | \"Never requery a tool whose result is already present in the conversation\" |\n| Most LLM calls produce no tool action | Excessive reasoning-only LLM calls | Specify what the agent should do next at each stage rather than leaving it to deliberate |\n| Returns full document, uses 1–2 fields | Missing field projection | \"You MUST use `KEEP field1, field2` in all ES|QL queries on index X\" |\n| Calls `get_mapping` or runs `LIMIT 1` first | Agent exploring schema before working | List the relevant fields in the prompt directly so discovery is unnecessary |\n| Queries use a long default time range | Default range is too wide for the task | Specify the window in the instruction: \"Restrict login history to the last 24 hours unless instructed otherwise\" |\n| Query fails with case-mismatch error | Case-sensitive field comparison | \"Use `LOWER(field) == \\\"value\\\"` for all name comparisons\" |\n| `verification_exception` on query | Field used doesn't exist in that index | Add an explicit field-to-index mapping in the prompt: \"Do not use `field_x` in queries against `index_y`\" |\n| Ancestry traces on high-event processes | No skip list for noisy processes | List processes to log and skip (shells, integrated development environment [IDEs], system daemons, build tools) rather than trace further |\n| Conversation ends without a final answer | Agent hit an implicit LLM call limit | Add near the top of the prompt: \"Emit a verdict at the end of your investigation even if some hypotheses remain\" |\n| High `input_tokens` on the first LLM call | Pre-enrichment context injected into the first message | \"Do not requery any entity or field already present in the context you received. Cite it; do not restate it.\" |\n\n### A concrete example: Textual budgets versus stopping checklists\n\nOne of the most common and fixable issues is an ineffective budget instruction. Before we applied this loop to one of our forensics agents, the system prompt included the following instruction:\n\n```\nTarget 5–10 rounds for this investigation. Hard cap: 12 rounds.\n```\n\nIn practice, the agent consistently made 14–19 LLM calls on the same class of alert. It found another thing to check at the end of every LLM call, each one individually justifiable. The textual budget was not actionable. There was no mechanism to stop.\n\nWe replaced it with a concrete stopping checklist:\n\n```\nComplete your investigation in this order:\n1. Retrieve process context for the alerting process\n2. Trace one hop of process ancestry\n3. Run the entity behavioral correlation check\nAfter completing these three steps, emit your verdict. Do not continue investigating remaining hypotheses.\n```\nThe specific steps will differ for every agent. These are ours. The pattern is the same: a named, ordered list that ends with an explicit \"emit verdict\" instruction.\n\nThe same class of alert that previously took 14-19 LLM calls came in at 7-9 after this change. The prompt didn't get shorter; the stopping criterion got specific enough that the agent could follow it.\n\n### A second pattern: Redundant queries against enrichment context\n\nA related issue appears in agents that receive a pre-enrichment block at the start of a conversation (a workflow step that injects Elasticsearch Query Language \\[ES|QL\\] query results before the agent runs). The agent frequently requeries the same entities in subsequent LLM calls because the prompt doesn't say not to.\n\nAdding one explicit rule eliminates this: *\"Do not requery any entity or field that is already present in the enrichment context you received at the start of this conversation. Reference that data in your reasoning; do not call a tool to retrieve it again.\"*\n\n### Auditing the instructions for ambiguity and contradictions\n\nBeyond trace analysis, it's also worth reviewing the prompt itself for structural issues that don't always show up in conversation traces:\n\n- Logical contradictions between instructions.  \n- Ambiguous wording that leaves the agent guessing at runtime.  \n- Excessive nested conditions that increase cognitive load.  \n- Missing coverage for error cases (*\"What happens if this step fails?\"*).\n\nThese issues often explain why a prompt behaves inconsistently even when the conversation trace looks normal. Reading the prompt with those specific questions in mind (*\"Where is this ambiguous?\"*, *\"Does any instruction contradict another?\"*) surfaces a different class of problems than trace analysis does.\n\n## Step 4: Revise and verify\n\nTwo options exist for producing revised instructions: write the changes directly or use an AI assistant to analyze and rewrite them.\n\n1. **Write the changes directly.** If the trace analysis points to a small number of clear issues (a missing stopping criterion, a redundant query instruction, a field name typo), edit the system prompt directly. Small, targeted changes are easy to review and understand. They're also easier to isolate as the cause if something regresses.  \n     \n2. **Use an AI assistant to analyze and rewrite.** For agents with more complex issues, or where the trace suggests several overlapping problems, pairing with an AI coding assistant can produce a more thorough revision. What matters most is giving the assistant the right inputs: the current instructions, a compact conversation summary, and the optimization guidelines.\n\n   The compact summary doesn't need to be the full raw conversation JSON. Extract the number of LLM calls, the tool names and call counts, the approximate payload size of each result, any error messages, and short excerpts from the agent's reasoning steps where those are visible. This keeps the assistant's context small and focused on behavioral patterns rather than raw data.\n\n   Here's the analyzer prompt template we use at Elastic InfoSec, adapted for any AI coding assistant or chat interface:\n\n```\nYou are analyzing an AI agent's system prompt and recent conversation behavior to identify\ninefficiencies and produce a revised version of the instructions.\n\nYou will receive:\n1. High-volume entity noise: If the agent traces ancestry or queries raw events for known\n   high-volume processes (common shells, IDE tools, build agents, system services), add a named\n   skip list with instruction to log and proceed rather than query.\n\n10. The target metrics improved. LLM call count dropped, token count dropped, or token variance narrowed, whichever pattern you were targeting.\n2. The output quality held. The agent still reaches a coherent conclusion, covers the expected investigation steps, and doesn’t skip something it was previously doing correctly.\n\nIf the output quality regressed while the metrics improved, the revised instructions are too constraining. The stopping checklist is likely cutting off necessary steps. It means new inputs have surfaced a case that the current instructions don’t handle well. Return to Step 2, generate test conversations for the new case type, and run the loop again. Each pass through the loop narrows the gap between what the prompt expects and what the real world sends.\n\n## The four-part discipline behind agent optimization at scale\n\nThe five-step loop is the process we run across all 14 Agent Builder agents in the Elastic InfoSec fleet.
