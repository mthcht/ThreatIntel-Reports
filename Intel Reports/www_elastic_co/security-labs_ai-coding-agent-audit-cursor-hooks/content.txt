lg:col-span-3"><div class="prose lg:prose-lg prose-invert w-full article-content"><div><p>We gave hundreds of developers an AI agent that can run shell commands, edit files, and call <a href="https://modelcontextprotocol.io">Model Context Protocol (MCP)</a> servers on their laptops, then realized we had no record of what it actually did. So we built one. One 280-line dependency-free bash script, fired by Cursor&#x27;s hooks, records every tool call as JSONL, and the <a href="https://www.elastic.co/docs/reference/fleet">Elastic Agent</a> already on each endpoint ships it to Elasticsearch. Since the May rollout we have logged over 13 million tool-call events from more than 1,100 machines. A question like &quot;which hosts ran an agent that read a .pem file last week?&quot; is one <a href="https://www.elastic.co/docs/reference/query-languages/esql">ES|QL</a> query. The worked example here is Cursor end to end, but the pattern works with any agent that offers lifecycle hooks.</p>
<p></p>
<p>By the end of this post, you will have:</p>
<ul>
<li>A hook script that logs every Cursor tool call, from both the IDE and the CLI.</li>
<li>The hook configuration, including the two deployment gotchas that cost us the most time.</li>
<li>A way to deliver the collector to machines your device management cannot reach.</li>
<li>an Elastic Agent filestream integration that parses the logs into structured fields</li>
<li>ES|QL queries you can run to hunt across agent activity.</li>
<li>The hardening and privacy decisions we made before rolling this out to the whole company.</li>
</ul>
<p>Everything here works on the current 9.x release of the Elastic Stack.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="why-ai-coding-agent-activity-is-a-blind-spot" class="absolute -top-32"></span>Why AI coding agent activity is a blind spot</h2>
<p>A coding agent with shell access is an automated operator on the endpoint. It runs <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">curl</code>, installs packages, edits configuration, and reads whatever files its task seems to require. From the point of view of endpoint detection and response (EDR) tooling, this is indistinguishable from the developer doing the same things, because it happens under the developer&#x27;s account inside processes the developer launched.</p>
<p>That ambiguity matters in three situations:</p>
<ol>
<li>During an incident, you need to know whether a command was typed by a person or generated by a model that may have been steered by a poisoned README or a malicious MCP server (think of <a href="https://attack.mitre.org/techniques/T1059/">T1059, Command and Scripting Interpreter</a>, with the model as the interpreter).</li>
<li>uring threat hunting, you want to ask &quot;which machines ran an agent that read a file matching <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">*.pem</code> last week?&quot; and get an answer.</li>
<li>For governance, you need an inventory of which MCP servers your engineers actually connect to, because each one is a third party with tool-level access to a developer conversation.</li>
</ol>
<p>The industry has converged on inventory as half of this problem: several major EDR and XDR vendors now ship Shadow AI discovery to find AI tools on endpoints. Inventory shows which machines have Cursor installed. Hooks record what Cursor does once it runs.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="what-are-agent-hooks" class="absolute -top-32"></span>What are agent hooks?</h2>
<p>Cursor can invoke an external program at defined points in the agent loop: when a session starts, before a shell command runs, after a file edit, when an MCP tool is called, when a sub-agent spawns. The agent writes a JSON payload describing the event to the program&#x27;s stdin. For some events, the program&#x27;s stdout response decides whether the action proceeds. Cursor is not alone in offering hooks like these: Claude Code exposes an equivalent set, and we will walk that side in a follow-up post. Here we stay on Cursor.</p>
<p>The stdout response property means hooks can be a control point. We deliberately chose to use them as a sensor instead. Our script approves everything and records everything, which is the same trade a flight recorder makes: it never flies the plane, but after something goes wrong it is the only honest witness. A blocking hook is one where Cursor pauses the action and waits for the hook&#x27;s stdout response before proceeding: the agent won&#x27;t run the shell command / call the MCP tool / read the file / spawn the sub-agent until the hook answers allow, deny, or ask. Blocking was tempting, and we may add targeted controls later, but for a first deployment the goal was visibility without breaking anyone&#x27;s workflow. An agent rollout that slows developers down gets uninstalled.</p>

<h2 class="font-bold text-2xl md:text-4xl relative"><span id="how-does-the-hook-collector-script-work" class="absolute -top-32"></span>How does the hook collector script work?</h2>
<p>The full script is about 280 lines of bash with no dependencies, available in the <a href="https://github.com/elastic/elasticsearch-labs/tree/main/supporting-blog-content/security-labs/ai-hooks-collector-scripts">elastic/elasticsearch-labs repository</a> along with a PowerShell port for Windows (which will be shared at a later stage). It reads one JSON payload from stdin, extracts the fields we care about, and appends one line to a JSONL formatted date-rotated log file. Three design decisions shaped it.</p>
<p><strong>Answer blocking hooks first.</strong> A sensor-only collector still registers the blocking events, because they carry the richest telemetry: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">beforeShellExecution</code> captures the command before it runs, and `<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">beforeReadFil</code>e` is the only read event Cursor offers. Registering them means Cursor pauses those actions and waits for a verdict, whether or not you ever intend to say no. The script therefore answers before it does anything else. If it crashed after the response was sent, nothing would hang; if it crashed before, the agent could stall on filesystem errors that have nothing to do with the user. So the very first thing the script does after reading stdin is approve (trimmed here to the Cursor events):</p>
<pre><code># Respond to blocking hooks before any filesystem work, so a
# logging failure can never hold up the agent.
if [[ &quot;$INPUT&quot; == *&#x27;&quot;hook_event_name&quot;&#x27;*&#x27;&quot;beforeMCPExecution&quot;&#x27;* ]] || \
   [[ &quot;$INPUT&quot; == *&#x27;&quot;hook_event_name&quot;&#x27;*&#x27;&quot;beforeShellExecution&quot;&#x27;* ]] || \
   [[ &quot;$INPUT&quot; == *&#x27;&quot;hook_event_name&quot;&#x27;*&#x27;&quot;beforeReadFile&quot;&#x27;* ]] || \
   [[ &quot;$INPUT&quot; == *&#x27;&quot;hook_event_name&quot;&#x27;*&#x27;&quot;subagentStart&quot;&#x27;* ]]; then
  echo &#x27;{&quot;permission&quot;:&quot;allow&quot;}&#x27;
fi</code></pre>
<p>In Cursor&#x27;s response schema, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">allow</code> proceeds, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">deny</code> blocks, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ask</code> forces a confirmation prompt. Cursor also fails open by default: if the hook process dies without responding, the action proceeds, and a hook that should block on failure can opt into <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">failClosed: true</code> instead. The combination means the worst case of a collector bug is a missing log line rather than a blocked engineer.</p>
<p><strong>Detect which surface fired the hook.</strong> By surface we mean the client the agent ran in: the IDE, the CLI, or a remote session. A single log stream stays useful only if you can tell them apart, and the environment gives it away: the Cursor IDE is a VS Code fork, so hook processes it spawns inherit VS Code environment variables, while the CLI sets none of them (trimmed to the Cursor branch; the full script uses the same technique to tag other agents&#x27; surfaces)</p>
<pre><code>if [[ &quot;$INPUT&quot; == *&#x27;&quot;cursor_version&quot;&#x27;* ]] || [ -n &quot;${CURSOR_VERSION:-}&quot; ]; then
  AGENT=&quot;cursor&quot;
  if [ &quot;${CURSOR_CODE_REMOTE:-}&quot; = &quot;true&quot; ]; then
    IDE=&quot;remote&quot;
  elif [ -n &quot;${VSCODE_PID:-}&quot; ] || [ -n &quot;${VSCODE_CWD:-}&quot; ] || [ -n &quot;${VSCODE_IPC_HOOK:-}&quot; ]; then
    IDE=&quot;cursor&quot;      # the IDE is a VS Code fork; its env vars leak through
  else
    IDE=&quot;cursor-cli&quot;  # the CLI sets none of them
  fi
fi</code></pre>
<p><strong>Promote the fields you will query.</strong> Each log entry carries the original hook payload under a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">raw</code> key, plus identity (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">user</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">email</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">host</code>) and a set of top-level fields extracted from the payload: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hook_event_name</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tool_name</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">command</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file_path</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">mcp_server</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">model</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">session_id</code>, and duration. A finished entry looks like this:</p>
<pre><code>{
  &quot;timestamp&quot;: &quot;2026-06-02T09:14:31Z&quot;,
  &quot;user&quot;: &quot;adeveloper&quot;,
  &quot;email&quot;: &quot;adeveloper@example.com&quot;,
  &quot;host&quot;: &quot;macbook-dev42&quot;,
  &quot;agent&quot;: &quot;cursor&quot;,
  &quot;ide&quot;: &quot;cursor-cli&quot;,
  &quot;model&quot;: &quot;some-model-id&quot;,
  &quot;session_id&quot;: &quot;f3b9...&quot;,
  &quot;hook_event_name&quot;: &quot;beforeShellExecution&quot;,
  &quot;tool_name&quot;: &quot;Shell&quot;,
  &quot;command&quot;: &quot;npm test -- --watch=false&quot;,
  &quot;file_path&quot;: null,
  &quot;mcp_server&quot;: null,
  &quot;final_status&quot;: null,
  &quot;duration&quot;: null,
  &quot;duration_ms&quot;: null,
  &quot;event&quot;: { &quot;kind&quot;: &quot;event&quot;, &quot;category&quot;: &quot;process&quot;, &quot;type&quot;: &quot;start&quot;,
             &quot;action&quot;: &quot;beforeShellExecution&quot;, &quot;outcome&quot;: null, &quot;duration&quot;: null },
  &quot;raw&quot;: { &quot;...&quot;: &quot;original hook payload, abridged&quot; }
}</code></pre>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event</code> object follows <a href="https://www.elastic.co/docs/reference/ecs">Elastic Common Schema (ECS)</a> conventions (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.category</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.type</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.outcome</code>), which makes the data line up with the rest of your security indices for correlation. We did not start with these promoted fields, and the section on shipping explains why we added them.</p>
<p>The script keeps logs readable only by the owner (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">chmod 0600</code>), rotates by date, and opportunistically deletes files older than 30 days. Local retention is short on purpose; Elasticsearch is the system of record.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="configuring-cursor-hooks" class="absolute -top-32"></span>Configuring Cursor hooks</h2>
<p>Cursor reads a <a href="https://cursor.com/docs/agent/hooks"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hooks.json</code></a> that maps each event to a command. Deployed system-wide on macOS, it lives at <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/Library/Application Support/Cursor/hooks.json</code>, and both the IDE and the CLI pick it up, so one file covers both surfaces:</p>
<pre><code>{
  &quot;version&quot;: 1,
  &quot;hooks&quot;: {
    &quot;sessionStart&quot;:          [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;beforeShellExecution&quot;:  [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;afterShellExecution&quot;:   [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;beforeMCPExecution&quot;:    [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;afterMCPExecution&quot;:     [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;postToolUse&quot;:           [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;postToolUseFailure&quot;:    [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;afterFileEdit&quot;:         [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;beforeReadFile&quot;:        [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;subagentStart&quot;:         [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;subagentStop&quot;:          [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;sessionEnd&quot;:            [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }],
    &quot;stop&quot;:                  [{ &quot;command&quot;: &quot;/usr/local/share/ai-hooks/log-tool-calls.sh&quot; }]
  }
}</code></pre>
<p>Two gotchas cost us real time. The first: the script must not live under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/Library/Application Support/</code>. Cursor splits hook command paths on spaces, so a script under a path containing a space silently never runs. We keep the script at <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/local/share/ai-hooks/</code> and only the JSON config under the Cursor directory.</p>
<p>The second: Cursor reads <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hooks.json</code> only at startup, so the hooks stay dormant on every machine until Cursor restarts. Our deployment showed green everywhere while the pipeline stayed silent, and the fix was operational rather than technical: the MDM deployment tooling now detects a running Cursor and prompts the user to restart it. Budget for that restart in your rollout plan, because until it happens you are deployed but not collecting.</p>
<p>Cursor also ships a headless CLI agent (cursor-agent), the same one used in CI jobs or scripted runs, and it fires the same hooks as the IDE. Confirm that path is covered too:</p>
<pre><code>cursor-agent --print &quot;say hello&quot;
tail -1 ~/.config/ai-hooks/logs/tool-calls-$(date -u +%F).jsonl</code></pre>
<p>The output shows <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">&quot;agent&quot;:&quot;cursor&quot;,&quot;ide&quot;:&quot;cursor-cli&quot;</code> instead of ide=cursor, confirming the CLI path is tagged and captured separately from the IDE.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="deploying-cursor-hooks-without-mdm" class="absolute -top-32"></span>Deploying Cursor hooks without MDM</h2>
<p>Not every machine sits under device management. Our macOS and Windows fleets received the script and hooks file through their management tooling, but our Linux workstations have no equivalent channel. What they do have is Cursor itself, enrolled in our enterprise tenant, and Cursor&#x27;s console can push a hook configuration to every enrolled client through <a href="https://cursor.com/docs/agent/hooks#cloud-distribution-enterprise-only">Cloud Distribution</a>. The console distributes a command rather than files, so a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hooks.json</code> that points at <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/local/share/ai-hooks/log-tool-calls.sh</code> is useless if nothing ever placed that script on the box.</p>
<p>We solved this by making the hook command carry its own payload. The command holds the collector script gzipped and base64-encoded, pinned to a SHA-256 hash. On each invocation, it checks whether the installed script matches the hash, and if it is missing or stale, it decodes the payload, verifies the hash again before writing, installs the script to the user&#x27;s Cursor directory, and then executes it. Every failure path exits zero, so a decode or write problem degrades to a missing log line rather than a broken agent, which is the same fail-open contract as the rest of the pipeline. A machine with no prior collector self-installs the first time an agent fires a hook, and a version bump is one hash change in the console. The full command is in the repository next to the collector.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="sending-hook-logs-to-elasticsearch-with-elastic-agent" class="absolute -top-32"></span>Sending hook logs to Elasticsearch with Elastic Agent</h2>
<p>As InfoSec is Customer Zero at Elastic, the Elastic Agent is already rolled out to every endpoint, so collection was one new integration policy: a <a href="https://www.elastic.co/docs/reference/integrations/filestream">Custom Logs (filestream)</a> input pointed at the hook log glob, with a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">decode_json_fields</code> processor to parse each line. Configuring the integration was done quickly; getting the log format right took much longer.</p>
<pre><code># Custom Logs (filestream) integration settings
paths:
  - /Users/*/.config/ai-hooks/logs/tool-calls-*.jsonl   # macOS
  - /home/*/.config/ai-hooks/logs/tool-calls-*.jsonl    # Linux
  - C:\Users\*\.config\ai-hooks\logs\tool-calls-*.jsonl # Windows
data_stream.dataset: ai_hooks
processors:
  - decode_json_fields:
      fields: [&quot;message&quot;]
      target: &quot;ai_hooks&quot;
      add_error_key: true</code></pre>
<p>Each line of the JSONL log file becomes one event in a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">logs-ai_hooks-*</code> data stream, with every field from that line under the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ai_hooks.*</code> prefix.</p>
<p>Here is the lesson that reshaped the log format. Our first version logged only identity plus the raw payload, on the theory that <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">decode_json_fields</code> would expand everything and Kibana would sort it out. That theory was technically true: the data was all there, nested under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ai_hooks.raw.*</code>, three levels deep, with payload shapes that varied by hook type. Building a dashboard on <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ai_hooks.raw.tool_input.command</code> for one event type and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ai_hooks.raw.command</code> for another was miserable, and our nested format turned Discover sessions into archaeology.</p>
<p>We extended the script to promote the queryable fields (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tool_name</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">command</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file_path</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">mcp_server</code>) to the top level, and every downstream artifact got simpler. If you adopt one thing from this post beyond the script itself, make it this: structure your log line for the queries you want to run, and keep <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">raw</code> as the escape hatch rather than the interface.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="hunting-across-agent-activity-with-esql" class="absolute -top-32"></span>Hunting across agent activity with ES|QL</h2>
<p>With promoted fields, the questions that motivated the project become ES|QL one-liners. Which tools do agents call most across the fleet:</p>
<pre><code>FROM logs-ai_hooks-*
| WHERE ai_hooks.tool_name IS NOT NULL
| STATS calls = COUNT(*) BY ai_hooks.tool_name
| SORT calls DESC
| LIMIT 10</code></pre>
<p>On our fleet, file reads dominate by roughly four to one over shell execution, which matched nobody&#x27;s intuition: picture what a coding agent does and you picture it running commands, so shell felt like the obvious leader. Most of what an agent actually does is reconnaissance of your own codebase, reading before acting.</p>
<p>Every shell command an agent ran on a given host, newest first:</p>
<pre><code>FROM logs-ai_hooks-*
| WHERE ai_hooks.hook_event_name == &quot;beforeShellExecution&quot;
  AND ai_hooks.host == &quot;macbook-dev42&quot;
| KEEP @timestamp, ai_hooks.user, ai_hooks.agent, ai_hooks.command
| SORT @timestamp DESC
| LIMIT 50</code></pre>
<p>Agents that touched credential material (<a href="https://attack.mitre.org/techniques/T1552/001/">T1552.001, Credentials in Files</a>):</p>
<pre><code>FROM logs-ai_hooks-*
| WHERE ai_hooks.file_path LIKE &quot;*.env&quot;
   OR ai_hooks.file_path LIKE &quot;*.pem&quot;
   OR ai_hooks.file_path RLIKE &quot;.*/credentials(\\.[A-Za-z0-9]+)?$&quot;
| STATS reads = COUNT(*) BY ai_hooks.user, ai_hooks.host, ai_hooks.file_path
| SORT reads DESC</code></pre>
<p>Expect this one to be noisy in a good way: agents read <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.env</code> files constantly because that is where connection settings live. The value is the baseline. One tuning note: a bare <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">*credentials*</code> wildcard also matches project and plan file names that happen to contain the word, so we anchor the pattern to the filename itself, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">credentials</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">credentials.&lt;ext&gt;</code>, to keep the results to actual credential files. Once you know a host normally shows about four such reads a day, twenty reads in an hour against paths outside the working repo is a signal worth a look. One operational note: ES|QL returns at most 1,000 rows unless you raise the `LIMIT``, so treat a result that comes back at exactly 1,000 rows as truncated.</p>
<p>Which MCP servers are in use, and how widely:</p>
<pre><code>FROM logs-ai_hooks-*
| WHERE ai_hooks.mcp_server IS NOT NULL
| STATS calls = COUNT(*), users = COUNT_DISTINCT(ai_hooks.user) BY ai_hooks.mcp_server
| SORT users DESC</code></pre>
<p>This query answers a question that has nothing to do with security: who&#x27;s actually running which MCP server. Before hooks, our list of MCP servers in use was whatever people remembered to mention. After, it was a live table, and the long tail surprised us: more than 300 distinct servers, and 86% of them used by only one or two people.</p>
<p>Download-and-execute patterns worth reviewing (<a href="https://attack.mitre.org/techniques/T1105/">T1105, Ingress Tool Transfer</a>):</p>
<pre><code>FROM logs-ai_hooks-*
| WHERE ai_hooks.command LIKE &quot;*curl*&quot;
  AND (ai_hooks.command LIKE &quot;*| sh*&quot; OR ai_hooks.command LIKE &quot;*| bash*&quot;)
| KEEP @timestamp, ai_hooks.user, ai_hooks.host, ai_hooks.command
| SORT @timestamp DESC</code></pre>
<p>We run variants of these as saved queries behind two dashboards: an activity overview (events over time by surface, top tools, models in use, active machines) and a security monitor (shell commands, MCP calls, failed tool calls, file edits, per-user activity). Both are standard <a href="https://www.elastic.co/docs/explore-analyze/visualize/lens">Lens</a> panels over the same data stream; nothing about the visualization layer is exotic, which is the point of normalizing early.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="hardening-and-privacy-for-agent-audit-logs" class="absolute -top-32"></span>Hardening and privacy for agent audit logs</h2>
<p>Once this data existed, the decisions that mattered most had little to do with the pipeline.</p>
<ul>
<li><strong>Restrict who can read it.</strong> Hook logs are a detailed record of how individual engineers work, so we treated them like DNS logs: useful in aggregate, sensitive per-person. In Elasticsearch we excluded the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ai_hooks.*</code> field namespace from general-purpose security roles using <a href="https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level">field-level security</a>, leaving full access to the small team that owns the pipeline:</li>
</ul>
<pre><code>POST /_security/role/secops_general
{
  &quot;indices&quot;: [
    {
      &quot;names&quot;: [&quot;logs-*&quot;],
      &quot;privileges&quot;: [&quot;read&quot;],
      &quot;field_security&quot;: {
        &quot;grant&quot;: [&quot;*&quot;],
        &quot;except&quot;: [&quot;ai_hooks.*&quot;]
      }
    }
  ]
}</code></pre>
<ul>
<li>
<p><strong>Collect metadata and leave content alone.</strong> The script logs the command line, the file path, and the tool name. It does not log file contents, prompts, or model responses. That line is what made the rollout conversation with engineering straightforward instead of adversarial: we could state plainly that this is security telemetry, on par with process auditing, and that nobody is reading code or conversations.</p>
</li>
<li>
<p><strong>Say all of that out loud.</strong> We published an internal page describing exactly what is collected, who can query it, and why, before the fleet deployment started, and linked it from the rollout announcement. The questions we got afterward were about edge cases, and there was no pushback on the premise.</p>
</li>
</ul>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="what-13-million-tool-calls-reveal-about-ai-coding-agent-behavior" class="absolute -top-32"></span>What 13 million tool calls reveal about AI coding agent behavior</h2>
<p>The aggregate numbers from the first two months after the May rollout, rounded, came to over 13 million tool-call events from more than 1,100 machines and nearly 900 distinct users. The CLI surface alone accounts for nearly a fifth of the events, which we would never have guessed from install counts. The busiest single event type was <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">postToolUse</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">beforeReadFile</code> came second. That confirmed the read-heavy profile held across the whole fleet, not only on early-adopter machines.</p>
<p>Those numbers arrived fast. The proof-of-concept ran on one laptop for about six weeks while the script grew the field promotion, the CLI detection, and a series of small survival fixes (resolve the home directory from the passwd database when <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">HOME</code> is unset; refuse to run without piped stdin so a stray manual invocation cannot hang on <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cat</code>). Then management tooling pushed it to the whole fleet, and within a week the pipeline went from a trickle to nearly a million events.</p>
<p>Here are two operational notes for anyone repeating this. First, fail-open is the correct default and you should still measure it: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">postToolUseFailure</code> events told us when hooks themselves misbehaved after agent updates. Second, agent vendors ship fast and hook payloads change; the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">raw</code> field meant new payload fields were captured from day one even before we promoted them.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="what-are-the-limitations-of-hook-based-ai-agent-auditing" class="absolute -top-32"></span>What are the limitations of hook-based AI agent auditing?</h2>
<p>This section exists because a defender will ask all of these questions anyway.</p>
<p>A developer with admin rights can remove the hooks configuration or edit the script, and on macOS the per-user log file is writable by its owner before shipping. This is workforce telemetry under the same trust model as any endpoint agent, and it is tamper-evident at the fleet level (a host whose events stop while the machine stays active is itself a signal) rather than tamper-proof. Pair it with an inventory source you control, such as <a href="https://www.elastic.co/docs/reference/integrations/osquery">osquery</a>, to detect machines where the agent is installed, but no hook events arrive. Elastic has released Shadow AI detection packs with <a href="https://www.elastic.co/docs/reference/integrations/osquery_manager">OSquery Manager v1.3.3</a> that inventory local LLMs, MCP configurations, and AI browser extensions across the fleet; hooks tell you what agents do, OSquery tells you where they exist. If you want to build something more custom, this blog is here to help you out; a future post will cover OSquery packs and Shadow AI detection in depth.</p>
<p>Coverage is also bounded by the hook events the vendor chooses to expose. We see tool calls, and we do not see the prompt or the model&#x27;s reasoning, so intent stays out of frame. A hostile agent steered through prompt injection would show up here only through its actions. That is still far more than we could see before, and actions are ultimately what an incident responder needs. Cloud Distribution-pushed hooks only reach the enterprise tenant, so a personal Cursor login is invisible to this pipeline.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="getting-started-try-it-on-one-laptop" class="absolute -top-32"></span>Getting started: try it on one laptop</h2>
<p>The collector script, the hooks configuration, the self-installing console command, and the platform installers are in the <a href="https://github.com/elastic/elasticsearch-labs/tree/main/supporting-blog-content/security-labs/ai-hooks-collector-scripts">supporting repo</a>. With Elastic Agent already deployed, the path from zero to first dashboard is short: install the script and the hooks file, then add one custom logs integration. Start on your own laptop, run one agent session, and look at what lands in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">logs-ai_hooks-*</code>. The agent writes a JSON payload describing the event to the program's stdin. For some events, the program's stdout response decides whether the action proceeds. Cursor is not alone in offering hooks like these: Claude Code exposes an equivalent set, and we will walk that side in a follow-up post. It reads one JSON payload from stdin, extracts the fields we care about, and appends one line to a JSONL formatted date-rotated log file. Three design decisions shaped it.\n\n**Answer blocking hooks first.** A sensor-only collector still registers the blocking events, because they carry the richest telemetry: `beforeShellExecution` captures the command before it runs, and \\``beforeReadFil`e\\` is the only read event Cursor offers. Registering them means Cursor pauses those actions and waits for a verdict, whether or not you ever intend to say no. The script therefore answers before it does anything else. If it crashed after the response was sent, nothing would hang; if it crashed before, the agent could stall on filesystem errors that have nothing to do with the user. So the very first thing the script does after reading stdin is approve (trimmed here to the Cursor events):\n\n```shell\n# Respond to blocking hooks before any filesystem work, so a\n# logging failure can never hold up the agent.\nif [[ \"$INPUT\" == *'\"hook_event_name\"'*'\"beforeMCPExecution\"'* ]] || \\\n   [[ \"$INPUT\" == *'\"hook_event_name\"'*'\"beforeShellExecution\"'* ]] || \\\n   [[ \"$INPUT\" == *'\"hook_event_name\"'*'\"beforeReadFile\"'* ]] || \\\n   [[ \"$INPUT\" == *'\"hook_event_name\"'*'\"subagentStart\"'* ]]; then\n  echo '{\"permission\":\"allow\"}'\nfi\n```\n\nIn Cursor's response schema, `allow` proceeds, `deny` blocks, and `ask` forces a confirmation prompt. Cursor also fails open by default: if the hook process dies without responding, the action proceeds, and a hook that should block on failure can opt into `failClosed: true` instead. Local retention is short on purpose; Elasticsearch is the system of record.\n\n## Configuring Cursor hooks\n\nCursor reads a [`hooks.json`](https://cursor.com/docs/agent/hooks) that maps each event to a command. Deployed system-wide on macOS, it lives at `/Library/Application Support/Cursor/hooks.json`, and both the IDE and the CLI pick it up, so one file covers both surfaces:\n\n```json\n{\n  \"version\": 1,\n  \"hooks\": {\n    \"sessionStart\":          [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"beforeShellExecution\":  [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"afterShellExecution\":   [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"beforeMCPExecution\":    [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"afterMCPExecution\":     [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"postToolUse\":           [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"postToolUseFailure\":    [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"afterFileEdit\":         [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"beforeReadFile\":        [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"subagentStart\":         [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"subagentStop\":          [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"sessionEnd\":            [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }],\n    \"stop\":                  [{ \"command\": \"/usr/local/share/ai-hooks/log-tool-calls.sh\" }]\n  }\n}\n```\n\nTwo gotchas cost us real time. The first: the script must not live under `/Library/Application Support/`. Cursor splits hook command paths on spaces, so a script under a path containing a space silently never runs. We keep the script at `/usr/local/share/ai-hooks/` and only the JSON config under the Cursor directory.\n\nThe second: Cursor reads `hooks.json` only at startup, so the hooks stay dormant on every machine until Cursor restarts. Our deployment showed green everywhere while the pipeline stayed silent, and the fix was operational rather than technical: the MDM deployment tooling now detects a running Cursor and prompts the user to restart it. Budget for that restart in your rollout plan, because until it happens you are deployed but not collecting.\n\nCursor also ships a headless CLI agent (cursor-agent), the same one used in CI jobs or scripted runs, and it fires the same hooks as the IDE. Confirm that path is covered too:\n\n```shell\ncursor-agent --print \"say hello\"\ntail -1 ~/.config/ai-hooks/logs/tool-calls-$(date -u +%F).jsonl\n```\n\nThe output shows `\"agent\":\"cursor\",\"ide\":\"cursor-cli\"` instead of ide=cursor, confirming the CLI path is tagged and captured separately from the IDE.\n\n## Deploying Cursor hooks without MDM\n\nNot every machine sits under device management. Our macOS and Windows fleets received the script and hooks file through their management tooling, but our Linux workstations have no equivalent channel. What they do have is Cursor itself, enrolled in our enterprise tenant, and Cursor's console can push a hook configuration to every enrolled client through [Cloud Distribution](https://cursor.com/docs/agent/hooks#cloud-distribution-enterprise-only). The console distributes a command rather than files, so a `hooks.json` that points at `/usr/local/share/ai-hooks/log-tool-calls.sh` is useless if nothing ever placed that script on the box.\n\nWe solved this by making the hook command carry its own payload. The command holds the collector script gzipped and base64-encoded, pinned to a SHA-256 hash. On each invocation, it checks whether the installed script matches the hash, and if it is missing or stale, it decodes the payload, verifies the hash again before writing, installs the script to the user's Cursor directory, and then executes it. Every failure path exits zero, so a decode or write problem degrades to a missing log line rather than a broken agent, which is the same fail-open contract as the rest of the pipeline. A machine with no prior collector self-installs the first time an agent fires a hook, and a version bump is one hash change in the console. The full command is in the repository next to the collector.\n\n## Sending hook logs to Elasticsearch with Elastic Agent\n\nAs InfoSec is Customer Zero at Elastic, the Elastic Agent is already rolled out to every endpoint, so collection was one new integration policy: a [Custom Logs (filestream)](https://www.elastic.co/docs/reference/integrations/filestream) input pointed at the hook log glob, with a `decode_json_fields` processor to parse each line. Configuring the integration was done quickly; getting the log format right took much longer.\n\n```\n# Custom Logs (filestream) integration settings\npaths:\n  - /Users/*/.config/ai-hooks/logs/tool-calls-*.jsonl   # macOS\n  - /home/*/.config/ai-hooks/logs/tool-calls-*.jsonl    # Linux\n  - C:\\Users\\*\\.config\\ai-hooks\\logs\\tool-calls-*.jsonl # Windows\ndata_stream.dataset: ai_hooks\nprocessors:\n  - decode_json_fields:\n      fields: [\"message\"]\n      target: \"ai_hooks\"\n      add_error_key: true\n```\n\nEach line of the JSONL log file becomes one event in a `logs-ai_hooks-*` data stream, with every field from that line under the `ai_hooks.*` prefix.\n\nHere is the lesson that reshaped the log format. Our first version logged only identity plus the raw payload, on the theory that `decode_json_fields` would expand everything and Kibana would sort it out. That theory was technically true: the data was all there, nested under `ai_hooks.raw.*`, three levels deep, with payload shapes that varied by hook type. Building a dashboard on `ai_hooks.raw.tool_input.command` for one event type and `ai_hooks.raw.command` for another was miserable, and our nested format turned Discover sessions into archaeology.\n\nWe extended the script to promote the queryable fields (`tool_name`, `command`, `file_path`, `mcp_server`) to the top level, and every downstream artifact got simpler. If you adopt one thing from this post beyond the script itself, make it this: structure your log line for the queries you want to run, and keep `raw` as the escape hatch rather than the interface.\n\n## Hunting across agent activity with ES|QL\n\nWith promoted fields, the questions that motivated the project become ES|QL one-liners. Which tools do agents call most across the fleet:\n\n```\nFROM logs-ai_hooks-*\n| WHERE ai_hooks.tool_name IS NOT NULL\n| STATS calls = COUNT(*) BY ai_hooks.tool_name\n| SORT calls DESC\n| LIMIT 10\n```\n\nOn our fleet, file reads dominate by roughly four to one over shell execution, which matched nobody's intuition: picture what a coding agent does and you picture it running commands, so shell felt like the obvious leader. Most of what an agent actually does is reconnaissance of your own codebase, reading before acting.\n\nEvery shell command an agent ran on a given host, newest first:\n\n```\nFROM logs-ai_hooks-*\n| WHERE ai_hooks.hook_event_name == \"beforeShellExecution\"\n  AND ai_hooks.host == \"macbook-dev42\"\n| KEEP @timestamp, ai_hooks.user, ai_hooks.agent, ai_hooks.command\n| SORT @timestamp DESC\n| LIMIT 50\n```\n\nAgents that touched credential material ([T1552.001, Credentials in Files](https://attack.mitre.org/techniques/T1552/001/)):\n\n```\nFROM logs-ai_hooks-*\n| WHERE ai_hooks.file_path LIKE \"*.env\"\n   OR ai_hooks.file_path LIKE \"*.pem\"\n   OR ai_hooks.file_path RLIKE \".*/credentials(\\\\.[A-Za-z0-9]+)?$\"\n| STATS reads = COUNT(*) BY ai_hooks.user, ai_hooks.host, ai_hooks.file_path\n| SORT reads DESC\n```\n\nExpect this one to be noisy in a good way: agents read `.env` files constantly because that is where connection settings live. The value is the baseline. One tuning note: a bare `*credentials*` wildcard also matches project and plan file names that happen to contain the word, so we anchor the pattern to the filename itself, `credentials` or `credentials.\u003cext\u003e`, to keep the results to actual credential files. Once you know a host normally shows about four such reads a day, twenty reads in an hour against paths outside the working repo is a signal worth a look. One operational note: ES|QL returns at most 1,000 rows unless you raise the `LIMIT``, so treat a result that comes back at exactly 1,000 rows as truncated.\n\nWhich MCP servers are in use, and how widely:\n\n```\nFROM logs-ai_hooks-*\n| WHERE ai_hooks.mcp_server IS NOT NULL\n| STATS calls = COUNT(*), users = COUNT_DISTINCT(ai_hooks.user) BY ai_hooks.mcp_server\n| SORT users DESC\n```\n\nThis query answers a question that has nothing to do with security: who's actually running which MCP server. Before hooks, our list of MCP servers in use was whatever people remembered to mention. After, it was a live table, and the long tail surprised us: more than 300 distinct servers, and 86% of them used by only one or two people.\n\nDownload-and-execute patterns worth reviewing ([T1105, Ingress Tool Transfer](https://attack.mitre.org/techniques/T1105/)):\n\n```\nFROM logs-ai_hooks-*\n| WHERE ai_hooks.command LIKE \"*curl*\"\n  AND (ai_hooks.command LIKE \"*| sh*\" OR ai_hooks.command LIKE \"*| bash*\")\n| KEEP @timestamp, ai_hooks.user, ai_hooks.host, ai_hooks.command\n| SORT @timestamp DESC\n```\n\nWe run variants of these as saved queries behind two dashboards: an activity overview (events over time by surface, top tools, models in use, active machines) and a security monitor (shell commands, MCP calls, failed tool calls, file edits, per-user activity). Both are standard [Lens](https://www.elastic.co/docs/explore-analyze/visualize/lens) panels over the same data stream; nothing about the visualization layer is exotic, which is the point of normalizing early.\n\n## Hardening and privacy for agent audit logs\n\nOnce this data existed, the decisions that mattered most had little to do with the pipeline.\n\n* **Restrict who can read it.** Hook logs are a detailed record of how individual engineers work, so we treated them like DNS logs: useful in aggregate, sensitive per-person. In Elasticsearch we excluded the `ai_hooks.*` field namespace from general-purpose security roles using [field-level security](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level), leaving full access to the small team that owns the pipeline:\n\n```json\nPOST /_security/role/secops_general\n{\n  \"indices\": [\n    {\n      \"names\": [\"logs-*\"],\n      \"privileges\": [\"read\"],\n      \"field_security\": {\n        \"grant\": [\"*\"],\n        \"except\": [\"ai_hooks.*\"]\n      }\n    }\n  ]\n}\n```\n\n* **Collect metadata and leave content alone.** The script logs the command line, the file path, and the tool name. It does not log file contents, prompts, or model responses. That line is what made the rollout conversation with engineering straightforward instead of adversarial: we could state plainly that this is security telemetry, on par with process auditing, and that nobody is reading code or conversations.\n\n* **Say all of that out loud.** We published an internal page describing exactly what is collected, who can query it, and why, before the fleet deployment started, and linked it from the rollout announcement. The questions we got afterward were about edge cases, and there was no pushback on the premise.\n\n## What 13 million tool calls reveal about AI coding agent behavior\n\nThe aggregate numbers from the first two months after the May rollout, rounded, came to over 13 million tool-call events from more than 1,100 machines and nearly 900 distinct users. The CLI surface alone accounts for nearly a fifth of the events, which we would never have guessed from install counts. The busiest single event type was `postToolUse`, and `beforeReadFile` came second. That confirmed the read-heavy profile held across the whole fleet, not only on early-adopter machines.\n\nThose numbers arrived fast. The proof-of-concept ran on one laptop for about six weeks while the script grew the field promotion, the CLI detection, and a series of small survival fixes (resolve the home directory from the passwd database when `HOME` is unset; refuse to run without piped stdin so a stray manual invocation cannot hang on `cat`). Then management tooling pushed it to the whole fleet, and within a week the pipeline went from a trickle to nearly a million events.\n\nHere are two operational notes for anyone repeating this. First, fail-open is the correct default and you should still measure it: `postToolUseFailure` events told us when hooks themselves misbehaved after agent updates. Second, agent vendors ship fast and hook payloads change; the `raw` field meant new payload fields were captured from day one even before we promoted them.\n\n## What are the limitations of hook-based AI agent auditing?\n\nThis section exists because a defender will ask all of these questions anyway.\n\nA developer with admin rights can remove the hooks configuration or edit the script, and on macOS the per-user log file is writable by its owner before shipping. This is workforce telemetry under the same trust model as any endpoint agent, and it is tamper-evident at the fleet level (a host whose events stop while the machine stays active is itself a signal) rather than tamper-proof. Pair it with an inventory source you control, such as [osquery](https://www.elastic.co/docs/reference/integrations/osquery), to detect machines where the agent is installed, but no hook events arrive. Elastic has released Shadow AI detection packs with [OSquery Manager v1.3.3](https://www.elastic.co/docs/reference/integrations/osquery_manager) that inventory local LLMs, MCP configurations, and AI browser extensions across the fleet; hooks tell you what agents do, OSquery tells you where they exist. If you want to build something more custom, this blog is here to help you out; a future post will cover OSquery packs and Shadow AI detection in depth.\n\n\nCoverage is also bounded by the hook events the vendor chooses to expose. We see tool calls, and we do not see the prompt or the model's reasoning, so intent stays out of frame. A hostile agent steered through prompt injection would show up here only through its actions. That is still far more than we could see before, and actions are ultimately what an incident responder needs. Cloud Distribution-pushed hooks only reach the enterprise tenant, so a personal Cursor login is invisible to this pipeline.\n\n## Getting started: try it on one laptop\n\nThe collector script, the hooks configuration, the self-installing console command, and the platform installers are in the [supporting repo](https://github.com/elastic/elasticsearch-labs/tree/main/supporting-blog-content/security-labs/ai-hooks-collector-scripts).
