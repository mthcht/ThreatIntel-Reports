class="lg:max-w-7xl mx-auto relative mt-12 lg:grid lg:grid-cols-4 lg:gap-8 items-start"><div class="flex lg:col-span-3"><div class="prose lg:prose-lg prose-invert w-full article-content"><div><h2 class="font-bold text-2xl md:text-4xl relative"><span id="preamble" class="absolute -top-32"></span>Preamble</h2>
<p>In 2025 and 2026, we watched a pattern play out across the industry. Attackers stopped going after production servers directly and started targeting the automation that deploys to them. Compromised developer credentials, a modified workflow file, and suddenly every secret in a CI/CD environment is streaming to an attacker-controlled endpoint. We saw this play out across incidents involving <a href="https://blog.gitguardian.com/ghostaction-campaign-3-325-secrets-stolen">major open-source projects</a>, <a href="https://orca.security/resources/blog/pull-request-nightmare-github-actions-rce/">Fortune 500 companies</a>, and <a href="https://about.codecov.io/apr-2021-post-mortem/">critical infrastructure tooling</a>.</p>
<p>The attack chain is deceptively simple:</p>
<p>Stolen developer credentials → Modified workflow file → Harvested CI secrets → Lateral movement to cloud and production</p>
<p>Today we are open-sourcing <a href="https://github.com/elastic/cicd-abuse-detector">cicd-abuse-detector</a>, a drop-in CI template that uses regex-based signal extraction and LLM analysis to detect suspicious changes to CI/CD pipelines. It works across GitHub Actions, GitLab CI, and Azure DevOps, and is designed around the real-world attack techniques documented in public security research.</p>
<p></p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="key-takeaways" class="absolute -top-32"></span>Key takeaways</h2>
<ul>
<li>CI/CD environments are high-value targets because a single compromised workflow can exfiltrate cloud credentials, package registry tokens, code signing keys, deploy keys, and OIDC tokens simultaneously</li>
<li>The tool extracts 50+ regex and metadata signals from diffs, then passes them with the full diff to Claude for structured threat analysis. No Python, no dependencies beyond bash and the Claude Code CLI</li>
<li>Detection patterns were tested against offensive toolkits like <a href="https://github.com/synacktiv/nord-stream">Nord Stream</a> and <a href="https://github.com/AdnaneKhan/Gato-X">Gato-X</a>, and against real incidents including <a href="https://unit42.paloaltonetworks.com/github-repo-artifacts-leak-tokens/">ArtiPACKED</a> and <a href="https://orca.security/resources/blog/hackerbot-claw-github-actions-attack/">HackerBot-Claw</a></li>
<li>The project ships with 19 malicious and four benign example diffs modeled after specific incidents, and an automated test suite that validates every signal</li>
</ul>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="why-cicd-pipelines-are-a-top-target" class="absolute -top-32"></span>Why CI/CD pipelines are a top target</h2>
<p>If you spend time reviewing GitHub Actions or GitLab CI configurations, you might notice how much trust is concentrated in these files. A typical deployment workflow has access to AWS credentials, npm publish tokens, Docker Hub passwords, and a GitHub token with write permissions, all at the same time. The attack surface isn&#x27;t a server with a CVE, it&#x27;s a YAML file.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="credential-harvesting-at-scale" class="absolute -top-32"></span>Credential harvesting at scale</h3>
<p>An attacker with stolen developer credentials modifies a workflow to exfiltrate secrets available in the CI environment. The <a href="https://blog.gitguardian.com/ghostaction-campaign-3-325-secrets-stolen">GhostAction campaign</a> in September 2025 demonstrated this at scale, compromising 327 GitHub users across 817 repositories. 3,325 secrets were stolen through injected workflow files that POST&#x27;d credentials to attacker endpoints.</p>
<p>The <a href="https://www.reversinglabs.com/blog/shai-hulud-worm-npm">Shai-Hulud npm worm</a> went further. This self-propagating attack harvested GitHub Personal Access Tokens via gh auth token, ran <a href="https://github.com/trufflesecurity/trufflehog">TruffleHog</a> for secret reconnaissance, and used compromised tokens to silently inject malicious code into other packages owned by the same developer. Over 46,000 malicious packages were published in the first wave alone.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="privileged-trigger-exploitation" class="absolute -top-32"></span>Privileged trigger exploitation</h3>
<p>The pull_request_target trigger is one of the most dangerous features in GitHub Actions. Unlike a regular pull_request trigger, it runs workflows in the context of the base repository with access to secrets, but it can execute code from an untrusted fork. The <a href="https://orca.security/resources/blog/pull-request-nightmare-github-actions-rce/">Orca &quot;Pull Request Nightmare&quot;</a> research demonstrated this against repositories maintained by Google, Microsoft, and NVIDIA.</p>
<p>In February 2026, an automated campaign called <a href="https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation">HackerBot-Claw</a> systematically scanned public repositories for this exact misconfiguration. It used five different exploitation techniques, including poisoned Go <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">init()</code> functions, branch name command injection, filename-based injection, direct script injection, and AI prompt injection against Claude-based code reviewers. In the most severe case, Aqua Security&#x27;s Trivy repository was fully compromised, leading to a downstream supply chain attack that exposed 33,000 secrets across nearly 7,000 machines. As <a href="https://www.microsoft.com/en-us/security/blog/2026/03/24/detecting-investigating-defending-against-trivy-supply-chain-compromise/">documented</a>, this supply chain attack was made possible with compromised tokens that were valid weeks after initially stolen.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="the-rest-of-the-taxonomy" class="absolute -top-32"></span>The rest of the taxonomy</h3>
<p>Beyond credential harvesting and trigger exploitation, the threat model covers four additional categories that appear consistently in public research:</p>
<ul>
<li>Permission escalation, where adding permissions: write-all or id-token: write broadens the blast radius of any compromise</li>
<li>Runner targeting, redirecting jobs to self-hosted runners that often have network access to internal infrastructure, or specifying attacker-controlled container images</li>
<li>Supply chain manipulation through mutable action references (using @main instead of SHA-pinned versions), remote script execution (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">curl</code> | <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bash</code>), lockfile registry swaps, and dependency poisoning</li>
<li>Defense evasion via commit timestamp manipulation, making malicious files appear old and trusted. <a href="https://kl4r10n.tech/blog/when-git-history-lies">KL4R10N documented</a> this technique in DPRK-linked campaigns where backdated commits reference infrastructure that did not exist at the claimed date</li>
</ul>
<p>Each of these maps to specific <a href="https://attack.mitre.org/">MITRE ATT&amp;CK</a> techniques: <a href="https://attack.mitre.org/techniques/T1552/">T1552</a> (Unsecured Credentials), <a href="https://attack.mitre.org/techniques/T1195/">T1195</a> (Supply Chain Compromise), <a href="https://attack.mitre.org/techniques/T1070/006/">T1070.006</a> (Timestomp), and <a href="https://attack.mitre.org/techniques/T1059/">T1059</a> (Command and Scripting Interpreter).</p>

<h2 class="font-bold text-2xl md:text-4xl relative"><span id="how-the-detector-works" class="absolute -top-32"></span>How the detector works</h2>
<p>We wanted the templates to work without requiring Python, custom runtimes, or complex dependencies. Everything runs in standard shell utilities on a default ubuntu-latest runner, and the only installed tool is the <a href="https://docs.anthropic.com/en/docs/claude-code">Claude Code CLI</a> via npm, which handles authentication, retries, and model routing.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="stage-1-filter-and-diff" class="absolute -top-32"></span>Stage 1: Filter and diff</h3>
<p>When a pull request is opened (or a push lands on a protected branch), the workflow identifies changed files across three tiers of CI/CD-relevant paths. The first tier covers core CI files like workflow definitions, pipeline configs, and Makefiles. The second covers build and release artifacts like Dockerfiles, package manifests, lockfiles, and signing or deploy scripts. The third tier picks up developer environment configs like .vscode/tasks.json and .devcontainer files.</p>
<p>Each file is diffed individually and capped at 10,000 characters. We do this per-file rather than globally because a single cap on the combined diff is a bypass vector. An attacker can pad a malicious workflow change with a large benign Dockerfile edit to push the exploit past the character limit.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="stage-2-signal-extraction" class="absolute -top-32"></span>Stage 2: Signal extraction</h3>

<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="stage-3-llm-analysis" class="absolute -top-32"></span>Stage 3: LLM analysis</h3>
<p>The signal summary, full diff, author profile, and commit metadata are bundled and sent to Claude via the Claude Code CLI. The <a href="https://github.com/elastic/cicd-abuse-detector/blob/main/prompts/analyze-cicd-change.md">analysis prompt</a> walks the model through several areas:</p>
<ol>
<li>Diff comprehension and per-file risk assessment</li>
<li>Signal interpretation with context (a signal alone is not a verdict)</li>
<li>Temporal analysis for backdated commits</li>
<li>Author trust assessment using account age, contribution history, and org membership</li>
<li>Severity calibration against a signal combination table with 60+ entries</li>
<li>False positive recognition (e.g., cURL for downloading known tools is not exfiltration)</li>
<li>Concrete, actionable recommendations (&quot;Pin actions/setup-node@main to a specific SHA&quot; instead of &quot;review carefully&quot;)</li>
</ol>
<p>The output is a structured JSON verdict containing severity, confidence, reasoning, evidence, and recommendations, all validated against a <a href="https://github.com/elastic/cicd-abuse-detector/blob/main/schemas/verdict.schema.json">JSON Schema</a>.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="stage-4-alert-and-gate" class="absolute -top-32"></span>Stage 4: Alert and gate</h3>
<p>Based on the verdict severity, the workflow posts a step summary, creates an issue, sends a Slack notification, and optionally fails the PR check if severity meets a configured threshold.</p>
<p></p>
<p></p>
<p>Alerts in Slack and GitHub Issues solve the immediate notification problem, but they don&#x27;t give you a queryable history. Every verdict the detector produces (e.g. benign, suspicious, or malicious), can optionally ship to Elasticsearch as a structured document in the logs-cicd.abuse-default data stream. The workflow ships the verdict along with CI/CD metadata (platform, repository, actor, event type, run URL) into a single index that spans all three supported platforms.</p>
<p>This is where cross-platform correlation becomes practical. A GitHub Actions alert and a GitLab CI alert from the same actor land in the same data stream, queryable in a single ES|QL statement:</p>
<pre><code>FROM logs-cicd.abuse-* 
WHERE verdict.verdict IN (&quot;malicious&quot;, &quot;suspicious&quot;) AND @timestamp &gt; NOW() - 7 days 
EVAL platform = cicd.platform, repo = cicd.repository, actor = cicd.actor, severity = verdict.severity
KEEP @timestamp, platform, repo, actor, severity
SORT @timestamp DESC</code></pre>
<p></p>
<p>The schema includes  cicd.platform, cicd.repository, cicd.actor, and the full verdict object (verdict, severity, confidence, summary, reasons, evidence), making it straightforward to build detection rules. A coordinated campaign that hits multiple repos within an hour, a repeat offender flagged across platforms, or a spike in critical findings that warrants an incident response page can be correlated.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="validating-against-real-attacks" class="absolute -top-32"></span>Validating against real attacks</h2>
<p>To validate coverage, we compared our detection patterns against the actual source code of offensive tools, published research, and public post-mortems.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="nord-stream-verbatim-payload-matching" class="absolute -top-32"></span>Nord Stream: verbatim payload matching</h3>
<p>Nord Stream is Synacktiv&#x27;s open-source CI/CD secret extraction tool supporting GitHub, GitLab, and Azure DevOps. We pulled the YAML generator source (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nordstream/yaml/github.py</code>) and compared its output templates against our example diffs.</p>
<ul>
<li>The GitHub payload template uses <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">env -0 | awk -v RS=&#x27;0&#x27; &#x27;/^secret_/ {print $0}&#x27; | base64 -w0 | base64 -w0</code>. Our <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nord-stream-pipeline-exfil.diff</code> contains this line verbatim, and our <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">double_base64</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">env_null_dump</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">env_secret_grep</code> signals all fire.</li>
<li>The OIDC Azure template uses <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">azure/login@v1</code> with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">id-token: write</code> permissions followed by az account <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">get-access-token | base64 -w0 | base64 -w0</code>. Our diff captures this exact flow and triggers <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cloud_auth_action</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">id_token_write</code>.</li>
<li>The Azure DevOps pipeline techniques (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">addSpnToEnvironment</code> for SPN credential exposure, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">DownloadSecureFile</code> for secure file theft, SSH task source patching via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ssh.js</code> modification) are all present in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nord-stream-azure-devops.diff</code> and detected by platform-specific signals.</li>
</ul>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="artipacked-the-artifact-race-condition" class="absolute -top-32"></span>ArtiPACKED: the artifact race condition</h3>
<p>The <a href="https://unit42.paloaltonetworks.com/github-repo-artifacts-leak-tokens/">ArtiPACKED</a> research from Palo Alto Unit 42 showed that uploading the entire checkout directory as an artifact leaks the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.git/config</code> file containing the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">GITHUB_TOKEN</code>. With the v4 artifact API allowing mid-run downloads, an attacker can extract and use the token before the job completes.</p>
<p>Our <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">artifact-token-leak.diff</code> models this exact pattern, using <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">upload-artifact</code> with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">path: .</code> (the entire workspace). The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">upload_artifact</code> signal catches it, and the LLM evaluates whether the upload scope includes the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.git</code> directory.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="github_env-injection-ld_preload-to-rce" class="absolute -top-32"></span>GITHUB_ENV injection: LD_PRELOAD to RCE</h3>
<p><a href="https://www.legitsecurity.com/blog/github-privilege-escalation-vulnerability-0">Legit Security&#x27;s research</a> on Google Firebase and Apache showed that writing untrusted input to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">$GITHUB_ENV</code> allows an attacker to set arbitrary environment variables like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">LD_PRELOAD</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NODE_OPTIONS</code>, achieving code execution in privileged workflows.</p>
<p>Our <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">github-env-injection.diff</code> reproduces this technique with three distinct payloads, including <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">LD_PRELOAD</code> pointing to a malicious shared object, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NODE_OPTIONS</code> with a required injection, and $<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">GITHUB_PATH</code> manipulation. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">github_env_write</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ld_preload</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">github_path_write</code> signals all trigger as expected.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="contagious-interview-ide-config-as-initial-access" class="absolute -top-32"></span>Contagious Interview: IDE config as initial access</h3>
<p>The <a href="https://www.abstract.security/blog/contagious-interview-tracking-the-vs-code-tasks-infection-vector">Contagious Interview campaign</a> attributed to DPRK targets developers through fake job interviews, distributing repositories with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.vscode/tasks.json</code> files that auto-execute on folder open. The presentation is hidden (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">reveal: never</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">echo: false</code>), and the payload uses <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">curl</code> | <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">node</code> for silent execution.</p>
<p>Our <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ide-config-poisoning.diff</code> captures the full attack chain, including the auto-execute trigger (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">runOn: folderOpen</code>), the hidden presentation, the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">curl | node</code> payload, the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">files.exclude</code> entry that hides the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.vscode</code> directory, and a trojanized postinstall hook with base64-encoded URLs and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">eval()</code> for code execution. Six signals pick this up at once.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="defensive-recommendations" class="absolute -top-32"></span>Defensive recommendations</h2>
<p>Beyond deploying the detector, here are some hardening measures that came directly out of the attack patterns we studied:</p>
<ul>
<li>Pin all actions to SHA, not tags, not branches. SHA-pinned references prevent retroactive tag modification attacks like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tj-actions</code> (CVE-2025-30066).</li>
<li>Scope secrets to individual steps rather than using job-level environment variables. Each step should only have access to the secrets it actually needs.</li>
<li>Use short lived, ephemeral tokens when possible to reduce attack surface</li>
<li>Avoid <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">pull_request_target</code> unless strictly necessary. If you must use it, never checkout the PR head code in the same workflow. Use a separate <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">workflow_run-triggered workflow</code> for operations that need both secrets and PR context.</li>
<li>Set explicit permissions on every workflow because the default token permissions are far too broad. Set <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">permissions: {}</code> at the workflow level and add specific permissions per job.</li>
<li>Enable <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">persist-credentials: false</code> on checkout since the default behavior of actions/checkout persists the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">GITHUB_TOKEN</code> in the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.git</code> directory. If you upload artifacts, this token goes with them.</li>
</ul>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="summary" class="absolute -top-32"></span>Summary</h2>
<p>CI/CD pipelines have become a major attack surface for supply chain compromise. The same automation that makes modern software delivery possible is what attackers exploit to harvest credentials, poison packages, and pivot to cloud infrastructure. Traditional code review doesn&#x27;t catch these patterns well because they&#x27;re subtle, platform-specific, and designed to look like legitimate DevOps changes.</p>
<p>Combining regex-based signal extraction with LLM reasoning lets us surface these patterns at the pull request stage, before they reach production. The repo includes the full threat model, test suite, and example diffs if you want to dig into the details or adapt it to your own environment.</p>
<p>To get started, check out the <a href="https://github.com/elastic/cicd-abuse-detector">cicd-abuse-detector repo</a> for setup instructions, the full threat model, and example diffs. We&#x27;re always interested in hearing about new attack patterns and detection ideas. Chat with us in our <a href="http://ela.st/slack">community Slack</a>, and ask questions in our <a href="https://discuss.elastic.co/c/security/endpoint-security/80">Discuss forums</a>.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="cicd-abuse-through-mitre-attck" class="absolute -top-32"></span>CI/CD abuse through MITRE ATT&amp;CK</h2>
<p>We use the <a href="https://attack.mitre.org/">MITRE ATT&amp;CK</a> framework to map the tactics, techniques, and procedures that adversaries use against CI/CD pipelines.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="tactics" class="absolute -top-32"></span>Tactics</h3>

We saw this play out across incidents involving [major open-source projects](https://blog.gitguardian.com/ghostaction-campaign-3-325-secrets-stolen), [Fortune 500 companies](https://orca.security/resources/blog/pull-request-nightmare-github-actions-rce/), and [critical infrastructure tooling](https://about.codecov.io/apr-2021-post-mortem/).\n\nThe attack chain is deceptively simple:\n\nStolen developer credentials → Modified workflow file → Harvested CI secrets → Lateral movement to cloud and production\n\nToday we are open-sourcing [cicd-abuse-detector](https://github.com/elastic/cicd-abuse-detector), a drop-in CI template that uses regex-based signal extraction and LLM analysis to detect suspicious changes to CI/CD pipelines. It works across GitHub Actions, GitLab CI, and Azure DevOps, and is designed around the real-world attack techniques documented in public security research.  \n\n![CI/CD Abuse Detector execution flow](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image4.png \"CI/CD Abuse Detector execution flow\")\n\n## Key takeaways\n\n* CI/CD environments are high-value targets because a single compromised workflow can exfiltrate cloud credentials, package registry tokens, code signing keys, deploy keys, and OIDC tokens simultaneously  \n* The tool extracts 50+ regex and metadata signals from diffs, then passes them with the full diff to Claude for structured threat analysis. No Python, no dependencies beyond bash and the Claude Code CLI  \n* Detection patterns were tested against offensive toolkits like [Nord Stream](https://github.com/synacktiv/nord-stream) and [Gato-X](https://github.com/AdnaneKhan/Gato-X), and against real incidents including [ArtiPACKED](https://unit42.paloaltonetworks.com/github-repo-artifacts-leak-tokens/) and [HackerBot-Claw](https://orca.security/resources/blog/hackerbot-claw-github-actions-attack/)  \n* The project ships with 19 malicious and four benign example diffs modeled after specific incidents, and an automated test suite that validates every signal\n\n## Why CI/CD pipelines are a top target\n\nIf you spend time reviewing GitHub Actions or GitLab CI configurations, you might notice how much trust is concentrated in these files. A typical deployment workflow has access to AWS credentials, npm publish tokens, Docker Hub passwords, and a GitHub token with write permissions, all at the same time. The attack surface isn't a server with a CVE, it's a YAML file.\n\n### Credential harvesting at scale\n\nAn attacker with stolen developer credentials modifies a workflow to exfiltrate secrets available in the CI environment. The [GhostAction campaign](https://blog.gitguardian.com/ghostaction-campaign-3-325-secrets-stolen) in September 2025 demonstrated this at scale, compromising 327 GitHub users across 817 repositories. 3,325 secrets were stolen through injected workflow files that POST'd credentials to attacker endpoints.\n\nThe [Shai-Hulud npm worm](https://www.reversinglabs.com/blog/shai-hulud-worm-npm) went further. This self-propagating attack harvested GitHub Personal Access Tokens via gh auth token, ran [TruffleHog](https://github.com/trufflesecurity/trufflehog) for secret reconnaissance, and used compromised tokens to silently inject malicious code into other packages owned by the same developer. Over 46,000 malicious packages were published in the first wave alone. \n\n### Privileged trigger exploitation\n\nThe pull_request_target trigger is one of the most dangerous features in GitHub Actions. Unlike a regular pull_request trigger, it runs workflows in the context of the base repository with access to secrets, but it can execute code from an untrusted fork. The [Orca \"Pull Request Nightmare\"](https://orca.security/resources/blog/pull-request-nightmare-github-actions-rce/) research demonstrated this against repositories maintained by Google, Microsoft, and NVIDIA.\n\nIn February 2026, an automated campaign called [HackerBot-Claw](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation) systematically scanned public repositories for this exact misconfiguration. It used five different exploitation techniques, including poisoned Go `init()` functions, branch name command injection, filename-based injection, direct script injection, and AI prompt injection against Claude-based code reviewers. In the most severe case, Aqua Security's Trivy repository was fully compromised, leading to a downstream supply chain attack that exposed 33,000 secrets across nearly 7,000 machines. As [documented](https://www.microsoft.com/en-us/security/blog/2026/03/24/detecting-investigating-defending-against-trivy-supply-chain-compromise/), this supply chain attack was made possible with compromised tokens that were valid weeks after initially stolen. \n\n### The rest of the taxonomy\n\nBeyond credential harvesting and trigger exploitation, the threat model covers four additional categories that appear consistently in public research:\n\n* Permission escalation, where adding permissions: write-all or id-token: write broadens the blast radius of any compromise  \n* Runner targeting, redirecting jobs to self-hosted runners that often have network access to internal infrastructure, or specifying attacker-controlled container images  \n* Supply chain manipulation through mutable action references (using @main instead of SHA-pinned versions), remote script execution (`curl` | `bash`), lockfile registry swaps, and dependency poisoning  \n* Defense evasion via commit timestamp manipulation, making malicious files appear old and trusted. [KL4R10N documented](https://kl4r10n.tech/blog/when-git-history-lies) this technique in DPRK-linked campaigns where backdated commits reference infrastructure that did not exist at the claimed date\n\nEach of these maps to specific [MITRE ATT\u0026CK](https://attack.mitre.org/) techniques: [T1552](https://attack.mitre.org/techniques/T1552/) (Unsecured Credentials), [T1195](https://attack.mitre.org/techniques/T1195/) (Supply Chain Compromise), [T1070.006](https://attack.mitre.org/techniques/T1070/006/) (Timestomp), and [T1059](https://attack.mitre.org/techniques/T1059/) (Command and Scripting Interpreter).\n\n![CI/CD Abuse Detector attack taxonomy and detection paths](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image1.png \"CI/CD Abuse Detector attack taxonomy and detection paths\")\n\n## How the detector works\n\nWe wanted the templates to work without requiring Python, custom runtimes, or complex dependencies. Everything runs in standard shell utilities on a default ubuntu-latest runner, and the only installed tool is the [Claude Code CLI](https://docs.anthropic.com/en/docs/claude-code) via npm, which handles authentication, retries, and model routing.\n\n### Stage 1: Filter and diff\n\nWhen a pull request is opened (or a push lands on a protected branch), the workflow identifies changed files across three tiers of CI/CD-relevant paths. The first tier covers core CI files like workflow definitions, pipeline configs, and Makefiles. The second covers build and release artifacts like Dockerfiles, package manifests, lockfiles, and signing or deploy scripts. The third tier picks up developer environment configs like .vscode/tasks.json and .devcontainer files.\n\nEach file is diffed individually and capped at 10,000 characters. We do this per-file rather than globally because a single cap on the combined diff is a bypass vector. An attacker can pad a malicious workflow change with a large benign Dockerfile edit to push the exploit past the character limit.\n\n### Stage 2: Signal extraction\n\nBefore the LLM sees anything, 50+ regex patterns scan each diff for known-dangerous patterns. These signals are advisory. They never gate the analysis, but they provide the LLM with a pre-screened threat summary. A few examples:\n\n| Signal | Pattern | What it catches |\n| :---- | :---- | :---- |\n| `secrets_context` | `${{.*secrets.` | Direct secret interpolation in workflows |\n| `pull_request_target` | `pull_request_target` | The dangerous trigger that grants secrets to PR code |\n| `checkout_ref` | `ref:.*github.event.pull_request.head.(sha\\|ref)` | Untrusted PR code checked out in a privileged context |\n| `double_base64` | `base64.*\\|.*base64` | Double-encoding to evade log masking (Nord Stream technique) |\n| `ld_preload` | `LD_PRELOAD` | Arbitrary code execution via environment variable injection |\n| `vscode_auto_task` | `runOn.*folderOpen` | VS Code task that executes on folder open (Contagious Interview) |\n\nThe signal list is based on real adversarial tooling, including [Nord Stream](https://github.com/synacktiv/nord-stream) and [Gato-X](https://github.com/AdnaneKhan/Gato-X), and tested against 19 malicious example diffs modeled after specific incidents.\n\nThe detector runs identically across GitHub Actions, GitLab CI, and Azure DevOps. Here are detections firing on each platform:\n\n![GitHub CI/CD Abuse Detector alert](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image8.png \"GitHub CI/CD Abuse Detector alert\")\n\n![GitLab CI/CD Abuse Detector alert](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image7.png \"GitLab CI/CD Abuse Detector alert\")\n\n![Azure DevOps CI/CD Abuse Detector alert](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image2.png \"Azure DevOps CI/CD Abuse Detector alert\")\n\n### Stage 3: LLM analysis\n\nThe signal summary, full diff, author profile, and commit metadata are bundled and sent to Claude via the Claude Code CLI. The [analysis prompt](https://github.com/elastic/cicd-abuse-detector/blob/main/prompts/analyze-cicd-change.md) walks the model through several areas:\n\n1. Diff comprehension and per-file risk assessment  \n2. Signal interpretation with context (a signal alone is not a verdict)  \n3. Temporal analysis for backdated commits  \n4. Author trust assessment using account age, contribution history, and org membership  \n5. Severity calibration against a signal combination table with 60+ entries  \n6. False positive recognition (e.g., cURL for downloading known tools is not exfiltration)  \n7. Concrete, actionable recommendations (\"Pin actions/setup-node@main to a specific SHA\" instead of \"review carefully\")\n\nThe output is a structured JSON verdict containing severity, confidence, reasoning, evidence, and recommendations, all validated against a [JSON Schema](https://github.com/elastic/cicd-abuse-detector/blob/main/schemas/verdict.schema.json).\n\n### Stage 4: Alert and gate\n\nBased on the verdict severity, the workflow posts a step summary, creates an issue, sends a Slack notification, and optionally fails the PR check if severity meets a configured threshold.\n\n![Slack notification from the CI/CD Abuse Detector flagging a critical severity finding](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image3.png \"Slack notification from the CI/CD Abuse Detector flagging a critical severity finding\")  \n\n![Shipping verdicts to Elastic](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image6.png \"Shipping verdicts to Elastic\")\n\nAlerts in Slack and GitHub Issues solve the immediate notification problem, but they don't give you a queryable history. Every verdict the detector produces (e.g. benign, suspicious, or malicious), can optionally ship to Elasticsearch as a structured document in the logs-cicd.abuse-default data stream. The workflow ships the verdict along with CI/CD metadata (platform, repository, actor, event type, run URL) into a single index that spans all three supported platforms.\n\nThis is where cross-platform correlation becomes practical. A GitHub Actions alert and a GitLab CI alert from the same actor land in the same data stream, queryable in a single ES|QL statement:\n\n```sql\nFROM logs-cicd.abuse-* \nWHERE verdict.verdict IN (\"malicious\", \"suspicious\") AND @timestamp \u003e NOW() - 7 days \nEVAL platform = cicd.platform, repo = cicd.repository, actor = cicd.actor, severity = verdict.severity\nKEEP @timestamp, platform, repo, actor, severity\nSORT @timestamp DESC\n```\n\n![Cross Platform Verdicts From GitHub Actions, GitLab CI, Azure DevOps Pipelines](/assets/images/detecting-cicd-pipeline-abuse-with-llm-augmented-analysis/image5.png \"Cross Platform Verdicts From GitHub Actions, GitLab CI, Azure DevOps Pipelines\")  \n\nThe schema includes  cicd.platform, cicd.repository, cicd.actor, and the full verdict object (verdict, severity, confidence, summary, reasons, evidence), making it straightforward to build detection rules. A coordinated campaign that hits multiple repos within an hour, a repeat offender flagged across platforms, or a spike in critical findings that warrants an incident response page can be correlated.\n\n## Validating against real attacks\n\nTo validate coverage, we compared our detection patterns against the actual source code of offensive tools, published research, and public post-mortems.\n\n### Nord Stream: verbatim payload matching\n\nNord Stream is Synacktiv's open-source CI/CD secret extraction tool supporting GitHub, GitLab, and Azure DevOps. We pulled the YAML generator source (`nordstream/yaml/github.py`) and compared its output templates against our example diffs.\n\n* The GitHub payload template uses `env -0 | awk -v RS='0' '/^secret_/ {print $0}' | base64 -w0 | base64 -w0`. Our `nord-stream-pipeline-exfil.diff` contains this line verbatim, and our `double_base64`, `env_null_dump`, and `env_secret_grep` signals all fire.  \n* The OIDC Azure template uses `azure/login@v1` with `id-token: write` permissions followed by az account `get-access-token | base64 -w0 | base64 -w0`. Our diff captures this exact flow and triggers `cloud_auth_action` and `id_token_write`.  \n* The Azure DevOps pipeline techniques (`addSpnToEnvironment` for SPN credential exposure, `DownloadSecureFile` for secure file theft, SSH task source patching via `ssh.js` modification) are all present in `nord-stream-azure-devops.diff` and detected by platform-specific signals.\n\n### ArtiPACKED: the artifact race condition\n\nThe [ArtiPACKED](https://unit42.paloaltonetworks.com/github-repo-artifacts-leak-tokens/) research from Palo Alto Unit 42 showed that uploading the entire checkout directory as an artifact leaks the `.git/config` file containing the `GITHUB_TOKEN`. With the v4 artifact API allowing mid-run downloads, an attacker can extract and use the token before the job completes.\n\nOur `artifact-token-leak.diff` models this exact pattern, using `upload-artifact` with `path: .` (the entire workspace). The `upload_artifact` signal catches it, and the LLM evaluates whether the upload scope includes the `.git` directory.\n\n### GITHUB_ENV injection: LD_PRELOAD to RCE\n\n[Legit Security's research](https://www.legitsecurity.com/blog/github-privilege-escalation-vulnerability-0) on Google Firebase and Apache showed that writing untrusted input to `$GITHUB_ENV` allows an attacker to set arbitrary environment variables like `LD_PRELOAD` and `NODE_OPTIONS`, achieving code execution in privileged workflows.\n\nOur `github-env-injection.diff` reproduces this technique with three distinct payloads, including `LD_PRELOAD` pointing to a malicious shared object, `NODE_OPTIONS` with a required injection, and $`GITHUB_PATH` manipulation. The `github_env_write`, `ld_preload`, and `github_path_write` signals all trigger as expected.\n\n### Contagious Interview: IDE config as initial access\n\nThe [Contagious Interview campaign](https://www.abstract.security/blog/contagious-interview-tracking-the-vs-code-tasks-infection-vector) attributed to DPRK targets developers through fake job interviews, distributing repositories with `.vscode/tasks.json` files that auto-execute on folder open. The presentation is hidden (`reveal: never`, `echo: false`), and the payload uses `curl` | `node` for silent execution.\n\nOur `ide-config-poisoning.diff` captures the full attack chain, including the auto-execute trigger (`runOn: folderOpen`), the hidden presentation, the `curl | node` payload, the `files.exclude` entry that hides the `.vscode` directory, and a trojanized postinstall hook with base64-encoded URLs and `eval()` for code execution. Six signals pick this up at once.\n\n## Defensive recommendations\n\nBeyond deploying the detector, here are some hardening measures that came directly out of the attack patterns we studied:\n\n* Pin all actions to SHA, not tags, not branches. SHA-pinned references prevent retroactive tag modification attacks like `tj-actions` (CVE-2025-30066).  \n* Scope secrets to individual steps rather than using job-level environment variables. Each step should only have access to the secrets it actually needs.  \n* Use short lived, ephemeral tokens when possible to reduce attack surface  \n* Avoid `pull_request_target` unless strictly necessary. If you must use it, never checkout the PR head code in the same workflow. Use a separate `workflow_run-triggered workflow` for operations that need both secrets and PR context.  \n* Set explicit permissions on every workflow because the default token permissions are far too broad. Set `permissions: {}` at the workflow level and add specific permissions per job.  \n* Enable `persist-credentials: false` on checkout since the default behavior of actions/checkout persists the `GITHUB_TOKEN` in the `.git` directory. If you upload artifacts, this token goes with them.\n\n## Summary\n\nCI/CD pipelines have become a major attack surface for supply chain compromise. The same automation that makes modern software delivery possible is what attackers exploit to harvest credentials, poison packages, and pivot to cloud infrastructure. Traditional code review doesn't catch these patterns well because they're subtle, platform-specific, and designed to look like legitimate DevOps changes.\n\nCombining regex-based signal extraction with LLM reasoning lets us surface these patterns at the pull request stage, before they reach production. The repo includes the full threat model, test suite, and example diffs if you want to dig into the details or adapt it to your own environment.\n\nTo get started, check out the [cicd-abuse-detector repo](https://github.com/elastic/cicd-abuse-detector) for setup instructions, the full threat model, and example diffs.
