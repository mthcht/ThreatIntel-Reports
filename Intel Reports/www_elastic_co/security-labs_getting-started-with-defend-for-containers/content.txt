id="introduction" class="absolute -top-32"></span>Introduction</h2>
<p>Linux systems remain a critical foundation for modern infrastructure, particularly in cloud-native environments where containers and orchestration platforms are the norm. As workloads move from long-lived hosts to ephemeral containers, attacker tradecraft shifts as well. Activity that once left persistent artifacts on disk is increasingly confined to short-lived, runtime behavior that can be difficult to capture using traditional log sources.</p>
<p>Detection engineering in these environments, therefore, depends heavily on runtime visibility. Understanding how processes execute inside containers, how files are accessed, and how workloads interact with the host becomes more important than relying on static indicators or post-incident artifacts.</p>
<p>Elastic provides several Linux-focused telemetry sources to support this type of detection work. In <a href="https://www.elastic.co/security-labs/linux-detection-engineering-with-auditd">earlier posts in this series</a>, we focused on host-level visibility using Auditd and Auditd Manager, showing how low-level system events can be translated into high-fidelity detections. In this post, the focus shifts to Elastic’s Defend for Containers: a runtime security integration built specifically for containerized Linux workloads.</p>
<p>The goal of this article is not to document every Defend for Containers feature, but to provide a practical starting point for detection engineers: what data the integration produces and how to reason about that data. In the next part, we will look into how it can be applied to realistic container attack scenarios.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="streamlined-visibility-with-defend-for-containers" class="absolute -top-32"></span>Streamlined visibility with Defend for Containers</h2>
<p>We are excited to announce the arrival of Defend for Containers in the 9.3.0 release. This integration brings a streamlined approach to container security, offering a strong foundation for visibility in cloud-native infrastructures. Users can leverage a suite of detection rules tailored to defend against modern Kubernetes threats and container-specific vulnerabilities. The arrival of Defend for Containers is accompanied by <a href="https://github.com/elastic/detection-rules/tree/main/rules/integrations/cloud_defend">a container-specific detection ruleset</a>, designed around realistic container and Kubernetes threat models.</p>
<p>At the time of writing, the Defend for Containers ruleset provides baseline coverage for common container attack techniques, including reconnaissance activity, credential access attempts, kubelet attacks, service account token abuse, interactive process execution, file creation and modification, interpreter abuse, encoded payload execution, tooling installation, tunneling behavior, and multiple privilege escalation vectors. Importantly, all existing container- and Kubernetes-specific detection rules <a href="https://github.com/elastic/detection-rules/pull/5685">have been made compatible with Defend for Containers</a>, allowing previously host-centric logic to operate directly on container runtime telemetry.</p>
<p>This makes Defend for Containers a practical and immediately usable data source for Linux detection engineers focused on behavior-driven runtime detection. The remainder of this post focuses on how that telemetry looks in practice and how it can be applied to real-world container attack scenarios.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="introduction-to-defend-for-containers" class="absolute -top-32"></span>Introduction to Defend for Containers</h2>
<p><a href="https://www.elastic.co/docs/reference/integrations/cloud_defend">Defend for Containers</a> is a runtime security integration that provides visibility into Linux containers as they execute. Instead of relying on static image scanning or post-execution logs, it focuses on observing container behavior in real time.</p>
<p>At a high level, Defend for Containers captures security-relevant runtime events from running containers, such as process execution and file access. These events are enriched with container and orchestration context and shipped into Elasticsearch, where they can be analyzed and used as input for detection rules.</p>
<p>From a detection engineering perspective, Defend for Containers sits at the intersection of traditional Linux behavior and the container context. Processes, syscalls, and file activity remain core signals, but they are now scoped to containers, namespaces, and workloads that may only exist briefly.</p>
<p>Defend for Containers is deployed as part of the Elastic Agent and integrates directly with Elastic Security. Once enabled, it provides a dedicated stream of container runtime events that can be queried using KQL or ES|QL, or consumed directly by detection analytics. This allows detection engineers to apply familiar analysis techniques while accounting for the operational realities of cloud-native workloads.</p>
<p>In the sections that follow, we will examine Defend for Containers events in more detail and walk through several container attack scenarios to illustrate how this data can be used in practice.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="defend-for-containers-setup" class="absolute -top-32"></span>Defend for Containers setup</h3>
<p>Before you can take advantage of Defend for Containers&#x27; runtime visibility and analytics, you need to deploy the integration and configure a policy that defines which events to observe and what actions to take when matching activity is encountered. More information about the integration and its setup can be found <a href="https://www.elastic.co/docs/reference/integrations/cloud_defend">here</a>. At a high level, this setup consists of:</p>
<ol>
<li>Deploying the Defend for Containers integration via Elastic Agent in your Kubernetes environment.</li>
<li>Configuring or customizing the Defend for Containers policy, which consists of selectors that define which operations to match and responses that define what actions to take.</li>
<li>Validating and refining the policy based on observed workload behavior.</li>
</ol>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="deployment-methods" class="absolute -top-32"></span>Deployment methods</h3>
<p>Defend for Containers is delivered as an Elastic Agent integration and relies on Elastic Agent to collect and forward container runtime telemetry into your Elastic Stack. For Kubernetes workloads, you install the integration via the Elastic Security UI and then enroll agents on your cluster nodes.</p>
<p>The basic deployment flow is:</p>
<p>In the Elastic Security UI, navigate to <a href="https://www.elastic.co/docs/reference/fleet">Fleet</a> and create a new Agent Policy (or add the integration to an existing one). Once the Agent Policy is created, we can add the “Defend for Containers” integration to the policy.</p>
<p></p>
<p>Give the integration a name and optionally adjust the default selectors and responses (we will look into the available options further down in this publication). Once “Add integration” is selected, a new Agent Policy with the correct integration should be available.</p>
<p></p>
<p>For this demonstration, we will leverage the Kubernetes deployment method. To deploy this policy to a workload, we can navigate to Actions → Add agent → Kubernetes. Here, we see instructions for copying or downloading the Kubernetes manifest.</p>
<p></p>
<p>An important note to be aware of is: “<em>Note that the following manifest contains resource limits that may not be appropriate for a production environment. Review our guide on <a href="https://www.elastic.co/docs/reference/fleet/scaling-on-kubernetes#_specifying_resources_and_limits_in_agent_manifests">Scaling Elastic Agent on Kubernetes</a> before deploying this manifest.</em>”</p>
<p>You will need to include the following <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">capabilities</code> under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">securityContext</code> in your Kubernetes YAML for the service to work:</p>
<pre><code>securityContext:
    runAsUser: 0
    capabilities:
      add:
        - BPF ## Enables both BPF &amp; eBPF
        - PERFMON
        - SYS_RESOURCE</code></pre>
<p>After copying or downloading the provided <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">elastic-agent-managed-kubernetes.yml</code> manifest, you can edit the manifest as needed, and apply the manifest with:</p>
<pre><code>kubectl apply -f elastic-agent-managed-kubernetes.yml</code></pre>
<p>As also mentioned in the manifest, review the guide “<a href="https://www.elastic.co/docs/reference/fleet/running-on-kubernetes-managed-by-fleet">Run Elastic Agent on Kubernetes managed by Fleet</a>” for more deployment information.</p>
<p>Wait for the Elastic Agent pods to schedule and for data to begin flowing into Elasticsearch.</p>
<p></p>
<p>Once deployed, Elastic Agent will establish a connection to Fleet, enroll under the selected policy, and begin emitting Defend for Containers telemetry that Elastic Security can consume.</p>
<p>In the next section, we will take a look at the integration configuration options and explore which features are available to use.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="defend-for-containers-policies" class="absolute -top-32"></span>Defend for Containers policies</h3>
<p>At the heart of Defend for Containers&#x27; configuration is the policy. Policies determine what activity to observe and how to respond when matching events occur. Policies are composed of two fundamental building blocks:</p>
<ul>
<li><strong>Selectors:</strong> define which events are of interest by specifying operations and conditions;</li>
<li><strong>Responses:</strong> define what actions to take when a selector’s conditions are met.</li>
</ul>
<p>Defend for Containers policies can be edited before deployment or modified post-deployment via the Elastic Security UI’s policy editor.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="policy-structure" class="absolute -top-32"></span>Policy structure</h4>
<p>Each policy must contain at least one selector and at least one response. A typical selector specifies one or more operations (such as process events or file activities) and uses conditions (like container image name, namespace, or pod label) to narrow the scope. Responses reference selectors and indicate what action to take when events match.</p>
<p>The default Defend for Containers policy includes two selector-response pairs: “Threat Detection” and “Drift Detection &amp; Prevention”.</p>
<p><strong>Threat detection:</strong> A <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">selector</code> named <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">allProcesses</code> matches all <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">fork</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">exec</code> events from containers.</p>
<p></p>
<p>And the associated <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">response</code> has the action set to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Log</code>, ensuring that events are ingested and can be analyzed.</p>
<p></p>
<p><strong>Drift detection &amp; prevention:</strong> A selector named <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">executableChanges</code> matches <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">createExecutable</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">modifyExecutable</code> operations.</p>
<p></p>
<p>And the response is configured to create alerts (and can be modified to block those operations).</p>
<p></p>
<p>These can be modified via the UI, but under the hood, these policies are simple YAML configuration files that can be easily modified and used in any CI|CD flows:</p>
<pre><code>process:
  selectors:
    - name: allProcesses
      operation:
        - fork
        - exec
  responses:
    - match:
        - allProcesses
      actions:
        - log
file:
  selectors:
    - name: executableChanges
      operation:
        - createExecutable
        - modifyExecutable
  responses:
    - match:
        - executableChanges
      actions:
        - alert</code></pre>
<p>Next, we will take a look at some example selectors and responses and discuss the options you have for setting up the integration to your liking.</p>
<p><strong>Example selector snippet</strong></p>
<p>Selectors allow fine-grained matching using conditions on fields such as:</p>
<ul>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">containerImageFullName</code>: full image names like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">docker.io/nginx</code>;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">containerImageName</code>: partial image names;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">containerImageTag</code>: specific tags like latest;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubernetesClusterId</code>: Kubernetes cluster IDs;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubernetesClusterName</code>: Kubernetes cluster names;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubernetesNamespace</code>: namespaces where the workload runs;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubernetesPodName</code>: pod names, with support for trailing wildcards;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubernetesPodLabel</code>: label key/value pairs, with wildcard support.</li>
</ul>
<pre><code>selectors:
  - name: nodeExports
    file:
      operations:
        - createExecutable
        - modifyExecutable
      containerImageName:
        - &quot;nginx&quot;
      kubernetesNamespace:
        - &quot;prod-*&quot;</code></pre>
<p>In this example, the selector named <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nodeExports</code> matches file events that create or modify executables within containers whose image names contain “nginx” and whose Kubernetes namespace begins with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">“prod-”</code>.</p>
<p><strong>Example response snippet</strong></p>
<p>Responses determine what happens when selector conditions are met. Common actions include:</p>
<ul>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">log</code>: send the event as telemetry for analysis;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">alert</code>: create an alert in Elastic Security;</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">block</code>: prevent the operation (for supported types).</li>
</ul>
<pre><code>responses:
  - name: alertAndBlockNodeExports
    matchSelectors:
      - nodeExports
    actions:
      - alert
      - block</code></pre>
<p>Here, the response named <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">alertAndBlockNodeExports</code> references the previously defined nodeExports selector and will both generate an alert and block the operation.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="wildcards-and-matching" class="absolute -top-32"></span>Wildcards and matching</h4>
<p>Selectors in Defend for Containers support trailing wildcards in string-based conditions (such as pod names or image tags). This allows broad matching without enumerating every possible value. For example, a pod selector of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">backend-*</code> will match all pods whose names begin with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">backend-</code>, while a label condition such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">role:api*</code> matches label values that start with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">api</code>.</p>
<p>This wildcarding is essential in dynamic environments where workloads scale and shift rapidly.</p>
<p>In addition to simple string matching, Defend for Containers selectors also support <strong>path-based wildcard semantics</strong> when matching file paths. Consider the following selector example:</p>
<pre><code>- name:
  targetFilePath:
    - /usr/bin/echo
    - /usr/sbin/*
    - /usr/local/**</code></pre>
<p>In this example:</p>
<ul>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/bin/echo</code> matches only the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">echo</code> binary at that exact path.</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/sbin/*</code> matches everything that is a direct child of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/sbin</code>.</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/local/**</code> matches everything recursively under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/local</code>, including paths such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/local/bin/something</code>.</li>
</ul>
<p>These distinctions make it possible to precisely scope file-based selectors, balancing coverage and noise. In practice, they allow detection engineers to target specific binaries, entire directories, or deep directory trees, depending on the use case, without resorting to overly permissive rules.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="tying-it-all-together" class="absolute -top-32"></span>Tying it all together</h4>
<p>Up to this point, we have looked at Defend for Containers selectors, wildcard semantics, event types, and how they surface attacker behavior at runtime. The final step is to understand how these pieces come together within a policy to express real detection logic.</p>
<p>Consider the following policy fragment:</p>
<pre><code>file:
  selectors:
    - name: binDirExeMods
      operation:
        - createExecutable
        - modifyExecutable
      targetFilePath:
        - /usr/bin/**
    - name: etcFileChanges
      operation:
        - createFile
        - modifyFile
        - deleteFile
      targetFilePath:
        - /etc/**
    - name: nginx
      containerImageName:
        - nginx

  responses:
    - match:
        - binDirExeMods
        - etcFileChanges
      exclude:
        - nginx
      actions:
        - alert
        - block</code></pre>
<p>This policy defines three selectors. Two selectors (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">binDirExeMods</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">etcFileChanges</code>) describe file system activity of interest, while the third selector (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nginx</code>) describes a container context to exclude.</p>
<p>The response section ties these selectors together. The selectors listed under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">match</code> are logically <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">OR</code>’d, meaning that <em>either</em> condition is sufficient to trigger the response. The selector listed under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">exclude</code> acts as a logical <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NOT</code>, removing matching events when the container image is <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nginx</code>.</p>
<p>Read in plain language, the policy expresses the following logic:</p>
<p><em>If an executable is created or modified anywhere under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/bin</code>, <strong>or</strong> a file is created, modified, or deleted under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/etc</code>,  <strong>and</strong> the activity does not originate from an <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nginx</code> container, then generate an alert and block the action.</em></p>
<p>In Boolean form, this can be expressed as:</p>
<pre><code>IF (binDirExeMods OR etcFileChanges) AND NOT nginx
→ alert + block</code></pre>
<p>This is where Defend for Containers policies become powerful. Rather than writing complex detection logic in a query language, selectors let you decompose behavior into small, reusable building blocks and then combine them declaratively. By mixing path-based selectors, operation types, container context, and exclusions, you can express nuanced detection logic that remains readable and maintainable.</p>
<p>In practice, this model allows detection engineers to translate threat hypotheses directly into policy logic: <em>what</em> behavior matters, <em>where</em> it occurs, <em>in which workloads</em>, and <em>what should happen</em> when it does.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="policy-validation-and-refinement" class="absolute -top-32"></span>Policy validation and refinement</h4>
<p>Once a policy is deployed, it is critical to validate it against real workload behavior before enabling aggressive responses such as blocking. Policies that are too restrictive can disrupt normal container operations; policies that are too permissive may let unwanted activity go unnoticed.</p>
<p>A recommended workflow is:</p>
<ol>
<li>Deploy the default policy in monitoring mode (e.g., with selectors logging events).</li>
<li>Observe the events that appear in Elasticsearch to understand normal workload patterns.</li>
<li>Incrementally tighten selectors and responses, moving from <em>log only</em> → <em>alert</em> → <em>block</em>, testing at each stage.</li>
<li>Use a staging or test cluster to validate blocking behaviors before applying them in production.</li>
</ol>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="defend-for-containers-beta-limitations" class="absolute -top-32"></span>Defend for Containers Beta limitations</h3>
<p>As of writing, Defend for Containers is available as a Beta integration, and its current capabilities and platform support reflect that status.</p>
<p>Defend for Containers formally supports Amazon EKS and Google GKE. While the integration can be deployed on Azure AKS, this configuration is not officially supported. In particular, AKS deployments currently lack file event telemetry, which limits detection coverage for file-based attack techniques in those environments.</p>
<p>The current Beta also does not capture network events. As a result, detections related to outbound connections, lateral network movement, or data exfiltration must rely on complementary data sources, such as the <a href="https://www.elastic.co/docs/reference/integrations/network_traffic">Network Packet Capture integration</a> or <a href="https://www.elastic.co/beats/packetbeat">Packetbeat</a> integrations, rather than on Defend for Containers telemetry alone.</p>
<p>For file activity, Defend for Containers intentionally logs file open events only when opened with write intent. This design choice reduces noise and focuses on behavior that modifies the system state. However, it also means that read-only access to sensitive files, such as secret discovery, configuration scraping, or failed access attempts, is not currently observable.</p>
<p>This limitation impacts detection use cases such as:</p>
<ul>
<li>Searching and reading Kubernetes service account tokens,</li>
<li>Scanning for <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.env</code> files or credential material.</li>
</ul>
<p>These are areas where future Defend for Containers iterations may provide more granular telemetry to support advanced detection engineering use cases.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="enabling-the-defend-for-containers-pre-built-detection-rules" class="absolute -top-32"></span>Enabling the Defend for Containers pre-built detection rules</h3>
<p>Defend for Containers ships with a set of pre-built detection rules that provide baseline coverage for common container attack techniques. Once the integration is enabled, these rules can be activated directly from Elastic Security without additional configuration.</p>
<p>Enabling the pre-built rules is recommended as a starting point, as they are designed to align with Defend for Containers&#x27; runtime telemetry and cover execution, file modification, persistence, and post-compromise behavior inside containers. From there, the rules can be extended or refined to match environment-specific workloads and threat models.</p>
<p></p>
<p>By filtering for “Data Source: Elastic Defend for Containers”, you can find all rules associated with this integration.</p>
<p><strong>Note:</strong> if you do not see any rules pop up, make sure your stack is running version 9.3.0, as these rules are deployed only on 9.3.0+.</p>
<p>With all important Beta limitations mapped, the integration deployed, the pre-built detection rules installed and enabled, and a working policy in place, the next step is to explore the event semantics Defend for Containers produces, including fields commonly used in detection logic, performance considerations, and how these events differ from Elastic Defend events.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="analyzing-defend-for-containers-events" class="absolute -top-32"></span>Analyzing Defend for Containers events</h2>
<p>Now that Defend for Containers is deployed and policies are in place, the next step is understanding the events it generates. Similar to working with Elastic Defend or Auditd Manager, Defend for Containers telemetry becomes far more valuable once you develop a mental model of how events are structured and which fields are most relevant for detection engineering.</p>
<p>Defend for Containers produces multiple event types, most notably process events and file events, each enriched with container, host, and orchestration context. While the underlying signals remain rooted in Linux behavior, the additional Kubernetes and container metadata enable you to reason about activity in ways not possible with host-only telemetry.</p>
<p>The following sections walk through the most important field groups and event types, using real Defend for Containers events as reference points.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="common-fields" class="absolute -top-32"></span>Common fields</h3>
<p>Before diving into specific event categories, it is useful to understand the fields that consistently appear across Defend for Containers telemetry. These fields provide the contextual glue that ties individual runtime actions back to policies, selectors, and the underlying execution points inside the kernel.</p>
<p>While process and file events differ in their details, the fields described below are present across Defend for Containers data streams and are often the first place to look when validating detections or troubleshooting policy behavior.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="defend-for-containers-specific-context" class="absolute -top-32"></span>Defend for Containers-specific context</h4>
<p>Defend for Containers adds several fields specific to how events are collected and policies are applied.</p>
<p></p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cloud_defend.hook_point</code> field indicates where in the kernel the event was captured. In the example shown, values such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tracepoint__sched_process_fork</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tracepoint__sched_process_exec</code> reveal that the event was generated from kernel tracepoints associated with process creation and execution.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cloud_defend.matched_selectors</code> field shows which selectors in the active policy matched the event. In the example, the value <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">allProcesses</code> indicates that this event matched a broad selector that captures all process activity. When tuning policies or investigating alerts, this field is essential for understanding <em>why</em> an event was captured.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cloud_defend.package_policy_id</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cloud_defend.package_policy_revision</code> fields tie the event back to a specific Elastic Agent policy and its revision. This makes it possible to correlate events with configuration changes over time and to verify which version of a policy was active when the event occurred.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="event-metadata" class="absolute -top-32"></span>Event metadata</h4>
<p>Defend for Containers events follow the <a href="https://www.elastic.co/docs/reference/ecs">Elastic Common Schema</a> conventions and include standard event metadata that describes the activity&#x27;s type and lifecycle.</p>
<p></p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.category</code> field identifies the high-level type of activity, such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file</code>, and is typically the first field used when filtering Defend for Containers data. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.action</code> field describes what occurred, for example, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">fork</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">exec</code> for process activity, or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">open</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">creation</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">modification</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">deletion</code> for file events.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.type</code> field adds lifecycle context, such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">start</code> for process execution, and is often used together with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.action</code> to distinguish different phases of activity. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.dataset</code> field indicates the originating Defend for Containers data stream, such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cloud_defend.process</code>, which is useful when building dataset-scoped queries or detections.</p>
<p>Additional metadata fields like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.id</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.ingested</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.kind</code> are primarily used for correlation, ordering, and troubleshooting rather than detection logic.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="host-information" class="absolute -top-32"></span>Host information</h4>
<p>Defend for Containers events include full host context, similar to Elastic Defend and Auditd Manager. This makes it possible to correlate container runtime activity back to the underlying Kubernetes node.</p>
<p></p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">host.name</code> field identifies the node on which the container is running, while <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">host.os.*</code> provides operating system details such as distribution and kernel version. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">host.architecture</code> field indicates the CPU architecture, which can be relevant when analyzing binary execution or kernel-specific behavior.</p>
<p>One particularly useful field is <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">host.pid_ns_ino</code>, which identifies the PID namespace. This field allows container activity to be correlated with host-level process and kernel telemetry, and is especially valuable when investigating container escape attempts or node-level impact.</p>
<p>This host context is critical when analyzing cloud-native attacks, as multiple containers often share the same host and kernel, and a container&#x27;s runtime behavior can have implications beyond its boundaries.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="container-and-orchestrator-context" class="absolute -top-32"></span>Container and orchestrator context</h4>
<p>Defend for Containers&#x27; primary strength lies in its container awareness. Every runtime event is enriched with container and orchestration metadata, allowing activity to be analyzed in the context of <em>what</em> is running, <em>where it is running</em>, and <em>with which privileges</em>.</p>
<p></p>
<p>At the container level, fields such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">container.id</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">container.name</code> uniquely identify the running container, while <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">container.image.name</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">container.image.tag</code>, and the image hash provide visibility into the workload’s origin and version. This is especially useful for distinguishing between expected utility images and unexpected or ad hoc workloads.</p>
<p>A key field for risk assessment is <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">container.security_context.privileged</code>. This field explicitly indicates whether a container is running in privileged mode. When privileged execution is combined with other signals such as interactive shells or broad Linux capabilities, the risk profile of any detected activity increases significantly.</p>
<p></p>
<p>Defend for Containers also enriches events with orchestration context. Fields such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">orchestrator.cluster.name</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">orchestrator.namespace</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">orchestrator.resource.name</code> (typically the Pod name) tie runtime behavior back to Kubernetes workloads. Labels exposed via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">orchestrator.resource.label</code> further allow detections to incorporate workload intent and ownership.</p>
<p>For detection engineering, this context enables precise scoping of detections to:</p>
<ul>
<li>specific namespaces (for example, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kube-system</code>),</li>
<li>privileged or high-risk containers,</li>
<li>workloads with sensitive labels,</li>
<li>or known utility images such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netshoot</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubectl</code>, or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">curl</code>.</li>
</ul>
<p>This layer of enrichment allows container-aware detection logic to be expressed directly, without having to infer intent indirectly from filesystem paths, cgroups, or namespace identifiers.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="process-events" class="absolute -top-32"></span>Process events</h3>
<p>Process execution is one of the most important signal types that Defend for Containers provides. Process events capture <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">fork</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">exec</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">end</code> activities within containers and expose detailed lineage information critical to understanding how execution unfolds at runtime.</p>
<p></p>
<p>Several fields are particularly important for detection engineering. The combination of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.name</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.executable</code> identifies what was executed and from where, while <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.args</code> provides insight into how it was invoked. Fields such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.pid</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.start</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.end</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.exit_code</code> describe the process lifecycle and are useful for timing analysis and execution-flow reconstruction. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.entity_id</code> provides a stable identifier that allows processes to be tracked across multiple related events.</p>
<p>Defend for Containers also captures rich ancestry information. Fields under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.parent.*</code> describe the immediate parent process, making it possible to detect suspicious parent–child relationships such as shells spawned by unexpected binaries. In addition, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.entry_leader.*</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.session_leader.*</code> provide higher-level anchors within the process tree.</p>
<p>Much like Elastic Defend, Defend for Containers models processes as a graph rather than isolated events. The entry leader is especially useful in container environments, as it often represents the initial process launched by the container runtime (for example, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">containerd</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">runc</code>, or a shell specified as the container entrypoint). Anchoring detections to the entry leader allows process trees to be interpreted consistently, even when containers spawn many short-lived child processes.</p>
<p></p>
<p>Session leader fields provide additional context about interactive execution and session boundaries, helping distinguish background services from interactive or attacker-driven activity.</p>
<p>Together, these fields make it possible to express detection logic that goes beyond single executions and instead reasons about execution chains, lineage, and intent, which is essential for detecting real-world container attack techniques.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="capabilities-and-privilege-context" class="absolute -top-32"></span>Capabilities and privilege context</h4>
<p>One of the more powerful aspects of the Defend for Containers process events is the inclusion of Linux capability information. For each process, Defend for Containers exposes both the effective and permitted capability sets via:</p>
<ul>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.thread.capabilities.effective</code></li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.thread.capabilities.permitted</code></li>
</ul>
<p>These fields describe what a process is actually allowed to do at runtime, independent of its user ID or container boundary.</p>
<p></p>
<p>In privileged containers, processes often expose a broad set of effective capabilities, including highly sensitive ones such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CAP_SYS_ADMIN</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CAP_SYS_MODULE</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CAP_SYS_PTRACE</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CAP_SYS_RAWIO</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CAP_BPF</code>. The presence of these capabilities significantly changes the risk profile of any executed command, as they enable actions that can directly impact the host kernel or other workloads.</p>
<p>From a detection engineering perspective, this context is critical. It allows detections to move beyond simple process-name matching and instead reason about <em>impact</em>. The same binary execution can have vastly different implications depending on whether it runs with a minimal capability set or with near-host-level privileges.</p>
<p>In practice, capability data enables detection engineers to:</p>
<ul>
<li>Identify suspicious tooling executed inside overly permissive containers.</li>
<li>Correlate runtime behavior with dangerous capability combinations.</li>
<li>Prioritize alerts based on actual exploitation potential rather than surface-level activity.</li>
</ul>
<p>This becomes especially relevant to container breakout research, where the presence or absence of specific capabilities often determines whether an exploit is viable.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="interactive-execution" class="absolute -top-32"></span>Interactive execution</h4>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.interactive</code> field indicates whether a process is associated with an interactive session. In container environments, interactive execution is relatively rare for production workloads and often correlates strongly with post-compromise or hands-on-keyboard activity.</p>
<p></p>
<p>Defend for Containers exposes interactivity not only at the process level, but also across related execution contexts, including <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.parent.interactive</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.entry_leader.interactive</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">process.session_leader.interactive</code>. This makes it possible to determine whether an entire execution chain is interactive, rather than relying on a single process flag in isolation.</p>
<p>Common examples of interactive execution within containers include spawning a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bash</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">sh</code> shell, running interactive utilities such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">curl</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kubectl</code>, or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">busybox</code>, or operator-driven reconnaissance within a compromised Pod. While these actions may be legitimate during debugging, they are uncommon in steady-state production workloads.</p>
<p>When combined with container image, namespace, and privilege context, interactive execution becomes a strong anomaly signal. It allows detection logic to distinguish between expected automated container behavior and activity more consistent with manual intervention or attacker-driven exploration.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="file-events" class="absolute -top-32"></span>File events</h3>
<p>Defend for Containers file events capture filesystem activity inside containers, and are emitted for a variety of operations. Unlike traditional file integrity monitoring, these events are runtime-aware and scoped to container workloads, providing context about <em>how</em> and <em>why</em> file changes occur.</p>
<p>Defend for Containers can detect file activity such as file opens <strong>with write intent</strong>, content modifications, file creations, renames, permission changes, and deletions. By focusing on write-oriented operations, Defend for Containers emphasizes behavior that alters system state rather than passive file access.</p>
<p>This allows detection engineers to reason about file usage patterns at runtime, not just the result of a change.</p>
<p></p>
<p>Several fields are particularly important when building file-based detections. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file.path</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file.name</code> fields identify the affected file and its location, while <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file.extension</code> can help distinguish binaries, scripts, and configuration files. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.action</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.type</code> fields describe what operation occurred and how it should be interpreted in the event lifecycle.</p>
<p>Together, these fields allow Defend for Containers to distinguish benign file access from suspicious modification patterns, such as writing binaries or changing permissions within sensitive directories.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="bringing-it-together" class="absolute -top-32"></span>Bringing it together</h3>
<p>As with any other data source, Defend for Containers telemetry becomes truly valuable once you understand how to combine fields across the process, file, container, and orchestration domains. Rather than relying on static indicators, Defend for Containers enables detection engineering based on runtime behavior, privilege context, and workload identity.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="conclusion" class="absolute -top-32"></span>Conclusion</h2>
<p>Defend for Containers in Elastic Stack 9.3.0 includes container runtime detection as a core component of Linux detection engineering. It features a clear scope, a policy-driven configuration model, and runtime telemetry designed specifically for containerized workloads.</p>
<p>In this post, we examined how to deploy Defend for Containers, how its policy model is structured, and how runtime events are generated and enriched with container and orchestration context. We explored the structure of process and file events, capability metadata, interactive execution signals, and container-specific fields that allow detections to be expressed in a workload-aware manner.</p>
<p>The key takeaway is that effective container detection requires reasoning about runtime behavior in context: processes, file modifications, privileges, and workload identity must be evaluated together. Defend for Containers provides the necessary telemetry to make that possible.</p>

Policies determine what activity to observe and how to respond when matching events occur. Policies are composed of two fundamental building blocks:\n\n* **Selectors:** define which events are of interest by specifying operations and conditions;  \n* **Responses:** define what actions to take when a selector’s conditions are met.\n\nDefend for Containers policies can be edited before deployment or modified post-deployment via the Elastic Security UI’s policy editor.\n\n#### Policy structure\n\nEach policy must contain at least one selector and at least one response. A typical selector specifies one or more operations (such as process events or file activities) and uses conditions (like container image name, namespace, or pod label) to narrow the scope. Responses reference selectors and indicate what action to take when events match.\n\nThe default Defend for Containers policy includes two selector-response pairs: “Threat Detection” and “Drift Detection \u0026 Prevention”.\n\n**Threat detection:** A `selector` named `allProcesses` matches all `fork` and `exec` events from containers.\n\n![Figure 5: Defend for Containers allProcesses selector](/assets/images/getting-started-with-defend-for-containers/image13.png \"Figure 5: Defend for Containers allProcesses selector\")  \n\nAnd the associated `response` has the action set to `Log`, ensuring that events are ingested and can be analyzed.\n\n![Figure 6: Defend for Containers allProcesses `log` response](/assets/images/getting-started-with-defend-for-containers/image11.png \"Figure 6: Defend for Containers allProcesses `log` response\")  \n\n**Drift detection \u0026 prevention:** A selector named `executableChanges` matches `createExecutable` and `modifyExecutable` operations.\n\n![Figure 7: Defend for Containers executableChanges selector](/assets/images/getting-started-with-defend-for-containers/image7.png \"Figure 7: Defend for Containers executableChanges selector\")  \n\nAnd the response is configured to create alerts (and can be modified to block those operations).\n\n![Figure 8: Defend for Containers executableChanges `alert` response](/assets/images/getting-started-with-defend-for-containers/image18.png \"Figure 8: Defend for Containers executableChanges `alert` response\")  \n\nThese can be modified via the UI, but under the hood, these policies are simple YAML configuration files that can be easily modified and used in any CI|CD flows:\n\n```yaml\nprocess:\n  selectors:\n    - name: allProcesses\n      operation:\n        - fork\n        - exec\n  responses:\n    - match:\n        - allProcesses\n      actions:\n        - log\nfile:\n  selectors:\n    - name: executableChanges\n      operation:\n        - createExecutable\n        - modifyExecutable\n  responses:\n    - match:\n        - executableChanges\n      actions:\n        - alert\n```\n\nNext, we will take a look at some example selectors and responses and discuss the options you have for setting up the integration to your liking.\n\n**Example selector snippet**\n\nSelectors allow fine-grained matching using conditions on fields such as:\n\n* `containerImageFullName`: full image names like `docker.io/nginx`;  \n* `containerImageName`: partial image names;  \n* `containerImageTag`: specific tags like latest;  \n* `kubernetesClusterId`: Kubernetes cluster IDs;  \n* `kubernetesClusterName`: Kubernetes cluster names;  \n* `kubernetesNamespace`: namespaces where the workload runs;  \n* `kubernetesPodName`: pod names, with support for trailing wildcards;  \n* `kubernetesPodLabel`: label key/value pairs, with wildcard support.\n\n```yaml\nselectors:\n  - name: nodeExports\n    file:\n      operations:\n        - createExecutable\n        - modifyExecutable\n      containerImageName:\n        - \"nginx\"\n      kubernetesNamespace:\n        - \"prod-*\"\n```\n\nIn this example, the selector named `nodeExports` matches file events that create or modify executables within containers whose image names contain “nginx” and whose Kubernetes namespace begins with `“prod-”`.\n\n**Example response snippet**\n\nResponses determine what happens when selector conditions are met. Common actions include:\n\n* `log`: send the event as telemetry for analysis;  \n* `alert`: create an alert in Elastic Security;  \n* `block`: prevent the operation (for supported types).\n\n```yaml\nresponses:\n  - name: alertAndBlockNodeExports\n    matchSelectors:\n      - nodeExports\n    actions:\n      - alert\n      - block\n```\n\nHere, the response named `alertAndBlockNodeExports` references the previously defined nodeExports selector and will both generate an alert and block the operation.\n\n#### Wildcards and matching\n\nSelectors in Defend for Containers support trailing wildcards in string-based conditions (such as pod names or image tags). This allows broad matching without enumerating every possible value. For example, a pod selector of `backend-*` will match all pods whose names begin with `backend-`, while a label condition such as `role:api*` matches label values that start with `api`.\n\nThis wildcarding is essential in dynamic environments where workloads scale and shift rapidly.\n\nIn addition to simple string matching, Defend for Containers selectors also support **path-based wildcard semantics** when matching file paths. Consider the following selector example:\n\n```yaml\n- name:\n  targetFilePath:\n    - /usr/bin/echo\n    - /usr/sbin/*\n    - /usr/local/**\n```\n\nIn this example:\n\n* `/usr/bin/echo` matches only the `echo` binary at that exact path.  \n* `/usr/sbin/*` matches everything that is a direct child of `/usr/sbin`.  \n* `/usr/local/**` matches everything recursively under `/usr/local`, including paths such as `/usr/local/bin/something`.\n\nThese distinctions make it possible to precisely scope file-based selectors, balancing coverage and noise. In practice, they allow detection engineers to target specific binaries, entire directories, or deep directory trees, depending on the use case, without resorting to overly permissive rules.\n\n#### Tying it all together\n\nUp to this point, we have looked at Defend for Containers selectors, wildcard semantics, event types, and how they surface attacker behavior at runtime. The final step is to understand how these pieces come together within a policy to express real detection logic.\n\nConsider the following policy fragment:\n\n```yaml\nfile:\n  selectors:\n    - name: binDirExeMods\n      operation:\n        - createExecutable\n        - modifyExecutable\n      targetFilePath:\n        - /usr/bin/**\n    - name: etcFileChanges\n      operation:\n        - createFile\n        - modifyFile\n        - deleteFile\n      targetFilePath:\n        - /etc/**\n    - name: nginx\n      containerImageName:\n        - nginx\n\n  responses:\n    - match:\n        - binDirExeMods\n        - etcFileChanges\n      exclude:\n        - nginx\n      actions:\n        - alert\n        - block\n```\n\nThis policy defines three selectors. Two selectors (`binDirExeMods` and `etcFileChanges`) describe file system activity of interest, while the third selector (`nginx`) describes a container context to exclude.\n\nThe response section ties these selectors together. The selectors listed under `match` are logically `OR`’d, meaning that *either* condition is sufficient to trigger the response. The selector listed under `exclude` acts as a logical `NOT`, removing matching events when the container image is `nginx`.\n\nRead in plain language, the policy expresses the following logic:\n\n*If an executable is created or modified anywhere under `/usr/bin`, **or** a file is created, modified, or deleted under `/etc`,  **and** the activity does not originate from an `nginx` container, then generate an alert and block the action.*\n\nIn Boolean form, this can be expressed as:\n\n```text\nIF (binDirExeMods OR etcFileChanges) AND NOT nginx\n→ alert + block\n```\n\nThis is where Defend for Containers policies become powerful. Rather than writing complex detection logic in a query language, selectors let you decompose behavior into small, reusable building blocks and then combine them declaratively. By mixing path-based selectors, operation types, container context, and exclusions, you can express nuanced detection logic that remains readable and maintainable.\n\nIn practice, this model allows detection engineers to translate threat hypotheses directly into policy logic: *what* behavior matters, *where* it occurs, *in which workloads*, and *what should happen* when it does.\n\n#### Policy validation and refinement\n\nOnce a policy is deployed, it is critical to validate it against real workload behavior before enabling aggressive responses such as blocking. Policies that are too restrictive can disrupt normal container operations; policies that are too permissive may let unwanted activity go unnoticed.\n\nA recommended workflow is:\n\n1. Deploy the default policy in monitoring mode (e.g., with selectors logging events).  \n2. Observe the events that appear in Elasticsearch to understand normal workload patterns.  \n3. Incrementally tighten selectors and responses, moving from *log only* → *alert* → *block*, testing at each stage.  \n4. Use a staging or test cluster to validate blocking behaviors before applying them in production.\n\n### Defend for Containers Beta limitations\n\nAs of writing, Defend for Containers is available as a Beta integration, and its current capabilities and platform support reflect that status.\n\nDefend for Containers formally supports Amazon EKS and Google GKE. While the integration can be deployed on Azure AKS, this configuration is not officially supported. In particular, AKS deployments currently lack file event telemetry, which limits detection coverage for file-based attack techniques in those environments.\n\nThe current Beta also does not capture network events. As a result, detections related to outbound connections, lateral network movement, or data exfiltration must rely on complementary data sources, such as the [Network Packet Capture integration](https://www.elastic.co/docs/reference/integrations/network_traffic) or [Packetbeat](https://www.elastic.co/beats/packetbeat) integrations, rather than on Defend for Containers telemetry alone.\n\nFor file activity, Defend for Containers intentionally logs file open events only when opened with write intent. This design choice reduces noise and focuses on behavior that modifies the system state. However, it also means that read-only access to sensitive files, such as secret discovery, configuration scraping, or failed access attempts, is not currently observable.\n\nThis limitation impacts detection use cases such as:\n\n* Searching and reading Kubernetes service account tokens,  \n* Scanning for `.env` files or credential material.\n\nThese are areas where future Defend for Containers iterations may provide more granular telemetry to support advanced detection engineering use cases.\n\n### Enabling the Defend for Containers pre-built detection rules\n\nDefend for Containers ships with a set of pre-built detection rules that provide baseline coverage for common container attack techniques. Once the integration is enabled, these rules can be activated directly from Elastic Security without additional configuration.\n\nEnabling the pre-built rules is recommended as a starting point, as they are designed to align with Defend for Containers' runtime telemetry and cover execution, file modification, persistence, and post-compromise behavior inside containers. From there, the rules can be extended or refined to match environment-specific workloads and threat models.\n\n![Figure 9: Defend for Containers pre-built detection rule installation based on tag](/assets/images/getting-started-with-defend-for-containers/image17.png \"Figure 9: Defend for Containers pre-built detection rule installation based on tag\")  \n\nBy filtering for “Data Source: Elastic Defend for Containers”, you can find all rules associated with this integration.\n\n**Note:** if you do not see any rules pop up, make sure your stack is running version 9.3.0, as these rules are deployed only on 9.3.0+.\n\nWith all important Beta limitations mapped, the integration deployed, the pre-built detection rules installed and enabled, and a working policy in place, the next step is to explore the event semantics Defend for Containers produces, including fields commonly used in detection logic, performance considerations, and how these events differ from Elastic Defend events.\n\n## Analyzing Defend for Containers events\n\nNow that Defend for Containers is deployed and policies are in place, the next step is understanding the events it generates. Similar to working with Elastic Defend or Auditd Manager, Defend for Containers telemetry becomes far more valuable once you develop a mental model of how events are structured and which fields are most relevant for detection engineering.\n\nDefend for Containers produces multiple event types, most notably process events and file events, each enriched with container, host, and orchestration context. While the underlying signals remain rooted in Linux behavior, the additional Kubernetes and container metadata enable you to reason about activity in ways not possible with host-only telemetry.\n\nThe following sections walk through the most important field groups and event types, using real Defend for Containers events as reference points.\n\n### Common fields\n\nBefore diving into specific event categories, it is useful to understand the fields that consistently appear across Defend for Containers telemetry. These fields provide the contextual glue that ties individual runtime actions back to policies, selectors, and the underlying execution points inside the kernel.\n\nWhile process and file events differ in their details, the fields described below are present across Defend for Containers data streams and are often the first place to look when validating detections or troubleshooting policy behavior.\n\n#### Defend for Containers-specific context\n\nDefend for Containers adds several fields specific to how events are collected and policies are applied.\n\n![Figure 10: Defend for Containers’ important `cloud_defend.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image10.png \"Figure 10: Defend for Containers’ important `cloud_defend.*` fields overview\")\n\nThe `cloud_defend.hook_point` field indicates where in the kernel the event was captured. In the example shown, values such as `tracepoint__sched_process_fork` and `tracepoint__sched_process_exec` reveal that the event was generated from kernel tracepoints associated with process creation and execution. \n\nThe `cloud_defend.matched_selectors` field shows which selectors in the active policy matched the event. In the example, the value `allProcesses` indicates that this event matched a broad selector that captures all process activity. When tuning policies or investigating alerts, this field is essential for understanding *why* an event was captured.\n\nThe `cloud_defend.package_policy_id` and `cloud_defend.package_policy_revision` fields tie the event back to a specific Elastic Agent policy and its revision. This makes it possible to correlate events with configuration changes over time and to verify which version of a policy was active when the event occurred.\n\n#### Event metadata\n\nDefend for Containers events follow the [Elastic Common Schema](https://www.elastic.co/docs/reference/ecs) conventions and include standard event metadata that describes the activity's type and lifecycle.\n\n![Figure 11: Defend for Containers’ important `event.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image2.png \"Figure 11: Defend for Containers’ important `event.*` fields overview\")\n\nThe `event.category` field identifies the high-level type of activity, such as `process` or `file`, and is typically the first field used when filtering Defend for Containers data. The `event.action` field describes what occurred, for example, `fork` or `exec` for process activity, or `open`, `creation`, `modification`, and `deletion` for file events.\n\nThe `event.type` field adds lifecycle context, such as `start` for process execution, and is often used together with `event.action` to distinguish different phases of activity. The `event.dataset` field indicates the originating Defend for Containers data stream, such as `cloud_defend.process`, which is useful when building dataset-scoped queries or detections.\n\nAdditional metadata fields like `event.id`, `event.ingested`, and `event.kind` are primarily used for correlation, ordering, and troubleshooting rather than detection logic.\n\n#### Host information\n\nDefend for Containers events include full host context, similar to Elastic Defend and Auditd Manager. This makes it possible to correlate container runtime activity back to the underlying Kubernetes node.\n\n![Figure 12: Defend for Containers’ important `host.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image9.png \"Figure 12: Defend for Containers’ important `host.*` fields overview\")\n\nThe `host.name` field identifies the node on which the container is running, while `host.os.*` provides operating system details such as distribution and kernel version. The `host.architecture` field indicates the CPU architecture, which can be relevant when analyzing binary execution or kernel-specific behavior.\n\nOne particularly useful field is `host.pid_ns_ino`, which identifies the PID namespace. This field allows container activity to be correlated with host-level process and kernel telemetry, and is especially valuable when investigating container escape attempts or node-level impact.\n\nThis host context is critical when analyzing cloud-native attacks, as multiple containers often share the same host and kernel, and a container's runtime behavior can have implications beyond its boundaries.\n\n#### Container and orchestrator context\n\nDefend for Containers' primary strength lies in its container awareness. Every runtime event is enriched with container and orchestration metadata, allowing activity to be analyzed in the context of *what* is running, *where it is running*, and *with which privileges*.\n\n![Figure 13: Defend for Containers’ important `container.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image8.png \"Figure 13: Defend for Containers’ important `container.*` fields overview\")\n\nAt the container level, fields such as `container.id` and `container.name` uniquely identify the running container, while `container.image.name`, `container.image.tag`, and the image hash provide visibility into the workload’s origin and version. This is especially useful for distinguishing between expected utility images and unexpected or ad hoc workloads.\n\nA key field for risk assessment is `container.security_context.privileged`. This field explicitly indicates whether a container is running in privileged mode. When privileged execution is combined with other signals such as interactive shells or broad Linux capabilities, the risk profile of any detected activity increases significantly.\n\n![Figure 14: Defend for Containers’ important `orchestrator.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image3.png \"Figure 14: Defend for Containers’ important `orchestrator.*` fields overview\")\n\nDefend for Containers also enriches events with orchestration context. Fields such as `orchestrator.cluster.name`, `orchestrator.namespace`, and `orchestrator.resource.name` (typically the Pod name) tie runtime behavior back to Kubernetes workloads. Labels exposed via `orchestrator.resource.label` further allow detections to incorporate workload intent and ownership.\n\nFor detection engineering, this context enables precise scoping of detections to:\n\n* specific namespaces (for example, `kube-system`),  \n* privileged or high-risk containers,  \n* workloads with sensitive labels,  \n* or known utility images such as `netshoot`, `kubectl`, or `curl`.\n\nThis layer of enrichment allows container-aware detection logic to be expressed directly, without having to infer intent indirectly from filesystem paths, cgroups, or namespace identifiers.\n\n### Process events\n\nProcess execution is one of the most important signal types that Defend for Containers provides. Process events capture `fork`, `exec`, and `end` activities within containers and expose detailed lineage information critical to understanding how execution unfolds at runtime.\n\n![Figure 15: Defend for Containers’ important `process.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image12.png \"Figure 15: Defend for Containers’ important `process.*` fields overview\")\n\nSeveral fields are particularly important for detection engineering. The combination of `process.name` and `process.executable` identifies what was executed and from where, while `process.args` provides insight into how it was invoked. Fields such as `process.pid`, `process.start`, `process.end`, and `process.exit_code` describe the process lifecycle and are useful for timing analysis and execution-flow reconstruction. The `process.entity_id` provides a stable identifier that allows processes to be tracked across multiple related events.\n\nDefend for Containers also captures rich ancestry information. Fields under `process.parent.*` describe the immediate parent process, making it possible to detect suspicious parent–child relationships such as shells spawned by unexpected binaries. In addition, `process.entry_leader.*` and `process.session_leader.*` provide higher-level anchors within the process tree.\n\nMuch like Elastic Defend, Defend for Containers models processes as a graph rather than isolated events. The entry leader is especially useful in container environments, as it often represents the initial process launched by the container runtime (for example, `containerd`, `runc`, or a shell specified as the container entrypoint). Anchoring detections to the entry leader allows process trees to be interpreted consistently, even when containers spawn many short-lived child processes.\n\n![Figure 16: Defend for Containers’ important `process.session*` fields overview](/assets/images/getting-started-with-defend-for-containers/image15.png \"Figure 16: Defend for Containers’ important `process.session*` fields overview\")\n\nSession leader fields provide additional context about interactive execution and session boundaries, helping distinguish background services from interactive or attacker-driven activity.\n\nTogether, these fields make it possible to express detection logic that goes beyond single executions and instead reasons about execution chains, lineage, and intent, which is essential for detecting real-world container attack techniques.\n\n#### Capabilities and privilege context\n\nOne of the more powerful aspects of the Defend for Containers process events is the inclusion of Linux capability information. For each process, Defend for Containers exposes both the effective and permitted capability sets via:\n\n* `process.thread.capabilities.effective`  \n* `process.thread.capabilities.permitted`\n\nThese fields describe what a process is actually allowed to do at runtime, independent of its user ID or container boundary.\n\n![Figure 17: Defend for Containers’ important `process.thread.capabilities.*` fields overview](/assets/images/getting-started-with-defend-for-containers/image14.png \"Figure 17: Defend for Containers’ important `process.thread.capabilities.*` fields overview\")\n\nIn privileged containers, processes often expose a broad set of effective capabilities, including highly sensitive ones such as `CAP_SYS_ADMIN`, `CAP_SYS_MODULE`, `CAP_SYS_PTRACE`, `CAP_SYS_RAWIO`, and `CAP_BPF`. The presence of these capabilities significantly changes the risk profile of any executed command, as they enable actions that can directly impact the host kernel or other workloads.\n\nFrom a detection engineering perspective, this context is critical. It allows detections to move beyond simple process-name matching and instead reason about *impact*. The same binary execution can have vastly different implications depending on whether it runs with a minimal capability set or with near-host-level privileges.\n\nIn practice, capability data enables detection engineers to:\n\n* Identify suspicious tooling executed inside overly permissive containers.  \n* Correlate runtime behavior with dangerous capability combinations.  \n* Prioritize alerts based on actual exploitation potential rather than surface-level activity.\n\nThis becomes especially relevant to container breakout research, where the presence or absence of specific capabilities often determines whether an exploit is viable.\n\n#### Interactive execution\n\nThe `process.interactive` field indicates whether a process is associated with an interactive session. In container environments, interactive execution is relatively rare for production workloads and often correlates strongly with post-compromise or hands-on-keyboard activity.\n\n![Figure 18: Defend for Containers’ important `process.*.interactive` fields overview](/assets/images/getting-started-with-defend-for-containers/image4.png \"Figure 18: Defend for Containers’ important `process.*.interactive` fields overview\")\n\nDefend for Containers exposes interactivity not only at the process level, but also across related execution contexts, including `process.parent.interactive`, `process.entry_leader.interactive`, and `process.session_leader.interactive`. This makes it possible to determine whether an entire execution chain is interactive, rather than relying on a single process flag in isolation.\n\nCommon examples of interactive execution within containers include spawning a `bash` or `sh` shell, running interactive utilities such as `curl`, `kubectl`, or `busybox`, or operator-driven reconnaissance within a compromised Pod. While these actions may be legitimate during debugging, they are uncommon in steady-state production workloads.\n\nWhen combined with container image, namespace, and privilege context, interactive execution becomes a strong anomaly signal. It allows detection logic to distinguish between expected automated container behavior and activity more consistent with manual intervention or attacker-driven exploration.\n\n### File events\n\nDefend for Containers file events capture filesystem activity inside containers, and are emitted for a variety of operations. Unlike traditional file integrity monitoring, these events are runtime-aware and scoped to container workloads, providing context about *how* and *why* file changes occur.\n\nDefend for Containers can detect file activity such as file opens **with write intent**, content modifications, file creations, renames, permission changes, and deletions. By focusing on write-oriented operations, Defend for Containers emphasizes behavior that alters system state rather than passive file access.\n\nThis allows detection engineers to reason about file usage patterns at runtime, not just the result of a change.\n\n![Figure 19: Defend for Containers’ important `file` events overview](/assets/images/getting-started-with-defend-for-containers/image6.png \"Figure 19: Defend for Containers’ important `file` events overview\")\n\nSeveral fields are particularly important when building file-based detections. The `file.path` and `file.name` fields identify the affected file and its location, while `file.extension` can help distinguish binaries, scripts, and configuration files. The `event.action` and `event.type` fields describe what operation occurred and how it should be interpreted in the event lifecycle.\n\nTogether, these fields allow Defend for Containers to distinguish benign file access from suspicious modification patterns, such as writing binaries or changing permissions within sensitive directories.\n\n### Bringing it together\n\nAs with any other data source, Defend for Containers telemetry becomes truly valuable once you understand how to combine fields across the process, file, container, and orchestration domains. Rather than relying on static indicators, Defend for Containers enables detection engineering based on runtime behavior, privilege context, and workload identity.\n\n## Conclusion\n\nDefend for Containers in Elastic Stack 9.3.0 includes container runtime detection as a core component of Linux detection engineering.
