<h2 class="font-bold text-2xl md:text-4xl relative"><span id="why-developer-workstations-are-the-npm-supply-chain--gap" class="absolute -top-32"></span>Why developer workstations are the npm supply-chain  gap</h2>
<p>CI/CD pipelines have their own supply-chain guardrails that can be managed at the enterprise level. Workstations are where the gap usually sits. A developer running <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">npm install</code> on a freshly compromised package is a different surface from the build pipeline, and the package manager itself is the right place to apply a delay before a fresh release becomes installable. npm&#x27;s <a href="https://docs.npmjs.com/cli/v11/using-npm/config"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age</code></a> setting, available since npm 11.10, does exactly that: the value is a number of days, and npm excludes any version published more recently from resolution. In MITRE ATT&amp;CK terms, the technique it blunts is <a href="https://attack.mitre.org/techniques/T1195/001/">Compromise Software Dependencies and Development Tools (T1195.001)</a>.</p>
<p>Most other package managers have an equivalent flag; <a href="https://cooldowns.dev">cooldowns.dev</a> tracks which ones, what each flag is called, and recommended values. This post focuses on npm, and recent attacks have happened, but the technique applies to any of them.</p>
<p>We enforce the setting with Jamf: a script writes <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age=7</code> to each user&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> and the machine-global npmrc, and re-applies once a day. A removal therefore self-heals within 24 hours, and the telemetry is what makes the removal visible at all: the 6-hour heartbeat catches the gap window before Jamf closes it, and shows us which hosts keep removing the setting.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="what-does-an-npm-cooldown-config-file-look-like" class="absolute -top-32"></span>What does an npm cooldown config file look like?</h2>
<p>The target is small: npm writes the setting to a user-level <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code>, typically 10 to 50 bytes.</p>
<pre><code>~/.npmrc    →    min-release-age=7        # days</code></pre>
<p>Machine-global settings live in a handful of well-known paths (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/opt/homebrew/etc/npmrc</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/local/etc/npmrc</code> on macOS, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/etc/npmrc</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/lib/node_modules/npm/.npmrc</code> on Linux), so a complete inventory has to include those paths too. While we haven’t deployed a Windows version yet, we did include all the details to make this work in the Linux and Windows variants section. These can be found in the section Linux and Windows variants.</p>
<p>Two ingredients made this look easy. First, as InfoSec is Customer Zero at Elastic, the Elastic Agent is already rolled out to every endpoint and runs with the privileges to read these files. Second, the schema is essentially flat: one key, one value, one config file. So in theory, you configure a file input, tail the cooldown lines, and ship them to <a href="https://www.elastic.co/elasticsearch">Elasticsearch</a>.</p>
<p>The complication is that auth tokens for private registries (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">//registry.npmjs.org/:_authToken=...</code>) live in the same <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> file. None of that can leave the host. Any approach has to filter the file body before it transits anywhere.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="first-approach-monitoring-npmrc-with-the-custom-logs-filestream-integration" class="absolute -top-32"></span>First approach: Monitoring .npmrc with the Custom Logs Filestream integration</h2>
<p>The <a href="https://www.elastic.co/docs/reference/integrations/filestream">Custom Logs Filestream integration</a> in <a href="https://www.elastic.co/docs/reference/fleet">Fleet</a> wraps Filebeat&#x27;s modern <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">filestream</code> input and lets you specify path globs and an ingest pipeline. Note: this is a distinct Fleet integration from the older &quot;Custom Logs&quot; integration, which wraps the legacy <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">log</code> input. The two have different configuration surfaces and file-identity models, so if you&#x27;re migrating between them the reference linked above is worth reading before either direction.</p>
<p>We configured the integration across all users on macOS, plus the system-global npm paths:</p>
<pre><code>/Users/*/.npmrc
/opt/homebrew/etc/npmrc
/usr/local/etc/npmrc
/etc/npmrc</code></pre>
<p>The ingest pipeline did four things:</p>
<ol>
<li><a href="https://www.elastic.co/docs/reference/enrich-processor/grok-processor">Grok</a> the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">message</code> field to pull out the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age=value</code> pair.</li>
<li>Drop any line whose key wasn&#x27;t <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age</code>, so registry auth tokens never made it into Elasticsearch.</li>
<li>Convert the value to a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">long</code>.</li>
<li>Remove the raw <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">message</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">event.original</code> fields before indexing.</li>
</ol>
<p>It worked, with three caveats that changed our minds about whether it was the right integration for this job.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="three-filestream-behaviours-that-dont-fit-config-file-monitoring" class="absolute -top-32"></span>Three filestream behaviours that don&#x27;t fit config file monitoring</h3>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="native-file-identity-beats-fingerprint-for-small-files" class="absolute -top-32"></span>Native file identity beats fingerprint for small files</h4>
<p>Filebeat&#x27;s default file identity strategy is &quot;fingerprint&quot;, which hashes the first N bytes of a file to give it a stable ID across rotations. The fingerprint length defaults to 1024 bytes, and a file shorter than that minimum is silently held back from ingestion until it grows. A 22-byte <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> will never grow, so the data never moves. This is in line with the description of the Filestream integration and also apparent in the agent logs:</p>
<pre><code>&quot;ingestion from some files will be delayed, files need to be at least
 1024 in size for ingestion to start&quot;</code></pre>
<p>The fix is to switch the integration&#x27;s advanced options to use native file identity, which uses inode plus device and has no size floor. In our deployment on Elastic Agent 9.x, disabling fingerprint alone did not fall back to native; we had to flip both toggles explicitly.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="clean_inactive-and-ignore_older-are-coupled" class="absolute -top-32"></span>clean_inactive and ignore_older are coupled</h4>
<p>We wanted periodic re-emission of each config file so a stale event could be distinguished from a current one. filestream&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">clean_inactive</code> is the right knob for that, but it requires <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">ignore_older</code> to also be set. Together they cleanly trim files that haven&#x27;t moved recently, which is useful for rotating log files and not useful for static config files that may sit unchanged for months. We disabled <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">clean_inactive</code>.</p>
<h4 class="font-bold leading-tight text-lg md:text-2xl relative"><span id="filestream-emits-on-append-not-on-removal" class="absolute -top-32"></span>Filestream emits on append, not on removal</h4>
<p>This third learning is structural rather than a config gotcha. filestream is designed for log tailing: when bytes arrive at the end of a file, an event is emitted. When content disappears (because npm rewrites <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> without the cooldown line, or because the file is deleted), filestream sees a modification, but every resulting line is dropped by our allowlist filter, and nothing reaches Elasticsearch. The last &quot;set&quot; event for that host stays in the index indefinitely.</p>
<p>For application logs that&#x27;s correct behavior, since log lines aren&#x27;t usually retracted. For config file state monitoring, removal is the signal the adoption campaign needs most, and it never arrives. That&#x27;s why we switched to CEL.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="why-nvm-inflates-npm-version-counts-for-cooldown-adoption" class="absolute -top-32"></span>Why nvm inflates npm version counts for cooldown adoption</h3>
<p>Machines routinely report more than one npm version, because every Node.js version installed through nvm (Node Version Manager) ships its own npm binary. The distortion stood out as soon as we checked test pulls from our <a href="https://www.elastic.co/docs/reference/integrations/osquery_manager">osquery manager integration</a> package-version inventory: one machine reported 34 distinct npm versions.</p>
<p>The config side of this is forgiving. <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">npm config set min-release-age 7</code> writes to the user-level <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">~/.npmrc</code>, and every npm installation on the machine reads that file, including the per-Node copies nvm installs. Enforcement is the strict side: versions older than 11.10 ignore the key. A machine carrying npm 11.12 in one nvm environment and npm 10.9 in another is only protected when the newer npm is the one running <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">npm install</code>. A count of machines with any capable npm overstates who is protected, which is one more reason to track the config file directly rather than infer adoption from version counts.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="second-approach-monitoring-npmrc-with-cel-snapshot-semantics" class="absolute -top-32"></span>Second approach: Monitoring .npmrc with CEL snapshot semantics</h2>
<p>The <a href="https://www.elastic.co/docs/reference/beats/filebeat/filebeat-input-cel">CEL input</a> in Elastic Agent was designed for HTTP API polling, but it also exposes a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file()</code> function and a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">dir()</code> function for filesystem access. That enables a different model from filestream. filestream tails lines as they arrive; CEL takes a snapshot of the whole file each interval. For state monitoring, the snapshot is what we want: the unit of interest is the current contents of <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> as a whole.</p>
<p>Here is the complete script we run, trimmed to npm (our production version watches the other package managers&#x27; config files with the same pattern, and carries an extra guard for non-UTF-8 file content):</p>
<pre><code>(
  (
    try(dir(&quot;/Users&quot;)).as(entries, type(entries) != type(&quot;&quot;) ?
      entries.filter(u,
        u.is_dir
        &amp;&amp; !string(u.name).startsWith(&quot;.&quot;)
        &amp;&amp; string(u.name) != &quot;Shared&quot;
        &amp;&amp; string(u.name) != &quot;Guest&quot;
      ).map(u, &quot;/Users/&quot; + string(u.name) + &quot;/.npmrc&quot;)
    : [])
  ) + (
    try(dir(&quot;/home&quot;)).as(entries, type(entries) != type(&quot;&quot;) ?
      entries.filter(u,
        u.is_dir
        &amp;&amp; !string(u.name).startsWith(&quot;.&quot;)
      ).map(u, &quot;/home/&quot; + string(u.name) + &quot;/.npmrc&quot;)
    : [])
  ) + (has(state.files) ? state.files : [])
).map(f,
  try(file(f)).as(content,
    type(content) == type(&quot;&quot;) ?
      {&quot;file&quot;: f, &quot;exists&quot;: false}
    :
      {&quot;file&quot;: f, &quot;body&quot;: string(content),
       &quot;hash&quot;: content.sha256().hex(), &quot;exists&quot;: true}
  )
).as(file_data, {
  &quot;events&quot;: file_data.filter(fd, fd.exists).map(fd, {
    &quot;message&quot;: fd.body,
    &quot;file&quot;: {&quot;path&quot;: fd.file, &quot;hash&quot;: {&quot;sha256&quot;: fd.hash}},
  }),
  &quot;cursor&quot;: {&quot;hashes&quot;: file_data.filter(fd, fd.exists)
    .map(fd, {&quot;file&quot;: fd.file, &quot;hash&quot;: fd.hash})},
  &quot;url&quot;: state.url,
  &quot;files&quot;: has(state.files) ? state.files : [],
})</code></pre>
<p>The first block enumerates user home directories at runtime, with filtering that path globs can&#x27;t express, and appends the machine-global paths from <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">state.files</code>. <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">try(dir(...))</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">try(file(...))</code> return an error string when the path doesn&#x27;t exist, so each block checks the type of the result and collapses a missing directory or file to an empty result. A macOS host has no <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/home</code>, a Linux host has no <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/Users</code>, and the same script runs on both.</p>
<p>The initial state supplies the global paths and the poll interval is 6 hours:</p>
<pre><code>files:
  - /opt/homebrew/etc/npmrc
  - /usr/local/etc/npmrc
  - /etc/npmrc
  - /usr/lib/node_modules/npm/.npmrc</code></pre>
<p><strong>An aside on Fleet:</strong> the integration to add in the UI is called <a href="https://www.elastic.co/docs/reference/integrations/cel">&quot;Custom API using Common Expression Language&quot;</a>, not &quot;CEL&quot;. It exposes the full CEL runtime including file system access. Set <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">resource.url: file:///dev/null</code> to satisfy the required URL field without making an HTTP request, and put the initial state in the &quot;Custom request cursor&quot; YAML at the bottom of the form.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="how-the-cel-integration-evolved-emit-on-change-tombstones-and-heartbeat" class="absolute -top-32"></span>How the CEL integration evolved: emit-on-change, tombstones and heartbeat</h3>
<p>The CEL snapshot integration shown above is the third version. The path there is the useful part.</p>
<p><strong>Version one emitted only on change.</strong> Each heartbeat hashed every file and emitted an event only when the hash differs from the cursor, the state the input persists between runs. Efficient, and it produced the removal signal cleanly: npm rewrites <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> in place when a setting changes, the hash moves, the new snapshot carries no <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age</code> line, and the ingest pipeline marks the event <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.absent = true</code>.</p>
<p><strong>Version two added a deletion tombstone.</strong> Hash comparison can&#x27;t see a file that stopped existing (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">npm config delete min-release-age</code> removes <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> entirely when it&#x27;s the only setting), because version one filtered out non-existent files before emitting. A one-block extension emitted a stub event, once, for any file that was in the cursor but no longer on disk.</p>
<p><strong>Version three replaced both with a heartbeat, because the dashboard demanded it.</strong> The adoption dashboard counts hosts whose cooldown state falls inside the selected time window. Under emit-on-change, a host that sets a cooldown emits exactly one event and then goes silent. Once that single event ages past the dashboard&#x27;s window (say, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">now-7d</code>), the host disappears from the &quot;adopted&quot; count even though the cooldown is still in place. We watched adoption climb during rollout and then start to erode a few days later, purely as an artifact of one-shot events aging out of the window. The telemetry was correct; the time-windowed view of it was not.</p>
<p>So the final integration re-emits each existing file&#x27;s current state on every 6-hour heartbeat. Every host re-reports its cooldown posture four times a day, the windowed dashboard reflects live state, and a host that stops appearing is genuinely offline rather than merely quiet. Removal of the cooldown line still surfaces as <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.absent = true</code> in the next snapshot, and a deleted file drops out of subsequent snapshots, so the tombstone becomes unnecessary.</p>
<p>The cost is volume: a snapshot per file per host per interval instead of one event per change. At a 6-hour cadence that is a few thousand small documents a day across the fleet, which is immaterial. At a 60-second interval it stops being immaterial: always-emitting at 60s ships the same unchanged state every minute, which we measured at roughly a thousand-fold more documents for zero added signal. If you adopt the heartbeat, set the interval in hours.</p>
<p>The detection latency for a removal is the heartbeat interval, 6 hours in our case. For an adoption campaign measured over days and weeks against a 7-day cooldown, that is not a meaningful constraint. If you need lower-latency, discrete removal events for alerting, run the emit-on-change variant instead; the snapshot model supports both.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="how-to-filter-npmrc-auth-tokens-before-they-leave-the-host" class="absolute -top-32"></span>How to filter .npmrc auth tokens before they leave the host</h3>
<p>A snapshot-based integration sends the whole file body across the wire to the ingest pipeline. That&#x27;s fine for config keys; it is not fine for <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> registry auth tokens. Filtering at the ingest pipeline is too late, because by then the tokens have already transited the network.</p>
<p>The fix is an agent-side <a href="https://www.elastic.co/docs/reference/beats/filebeat/processor-script">script processor</a> in the integration&#x27;s Advanced options → Processors field. It keeps only <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age</code> lines and drops everything else before the event leaves the workstation:</p>
<pre><code>- script:
    lang: javascript
    source: &gt;
      function process(event) {
        var msg = event.Get(&quot;message&quot;);
        if (msg == null) return;
        var filtered = [];
        var lines = msg.split(&#x27;\n&#x27;);
        for (var i = 0; i &lt; lines.length; i++) {
          var line = lines[i].trim();
          if (line.indexOf(&#x27;min-release-age&#x27;) === 0) {
            filtered.push(line);
          }
        }
        event.Put(&quot;message&quot;, filtered.join(&#x27;\n&#x27;));
      }</code></pre>
<p>Tokens never reach the wire. We verified by adding a test token to a <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> on a managed host, running a cycle, and confirming zero search hits for the token string in Elasticsearch.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="the-npm-cooldown-ingest-pipeline" class="absolute -top-32"></span>The npm cooldown ingest pipeline</h3>
<p>The pipeline below is the npm-only variant of the one we run in production, and it is short enough to show whole. Grok extracts the key and value, a Set processor turns &quot;no key found&quot; into the explicit removal signal, and the raw message is removed before indexing:</p>
<pre><code>PUT _ingest/pipeline/npm-cooldown-workstation
{
  &quot;description&quot;: &quot;Parses min-release-age from .npmrc snapshots&quot;,
  &quot;processors&quot;: [
    {
      &quot;grok&quot;: {
        &quot;field&quot;: &quot;message&quot;,
        &quot;patterns&quot;: [
          &quot;(?&lt;cooldown.key&gt;min-release-age)\\s*=\\s*(?&lt;cooldown.value&gt;[^\\n\\r]*)&quot;
        ],
        &quot;ignore_missing&quot;: true,
        &quot;ignore_failure&quot;: true
      }
    },
    {
      &quot;set&quot;: {
        &quot;if&quot;: &quot;ctx.cooldown?.key == null&quot;,
        &quot;field&quot;: &quot;cooldown.absent&quot;,
        &quot;value&quot;: true
      }
    },
    {
      &quot;set&quot;: {
        &quot;if&quot;: &quot;ctx.cooldown?.key != null&quot;,
        &quot;field&quot;: &quot;cooldown.unit&quot;,
        &quot;value&quot;: &quot;days&quot;
      }
    },
    {
      &quot;convert&quot;: {
        &quot;field&quot;: &quot;cooldown.value&quot;,
        &quot;type&quot;: &quot;long&quot;,
        &quot;ignore_missing&quot;: true,
        &quot;ignore_failure&quot;: true
      }
    },
    {
      &quot;remove&quot;: {
        &quot;field&quot;: [&quot;message&quot;, &quot;event.original&quot;],
        &quot;ignore_missing&quot;: true
      }
    }
  ]
}</code></pre>
<p>Two details earned their place the hard way. The value capture is <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[^\n\r]*</code>, which stops at both LF and CRLF line endings; an earlier revision used <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[^ \r]*</code>, which truncated any value containing a space and could run across newlines. And <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.unit</code> is set explicitly even though npm&#x27;s unit is always days, because dashboard rows that read <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">7 days</code> stay unambiguous when the telemetry later grows beyond npm.</p>
<p>The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.absent = true</code> event is the payoff. The host was in the index six hours ago with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.key = min-release-age</code>; the next snapshot has no key; the dashboard shows the transition. That is the removal signal filestream could not produce.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="cel-vs-filestream-for-config-file-monitoring" class="absolute -top-32"></span>CEL vs. filestream for config file monitoring</h2>
<p>We ran both in parallel for a few weeks and then made a call.</p>
<p>The core reason is the shape of the data. filestream is built for append-only logs, where new lines arrive at the end of a file and the job is to harvest them. <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> is a state file: npm rewrites it in place when a setting changes and deletes it when the last setting is removed. The question the telemetry needs to answer, &quot;what is the cooldown state of this host right now, and when did it change,&quot; is a question about the current contents of a file. Tail offsets can&#x27;t answer it.</p>
<div class="table-container"><table style="width:100%;table-layout:fixed;word-wrap:break-word"><thead><tr><th style="text-align:left"></th><th style="text-align:left">CEL</th><th style="text-align:left">Filestream</th></tr></thead><tbody><tr><td style="text-align:left">Designed for</td><td style="text-align:left">State files (snapshot + hash)</td><td style="text-align:left">Append-only logs (tail)</td></tr><tr><td style="text-align:left">Cooldown-line removal detection</td><td style="text-align:left">Yes (next snapshot marks <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.absent</code>)</td><td style="text-align:left">No</td></tr><tr><td style="text-align:left">File deletion detection</td><td style="text-align:left">Yes (host drops out of snapshots)</td><td style="text-align:left">No</td></tr><tr><td style="text-align:left">Snapshot semantics</td><td style="text-align:left">Whole file</td><td style="text-align:left">Per line</td></tr><tr><td style="text-align:left">Auth-token posture</td><td style="text-align:left">Filtered agent-side before transit</td><td style="text-align:left">Same (agent-side allowlist)</td></tr><tr><td style="text-align:left">Fleet integration</td><td style="text-align:left">Custom API using Common Expression Language</td><td style="text-align:left">Custom Logs Filestream</td></tr><tr><td style="text-align:left">Config complexity</td><td style="text-align:left">~40-line CEL integration</td><td style="text-align:left">Declarative path globs</td></tr><tr><td style="text-align:left">State refresh / latency</td><td style="text-align:left">6h heartbeat</td><td style="text-align:left">~10s (tail)</td></tr></tbody></table></div>
<p>Running both meant every config change produced two events into two separate datasets, and we maintained two ingest pipelines with dashboards split across indices. The complexity cost outweighs any redundancy benefit, and the only thing filestream gives that CEL doesn&#x27;t is faster detection latency, which is not a meaningful constraint for adoption tracking on a 7-day cooldown.</p>
<p>We also considered osquery and auditd before settling on CEL. osquery can read config file contents on a schedule through its <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">file_lines</code> tables, and auditd can fire on file writes, but neither produces a clean current-state signal across ingestion, and both would mean standing up a second collection path next to the agent already deployed for endpoint telemetry.</p>
<p>CEL won. End-to-end validation on a single macOS workstation:</p>
<div class="table-container"><table style="width:100%;table-layout:fixed;word-wrap:break-word"><thead><tr><th style="text-align:left">Scenario</th><th style="text-align:left">Expected</th><th style="text-align:left">Result</th></tr></thead><tbody><tr><td style="text-align:left"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">npm config set min-release-age 5</code></td><td style="text-align:left"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.key = min-release-age</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.value = 5</code></td><td style="text-align:left">Pass</td></tr><tr><td style="text-align:left"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> exists with no cooldown key</td><td style="text-align:left"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">cooldown.absent = true</code></td><td style="text-align:left">Pass</td></tr><tr><td style="text-align:left"><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">npm config delete min-release-age</code> (deletes the file)</td><td style="text-align:left">path absent from subsequent snapshots</td><td style="text-align:left">Pass</td></tr><tr><td style="text-align:left">Auth token line in <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code></td><td style="text-align:left">No token in Elasticsearch</td><td style="text-align:left">Pass</td></tr></tbody></table></div>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="npm-cooldown-monitoring-on-linux-and-windows" class="absolute -top-32"></span>npm cooldown monitoring on Linux and Windows</h2>
<p>macOS was the primary platform; the design generalizes cleanly.</p>
<p>Linux needed no integration change at all. The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/home</code> block in the integration above already covers it: on each platform, the directory that doesn&#x27;t exist fails the type check and collapses to an empty list, and the other side fills in. The Linux variant runs the same integration through the same ingest pipeline into the same dataset, with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/etc/npmrc</code> and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">/usr/lib/node_modules/npm/.npmrc</code> in the global watch list.</p>
<p>Windows is a separate integration on the same dataset, and it&#x27;s the one variant we designed but haven&#x27;t deployed: our own fleet has too few Windows machines to justify the rollout yet. We&#x27;re documenting it anyway because Windows is the most common OS in corporate fleets, so for many readers this variant is the one that matters most. The integration enumerates <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">C:/Users/*</code> (forward slashes work on Windows under Go/CEL), excludes <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Public</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Default</code>, and <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Default User</code>, and watches each user&#x27;s <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> plus the system globals under <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">C:/ProgramData</code>. The Grok pattern&#x27;s value capture, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">[^\n\r]*</code>, stops at both LF and CRLF line endings, so it works unchanged on Windows without capturing the trailing <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">\r</code> in the value. The agent-side script processor is also unchanged.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="rollout-status-and-extending-beyond-npm" class="absolute -top-32"></span>Rollout status and extending beyond npm</h2>
<p>The pipeline is now reporting from several hundred macOS, each re-emitting its current npm cooldown state on the 6-hour heartbeat. We&#x27;re sharing the technique at this stage so other security engineering teams can build on it; once the rollout reaches the full fleet we&#x27;ll follow up with an org-wide adoption-rate post. The Windows variant stays on the shelf until our Windows population justifies the rollout; if your fleet is Windows-heavy, the design in this post is ready to adapt.</p>
<p>In production the same integration already watches the config files for pip, uv, pnpm, yarn Berry, and bun. That expansion deserves its own post, because cooldown values are not unit-comparable across package managers, and one manager&#x27;s documentation and implementation disagree about the unit by three orders of magnitude. If you&#x27;re extending this design beyond npm, check <a href="https://cooldowns.dev">cooldowns.dev</a> for each flag&#x27;s unit before you compare values across tools.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="what-we-learned-about-npm-cooldown-monitoring-with-elastic-agent" class="absolute -top-32"></span>What we learned about npm cooldown monitoring with Elastic Agent</h2>
<ul>
<li>npm cooldown adoption telemetry is state monitoring. The signal that matters most is a host removing <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">min-release-age</code>, and append-driven log tailing cannot see that happen.</li>
<li>A snapshot-based CEL integration produces the removal signal directly: re-emit each <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code>&#x27;s current state on a 6-hour heartbeat, and a removal shows up as the key&#x27;s absence in the next snapshot.</li>
<li>A time-windowed adoption dashboard needs the heartbeat, not one-shot change events, which age out of the window and make adoption look like it&#x27;s eroding when it isn&#x27;t.</li>
<li>Small config files (under 1024 bytes) need native file identity, not fingerprint, regardless of which integration you use.</li>
<li>An agent-side script processor keeps <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">.npmrc</code> registry auth tokens on the workstation: tokens never reach the wire.</li>
<li>nvm inflates capability counts: each Node.js version ships its own npm, all of them read the shared <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">~/.npmrc</code>, but only npm 11.10+ enforces the key. Track the config file, count enforcement-capable versions separately.</li>

Getting the setting onto developer workstations is straightforward. Knowing when someone quietly deletes it is a different problem entirely, and log-tailing inputs are no help because they only fire when lines are appended to a file. We built a \\~40-line Common Expression Language (CEL) integration in [Elastic Agent](https://www.elastic.co/elastic-agent) that snapshots every `.npmrc` on a 6-hour heartbeat. When `min-release-age` disappears from the next snapshot, the pipeline marks it `cooldown.absent = true`. This post walks through that pipeline, the filestream approach we tried first, and what we learned from three iterations before landing on the final design.\n\nThe full path from config file to dashboard looks like this:\n\n![npm's cooldown pipeline](/assets/images/npm-cooldown-removal-detection-elastic-agent/vertical_flowchart.png)\n\n## Why developer workstations are the npm supply-chain  gap\n\nCI/CD pipelines have their own supply-chain guardrails that can be managed at the enterprise level. Workstations are where the gap usually sits. A developer running `npm install` on a freshly compromised package is a different surface from the build pipeline, and the package manager itself is the right place to apply a delay before a fresh release becomes installable. npm's [`min-release-age`](https://docs.npmjs.com/cli/v11/using-npm/config) setting, available since npm 11.10, does exactly that: the value is a number of days, and npm excludes any version published more recently from resolution. In MITRE ATT\\\u0026CK terms, the technique it blunts is [Compromise Software Dependencies and Development Tools (T1195.001)](https://attack.mitre.org/techniques/T1195/001/).\n\nMost other package managers have an equivalent flag; [cooldowns.dev](https://cooldowns.dev) tracks which ones, what each flag is called, and recommended values. This post focuses on npm, and recent attacks have happened, but the technique applies to any of them.\n\nWe enforce the setting with Jamf: a script writes `min-release-age=7` to each user's `.npmrc` and the machine-global npmrc, and re-applies once a day. A removal therefore self-heals within 24 hours, and the telemetry is what makes the removal visible at all: the 6-hour heartbeat catches the gap window before Jamf closes it, and shows us which hosts keep removing the setting.\n\n## What does an npm cooldown config file look like?\n\nThe target is small: npm writes the setting to a user-level `.npmrc`, typically 10 to 50 bytes.\n\n```\n~/.npmrc    →    min-release-age=7        # days\n```\n\nMachine-global settings live in a handful of well-known paths (`/opt/homebrew/etc/npmrc` and `/usr/local/etc/npmrc` on macOS, `/etc/npmrc` and `/usr/lib/node_modules/npm/.npmrc` on Linux), so a complete inventory has to include those paths too. While we haven’t deployed a Windows version yet, we did include all the details to make this work in the Linux and Windows variants section. These can be found in the section Linux and Windows variants.\n\nTwo ingredients made this look easy. First, as InfoSec is Customer Zero at Elastic, the Elastic Agent is already rolled out to every endpoint and runs with the privileges to read these files. Second, the schema is essentially flat: one key, one value, one config file. So in theory, you configure a file input, tail the cooldown lines, and ship them to [Elasticsearch](https://www.elastic.co/elasticsearch).\n\nThe complication is that auth tokens for private registries (`//registry.npmjs.org/:_authToken=...`) live in the same `.npmrc` file. None of that can leave the host. Any approach has to filter the file body before it transits anywhere.\n\n## First approach: Monitoring .npmrc with the Custom Logs Filestream integration\n\nThe [Custom Logs Filestream integration](https://www.elastic.co/docs/reference/integrations/filestream) in [Fleet](https://www.elastic.co/docs/reference/fleet) wraps Filebeat's modern `filestream` input and lets you specify path globs and an ingest pipeline. Note: this is a distinct Fleet integration from the older \"Custom Logs\" integration, which wraps the legacy `log` input. The two have different configuration surfaces and file-identity models, so if you're migrating between them the reference linked above is worth reading before either direction.\n\nWe configured the integration across all users on macOS, plus the system-global npm paths:\n\n```\n/Users/*/.npmrc\n/opt/homebrew/etc/npmrc\n/usr/local/etc/npmrc\n/etc/npmrc\n```\n\nThe ingest pipeline did four things:\n\n1. [Grok](https://www.elastic.co/docs/reference/enrich-processor/grok-processor) the `message` field to pull out the `min-release-age=value` pair.  \n2. Drop any line whose key wasn't `min-release-age`, so registry auth tokens never made it into Elasticsearch.  \n3. Convert the value to a `long`.  \n4. Remove the raw `message` and `event.original` fields before indexing.\n\nIt worked, with three caveats that changed our minds about whether it was the right integration for this job.\n\n### Three filestream behaviours that don't fit config file monitoring\n\n#### Native file identity beats fingerprint for small files\n\nFilebeat's default file identity strategy is \"fingerprint\", which hashes the first N bytes of a file to give it a stable ID across rotations. The fingerprint length defaults to 1024 bytes, and a file shorter than that minimum is silently held back from ingestion until it grows. A 22-byte `.npmrc` will never grow, so the data never moves. This is in line with the description of the Filestream integration and also apparent in the agent logs:\n\n```\n\"ingestion from some files will be delayed, files need to be at least\n 1024 in size for ingestion to start\"\n```\n\nThe fix is to switch the integration's advanced options to use native file identity, which uses inode plus device and has no size floor. In our deployment on Elastic Agent 9.x, disabling fingerprint alone did not fall back to native; we had to flip both toggles explicitly.\n\n#### clean\\_inactive and ignore\\_older are coupled\n\nWe wanted periodic re-emission of each config file so a stale event could be distinguished from a current one. filestream's `clean_inactive` is the right knob for that, but it requires `ignore_older` to also be set. Together they cleanly trim files that haven't moved recently, which is useful for rotating log files and not useful for static config files that may sit unchanged for months. We disabled `clean_inactive`.\n\n#### Filestream emits on append, not on removal\n\nThis third learning is structural rather than a config gotcha. filestream is designed for log tailing: when bytes arrive at the end of a file, an event is emitted. When content disappears (because npm rewrites `.npmrc` without the cooldown line, or because the file is deleted), filestream sees a modification, but every resulting line is dropped by our allowlist filter, and nothing reaches Elasticsearch. The last \"set\" event for that host stays in the index indefinitely.\n\nFor application logs that's correct behavior, since log lines aren't usually retracted. For config file state monitoring, removal is the signal the adoption campaign needs most, and it never arrives. That's why we switched to CEL.\n\n### Why nvm inflates npm version counts for cooldown adoption\n\nMachines routinely report more than one npm version, because every Node.js version installed through nvm (Node Version Manager) ships its own npm binary. The distortion stood out as soon as we checked test pulls from our [osquery manager integration](https://www.elastic.co/docs/reference/integrations/osquery_manager) package-version inventory: one machine reported 34 distinct npm versions.\n\nThe config side of this is forgiving. `npm config set min-release-age 7` writes to the user-level `~/.npmrc`, and every npm installation on the machine reads that file, including the per-Node copies nvm installs. Enforcement is the strict side: versions older than 11.10 ignore the key. A machine carrying npm 11.12 in one nvm environment and npm 10.9 in another is only protected when the newer npm is the one running `npm install`. A count of machines with any capable npm overstates who is protected, which is one more reason to track the config file directly rather than infer adoption from version counts.\n\n## Second approach: Monitoring .npmrc with CEL snapshot semantics\n\nThe [CEL input](https://www.elastic.co/docs/reference/beats/filebeat/filebeat-input-cel) in Elastic Agent was designed for HTTP API polling, but it also exposes a `file()` function and a `dir()` function for filesystem access. That enables a different model from filestream. filestream tails lines as they arrive; CEL takes a snapshot of the whole file each interval. For state monitoring, the snapshot is what we want: the unit of interest is the current contents of `.npmrc` as a whole.\n\nHere is the complete script we run, trimmed to npm (our production version watches the other package managers' config files with the same pattern, and carries an extra guard for non-UTF-8 file content):\n\n```javascript\n(\n  (\n    try(dir(\"/Users\")).as(entries, type(entries) != type(\"\") ?\n      entries.filter(u,\n        u.is_dir\n        \u0026\u0026 !string(u.name).startsWith(\".\")\n        \u0026\u0026 string(u.name) != \"Shared\"\n        \u0026\u0026 string(u.name) != \"Guest\"\n      ).map(u, \"/Users/\" + string(u.name) + \"/.npmrc\")\n    : [])\n  ) + (\n    try(dir(\"/home\")).as(entries, type(entries) != type(\"\") ?\n      entries.filter(u,\n        u.is_dir\n        \u0026\u0026 !string(u.name).startsWith(\".\")\n      ).map(u, \"/home/\" + string(u.name) + \"/.npmrc\")\n    : [])\n  ) + (has(state.files) ? state.files : [])\n).map(f,\n  try(file(f)).as(content,\n    type(content) == type(\"\") ?\n      {\"file\": f, \"exists\": false}\n    :\n      {\"file\": f, \"body\": string(content),\n       \"hash\": content.sha256().hex(), \"exists\": true}\n  )\n).as(file_data, {\n  \"events\": file_data.filter(fd, fd.exists).map(fd, {\n    \"message\": fd.body,\n    \"file\": {\"path\": fd.file, \"hash\": {\"sha256\": fd.hash}},\n  }),\n  \"cursor\": {\"hashes\": file_data.filter(fd, fd.exists)\n    .map(fd, {\"file\": fd.file, \"hash\": fd.hash})},\n  \"url\": state.url,\n  \"files\": has(state.files) ? state.files : [],\n})\n```\n\nThe first block enumerates user home directories at runtime, with filtering that path globs can't express, and appends the machine-global paths from `state.files`. `try(dir(...))` and `try(file(...))` return an error string when the path doesn't exist, so each block checks the type of the result and collapses a missing directory or file to an empty result. A macOS host has no `/home`, a Linux host has no `/Users`, and the same script runs on both.\n\nThe initial state supplies the global paths and the poll interval is 6 hours:\n\n```\nfiles:\n  - /opt/homebrew/etc/npmrc\n  - /usr/local/etc/npmrc\n  - /etc/npmrc\n  - /usr/lib/node_modules/npm/.npmrc\n```\n\n**An aside on Fleet:** the integration to add in the UI is called [\"Custom API using Common Expression Language\"](https://www.elastic.co/docs/reference/integrations/cel), not \"CEL\". It exposes the full CEL runtime including file system access. Set `resource.url: file:///dev/null` to satisfy the required URL field without making an HTTP request, and put the initial state in the \"Custom request cursor\" YAML at the bottom of the form.\n\n### How the CEL integration evolved: emit-on-change, tombstones and heartbeat\n\nThe CEL snapshot integration shown above is the third version. The path there is the useful part.\n\n**Version one emitted only on change.** Each heartbeat hashed every file and emitted an event only when the hash differs from the cursor, the state the input persists between runs. Efficient, and it produced the removal signal cleanly: npm rewrites `.npmrc` in place when a setting changes, the hash moves, the new snapshot carries no `min-release-age` line, and the ingest pipeline marks the event `cooldown.absent = true`.\n\n**Version two added a deletion tombstone.** Hash comparison can't see a file that stopped existing (`npm config delete min-release-age` removes `.npmrc` entirely when it's the only setting), because version one filtered out non-existent files before emitting. A one-block extension emitted a stub event, once, for any file that was in the cursor but no longer on disk.\n\n**Version three replaced both with a heartbeat, because the dashboard demanded it.** The adoption dashboard counts hosts whose cooldown state falls inside the selected time window. Under emit-on-change, a host that sets a cooldown emits exactly one event and then goes silent. Once that single event ages past the dashboard's window (say, `now-7d`), the host disappears from the \"adopted\" count even though the cooldown is still in place. We watched adoption climb during rollout and then start to erode a few days later, purely as an artifact of one-shot events aging out of the window. The telemetry was correct; the time-windowed view of it was not.\n\nSo the final integration re-emits each existing file's current state on every 6-hour heartbeat. Every host re-reports its cooldown posture four times a day, the windowed dashboard reflects live state, and a host that stops appearing is genuinely offline rather than merely quiet. Removal of the cooldown line still surfaces as `cooldown.absent = true` in the next snapshot, and a deleted file drops out of subsequent snapshots, so the tombstone becomes unnecessary.\n\nThe cost is volume: a snapshot per file per host per interval instead of one event per change. At a 6-hour cadence that is a few thousand small documents a day across the fleet, which is immaterial. At a 60-second interval it stops being immaterial: always-emitting at 60s ships the same unchanged state every minute, which we measured at roughly a thousand-fold more documents for zero added signal. If you adopt the heartbeat, set the interval in hours.\n\nThe detection latency for a removal is the heartbeat interval, 6 hours in our case. For an adoption campaign measured over days and weeks against a 7-day cooldown, that is not a meaningful constraint. If you need lower-latency, discrete removal events for alerting, run the emit-on-change variant instead; the snapshot model supports both.\n\n### How to filter .npmrc auth tokens before they leave the host\n\nA snapshot-based integration sends the whole file body across the wire to the ingest pipeline. That's fine for config keys; it is not fine for `.npmrc` registry auth tokens. Filtering at the ingest pipeline is too late, because by then the tokens have already transited the network.\n\nThe fix is an agent-side [script processor](https://www.elastic.co/docs/reference/beats/filebeat/processor-script) in the integration's Advanced options → Processors field. It keeps only `min-release-age` lines and drops everything else before the event leaves the workstation:\n\n```\n- script:\n    lang: javascript\n    source: \u003e\n      function process(event) {\n        var msg = event.Get(\"message\");\n        if (msg == null) return;\n        var filtered = [];\n        var lines = msg.split('\\n');\n        for (var i = 0; i \u003c lines.length; i++) {\n          var line = lines[i].trim();\n          if (line.indexOf('min-release-age') === 0) {\n            filtered.push(line);\n          }\n        }\n        event.Put(\"message\", filtered.join('\\n'));\n      }\n```\n\nTokens never reach the wire. We verified by adding a test token to a `.npmrc` on a managed host, running a cycle, and confirming zero search hits for the token string in Elasticsearch.\n\n### The npm cooldown ingest pipeline\n\nThe pipeline below is the npm-only variant of the one we run in production, and it is short enough to show whole. Grok extracts the key and value, a Set processor turns \"no key found\" into the explicit removal signal, and the raw message is removed before indexing:\n\n```json\nPUT _ingest/pipeline/npm-cooldown-workstation\n{\n  \"description\": \"Parses min-release-age from .npmrc snapshots\",\n  \"processors\": [\n    {\n      \"grok\": {\n        \"field\": \"message\",\n        \"patterns\": [\n          \"(?\u003ccooldown.key\u003emin-release-age)\\\\s*=\\\\s*(?\u003ccooldown.value\u003e[^\\\\n\\\\r]*)\"\n        ],\n        \"ignore_missing\": true,\n        \"ignore_failure\": true\n      }\n    },\n    {\n      \"set\": {\n        \"if\": \"ctx.cooldown?.key == null\",\n        \"field\": \"cooldown.absent\",\n        \"value\": true\n      }\n    },\n    {\n      \"set\": {\n        \"if\": \"ctx.cooldown?.key != null\",\n        \"field\": \"cooldown.unit\",\n        \"value\": \"days\"\n      }\n    },\n    {\n      \"convert\": {\n        \"field\": \"cooldown.value\",\n        \"type\": \"long\",\n        \"ignore_missing\": true,\n        \"ignore_failure\": true\n      }\n    },\n    {\n      \"remove\": {\n        \"field\": [\"message\", \"event.original\"],\n        \"ignore_missing\": true\n      }\n    }\n  ]\n}\n```\n\nTwo details earned their place the hard way.
