First observed in August 2023 and attributed to <a href="https://malpedia.caad.fkie.fraunhofer.de/actor/storm-1747">Storm-1747</a> (per Microsoft Threat Intelligence), the kit provides turnkey adversary-in-the-middle (AiTM) capabilities that bypass multi-factor authentication and steal authenticated session tokens from Microsoft 365 and Google Workspace accounts. At its peak, Tycoon 2FA <a href="https://blogs.microsoft.com/on-the-issues/2026/03/04/how-a-global-coalition-disrupted-tycoon/">accounted</a> for roughly 62% of phishing attempts blocked by Microsoft, reaching over 500,000 organizations monthly.</p>
<p>Despite a coordinated <a href="https://blogs.microsoft.com/on-the-issues/2026/03/04/how-a-global-coalition-disrupted-tycoon/">takedown</a> in March 2026 led by Microsoft and Europol, with support from Cloudflare, SpyCloud, eSentire, and other partners that seized over 300 domains, operators adapted within weeks. By late April 2026, <a href="https://www.esentire.com/blog/tycoon-2fa-infrastructure-update-threat-actors-adapt-following-global-coalition-takedown">eSentire</a> documented campaigns combining Tycoon tradecraft with OAuth Device Code phishing flows, and the kit remains the #1 entry on <a href="https://any.run/malware-trends/tycoon/">ANY.RUN</a>&#x27;s malware trends tracker.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="how-tycoon-2fa-works" class="absolute -top-32"></span>How Tycoon 2FA works</h2>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="the-aitm-mechanism" class="absolute -top-32"></span>The AiTM mechanism</h3>
<p>Tycoon 2FA operates as a reverse proxy between the victim and the legitimate identity provider (Entra ID or Google). It is not a static credential harvester. It proxies the real login flow in real time:</p>
<ol>
<li>The victim receives a phishing email containing a link or QR code embedded in a PDF, SVG, HTML, or PPTX attachment.</li>
<li>The link routes through a multi-layer redirect chain. The kit performs browser fingerprinting, CAPTCHA challenges, and anti-analysis checks before presenting the login page.</li>
<li>The victim sees a pixel-perfect replica of the Microsoft or Google login page, often including the target organization&#x27;s branding dynamically fetched from the real service.</li>
<li>Credentials are relayed in real time to the legitimate identity provider. The real MFA challenge is triggered and proxied back to the victim.</li>
<li>The victim completes MFA normally. The identity provider issues a session token. The proxy intercepts this token before it reaches the victim&#x27;s browser.</li>
<li>The attacker now holds a fully authenticated access token.</li>
</ol>
<p>The session cookie is the value the operator monetizes. Once captured, MFA is moot because the operator replays minted tokens post-MFA.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="two-structural-variants-in-current-rotation" class="absolute -top-32"></span>Two structural variants in current rotation</h3>
<p>Two distinct kit variants we analyzed were in active use:</p>
<p>WebSocket AiTM (the &quot;classic&quot; Tycoon 2FA flow): The victim authenticates through a kit-hosted proxy that forwards traffic to Microsoft or Google over WebSocket (Socket.IO) and captures the post-MFA session cookie. The kit&#x27;s JavaScript client controller maintains a real-time bidirectional channel to the C2 server, relaying credentials and authentication responses as the victim types. These responses include minted access and refresh tokens for use.</p>
<p>Device-code-grant abuse (Microsoft only): The kit relay obtains a device code from Microsoft&#x27;s oauth2/devicecode endpoint with Microsoft Authentication Broker (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">29d9ed98-a469-4536-ade2-f981bc1d605e</code>) as the client, displays it to the victim through a &quot;verification code&quot; lure, and exchanges the code for access/refresh tokens after the victim signs in at the legitimate microsoft.com/devicelogin endpoint.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="evasion-techniques" class="absolute -top-32"></span>Evasion techniques</h3>
<p>The kit employs layered anti-analysis mechanisms confirmed through JavaScript decompilation:</p>
<ul>
<li>IP-based researcher filtering: Before any content is shown, the kit calls <em>api.ipapi.is</em> (or equivalent service) to check the visitor&#x27;s IP against a blocklist of cloud/hosting providers (Leaseweb, M247, DigitalOcean, Linode, Amazon, OVH, Hetzner, Google, Microsoft, Cloudflare, Akamai, Fastly, stored as reversed strings to evade static scanning). Visitors on cloud infrastructure are redirected to a benign decoy site.</li>
<li>Bot/tool detection: Checks for <em>navigator.webdriver</em> (Selenium), <em>window.callPhantom</em> / <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">window._phantom</code> (PhantomJS), and &quot;Burp&quot; in the user-agent string. Detection triggers a redirect to <em>about:blank</em>.</li>
<li>DevTools blocking: Intercepts keyboard shortcuts for developer tools (F12, Ctrl+Shift+I/J/C, Ctrl+U, macOS equivalents) and disables right-click context menus.</li>
<li>Debugger trap: A <em>setInterval</em> loop running every 100ms inserts a debugger statement and measures execution time. If <em>DevTools</em> are open (execution pauses &gt;100ms), the victim is redirected to a decoy site.</li>
<li>DOM vanishing: Malicious JavaScript removes itself from the <em>DOM</em> after execution, leaving no trace for static inspection.</li>
<li>Per-victim encryption: The payload uses a custom two-stage cipher (Caesar shift + XOR with a PRNG-generated keystream) seeded with per-session values. The seed, key, and encrypted blob are generated server-side for each victim, making static signature detection impossible.</li>
<li>Platform targeting: On Linux desktops, it writes an empty string to blank the page: likely assuming Linux users are more likely to be security researchers.</li>
<li>Fake CAPTCHA: A custom image-grid CAPTCHA replaces Cloudflare Turnstile in the current variant. Unsplash-sourced images in a 3×3 grid provide human verification before the phishing page loads.</li>
</ul>
<p></p>
<p></p>
<p>For Google-targeted campaigns, the first-hop lure is frequently staged on legitimate Google infrastructure, such as Google Storage or Google Sites, though operator-controlled or compromised domains are also observed. When Google&#x27;s own hosting is used, the <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">storage.googleapis.com</code> or <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">sites.google.com</code> origin provides built-in reputation cover before the victim reaches the AiTM relay.</p>
<p></p>
<p></p>
<p>In other instances the victim&#x27;s email is auto-filled and the &quot;Next&quot; button is auto-clicked: the victim lands directly on the password page, making it look like they&#x27;re already partially authenticated (increasing trust) :</p>
<pre><code>
var emailcheck = &quot;victim@email.corp&quot;;
// ...
function tryfindingele(email) {
   emailinputcheck.value = email;
   emailsectionelecheck.querySelector(&quot;.btn-blue-next-btn&quot;).click();
}
if (emailcheck !== &quot;0&quot;) { tryfindingele(emailcheck); }</code></pre>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="microsoft-365--entra-id" class="absolute -top-32"></span>Microsoft 365 / Entra ID</h2>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="a-two-tier-operational-architecture" class="absolute -top-32"></span>A two-tier operational architecture</h3>
<p>Tycoon 2FA&#x27;s current operational model splits across two distinct infrastructure tiers, each with its own ASN, role, and behavioral signature. Defenders looking for a single pattern will catch one tier and miss the other.</p>
<p></p>
<p>Tier 1 - Kit Relay</p>
<p>The automated backend that handles token acquisition and renewal. Characteristics:</p>
<ul>
<li>Cloud-VPS egress IPs from hosting providers (Alibaba Cloud, similar cheap-VPS ASNs), rotating across multiple IPs in different /16 blocks during a single engagement.</li>
<li>Node.js HTTP client user agents: node (bare, default Node.js UA), axios/1.15.2, node-fetch/1.0, undici.</li>
<li>Client app: Microsoft Authentication Broker (29d9ed98-a469-4536-ade2-f981bc1d605e), later used with <a href="https://learn.microsoft.com/en-us/entra/identity/devices/device-registration-how-it-works">Device Registration Service (DRS)</a> to mint a primaryRefreshToken (PRT).</li>
<li>Token-type progression: incomingTokenType: none (initial victim auth) &gt; refreshToken (kit relay renewal loop, repeated across rotating IPs) &gt; Rogue Device Registration &gt; primaryRefreshToken (PRT replay, broader scope).</li>
<li>Non-interactive sign-ins: After the initial interactive device-code completion, subsequent token operations are server-to-server refreshes.</li>
</ul>
<p>Tier 2 - Operator Console</p>
<p>The human (or human-simulating tool) that performs post-compromise reconnaissance. Characteristics:</p>
<ul>
<li>Residential-shaped ISP or proxy egress, typically a small ASN not present in common hosting-provider threat feeds. Multiple IPs in a single /24, all acting in coordination.</li>
<li>Single browser user agent (e.g., Firefox on Windows) fixed across all IPs in the cluster. A configured tool, not independent users.</li>
<li>Browser-based interactive sign-ins to Microsoft web apps: My Profile, My Signins, Microsoft Approval Management, Outlook Web and OfficeHome.</li>
<li>Single c_sid (client session ID in Graph Activity Logs) shared across all IPs, confirming a single session distributed across the pool.</li>
<li>Operational tempo: Typically appears 10-20 minutes after the kit relay&#x27;s first successful token issuance. The gap represents the kit-to-operator handoff window.</li>
</ul>
<p>The durable cross-tier detection signal: Two distinct ASNs (one cloud-VPS, one residential-shaped) authenticating as the same user principal within minutes. Single-ASN rules catch one tier; the cross-tier pivot is the high-confidence indicator.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="post-compromise-graph-api-enumeration" class="absolute -top-32"></span>Post-compromise Graph API enumeration</h3>
<p>Once the operator console has a valid token, a rapid burst of Microsoft Graph API calls follows, typically dozens of requests within 30-60 seconds, hitting high-value reconnaissance endpoints:</p>
<div class="table-container"><table style="width:100%;table-layout:fixed;word-wrap:break-word"><thead><tr><th style="text-align:left">Recon Category</th><th style="text-align:left">Example Endpoints</th><th style="text-align:left">Purpose</th></tr></thead><tbody><tr><td style="text-align:left">Role Discovery</td><td style="text-align:left">transitiveRoleAssignments, memberOf/directoryRole, roleManagement/directory/roleAssignments</td><td style="text-align:left">Check what Entra ID roles the compromised identity holds</td></tr><tr><td style="text-align:left">Cross-Tenant Recon</td><td style="text-align:left">tenantRelationships/getResourceTenants</td><td style="text-align:left">Enumerate trusted cross-tenant relationships for lateral movement</td></tr><tr><td style="text-align:left">Mailbox Recon</td><td style="text-align:left">me/mailboxSettings</td><td style="text-align:left">Read forwarding rules, auto-replies, timezone</td></tr><tr><td style="text-align:left">Contact Harvesting</td><td style="text-align:left">me/contactFolders/contacts ($top=1000)</td><td style="text-align:left">Dump contact list for next-wave phishing targets</td></tr><tr><td style="text-align:left">Org &amp; Licensing</td><td style="text-align:left">subscribedSkus, organization, appRoleAssignedResources ($top=999)</td><td style="text-align:left">Map tenant licensing, org structure, app landscape</td></tr></tbody></table></div>
<p>Key telemetry indicators of automated post-compromise recon:</p>
<ul>
<li>Volume and speed: 20-30+ calls within a 30-60 second window, each hitting a different endpoint.</li>
<li>Mixed HTTP methods: GET for most endpoints, POST for actions like <em>getResourceTenants</em>.</li>
<li>Structured query parameters: <em>$select</em>, <em>$top=999</em>, <em>$count=true</em> - optimized for maximum data extraction per call.</li>
<li>/beta/ API usage: Disproportionately used by offensive tooling versus normal portal navigation.</li>
<li>Mixed success/failure: Some endpoints return 400 or 403 (the kit probes everything regardless), while most return 200. Failed recon attempts are still recon.</li>
<li>Empty C_DeviceId: The token was issued to an unmanaged, unregistered device.</li>
<li>First-party apps with broad pre-consented scopes: Tokens for My Profile carry scopes including <em>RoleManagement.ReadWrite.Directory</em>, <em>MailboxSettings.ReadWrite</em>, <em>UserAuthenticationMethod.ReadWrite</em>, and <em>User.RevokeSessions.All</em> - all pre-consented, requiring no OAuth consent prompt.</li>
</ul>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="device-prt-persistence" class="absolute -top-32"></span>Device-PRT persistence</h3>
<p>As stated earlier, the kit can establish device-registration persistence that survives standard session-revocation playbooks. The mechanism:</p>
<ol>
<li>MAB refresh token is resource-swapped at <em>oauth2/token</em> for an access token whose <em>aud</em> is <em>urn:ms-drs:enterpriseregistration.windows.net</em> (same client ID, new audience, no consent prompt).</li>
<li>The kit uses the <em>urn:ms-drs:enterpriseregistration.windows.net</em> access token to POST endpoint <em>EnrollmentServer/device</em> with a locally-generated PKCS#10 CSR, synthetic device metadata and transport key blob. DRS creates a device object, assigns a device ID, signs and returns a device certificate.</li>
<li>The kit builds a JWT containing the user’s refresh token, signs it RS256 with the device private key, and embeds the device certificate in the JWT header. It POSTs this to <em>login.microsoftonline.com/common/oauth2/token</em> as a JWT bearer grant. Entra validates the signature against the cert and returns the PRT plus a session key encrypted (JWE).</li>
<li>When a defender fires <em>revokeSignInSessions</em> (which invalidates all user-level tokens and refresh tokens), the device PRT remains valid because the device is a separate principal in Entra ID.</li>
<li>From the new relay IPs, the kit uses the PRT plus session key to sign per-request <em>HMAC-SHA256</em> assertions to <em>/oauth2/token</em>, brokering access tokens for any first-party <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">client_id</code> it names (Teams, Outlook, OneDrive, Office, Intune).</li>
</ol>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="why-doesnt-revoking-sessions-stop-tycoon-2fa" class="absolute -top-32"></span>Why doesn&#x27;t revoking sessions stop Tycoon 2FA?</h3>
<p>This means the standard incident response sequence of &quot;revoke sessions &gt; reset password&quot; is insufficient. Defenders must enumerate and delete registered devices before revoking sessions to break the device-PRT chain atomically.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="detection-nuances---microsoft" class="absolute -top-32"></span>Detection nuances - Microsoft</h3>
<p><strong>Identity Protection may not flag kit infrastructure.</strong> Tycoon 2FA&#x27;s current egress IPs rotate aggressively and may not be in Microsoft&#x27;s risk corpus. Defenders relying solely on Entra ID risk signals for AiTM detection will see nothing.</p>
<p><strong>c_sid in Graph Activity Logs is NOT the user object ID.</strong> It&#x27;s a session/security-context identifier. Analysts filtering Graph Activity Logs by <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">c_sid == user_object_id</code> will get empty results and conclude the attacker didn&#x27;t use Graph tokens. The correct hunt pivot is source IP + appId, cross-referenced with sign-in logs to map IP to user.</p>
<p><strong>Geolocation is unreliable for cloud-provider IPs.</strong> The same kit relay IP can geolocate to different cities within the same sign-in session. ASN is the only reliable enrichment for detection rules.</p>
<p><strong>Token minting visibility.</strong> Token minting or issuance is not logged; authentication events leveraging these tokens propose a more reactive hunting signal.</p>
<p><strong>Entra ID Protection Risky User Status.</strong> Entra ID protection analyzes sign-in events, sessions, tokens and more to apply a risk level and status to users. <em>aiConfirmedSafe</em> was observed during tier 2 relay, marking the user with no risk. Then User Risk anomalies were identified based on <em>anomalousToken</em> which then placed the user back into a medium risk. Simply excluding events where <em>aiConfirmedSafe</em> can blind organizations to false-negatives from Microsoft’s labeling.</p>
<p></p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="google-workspace" class="absolute -top-32"></span>Google Workspace</h2>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="single-tier-kit-relay" class="absolute -top-32"></span>Single-tier kit relay</h3>
<p>The Google variant operates as a single-tier kit relay without the distinct operator console tier seen on the Microsoft side. Multiple kit relay IPs (typically from cheap hosting ASNs like Clouvider, Host Telecom, or similar) authenticate the same user within minutes, each performing the same four-event sequence:</p>
<ol>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">login_success</code>  password validated (T+0.000s)</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">login_verification</code> with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">is_second_factor: true</code> - kit relays the TOTP/SMS/push code in real time, completing 2SV (T+0.000s)</li>
<li>token: authorize for Google&#x27;s Chrome OAuth client (77185425430) (T+0.4 to 0.6s)</li>
<li><code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">DEVICE_REGISTER_UNREGISTER_EVENT</code> (new device is registered by Google due to profile authentication) (T+0.6 to 1.2s)</li>
</ol>
<p>That ~1-second compression is a signal of automated logins.</p>
<p></p>
<p>The kit consistently authorizes the same OAuth client across every relay session:</p>
<div class="table-container"><table style="width:100%;table-layout:fixed;word-wrap:break-word"><thead><tr><th style="text-align:left">Field</th><th style="text-align:left">Value</th></tr></thead><tbody><tr><td style="text-align:left">google_workspace.token.client.id</td><td style="text-align:left">77185425430.apps.googleusercontent.com</td></tr><tr><td style="text-align:left">google_workspace.token.app_name</td><td style="text-align:left">Google Chrome</td></tr><tr><td style="text-align:left">google_workspace.token.client.type</td><td style="text-align:left">NATIVE_DESKTOP</td></tr><tr><td style="text-align:left">google_workspace.device.type</td><td style="text-align:left">WINDOWS</td></tr><tr><td style="text-align:left">google_workspace.token.scope.value</td><td style="text-align:left"><a href="https://www.google.com/accounts/OAuthLogin">https://www.google.com/accounts/OAuthLogin</a></td></tr><tr><td style="text-align:left">google_workspace.token.method_name</td><td style="text-align:left">authorize</td></tr></tbody></table></div>
<p>The <em>OAuthLogin</em> scope is Chrome&#x27;s internal bootstrap sign-in scope. It is not a data-plane scope (it does not by itself grant Gmail, Drive, or Calendar access). The kit&#x27;s blast radius from this single scope is bound to a long-lived sign-in capable of becoming a Chrome Sync session, not direct mailbox or file access without further token-exchange calls.</p>
<p></p>
<p>What the <em>token.authorize</em> event from a VPS ASN confirms is that the authorization happens server-side during the relay, not from the victim&#x27;s device, making it suspicious regardless of operator intent.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="kit-javascript-architecture-google-variant" class="absolute -top-32"></span>Kit JavaScript architecture (Google variant)</h3>
<p>Decompilation of the Google-targeting WebSocket variant reveals a 5-layer architecture:</p>
<div class="table-container"><table style="width:100%;table-layout:fixed;word-wrap:break-word"><thead><tr><th style="text-align:left">Layer</th><th style="text-align:left">Function</th></tr></thead><tbody><tr><td style="text-align:left">1. Anti-Analysis</td><td style="text-align:left">IP filtering via api.ipapi.is (cloud provider blocklist with reversed strings), bot/debugger detection, DOM vanishing</td></tr><tr><td style="text-align:left">2. <p>The 15 input fields capture every Google 2FA method: password, TOTP, SMS, voice call, backup codes, recovery email, phone verification, security key fallback, mobile prompt, and forced password change. The “recieveid” Socket.IO event name (note the typo) is a consistent kit fingerprint.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="detection-nuances---google" class="absolute -top-32"></span>Detection nuances - Google</h3>
<p><strong>Google Alert Center may stay silent.</strong> Even when multiple sign-ins from multiple ASNs hit the same user within minutes, Alert Center records may not flow to the Alert API. Google&#x27;s victim-mailbox security alert emails are not a substitute, since they go to the compromised user&#x27;s inbox, not the admin surface.</p>
<p><strong>is_suspicious may not fire.</strong> Kit relay IPs from cheap hosting ASNs may not be in Google&#x27;s risk corpus. Defenders relying on this field as a primary signal will have blind spots. In the canary engagement, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">is_suspicious</code> was false on every <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">login_success</code> from all four kit IPs across both Clouvider and Host Telecom.</p>
<p></p>
<p><strong>No user-agent on login events:</strong> The Reports API login events do not include user-agent or device-fingerprint data. The UA-based detections that work on the Entra side (node / axios / undici) have no direct Google equivalent.</p>
<p><strong>OAuth workflow visibility is shallow:</strong> Google&#x27;s <em>token.authorize</em> event surfaces <em>client.id</em>, <em>app_name</em>, <em>client.type</em>, and <em>scope.value</em>, and that&#x27;s the full set. There is no <em>resource_id</em> distinct from scope, no grant-type field, and no incoming-token-type field.</p>
<p><strong>Most auxiliary streams stay quiet:</strong> no <em>google_workspace.context_aware_access</em> events fired (despite five new device records on the user) and no Alert Center records reached the Alert API. The kit footprint lives in three streams only: login, token, and device. Hunts that depend on any other stream will not detect this kit.</p>

<h2 class="font-bold text-2xl md:text-4xl relative"><span id="tycoon-2fa-behavior-detection-rules" class="absolute -top-32"></span>Tycoon 2FA behavior detection rules</h2>
<p>We shipped detection rules across Microsoft and Google telemetry sources covering the full attack chain: initial AiTM phish, token relay, operator console recon and device persistence.</p>
<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="microsoft---kit-relay-detection" class="absolute -top-32"></span>Microsoft - Kit relay detection</h3>
<p><a href="https://github.com/elastic/detection-rules/blob/9bd94c62a54c6b3d6054e4f1d57f014538be70bf/rules/integrations/azure/initial_access_tycoon_entra_id.toml#L27">Entra ID Potential AiTM Sign-In via OfficeHome (Tycoon2FA)</a> -  This is a high signal detection that triggers on Auth Broker or OfficeHome sign-ins to Graph/Exchange with Node.js-style user agents (<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">node</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">axios</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">undici</code>). Catches the kit relay tier&#x27;s server-side token operations.</p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/9bd94c62a54c6b3d6054e4f1d57f014538be70bf/rules/integrations/o365/initial_access_tycoon_o365.toml#L28">M365 Potential AiTM UserLoggedIn via Office App (Tycoon2FA)</a> - Same detection logic as the Entra sign-in rule but against the M365 Unified Audit Log for tenants ingesting <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">o365.audit</code> instead of (or in addition to) Entra sign-in logs.</p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/9bd94c62a54c6b3d6054e4f1d57f014538be70bf/rules/integrations/azure/initial_access_entra_id_oauth_device_code_phishing_tycoon_aitm.toml#L27">Entra ID OAuth Device Code Phishing via AiTM</a> :  Detects successful interactive device-code-flow sign-ins through the Auth Broker targeting Exchange, Graph, or SharePoint. Catches the device-code-grant abuse variant specifically.</p>
<p><a href="https://github.com/elastic/detection-rules/blob/9bd94c62a54c6b3d6054e4f1d57f014538be70bf/rules/integrations/azure/initial_access_entra_id_microsoft_auth_broker_unusual_resource.toml#L28">Entra ID Microsoft Authentication Broker Sign-In to Unusual Resource</a> : Detects successful Auth Broker sign-ins where the target resource is outside the commonly-observed first-party set. <h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="microsoft---persistence-detection" class="absolute -top-32"></span>Microsoft - Persistence detection</h3>
<p><a href="https://github.com/elastic/detection-rules/blob/8089df918f81850b28dfc3e691495f55bf30c94a/rules/integrations/azure/persistence_entra_id_register_device_unusual_user_agent.toml#L26">Entra ID Register Device with Unusual User Agent (Azure AD Join)</a> :  Detects successful device registration events where the user agent is not one of the known native registration clients <em>(<code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Dsreg</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">DeviceRegistrationClient</code>, <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Dalvik</code>)</em>. Catches the kit&#x27;s device-PRT persistence play also originating from the axios user agent:</p>

<h3 class="font-bold leading-tight text-xl md:text-3xl relative"><span id="post-compromise-graph-api-enumeration-esql" class="absolute -top-32"></span>Post-compromise Graph API enumeration (ES|QL)</h3>
<p>For the operator console tier&#x27;s post-compromise recon, we built an ES|QL <a href="https://github.com/elastic/detection-rules/blob/b87d2f58938f67c3b74bf5ae334fad06371d4dac/rules/integrations/azure/discovery_graph_activity_delegated_user_multi_category_recon.toml">rule</a> that tags each Microsoft Graph API request into one of five reconnaissance categories and fires when 4 or more distinct categories are hit within the aggregation window (&lt;= 60s):</p>
<p></p>
<p><a href="https://github.com/elastic/detection-rules/blob/d623721ec303064d1f47bcea15ae5bc3062f2b54/rules/integrations/azure/discovery_graph_activity_delegated_user_multi_category_recon.toml#L26">Microsoft Graph Multi-Category Reconnaissance Burst</a> catches systematic post-compromise enumeration while filtering out organic portal usage. Normal user activity might touch one or two of these categories, hitting 4 or more distinct recon categories from a single session within a short window (33 seconds) is the automated-tooling fingerprint.</p>

<h2 class="font-bold text-2xl md:text-4xl relative"><span id="automating-containment-with-elastic-workflows" class="absolute -top-32"></span>Automating containment with Elastic Workflows</h2>
<p>Once the detection content is in place, the next gap is the time between alert and action. The Tycoon 2FA M365 kit-to-operator handoff window we documented earlier is 10-20 minutes, the time between the kit relay&#x27;s first successful token issuance and the operator-tier session beginning its post-compromise Graph recon.</p>
<p>A manual SOC response routinely takes longer than that window, which is why the operator gets recon work done before containment lands. Closing that gap is what makes detection actionable.</p>
<p><a href="https://www.elastic.co/docs/explore-analyze/workflows">Elastic Workflows</a>, shipped with the stack (9.4+), lets detection rules invoke custom <a href="https://github.com/elastic/workflows">workflows</a> with a YAML-defined pipeline of steps on every alert.</p>
<p></p>
<p>As a PoC, we built a custom workflow wired to an <a href="https://github.com/elastic/detection-rules/blob/9bd94c62a54c6b3d6054e4f1d57f014538be70bf/rules/integrations/azure/initial_access_tycoon_entra_id.toml#L27">Entra ID Potential AiTM Sign-In via OfficeHome (Tycoon2FA)</a> detection rule that mirrors the required response actions.</p>
<p>On every alert the workflow:</p>
<ol>
<li>Acquires a Graph bearer via <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">client_credentials</code> (one-time per execution).</li>
<li>PATCHes the compromised UPN with <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">accountEnabled: false</code> to halt new authentications.</li>
<li>Enumerates <em>registeredDevices</em> and <em>ownedDevices</em> on the user.</li>
<li>DELETEs each device principal, which is what actually invalidates a device-bound PRT.</li>
<li>POSTs to <em>revokeSignInSessions</em> to invalidate user-level refresh tokens and session cookies.</li>
<li>Opens a Kibana case populated with the alert context for post-IR audit (password reset, auth method review, OAuth grant audit).</li>
</ol>
<p>The chain executes in less than 10 seconds end-to-end against Microsoft Graph, well inside the 10-20 minute Tycoon 2FA handoff window. The operator-tier session never gets a chance to begin recon.</p>
<p></p>
<p>The pattern scales beyond this one rule. The same workflow shape works for any cloud-identity detection that benefits from immediate containment: AiTM sign-ins, impossible travel, illicit OAuth consent grants, role escalation, MFA fatigue, anomalous device registration. Wire the rule to a workflow that calls the relevant cloud API and the SOC gets seconds-level containment.</p>
<h2 class="font-bold text-2xl md:text-4xl relative"><span id="defending-against-tycoon-2fa-aitm-attacks" class="absolute -top-32"></span>Defending against Tycoon 2FA AiTM attacks</h2>
<ul>
<li>Deploy phishing-resistant MFA: FIDO2 security keys and passkeys are the only methods immune to AiTM session theft. TOTP, SMS, and push-based MFA can all be proxied.</li>
<li>Enforce device compliance via Conditional Access: Require managed, compliant devices for token issuance. This is the single most effective control against AiTM token theft.</li>
<li>Block device code flows: The <code class="px-1.5 py-1 rounded not-prose bg-[var(--tw-prose-invert-pre-bg)] whitespace-break-spaces text-[85%] text-emerald-600">Block device code flow</code> Conditional Access policy cleanly rejects the kit relay at the grant phase (error 53003). Enable it for all users except explicitly approved kiosk/headless scenarios.</li>
<li>Enable token protection (token binding): <a href="https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-token-protection">Binds</a> tokens to the device they were issued to. A stolen token replayed from a different device is rejected.</li>
<li>Enable Continuous Access Evaluation (CAE): Near real-time token revocation when risk conditions change.</li>
<li>Enable Security Defaults in Entra ID (only for tenants without custom Conditional Access): rejects legacy authentication such as ROPC and blocks device code flow by default. Enabling Security Defaults disables custom CA policies, so this is not applicable to tenants already running granular CA.</li>
</ul>

It is not a static credential harvester. It proxies the real login flow in real time:\n\n1. The victim receives a phishing email containing a link or QR code embedded in a PDF, SVG, HTML, or PPTX attachment.  \n2. The link routes through a multi-layer redirect chain. The kit performs browser fingerprinting, CAPTCHA challenges, and anti-analysis checks before presenting the login page.  \n3. The victim sees a pixel-perfect replica of the Microsoft or Google login page, often including the target organization's branding dynamically fetched from the real service.  \n4. Credentials are relayed in real time to the legitimate identity provider. The real MFA challenge is triggered and proxied back to the victim.  \n5. The victim completes MFA normally. The identity provider issues a session token. The proxy intercepts this token before it reaches the victim's browser.  \n6. Once captured, MFA is moot because the operator replays minted tokens post-MFA.\n\n### Two structural variants in current rotation\n\nTwo distinct kit variants we analyzed were in active use:\n\nWebSocket AiTM (the \"classic\" Tycoon 2FA flow): The victim authenticates through a kit-hosted proxy that forwards traffic to Microsoft or Google over WebSocket (Socket.IO) and captures the post-MFA session cookie. The kit's JavaScript client controller maintains a real-time bidirectional channel to the C2 server, relaying credentials and authentication responses as the victim types. Visitors on cloud infrastructure are redirected to a benign decoy site.\n- Bot/tool detection: Checks for *navigator.webdriver* (Selenium), *window.callPhantom* / `window._phantom` (PhantomJS), and \"Burp\" in the user-agent string. Defenders looking for a single pattern will catch one tier and miss the other.\n\n![](/assets/images/tycoon-2fa-aitm-detection-engineering/image4.png)\n\nTier 1 - Kit Relay\n\nThe automated backend that handles token acquisition and renewal. Characteristics:\n\n- Cloud-VPS egress IPs from hosting providers (Alibaba Cloud, similar cheap-VPS ASNs), rotating across multiple IPs in different /16 blocks during a single engagement.  \n- Node.js HTTP client user agents: node (bare, default Node.js UA), axios/1.15.2, node-fetch/1.0, undici.   \n- Client app: Microsoft Authentication Broker (29d9ed98-a469-4536-ade2-f981bc1d605e), later used with [Device Registration Service (DRS)](https://learn.microsoft.com/en-us/entra/identity/devices/device-registration-how-it-works) to mint a primaryRefreshToken (PRT).  \n- Token-type progression: incomingTokenType: none (initial victim auth) \u003e refreshToken (kit relay renewal loop, repeated across rotating IPs) \u003e Rogue Device Registration \u003e primaryRefreshToken (PRT replay, broader scope).   \n- Non-interactive sign-ins: After the initial interactive device-code completion, subsequent token operations are server-to-server refreshes.\n\nTier 2 - Operator Console\n\nThe human (or human-simulating tool) that performs post-compromise reconnaissance. Characteristics:\n\n- Residential-shaped ISP or proxy egress, typically a small ASN not present in common hosting-provider threat feeds. Multiple IPs in a single /24, all acting in coordination.  \n- Single browser user agent (e.g., Firefox on Windows) fixed across all IPs in the cluster. A configured tool, not independent users.  \n- Browser-based interactive sign-ins to Microsoft web apps: My Profile, My Signins, Microsoft Approval Management, Outlook Web and OfficeHome.  \n- Single c_sid (client session ID in Graph Activity Logs) shared across all IPs, confirming a single session distributed across the pool.  \n- Operational tempo: Typically appears 10-20 minutes after the kit relay's first successful token issuance. The gap represents the kit-to-operator handoff window.\n\nThe durable cross-tier detection signal: Two distinct ASNs (one cloud-VPS, one residential-shaped) authenticating as the same user principal within minutes. Single-ASN rules catch one tier; the cross-tier pivot is the high-confidence indicator.\n\n### Post-compromise Graph API enumeration\n\nOnce the operator console has a valid token, a rapid burst of Microsoft Graph API calls follows, typically dozens of requests within 30-60 seconds, hitting high-value reconnaissance endpoints:\n\n| Recon Category | Example Endpoints | Purpose |\n| :---- | :---- | :---- |\n| Role Discovery | transitiveRoleAssignments, memberOf/directoryRole, roleManagement/directory/roleAssignments | Check what Entra ID roles the compromised identity holds |\n| Cross-Tenant Recon | tenantRelationships/getResourceTenants | Enumerate trusted cross-tenant relationships for lateral movement |\n| Mailbox Recon | me/mailboxSettings | Read forwarding rules, auto-replies, timezone |\n| Contact Harvesting | me/contactFolders/contacts ($top=1000) | Dump contact list for next-wave phishing targets |\n| Org \u0026 Licensing | subscribedSkus, organization, appRoleAssignedResources ($top=999) | Map tenant licensing, org structure, app landscape |\n\nKey telemetry indicators of automated post-compromise recon:\n\n- Volume and speed: 20-30+ calls within a 30-60 second window, each hitting a different endpoint.  \n- Mixed HTTP methods: GET for most endpoints, POST for actions like *getResourceTenants*.  \n- Structured query parameters: *$select*, *$top=999*, *$count=true* - optimized for maximum data extraction per call.  \n- /beta/ API usage: Disproportionately used by offensive tooling versus normal portal navigation.  \n- Mixed success/failure: Some endpoints return 400 or 403 (the kit probes everything regardless), while most return 200. Failed recon attempts are still recon.  \n- Empty C_DeviceId: The token was issued to an unmanaged, unregistered device.  \n- First-party apps with broad pre-consented scopes: Tokens for My Profile carry scopes including *RoleManagement.ReadWrite.Directory*, *MailboxSettings.ReadWrite*, *UserAuthenticationMethod.ReadWrite*, and *User.RevokeSessions.All* - all pre-consented, requiring no OAuth consent prompt.\n\n### Device-PRT persistence\n\nAs stated earlier, the kit can establish device-registration persistence that survives standard session-revocation playbooks. The mechanism:\n\n1. MAB refresh token is resource-swapped at *oauth2/token* for an access token whose *aud* is *urn:ms-drs:enterpriseregistration.windows.net* (same client ID, new audience, no consent prompt).  \n2. The kit uses the *urn:ms-drs:enterpriseregistration.windows.net* access token to POST endpoint *EnrollmentServer/device* with a locally-generated PKCS#10 CSR, synthetic device metadata and transport key blob. DRS creates a device object, assigns a device ID, signs and returns a device certificate.  \n3. The kit builds a JWT containing the user’s refresh token, signs it RS256 with the device private key, and embeds the device certificate in the JWT header. It POSTs this to *login.microsoftonline.com/common/oauth2/token* as a JWT bearer grant. Entra validates the signature against the cert and returns the PRT plus a session key encrypted (JWE).   \n4. When a defender fires *revokeSignInSessions* (which invalidates all user-level tokens and refresh tokens), the device PRT remains valid because the device is a separate principal in Entra ID.  \n5. From the new relay IPs, the kit uses the PRT plus session key to sign per-request *HMAC-SHA256* assertions to */oauth2/token*, brokering access tokens for any first-party `client_id` it names (Teams, Outlook, OneDrive, Office, Intune). \n\n### Why doesn't revoking sessions stop Tycoon 2FA?\n\nThis means the standard incident response sequence of \"revoke sessions \u003e reset password\" is insufficient. Defenders must enumerate and delete registered devices before revoking sessions to break the device-PRT chain atomically.\n\n### Detection nuances - Microsoft\n\n**Identity Protection may not flag kit infrastructure.** Tycoon 2FA's current egress IPs rotate aggressively and may not be in Microsoft's risk corpus. Defenders relying solely on Entra ID risk signals for AiTM detection will see nothing.\n\n**c_sid in Graph Activity Logs is NOT the user object ID.** It's a session/security-context identifier. Analysts filtering Graph Activity Logs by `c_sid == user_object_id` will get empty results and conclude the attacker didn't use Graph tokens. The correct hunt pivot is source IP + appId, cross-referenced with sign-in logs to map IP to user.\n\n**Geolocation is unreliable for cloud-provider IPs.** The same kit relay IP can geolocate to different cities within the same sign-in session. ASN is the only reliable enrichment for detection rules.\n\n**Token minting visibility.** Token minting or issuance is not logged; authentication events leveraging these tokens propose a more reactive hunting signal.\n\n**Entra ID Protection Risky User Status.** Entra ID protection analyzes sign-in events, sessions, tokens and more to apply a risk level and status to users. *aiConfirmedSafe* was observed during tier 2 relay, marking the user with no risk. Then User Risk anomalies were identified based on *anomalousToken* which then placed the user back into a medium risk. Simply excluding events where *aiConfirmedSafe* can blind organizations to false-negatives from Microsoft’s labeling.\n\n![](/assets/images/tycoon-2fa-aitm-detection-engineering/image19.png)\n\n## Google Workspace\n\n### Single-tier kit relay\n\nThe Google variant operates as a single-tier kit relay without the distinct operator console tier seen on the Microsoft side. Multiple kit relay IPs (typically from cheap hosting ASNs like Clouvider, Host Telecom, or similar) authenticate the same user within minutes, each performing the same four-event sequence:\n\n1. `login_success`  password validated (T+0.000s)  \n2. `login_verification` with `is_second_factor: true` - kit relays the TOTP/SMS/push code in real time, completing 2SV (T+0.000s)  \n3. token: authorize for Google's Chrome OAuth client (77185425430) (T+0.4 to 0.6s)  \n4. `DEVICE_REGISTER_UNREGISTER_EVENT` (new device is registered by Google due to profile authentication) (T+0.6 to 1.2s)\n\nThat ~1-second compression is a signal of automated logins.\n\n![](/assets/images/tycoon-2fa-aitm-detection-engineering/image13.png)\n\nThe kit consistently authorizes the same OAuth client across every relay session:\n\n| Field | Value |\n| :---- | :---- |\n| google_workspace.token.client.id | 77185425430.apps.googleusercontent.com |\n| google_workspace.token.app_name | Google Chrome |\n| google_workspace.token.client.type | NATIVE_DESKTOP |\n| google_workspace.device.type | WINDOWS |\n| google_workspace.token.scope.value | https://www.google.com/accounts/OAuthLogin |\n| google_workspace.token.method_name | authorize |\n\nThe *OAuthLogin* scope is Chrome's internal bootstrap sign-in scope. It is not a data-plane scope (it does not by itself grant Gmail, Drive, or Calendar access). The kit's blast radius from this single scope is bound to a long-lived sign-in capable of becoming a Chrome Sync session, not direct mailbox or file access without further token-exchange calls. \n\n![](/assets/images/tycoon-2fa-aitm-detection-engineering/image15.png)\n\nWhat the *token.authorize* event from a VPS ASN confirms is that the authorization happens server-side during the relay, not from the victim's device, making it suspicious regardless of operator intent.\n\n### Kit JavaScript architecture (Google variant)\n\nDecompilation of the Google-targeting WebSocket variant reveals a 5-layer architecture:\n\n| Layer | Function |\n| :---- | :---- |\n| 1. Anti-Analysis | IP filtering via api.ipapi.is (cloud provider blocklist with reversed strings), bot/debugger detection, DOM vanishing |\n| 2. Phishing HTML | ~747KB base64-decoded Google sign-in clone with 15 input fields covering every Google auth method |\n| 3. WebSocket C2 | Socket.IO 4.6.0 real-time relay (send_to_browser / response_from_browser events) |\n| 4. Encrypted Payload | Per-victim Caesar+XOR cipher (LCG PRNG, unique seed per session), eval()'d at runtime |\n| 5. Libraries | CryptoJS 4.2.0 for AES-CBC credential encryption (hardcoded key 1234567890123456 to encrypt collected credentials), list.js |\n\nThe 15 input fields capture every Google 2FA method: password, TOTP, SMS, voice call, backup codes, recovery email, phone verification, security key fallback, mobile prompt, and forced password change. The “recieveid” Socket.IO event name (note the typo) is a consistent kit fingerprint.\n\n### Detection nuances - Google\n\n**Google Alert Center may stay silent.** Even when multiple sign-ins from multiple ASNs hit the same user within minutes, Alert Center records may not flow to the Alert API. Google's victim-mailbox security alert emails are not a substitute, since they go to the compromised user's inbox, not the admin surface.\n\n**is_suspicious may not fire.** Kit relay IPs from cheap hosting ASNs may not be in Google's risk corpus. Defenders relying on this field as a primary signal will have blind spots. In the canary engagement, `is_suspicious` was false on every `login_success` from all four kit IPs across both Clouvider and Host Telecom.\n\n![](/assets/images/tycoon-2fa-aitm-detection-engineering/image11.png)\n\n**No user-agent on login events:** The Reports API login events do not include user-agent or device-fingerprint data. The UA-based detections that work on the Entra side (node / axios / undici) have no direct Google equivalent.\n\n**OAuth workflow visibility is shallow:** Google's *token.authorize* event surfaces *client.id*, *app_name*, *client.type*, and *scope.value*, and that's the full set. There is no *resource_id* distinct from scope, no grant-type field, and no incoming-token-type field.\n\n**Most auxiliary streams stay quiet:** no *google_workspace.context_aware_access* events fired (despite five new device records on the user) and no Alert Center records reached the Alert API. The kit footprint lives in three streams only: login, token, and device. Hunts that depend on any other stream will not detect this kit.\n\n## Tycoon 2FA across Entra ID and Google Workspace\n\n| Dimension | Microsoft 365 (Entra ID) | Google Workspace |\n| :---- | :---- | :---- |\n| Kit relay infrastructure | Cloud-VPS hosting ASNs, rotating IPs | Cloud-VPS hosting ASNs, rotating IPs |\n| Kit relay user agents | `node`, `axios`, `undici`, `node-fetch` | Not exposed (Reports API lacks UA) |\n| Auth flow targeted | Auth Broker device-code grant | Google Chrome OAuth sign-in |\n| Persistence scope | Device registration leading to primaryRefreshToken (PRT) | Not observed |\n| Persistence durability | High - device-PRT can survive session revocation | Low - single OAuth revoke sufficient |\n| Operator console tier | Yes - residential-proxy IPs, browser-based M365 web app recon | Not observed |\n| Risk engine flagged kit egress | Yes - User Risk detection for *anomalousToken* | No (`is_suspicious` silent) |\n| SOC log latency | \\\u003c5 minutes (sign-in logs near-real-time) | Up to ~3 hours (Reports API lag) |\n| CA / policy defense available | Block device-code-flow CA \u003e clean 53003 rejection | No equivalent policy |\n| Kill-switch complexity | Must delete registered devices before revoking sessions | Single OAuth revoke sufficient |\n\nThe M365 variant is operationally heavier, and logging provides extensive detail before and after identity compromise. Closing that gap is what makes detection actionable.\n\n[Elastic Workflows](https://www.elastic.co/docs/explore-analyze/workflows), shipped with the stack (9.4+), lets detection rules invoke custom [workflows](https://github.com/elastic/workflows) with a YAML-defined pipeline of steps on every alert.\n\n![](/assets/images/tycoon-2fa-aitm-detection-engineering/image17.png)\n\nAs a PoC, we built a custom workflow wired to an [Entra ID Potential AiTM Sign-In via OfficeHome (Tycoon2FA)](https://github.com/elastic/detection-rules/blob/9bd94c62a54c6b3d6054e4f1d57f014538be70bf/rules/integrations/azure/initial_access_tycoon_entra_id.toml#L27) detection rule that mirrors the required response actions. \n\nOn every alert the workflow:\n\n1. Acquires a Graph bearer via `client_credentials` (one-time per execution).  \n2. PATCHes the compromised UPN with `accountEnabled: false` to halt new authentications.  \n3. Enumerates *registeredDevices* and *ownedDevices* on the user.  \n4. DELETEs each device principal, which is what actually invalidates a device-bound PRT.  \n5. POSTs to *revokeSignInSessions* to invalidate user-level refresh tokens and session cookies.  \n6. Opens a Kibana case populated with the alert context for post-IR audit (password reset, auth method review, OAuth grant audit).\n\nThe chain executes in less than 10 seconds end-to-end against Microsoft Graph, well inside the 10-20 minute Tycoon 2FA handoff window. The operator-tier session never gets a chance to begin recon.\n\n![Account disabled and all associated refresh tokens and devices invalidated.](/assets/images/tycoon-2fa-aitm-detection-engineering/image9.png \"Account disabled and all associated refresh tokens and devices invalidated.\")\n\nThe pattern scales beyond this one rule. The same workflow shape works for any cloud-identity detection that benefits from immediate containment: AiTM sign-ins, impossible travel, illicit OAuth consent grants, role escalation, MFA fatigue, anomalous device registration. Wire the rule to a workflow that calls the relevant cloud API and the SOC gets seconds-level containment.\n\n## Defending against Tycoon 2FA AiTM attacks\n\n- Deploy phishing-resistant MFA: FIDO2 security keys and passkeys are the only methods immune to AiTM session theft. TOTP, SMS, and push-based MFA can all be proxied.  \n- Enforce device compliance via Conditional Access: Require managed, compliant devices for token issuance. This is the single most effective control against AiTM token theft.  \n- Block device code flows: The `Block device code flow` Conditional Access policy cleanly rejects the kit relay at the grant phase (error 53003). Enable it for all users except explicitly approved kiosk/headless scenarios.  \n- Enable token protection (token binding): [Binds](https://learn.microsoft.com/en-us/entra/identity/conditional-access/concept-token-protection) tokens to the device they were issued to. A stolen token replayed from a different device is rejected.   \n- Enable Continuous Access Evaluation (CAE): Near real-time token revocation when risk conditions change.  \n- Enable Security Defaults in Entra ID (only for tenants without custom Conditional Access): rejects legacy authentication such as ROPC and blocks device code flow by default. Enabling Security Defaults disables custom CA policies, so this is not applicable to tenants already running granular CA.\n\n## MITRE ATT\u0026CK Mapping\n\n| Technique | ID | Observable |\n| :---- | :---- | :---- |\n| Phishing: Spearphishing Link | T1566.002 | Lure emails with embedded links, QR codes, PDF/SVG/HTML attachments |\n| Steal Web Session Cookie | T1539 | AiTM proxy captures post-MFA session tokens |\n| Valid Accounts: Cloud Accounts | T1078.004 | Stolen tokens used for Graph API access and M365 web app browsing |\n| Account Manipulation: Device Registration | T1098.005 | Kit registers device for PRT persistence |\n| Use Alternate Authentication Material: Application Access Token | T1550.001 | FOCI token exchange across Auth Broker app family |\n| Account Discovery: Cloud Account | T1087.004 | Graph enumeration of user profile, role memberships, contacts |\n| Permission Groups Discovery: Cloud | T1069.003 | Enumerating directory roles and transitive role assignments |\n| Cloud Service Discovery | T1526 | Listing subscribedSkus, organization metadata, app inventory |\n\n## References\n\n- [Microsoft Security Blog -
